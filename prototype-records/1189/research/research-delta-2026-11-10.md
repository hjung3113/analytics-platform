## Conclusions

1. **Popover layout: 1-column list.** No menu doc in Primer, React Aria or Fluent describes a grid menu (React Aria's grid is on ListBox and GridList, not Menu); grid appears in launcher form (Ant ProLayout, and M365/Google in the earlier notes). For 7 items a list avoids ProLayout's 3-per-row orphan (3+3+1). Sources: Primer ActionMenu, Fluent Menu, ProLayout `style/simple.ts`.
2. **Semantics: links first, menu role only with the full contract.** Primer says ActionMenu is not semantically navigation, and APG's site-nav example avoids the menu role. APG also publishes a link-based menu button, so `role=menu` is legal if it is fully implemented: focus first item on open, arrows inside, Tab closes, Esc returns focus. Choosing `nav` + list means Tab order and `aria-current`. Destinations that change the URL lean to disclosure + `aria-current=page`; dialog/listbox fits only with a filter, which 7 items do not need. Sources: Primer navigation, APG disclosure and menu-button links, SelectPanel.
3. **Current mark: one mark, matched to the semantics.** Link list: `aria-current` with a selection indicator (Primer NavList, Fluent Nav, never color alone). Menu role: leading check with `menuitemradio` and `aria-checked` (Primer). Neither system documents combining the two, so use one (my inference). ProLayout has no current mark at all, which is a gap, not a model.
4. **Descriptions: all or none, and off for known systems.** ProLayout switches layout on this exact rule (any item without `desc` gives the compact form). Primer's icon rule is the same all-or-none. React Aria keeps description as a separate slot so it is announced. Fluent reserves secondary content for shortcuts. Secondary global links go below a divider or in a section, not in a popover footer by default: Primer uses sections for added function, and SelectPanel's footer link is tied to a dialog. Fluent advises against its Nav footer slot; Toolpad's `sidebarFooter` shows the account at the rail bottom.
5. **Portal home: compact rows or small cards with name + one short line, whole surface as the single target.** Fluent says one clear action can make the whole surface a button and to keep content brief; Primer's list-of-cards belongs in `li`; Ant's Workplace shows only title, one line and time. Mixing several actions on a tile forces Fluent `focusMode` or GridList `tab` mode, so keep resume as the only extra text or a separate list. Tile vs row for known systems is my inference; no source rules on it.
6. **Resume and uneven groups have no design-system answer, so this is our own call.** Closest precedent: Ant Workplace puts a relative time on the item and a separate activity list; Power BI uses one recents strip. For uneven groups, ProLayout stacks titled groups with wrapping items, which by inference leaves uneven row ends at 4 groups of different sizes; a shared grid with group headers is unconfirmed by any source and needs a prototype check.

### Conclusions

Items marked (inference) apply the evidence to our case and are not vendor statements.

1. **(a) Three shapes exist; the choice follows whether the units share pages.** Switcher replaces the nav: Salesforce, Atlassian apps, AWS services, M365. Scope over one nav: Vercel projects, Google Cloud projects, Fabric workspaces, Slack Enterprise, Linear teams. No unit: Grafana, Datadog. MARS, CLAS and BRAVO will share pages after merging, so they fit scope or no unit, while unrelated spaces can stay destinations (inference).
2. **(a) A scope needs an identical page set and must keep your place.** Vercel states both conditions ("consistent links", "without losing context"). Where a system lacks a page during the merge, a filter would dead-end, so per-system gaps must be shown, not hidden (inference).
3. **(a) Nobody I surveyed made task order the sole primary navigation.** Task-order appears as an added layer: Fabric task flows, Vercel's workflow ordering, Grafana's Drilldown section, AWS applications. Regrouping by analysis order has partial precedent only, so it should keep a filter or origin view until proven (inference). Task-first primary nav: NPSF.
4. **(b) Rename labels, freeze addresses.** GitHub says URLs and APIs stay; Grafana keeps plugin IDs under new display names; Microsoft and Data Studio redirect old domains. Salesforce and Fabric instead keep the old experience reachable. For us: existing system URLs and saved views should redirect or stay valid (inference; this is linkable state, so owner confirmation applies under AGENTS.md test B).
5. **(b) Old names survive mainly in search and docs, not in the nav.** Google Cloud maps other vendors' names in search; Data Studio docs say "formerly known as". I found no vendor documenting a "formerly X" label inside its navigation (NPSF). Search aliases for MARS, CLAS and BRAVO plus an origin tag on menu entries would go beyond what these vendors document (inference).
6. **(b) Staged cutover is the norm, and its length varies widely.** Opt-in, then default, then a dated opt-out end: Vercel 35 days, GitHub about 6 months, Atlassian about 9 months from Early Access to hard stop. Atlassian reported 2.6-2.7% opt-out (vendor figures). Fabric shows the other path: old view left in place with no announced end found.
7. **(c) Once the boundary goes, home stops being a directory.** Homes resume work across scopes: Google Cloud Quick access is "a cross project view", Atlassian has For you and Recent, Fabric has recent workspaces, items and favorites, AWS has widgets. The full catalog moves elsewhere (All products, Services, Workload hub), and Atlassian moved Projects out of Home. Google reports navigation "up to 43% faster" after its home change (vendor claim, method not given).
