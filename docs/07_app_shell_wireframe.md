# 07. App Shell 요구사항 → IA → 와이어프레임 (UI/UX 담당자용)

`.claude/skills/analysis-platform-wireframe` 스킬로 진행한 산출물. 플랫폼 전체를 감싸는 공통 프레임(사이드바/헤더/전역 필터바)을 설계한다 — 개별 분석 화면(생산성 분석 등)은 이 셸 안의 "Main Analysis Workspace" 영역만 갈아끼우는 구조가 된다.

**`docs/06_saas_design.md`와의 관계**: `06_saas_design.md`는 플랫폼 아키텍처 레벨 계약(Platform Kernel/Menu Registry/Shell Slot/Design Token/Governance)을 정의하는 **상위 문서**다. 이 문서는 그 계약 중 App Shell 한 화면을 Requirements→IA→Screen Spec→Wireframe→Data Requirements 단계로 더 구체화한 **하위 산출물**이다. 두 문서가 각자 만든 7그룹 IA(운영개요/설비관리/기준정보관리/생산성분석/지표관리/공지·VOC/관리·감사 ↔ `06_saas_design.md` §31의 Overview/Equipment/Master Data/Analytics/Metrics/Notice & VOC/Admin)는 명칭 언어만 다를 뿐 그룹 구성이 동일하다 — 상호 검증된 것으로 간주하고 이 문서에서 "미확정" 표기는 걷어냈다. 딥링크/URL 계약의 authoritative source는 `04_frontend_ui_ux.md`이고(`06_saas_design.md` §"Menu Extension Contract" 절 인용대로), 이 문서 §6은 그 계약을 App Shell 구현 단위로 구체화한 것이다.

**범위 주의**: 이 문서는 **셸 하나**의 설계다. 아래 IA 트리는 전체 정보구조 스케치이지 Phase 1에 동시 제공되는 화면 목록이 아니다 — Phase별 제공 범위는 `05_roadmap_and_open_questions.md`, `06_saas_design.md` §30(Phase Alignment)을 따른다. 이 플랫폼의 목적 자체가 "메뉴를 다 만드는 것"이 아니라 **그 메뉴들을 계속 얹어갈 수 있는 플랫폼(코어 셸 + 공통 기능)을 만드는 것**이라는 전제는 루트 `CLAUDE.md`와 `06_saas_design.md` §1에 명시돼 있다.

codex(gpt-6-astra, medium)의 리뷰를 반영해 1차 초안에서 수정한 버전이다. 리뷰에서 지적된 P1 4건은 본문에 반영, P2 2건은 미결 항목으로 명시해뒀다.

## 1. USER TASK

- **주 사용자**: 공정/설비 엔지니어(분석), 마스터데이터 관리자(설비관리·기준정보), 지표 관리자, 운영 관리자(권한·감사), 현업 문의자(VOC)
- **주요 작업**: 여러 메뉴를 오가며 같은 기간/설비 컨텍스트를 유지한 채 분석 → 상세 데이터로 드릴다운 → 필요시 VOC/공지 확인
- **셸이 다루는 결정**: 지금 보고 있는 데이터가 어떤 조직/기간/설비 스코프인지, 그 스코프가 화면 전환 후에도 유지되는지, 내 권한 범위에 어떤 메뉴가 보이는지
- **데이터 볼륨**: 메뉴 레지스트리 수십 개 이하, 즐겨찾기/최근방문은 사용자당 수십 건
- **사용 빈도**: 교대 내내 상주(lived-in)라고 가정했으나, 이는 검증된 요구가 아니라 가정이다 — 실사용 빈도 확인 전까지 UI 밀도·새로고침 정책의 근거로만 쓰고 확정 요구로 취급하지 않는다.
- **우선순위**: Desktop-first (기본 원칙 그대로)

## 2. IA

`docs/02`(도메인 메뉴 6개)와 `docs/04`(내비게이션 그룹 7개, 운영개요·관리·감사 포함)가 1:1로 안 맞는다고 두 문서 모두 명시했었다. 아래 7그룹 배치는 `06_saas_design.md` §31의 canonical wireframe(Overview/Equipment/Master Data/Analytics/Metrics/Notice & VOC/Admin)과 그룹 구성이 동일해 — 명칭 언어 차이만 있고 서로 다른 세션에서 독립적으로 같은 결론에 도달했다 — **7그룹안으로 확정 취급**한다. `wireframe-rules.md` L35("6개 도메인이 최상위")는 이 확정에 맞춰 갱신이 필요하다(별도 후속 작업).

### 교차 탐색 키 (리뷰 반영 — 수정됨)

1차 초안은 `(equipmentId, entityType, anchor)`를 모든 교차 탐색의 공통 키로 일반화했는데, 이는 잘못된 일반화였다. 정정:

- `(equipmentId, entityType, anchor)`는 **occurrence(분석 실행) 식별 우선 키**다 — 생산성 분석의 실행 상세, 설비 상세의 특정 구간 하이라이트처럼 "어느 occurrence를 보고 있는가"가 의미 있는 화면에만 적용.
- 설비 마스터 상세는 `equipment_id` 단독이 키(occurrence 없이도 열림).
- VOC·지표는 각각 자체 도메인 식별자(`vocId`, `metricId`+`metricVersion`)를 갖는 별개 객체 — occurrence 키로 대체하지 않는다.
- 화면 간 이동 시에는 **목적지 객체 식별자**(예: `equipmentId` 또는 `vocId`)와 **분석 컨텍스트**(occurrence anchor, 있다면)를 분리해서 전달한다. 구체적 필드명은 Phase 1 URL 계약에서 확정.

## 3. SCREEN SPECIFICATION — App Shell (이번 단계 대상)

| 항목 | 내용 |
|---|---|
| Purpose | 모든 화면 공통 골격 제공: 조직 컨텍스트, 메뉴 탐색, 전역 필터 상태 표시/편집 |
| Primary task | 메뉴 전환 + 조직/기간/설비 스코프 설정·확인 |
| Input | 사이트/공장/라인 선택, 메뉴 클릭/검색, 필터 칩 편집, 즐겨찾기 토글 |
| Output | 현재 스코프가 반영된 하위 화면, 딥링크 가능한 URL |
| Primary action | 메뉴 이동 |
| Secondary actions | Command Palette 검색, 즐겨찾기 추가, 필터 칩 제거/편집, 저장된 조회조건 불러오기(자리만 예약, Phase 3) |
| Navigation | 앱 진입점(로그인 후 랜딩) — 모든 하위 화면에 상주 |
| Data requirements | §6 참조 |
| Empty state | 즐겨찾기/최근방문 없음 → 안내 문구, 메뉴 자체는 항상 표시 |
| Loading state | 메뉴 레지스트리 로딩 중 스켈레톤 사이드바, 조직 컨텍스트는 마지막 세션값(미검증 후보)을 우선 표시하되 서버 재검증 전까지 확정 취급하지 않음 |
| Error state | 권한 조회 실패 시 메뉴 전체 숨김 아님 — 접근 가능 확인된 항목만 노출, 조회 실패 배너 |

- 사이드바: 그룹 접기/펼치기, 메뉴 검색, 권한/스코프에 따른 자동 숨김, 즐겨찾기(★)/최근방문 하단 고정 섹션

## 6. DATA REQUIREMENTS (리뷰 반영 — 대폭 확장)

### URL이 소유하는 상태 (셸 책임)

- 1급 분석 컨텍스트 키: `from`/`to`(기간), `equipmentIds`(복수), `lotIds`(검색 보조), `metricVersion`, `scopeId`(조직 컨텍스트 — **세션 전용이 아니라 URL 포함, 아래 참조**), 대시보드 탭/저장된 조회조건 식별자
- `savedViewToken` 자리 예약(비활성, Phase 3)
- occurrence anchor(`equipmentId, entityType, anchor`) — 해당하는 화면에서만

### 조직 컨텍스트(scopeId)는 URL 계약에 포함한다 — 1차 초안 정정

1차 초안은 "조직 스코프는 보안 재검증 대상이라 서버 세션이 근거"라는 이유로 URL에서 뺐는데, `docs/04` L50-59는 `scopeId`를 URL 계약 항목으로 명시하면서 **동시에** 서버가 권한을 재검증하도록 요구한다 — 둘은 상충하지 않고 함께 적용된다.

- URL에는 **요청된** 조직 컨텍스트를 담는다.
- 서버는 매 요청마다 현재 사용자가 그 조직 컨텍스트에 접근 가능한지 재검증한다.
- 접근 불가 시 **조용히 다른 조직으로 대체하지 않는다** — 명시적 오류/선택 화면으로 처리.
- 같은 URL을 다른 조직 권한을 가진 세션에서 열었을 때 결과가 달라질 수 있다는 것은 딥링크의 정상 동작이다(재현되는 것은 "요청한 조회조건"이지 "동일 조직 접근 권한"이 아님).

### 그 외 아직 열려 있는 항목 (Phase 1 계약에서 확정 필요)

- URL과 세션/최근방문 필터 스냅샷이 충돌할 때의 우선순위
- URL 계약 버전, 폐기된 필드, 잘못된 값 처리
- 뒤로가기 시 복원 범위(전역 필터만 vs 차트 로컬 확대까지)와 미지원 필터의 보존·재적용 규칙
- **시간 계약(Phase 0 미결, `docs/03` L24-33)**: 조회 구간 포함/제외 경계, 설비·사업장 원천 시간대 미확인 시 처리, 여러 사업장의 "같은 날짜" 의미, 날짜만 선택했을 때 시작/종료 시각 해석. wall-clock을 임의 변환하지 않는다는 원칙은 확정이지만 이 하위 항목들은 **미해결**이다. 셸은 이 계약이 확정되기 전까지 원본 wall-clock 값을 그대로 표시/전달하고, 다중 사업장 동시 조회는 계약 확정 전까지 범위를 좁혀둔다(단일 사업장 우선).

### 기타

- 메뉴 레지스트리: `{ id, group, label, path, requiredPermission, requiredScope }[]` — 코드 선언
- 조직 계층: 사이트 → 공장 → 라인 트리, 사용자 접근 가능 범위로 사전 필터링
- 즐겨찾기/최근방문: 사용자별, 메뉴 경로 + 마지막 필터 스냅샷(선택) — 이 스냅샷은 재적용 전 유효성 재검증 대상(§7)

## 7. INTERACTION RULES

- **필터 적용범위 혼용 금지**: 전역/탭/위젯/교차필터/저장된 조회조건 칩은 동일 스타일로 섞어 보여주지 않는다.
- **딥링크 왕복**: 셸에서 만들어지는 모든 URL은 재방문 시 동일 조회조건 + 지표 버전을 재현해야 한다. "같은 숫자"는 보장하지 않으므로 하위 화면에는 계산 기준시각을 표시할 책임이 있다(화면 스펙에서 재확인).
- **대상 화면이 필터를 지원하지 않을 때**: 조용히 버리지 않고 "이 화면에는 적용되지 않음" 배지 표시.
- **URL은 보안 경계 아님**: 조직 컨텍스트를 포함한 모든 URL 파라미터를 서버가 매 요청마다 재검증한다.
- **컨텍스트 변경 시 이전 데이터 미유지 — 조직 전환에 한정하지 않음(정정)**: 조직뿐 아니라 설비·기간이 바뀔 때도 이전 결과를 새 조건의 결과처럼 보여주지 않는다. "동일 컨텍스트 재조회 중 갱신 표시" 원칙은 컨텍스트가 바뀌지 않은 경우에만 적용.
- **마지막 세션값은 미검증 후보값**: 조직 전환 시 기존 설비·Lot 선택이 새 조직에서도 유효한지 재검증 없이 이어 쓰지 않는다.
- **차트 로컬 확대 vs 명시적 구간 선택**: 셸의 전역 필터/URL에는 후자만 반영, 전자는 화면 로컬 상태.
- **메뉴 자동 숨김**: 권한 없는 메뉴는 사이드바에서 완전히 숨김(비활성 표시 아님).
- **공지·VOC 미확인 배지 (미확정 — 리뷰 반영)**: 1차 초안의 "사이드바 통합 배지"는 문서에 없는 요구였다. 확정 요구는 (a) 공지 배너/목록 노출, (b) 분석 화면에 권한 범위 내 관련 VOC 수 표시, 두 가지뿐이다. 전역 통합 미확인 건수·알림 벨은 별도 제안으로 분리하고, 읽음 상태·집계 기준·권한 필터링 계약이 정해지기 전까지 셸 필수 요소로 만들지 않는다. 공지 배너 자체는 Phase 1 요구이므로 셸 내 위치/노출 조건(게시기간·대상 메뉴·권한 스코프)은 다음 이터레이션에서 확정한다.

## 8. DESIGN DECISIONS

1. IA 그룹 7개는 `docs/06_saas_design.md` §31 canonical wireframe과 그룹 구성이 일치해 확정으로 취급 — `wireframe-rules.md`의 6개 도메인 최상위 서술은 이 문서 작업에서 7그룹으로 갱신했다.
2. 전역 필터바는 헤더 바로 아래, 사이드바 밖에 고정 — 조직 컨텍스트(헤더)와 분석 필터(필터바)를 시각적으로 분리. **단 시각적 분리와 URL 계약 포함 여부는 별개 — 조직 컨텍스트도 URL에 포함(§6).**
3. 공지·VOC는 사이드바 한 그룹으로 묶되 내부적으로는 별도 도메인 모델 유지. 통합 배지는 채택하지 않음(§7).
4. `savedViewToken` UI는 비활성 placeholder로만 배치.
5. 교차 탐색 키를 "occurrence 전용"과 "목적지 객체 식별자"로 분리(§2) — 1차 초안의 과잉 일반화 수정.
6. 시각 스타일(색상/타이포/간격)은 여기서 결정하지 않음 — Step 5(Design System)로 이연.
