# 플랫폼의 가치 — 사용자·운영자 입장에서 (소개 사이트 재구성 입력)

작성 2026-10-19, 에이전트 의견(사용자 요청). 상태: **Candidate** — 사이트 재구성(#468)의 입력이다. 결정 문서가 아니며, 아래 "정할 것"은 사용자가 정한다.

## 1. 왜 이 문서인가

사용자 지적(2026-10-19): 지금 소개 사이트(`site/`, GitHub Pages)는 개발자 입장에서는 좋은 점이 보이지만, **사용자나 운영자 입장에서 플랫폼이 무엇을 갖고 있고 왜 그걸 하는지**가 안 보인다. 플랫폼으로서의 기능 요구사항이 명확하지 않고, 그래서 설득이 안 된다. 목표는 다른 사람이 봐도 "플랫폼이면 이런 걸 가져야 하고, 그래서 이걸 한다"를 이해하게 하는 것이다.

## 2. 지금 사이트 진단

섹션 제목을 순서대로 보면 거의 전부 **만드는 쪽의 논리**다.

| 지금 섹션 | 말하는 것 | 사용자·운영자에게 빠진 것 |
| --- | --- | --- |
| 메뉴마다 따로 만들면, 같은 기능이 메뉴 수만큼 생깁니다 | 중복 구현 비용 | "그래서 내 일이 어떻게 달라지나" |
| 플랫폼이 맡는 다섯 가지 | Kernel·컴포넌트·차트·레이아웃·연결(내부 구조) | 구조 이름이지 사용자가 겪는 장면이 아님 |
| 업무 시스템을 한 셸에 모으면 | 조건과 근거가 끊기지 않음 | 거의 유일한 사용자 관점 — 그러나 장면 없이 문장뿐 |
| 새 메뉴가 처음부터 받는 것 | 컴포넌트 21개, primitive | 개발자용 |
| 단독 앱으로 만들 때와 무엇이 다른가 | 조립 비용 | 개발자·아키텍트용 |
| 목표는 사용자가 직접 만드는 분석 | 비전 | 지금 없는 것 — 근거 약함 |
| 붙이면 좋아지는 기술 | 라이브러리 후보 | 개발자용 |

진단 세 줄:

1. **기능 요구사항이 없다.** "플랫폼이라면 이것을 보장해야 한다"는 목록이 사용자·운영자 언어로 한 번도 나오지 않는다. 다섯 갈래(Kernel 등)는 구현 분류다.
2. **장면이 없다.** 사용자가 실제로 하는 일(이상을 보고, 원인을 찾고, 알리고, 고쳐졌는지 확인한다)이 처음부터 끝까지 이어지는 이야기가 없다.
3. **비교 대상이 틀렸다.** "단독 앱과 비교"는 개발 방식 비교다. 의사결정자와 현업이 실제로 비교하는 것은 "지금 쓰는 엑셀·BI 도구·팀별 화면"이다.

## 3. 플랫폼 기능 요구사항 — 사용자·운영자 언어로

형식: **요구** — 이게 없을 때 겪는 일 → 플랫폼이 보장하는 것. 상태는 mock 위 구현 기준이다(실서버·SSO 연결은 M4 대기).

### 3.1 사용자(현업 분석가·엔지니어)

| ID | 요구 | 없으면 | 플랫폼이 보장하는 것 | 상태·근거 |
| --- | --- | --- | --- | --- |
| U1 | 조건이 따라온다 | 메뉴를 옮길 때마다 사이트·기간·room·설비를 다시 고른다 | 전역 Context가 메뉴를 넘어 유지된다. 범위가 바뀌면 맞지 않는 값은 지우고 알린다 | 구현, 06 §6 |
| U2 | 본 화면을 그대로 넘긴다 | 캡처를 붙이고 "기간은 이렇게, 필터는…"을 설명한다 | 주소가 곧 화면이다. 링크 복사·새로고침·뒤로가기에 같은 화면 | 구현, 06 §6, E2E |
| U3 | 숫자를 믿을 수 있는지 안다 | 빈 표가 "0건"인지 "조회 실패"인지 모른다. 잘못된 조건이 조용히 바뀐다 | 0건·실패·과대·모집단 상태를 구분해 보인다. 잘못된 값은 필드 이름과 원래 값으로 알린다 | 구현, 06 §19, ADR-0034 |
| U4 | 원인까지 내려갔다 돌아온다 | 지표 화면과 설비 화면이 따로 놀아 원인을 손으로 맞춘다 | 지표 → 느린 실행 → 설비 상세 드릴다운과 복귀 | 구현, 06 §22, #225 |
| U5 | 어느 메뉴든 같은 손버릇 | 메뉴마다 표·필터·차트 쓰는 법이 다르다 | 표(정렬·컬럼·복사·내보내기), 상세 패널, 차트(확대·구간·비교·주석), 필터 줄이 공통 | 구현, 06 §13·§16 |
| U6 | 원하는 곳에 바로 간다 | 메뉴 트리를 뒤진다 | 업무 시스템 전환기, Ctrl+K 팔레트, 최근·즐겨찾기, 시스템별 마지막 화면 복원 | 구현, ADR-0028·0042 |
| U7 | 본 자리에서 바로 알린다 | 화면을 캡처해 메일·메신저로 따로 신고한다 | 그 시스템으로 좁힌 VOC 등록 링크, FeedbackOps에서 원래 화면으로 복귀, 내 VOC 상태 | 구현, ADR-0045, #448·#451 |
| U8 | 해석을 남긴다 | 차트 위 판단이 대화방에 흩어진다 | 차트 주석(작성자만 삭제, 감사에 남음) | 구현, ADR-0041 |

### 3.2 운영자(권한·메뉴·감사 담당)

| ID | 요구 | 없으면 | 플랫폼이 보장하는 것 | 상태·근거 |
| --- | --- | --- | --- | --- |
| O1 | 권한은 한 곳에서 | 메뉴마다 권한이 따로 있어 회수·점검이 메뉴 수만큼 | 공간 진입·메뉴 열기·사이트 범위를 한 규칙으로 판정. 다른 범위 데이터 노출은 최우선 결함 | 구현(mock 세션), 06 §9, ADR-0026 |
| O2 | 누가 무엇을 바꿨나 | 변경 이력이 메뉴마다 다르거나 없다 | 설비·지표·차트 주석 변경이 공용 감사 저장소 하나에, 감사 화면 하나에서 조회 | 구현, ADR-0048 |
| O3 | 무엇이 실제로 쓰이나 | 메뉴 정리·투자를 감으로 정한다 | 메뉴 활용률을 플랫폼이 공통 계측(식별 필드만) | 구현, ADR-0020 |
| O4 | 등록된 것을 한눈에 | 어떤 화면이 어떤 권한으로 열리는지 문서로 쫓는다 | 운영 콘솔의 Registry 카탈로그(메뉴·페이지 유형·권한) | 구현 |
| O5 | 새 메뉴도 같은 품질 | 만든 사람마다 상태 표시·권한·감사 수준이 다르다 | 공통 계약과 E2E 계약 검사가 새 메뉴에도 같은 기준을 건다 | 구현, `apps/platform-e2e` |
| O6 | 알림·의견 창구가 하나 | 공지·VOC가 시스템마다 다르다 | 공지·내 VOC는 공간 밖 전역 화면, VOC 처리는 FeedbackOps 하나 | 구현, ADR-0027·0028 |

요구 ID(U1–U8, O1–O6)는 사이트가 그대로 인용할 수 있게 둔다. 각 행의 근거는 사이트 원장(`site/SOURCES.md`)에 행으로 옮긴 뒤 쓴다(site/AGENTS.md 규칙).

## 4. 왜 메뉴가 아니라 플랫폼이 해야 하나 (사용자 언어로)

위 요구는 **메뉴 하나가 잘 만든다고 생기지 않는다.** 모두 "메뉴와 메뉴 사이"에서 깨지는 것들이다.

- U1·U2·U4는 메뉴를 **옮길 때** 깨진다. 메뉴 하나 안에서는 문제가 없다.
- U5는 메뉴가 **여러 개일 때만** 생기는 문제다.
- O1·O2·O3는 메뉴마다 따로 하면 **운영자가 메뉴 수만큼 일한다.**

그래서 "플랫폼이 공통으로 맡는다"는 말은 개발 편의가 아니라 **이 요구들을 지킬 수 있는 유일한 자리**라는 뜻이다. 지금 사이트의 첫 문장("같은 기능이 메뉴 수만큼 생긴다")은 이 논리의 개발자 쪽 절반만 말한다.

## 5. 무엇과 비교되나 — 솔직하게

| 비교 대상 | 플랫폼이 이기는 곳 | 이기기 어려운 곳 |
| --- | --- | --- |
| 팀별로 따로 만든 화면들 | U1–U5, O1–O5 전부. 문제를 겪어 본 사람에게 강하다 | 겪어 보지 않은 사람에게는 와닿지 않는다 → 장면으로 보여야 한다 |
| BI 도구(Tableau·Power BI·Grafana 등) | 반도체 도메인 맥락(사이트 범위, EquipmentID·Lot·Recipe)이 기본, 지표에서 설비·실행 단위까지 드릴, 사이트별 권한·감사, VOC·개선과의 연결 | 대시보드·공유 링크·권한은 BI도 있다. U2·U5만으로는 못 이긴다 |
| 엑셀·수작업 | 재현성(U2), 신뢰 표시(U3), 이력(O2) | 자유도. 사용자가 직접 조합하는 분석(#294)이 생기기 전까지는 엑셀이 더 자유롭다 |

## 6. 핵심 이야기 — 끊기지 않는 개선 고리

기능을 나열하는 것보다 **고리 하나를 끝까지** 보여 주는 쪽이 설득력이 크다고 본다. BI 도구로는 이 흐름이 중간에 끊긴다.

| 단계 | 사용자가 하는 일 | 기대는 요구 | 지금 mock 데모로 |
| --- | --- | --- | --- |
| 1 | 지표관리·생산성에서 이상을 본다 | U1·U3 | 가능 |
| 2 | 느린 실행 → 원인 설비까지 내려간다 | U4·U5 | 가능 |
| 3 | 그 화면에서 VOC를 낸다(그 시스템으로 좁혀 열림) | U7 | 링크까지 가능. FeedbackOps 화면은 별도 제품 |
| 4 | FeedbackOps에서 개선 Task로, 원인 설비 링크로 플랫폼에 돌아온다 | U7, 딥링크 B 방향 | 계약·링크 구현. 실제 FeedbackOps 연결은 세션 공유(#150) 뒤 |
| 5 | 개선 뒤 같은 지표를 이전 기간과 비교해 효과를 본다 | U2·차트 Compare | 가능(mock 값) |
| 6 | 누가 무엇을 바꿨는지 감사로 확인한다 | O2 | 가능 |

한 문장: **"보는 데서 끝나지 않고, 고쳐졌는지 확인하는 데까지 이어지는 곳."** 사이트의 첫 화면은 이 문장과 이 표에서 시작하는 것이 좋다고 본다.

## 7. 아직 약한 것 (사이트에서 숨기지 않는다)

- **숫자가 없다.** 도입 전 기준선(#233: 원인을 찾는 데 걸리는 시간, 조건을 다시 고르는 횟수 등)이 정해지지 않아 "빨라진다"를 말할 수 없다. 숫자 자리는 비워 두고, 무엇을 잴지만 적는다.
- **실데이터가 없다.** 실서버·SSO(M4)가 사내 답 대기다. 장점은 아직 "구조로 보장된 약속"이다. 사이트에는 "mock 위에서 끝까지 동작"과 "실연결 대기"를 지금처럼 구분해 적는다.
- **"와" 기능이 아직 없다.** 사용자가 직접 분석 화면을 조합하는 단계(#294)는 결정 대기다. 비전으로만 짧게 둔다.

## 8. 사이트 재구성 제안

독자를 앞에 두고, 개발자 내용은 뒤로 보낸다.

1. **첫 화면 — 한 문장 + 고리**: §6의 한 문장과 6단계 고리. 각 단계에 데모 링크(D1–D10 체계 재사용).
2. **플랫폼이 보장하는 것 — 사용자**: U1–U8을 "없으면 → 있으면" 카드로. 화면 캡처 한 장씩(기존 `shots.mjs` 갤러리 재사용).
3. **플랫폼이 보장하는 것 — 운영자**: O1–O6 같은 형식.
4. **왜 메뉴가 아니라 플랫폼인가**: §4의 세 줄(메뉴 사이에서 깨지는 것).
5. **무엇과 비교되나**: §5 표(BI·팀별 화면·엑셀), 약한 곳도 그대로.
6. **지금 되는 것과 아직 아닌 것 / 남은 위험과 부탁드리는 것**: 지금 섹션 유지, §7 반영.
7. **개발자를 위한 부록**: 지금의 다섯 갈래, 새 메뉴가 받는 것, 단독 앱 비교, 기술 후보는 여기로 옮긴다(지우지 않는다).

지켜야 할 것(`site/AGENTS.md`): 모든 주장은 `SOURCES.md` 원장 행부터, 합성 값은 예시로 표시, 제품 토큰 사용, D1–D10 문장은 템플릿 한 곳, 배포 전 데모 링크를 브라우저로 확인, 캡처 선택자는 한국어 역할 이름(문구가 바뀌면 shots가 깨진다).

## 9. 정할 것 (사용자)

1. **주 독자**: 의사결정자(승인) / 현업(쓸 사람) / 운영자 중 첫 화면을 누구에게 맞출지. 권고: 의사결정자 — 고리 + 비교표가 승인 논리이고, 현업·운영자는 2·3절로 이어진다.
2. **고리 시나리오 채택**: §6을 첫 화면 이야기로 쓸지, 다른 대표 장면이 있는지(사내에서 실제로 아픈 장면이 있으면 그쪽이 낫다).
3. **숫자 없는 상태의 표현 수위**: 기준선이 없으니 "줄어든다" 대신 "다시 고르지 않는다"처럼 동작으로만 말할지.
4. **화면 확인 방식**: 사이트도 보이는 모양이 바뀌므로 `?variant=`가 아닌 정적 페이지 시안 2–3안(첫 화면 구성)을 보고 고를지.

## 10. 다음 세션 순서

1. 위 "정할 것"을 한 번에 묻는다.
2. `SOURCES.md`에 U·O 요구별 근거 행을 더한다(새 주장은 원장부터).
3. 첫 화면 시안 2–3안 → 사용자 선택 → 본문 재구성 → 캡처 재생성(`shots.mjs`) → 데모 링크 브라우저 확인 → Pages 배포.
