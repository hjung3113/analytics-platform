# 16. 분석 보드 — 하단 시트 탭 · 그리드 칸 · 칸별 조건

상태: **Candidate — 방향(소유자, 2026-10-18)** / **Open — 이 문서 §10의 결정 전부**. **구현하지 않는다.** 셸 구조 결정([15](15_multi_workspace_ui.md), #249)이 먼저이고, 이 문서는 그 결정이 보드를 막지 않도록 미리 정할 자리(§8)를 적는다. 추적: [#421](https://github.com/hjung3113/analytics-platform/issues/421).

> 전역 계약은 [06](06_platform_ui_contract.md)이 소유한다. 이 문서는 보드가 06의 어느 계약을 넓혀야 하는지 적을 뿐, 06을 바꾸지 않는다. 바꿀 때는 06과 ADR에서 바꾼다.

## 1. 문제

분석은 한 메뉴만 보지 않는다. 엔지니어는 관련된 여러 메뉴(사이클타임 상세 + 설비 Top View + 지표 상세)를 함께 보거나, 같은 메뉴를 다른 조건(지난달 vs 이번 달, PHOTO vs ETCH)으로 나란히 본다. 지금 플랫폼은 화면 하나 = URL 하나라서, 그때마다 브라우저 창이나 탭을 새로 연다. 창마다 셸과 사이드바가 반복되고, 창 사이의 배치는 저장되지 않으며, 다음 날 같은 비교를 다시 만들어야 한다.

## 2. 범위

- **들어감**: 본 화면과 따로 여는 작업대(보드), 화면 아래 시트 탭, 탭마다 그리드 배치, 칸마다 업무 시스템의 분석 메뉴 하나, 칸마다 독립 조건, 보드 저장·공유.
- **빠짐**:
  - 칸끼리 값을 합치는 계산(이 칸의 P95 − 저 칸의 P95). 서로 다른 시스템의 데이터를 합치는 교차 분석이라 별도 결정이다(사이트 비전 ③ 사용자 비정형 분석).
  - 메뉴를 누르면 기본으로 새 탭에 여는 동작. §7 참조.
  - 본 화면 레이아웃 변경. 보드를 쓰지 않는 사람에게는 지금 화면 그대로다.

## 3. 용어

| 용어 | 뜻 |
| --- | --- |
| 보드(Board) | 사용자가 만든 작업대 하나. 시트 여러 장을 가진다. |
| 시트(Sheet) | 화면 아래 탭 하나. 레이아웃과 칸들을 가진다. |
| 칸(Pane) | 시트의 그리드 한 칸. 메뉴 화면 하나와 그 화면의 page 상태를 가진다. |
| 기본 조건 | 새 시트·새 칸이 처음 받는 Context 값(기간·Scope 등, 06 §6). 본 화면의 전역 Context에서 시작한다. 받은 뒤에는 연결이 없다. |
| 칸 조건 | 칸 하나가 가진 Context 전체. 칸마다 독립이고 사용자가 모두 바꿀 수 있다. |

## 4. 화면 구조 (Candidate)

- **진입**: 레일 도구 영역의 `분석 보드`(메뉴 검색 아래). 메뉴의 `보드에 열기`(사이드바 행의 ⋯ 메뉴·가운데 클릭)와 페이지 머리의 같은 동작.
- **보드 화면**: 업무 시스템 사이드바를 붙이지 않는다(홈·전역 유틸리티와 같은 취급, ADR-0028). 페이지 머리 50px에 보드 이름, 레이아웃 선택(1×1 · 1×2 · 2×1 · 2×2), 지금 고른 칸의 조건(Context 바).
- **시트 탭 띠**: 본문 맨 아래, 높이 36px 안팎. 탭 추가(+), 이름 바꾸기(더블클릭), 끌어서 순서 바꾸기, 복제, 삭제(되돌리기 제공). 위쪽은 브라우저 탭이 쓰므로 아래에 둔다.
- **칸 머리**: 업무 시스템 이름 칩, 메뉴 이름, 조건 칩(그 칸의 조건 요약, 같은 시트의 다른 칸과 다른 키는 강조), `본 화면에서 열기`, `바꾸기`, `복제`, `비우기`.
- **빈 칸**: `분석 화면 넣기` — 권한 있는 시스템의 보드 지원 메뉴만 고른다.
- **칸 묶음**(후속): 칸 몇 개만 같은 조건을 따르게 묶는다(엑셀의 셀 참조와 비슷).

시안: 셸 탑재 비교 시안의 "분석 보드" 화면(#249 코멘트 링크). 시안은 버리는 코드이고 결정은 이 문서와 이슈에 남는다.

## 5. 조건 모델 (Open — 방향은 소유자 2026-10-18)

- **칸마다 자기 Context를 통째로 가진다.** 새 시트·새 칸은 기본 조건(본 화면의 전역 Context, 또는 `보드에 열기`를 누른 화면의 Context)을 **복사해서** 시작한다. 그 뒤로는 칸끼리, 그리고 기본 조건과 연결이 없다. 사용자는 칸마다 기간·Scope·설비 선택 등 모든 키를 다르게 둘 수 있다. 위층 값을 물려받는 상속은 두지 않는다.
- 같은 조건을 여러 칸에 맞추고 싶을 때는 **명시적 일괄 동작**을 쓴다: 칸 머리의 `이 조건을 시트의 모든 칸에 적용`, 시트 탭의 `이 시트 조건을 다른 시트에 복사`. 한 번 복사하는 동작이고 이후 연결은 남지 않는다. 기본 조건을 바꿔도 이미 있는 칸은 바뀌지 않는다.
- 칸 머리에는 그 칸의 조건 요약을 늘 보인다. 한 시트 안에서 칸끼리 다른 키는 강조해, 무엇이 다른 비교인지 한눈에 보이게 한다.
- **"화면당 전역 Context 하나"는 보드에서 성립하지 않는다.** 지금 06 §6은 한 화면에 전역 Context 하나를 두고(`usePlatform().global`), 셸 Context 바가 그것을 편집한다. 보드에서는 Context가 칸마다 하나씩 있다. 본 화면을 "칸이 하나뿐인 경우"로 보면 06의 "전역 Context"는 "현재 칸의 Context"로 일반화되고, 본 화면에서는 지금과 똑같이 동작한다. 이 일반화는 06 계약 변경이라 ADR로 정한다(§10).
- 보드 화면의 Context 바는 **지금 고른 칸의 조건**을 편집한다(칸을 누르면 바가 그 칸을 가리킨다). 칸 머리의 조건 칩도 같은 편집기를 연다.
- Kernel이 칸마다 Context Provider를 주고, 메뉴 화면은 화면 전역이 아니라 자기 칸의 Context를 읽는다. 메뉴 코드가 이미 Kernel 훅으로만 Context를 읽으므로 바꾸는 쪽은 Kernel 한 곳이다(§8).
- Scope도 칸마다 다를 수 있다. 칸마다 서버가 그 Scope 권한을 다시 판정한다(06 §6.2). 한 칸이 거부되면 그 칸만 권한 상태가 된다.
- 지원하지 않는 Context(06 §6.4 보존 규칙)와 Context 변경 시 지울 page 키(`contextResetKeys`)는 칸 단위로 같은 규칙을 따른다.

## 6. 메뉴 쪽 요구 (Candidate)

- **보드 지원 선언**: manifest에 보드 지원 여부를 선언한다(필드명 미정). 선언하지 않은 메뉴는 `분석 화면 넣기` 목록에 나오지 않는다.
- **좁은 칸**: 2×2 칸은 1440 화면에서 본문 폭의 절반 안팎이다. 화면은 자기 컨테이너 폭으로 반응해야 한다(뷰포트 기준 아님). 표 폭 맞춤(`tableFit`)과 동작 열 compact(ADR-0037)는 이미 자기 폭 기준이다.
- **page 상태**: 칸의 page 키(탭·정렬·페이지·드릴 단계)는 브라우저 URL이 아니라 칸 상태에 산다. 메뉴는 Kernel의 page 상태 API로만 읽고 쓴다(지금 `pageParam`/`setPage`) — 그러면 칸에서는 Kernel이 저장 위치만 바꾼다.
- **상세 패널**: 오른쪽 440px 상세 슬롯(ADR-0011·0013)은 한 화면에 하나다. 보드에서는 칸 안 드로어로 열지, 보드 전체 슬롯 하나를 칸들이 나눠 쓸지 정해야 한다(§10).
- **모듈 화면**(ADR-0038·0039): FeedbackOps·EV 모듈 화면도 호스트 포트로 Context·page 상태를 받으므로, 같은 규칙으로 칸에 들어갈 수 있다.

## 7. 메뉴 클릭의 기본 동작

메뉴를 누르면 기본으로 새 시트·칸에 여는 방식은 쓰지 않는다(권장). 지금은 화면 하나 = URL 하나라서 새로고침·뒤로가기·링크 복사가 그대로 된다(06 §6.4). 기본을 탭으로 바꾸면 탭 묶음 전체를 URL이나 서버에 저장해야 하고, 뒤로가기가 무엇을 되돌리는지(칸 안 이동인지 시트 전환인지)를 새로 정해야 한다. 기본은 지금처럼 이동하고, `보드에 열기`로 보드를 쓴다.

## 8. 셸 결정에서 지금 정해 둘 것

셸 구조 ADR(#249)에 함께 적어 보드를 막지 않게 한다.

- **진입 자리**: 레일 도구 영역(메뉴 검색 아래)에 플랫폼 소유 도구 하나. 셸 안이 시스템 전환 아이콘 방식(시안 D안)이든 공간 레일 방식이든 같은 자리다.
- **하단 띠 공간**: 보드 화면에서만 본문 아래 36px 안팎을 쓴다. 표 높이 맞춤(`tableFit`)이 본문 영역(`data-platform-page-content`)을 관찰하므로, 띠는 그 영역 밖(아래)에 둔다.
- **전역 Context 바와의 관계**: 보드 화면의 Context 바는 지금 고른 칸의 조건을 편집한다. 셸 ADR은 Context 바를 "현재 칸의 Context 편집기"로 적어 두어, 보드가 생겨도 바의 의미가 바뀌지 않게 한다(본 화면은 칸이 하나).
- **Context를 읽는 길은 Kernel 훅 하나**: 지금 메뉴 코드는 URL을 직접 읽지 않고 Kernel 훅(`usePlatform`의 전역 Context·`pageParam`·`setPage`)만 쓴다(2026-10-18 확인). 이것을 메뉴·모듈 규칙으로 유지한다. 깨지면 칸 범위 Context를 Kernel 한 곳에서 바꿀 수 없다.

## 9. 단계 (Candidate)

1. 셸 여지(§8)를 셸 ADR에 적는다.
2. 1×1 · 1×2 · 2×1 · 2×2, 모든 칸이 같은 기본 조건(칸별 편집 없음), 탭 세션 범위 저장.
3. 06 칸 단위 Context ADR, 칸 Context(Kernel), 칸마다 조건 편집과 일괄 적용·복사 동작, 보드 지원 선언, 좁은 칸 점검.
4. 서버 저장·공유(새 쓰기 포트), 칸별 권한 재판정, 시트 복제·칸 복제·칸 묶음.
5. 칸끼리 값을 합치는 교차 분석 — 별도 결정.

다시 볼 조건: 셸 구조 ADR이 Decided가 되고, 실제 메뉴 2–3곳에서 "여러 화면을 나란히 본다"는 요구가 확인될 때(06 §24).

| 보드 URL | 보드 ID + 시트 순번만 / 칸 상태까지 URL에 인코딩 | 보드 ID + 시트 — 칸 상태는 저장소에 |
| 보드 저장 위치 | 플랫폼 백엔드 새 쓰기 포트 / 사용자 설정 저장소 공용(15 Candidate의 "다른 사용자 설정 저장") | 미정 — 쓰기 포트가 아직 없다(ADR-0039도 쓰기는 범위 밖) |
| 상세 패널 | 칸 안 드로어 / 보드 전체 슬롯 하나 공유 | 미정 |
| 동시 조회 | 칸마다 조회 수명주기(취소·세대) 그대로 + 서버 동시 실행 상한·캐시 | 서버 상한 값은 실서버 연결(#154) 때 |
| 활용률 계측 | 칸 열림을 메뉴 사용으로 셈 / 보드 사용을 따로 셈 | 미정 |
| 공유 | 받는 사람 권한으로 칸마다 다시 판정, 볼 수 없는 칸은 권한 상태 | 이 방향(06 §6.2) |

## 11. 백엔드에 생기는 일

- **보드 저장소**: 보드·시트·레이아웃·칸별 메뉴 ID·칸 조건·page 상태를 사용자별 문서로 저장한다. 공유하면 소유자·공유 대상·감사 기록이 필요하다.
- **쓰기 포트**: 지금 `PlatformAdapter`는 읽기 중심이다(쓰기는 주석 등 일부). 보드 저장은 새 쓰기 포트와 서버 저장소 소유자 결정이 필요하다.
- **동시 조회 부하**: 2×2 시트는 한 화면 질의가 네 배다. 시트를 바꿀 때 보이지 않는 시트의 칸은 조회하지 않는다(화면에 보이는 시트만 마운트).
- **시스템마다 다른 서버**: 칸 하나는 플랫폼 마트, 다른 칸은 FeedbackOps·EV 서버를 부른다. 모듈이 자기 서버를 부르는 구조(ADR-0038) 그대로면 보드는 배치만 하고 데이터를 합치지 않는다.
