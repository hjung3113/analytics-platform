# 16. 분석 보드 — 하단 시트 탭 · 그리드 칸 · 칸별 조건

상태: **Decided — 1차 범위의 동작(사용자, 2026-10-19 #421 설계 질의 Q1–Q25)** / **Decided — 칸 머리·선택 표시([ADR-0051](adr/0051-analysis-board-pane-header-signal-chips-numbered-selection.md), 2026-10-19)** / **Deferred — §10**. 구현은 나눠 진행한다: Kernel 칸 Context(#496) 완료, 보드 골격(#497a: `/board` 플랫폼 화면·시트 탭 띠·그리드·칸 선택·Context 바·저장·되돌리기·레일 진입)은 이 사양대로 구현했고 칸 머리 차이 칩·`⋯` 동작·일괄 적용/복사·`분석 보드에 열기…`·상세 슬롯 공유(#497b)와 메뉴 보드 지원(#498)은 남았다. 추적: [#421](https://github.com/hjung3113/analytics-platform/issues/421). 용어는 [GLOSSARY](../GLOSSARY.md) "분석 조건과 분석 보드".

> 분석 Context의 범위 계약은 [06 §6.5](06_platform_ui_contract.md#65-분석-context의-범위--칸-decided-adr-0049)와 [ADR-0049](adr/0049-analysis-context-belongs-to-a-pane.md)가 소유한다. 이 문서는 보드 화면과 동작을 적는다.

## 1. 문제

분석은 한 메뉴만 보지 않는다. 엔지니어는 관련된 여러 메뉴(사이클타임 상세 + 설비 Top View + 지표 상세)를 함께 보거나, 같은 메뉴를 다른 조건(지난달 vs 이번 달, PHOTO vs ETCH)으로 나란히 본다. 지금 플랫폼은 화면 하나 = URL 하나라서, 그때마다 브라우저 창이나 탭을 새로 연다. 창마다 셸과 사이드바가 반복되고, 창 사이의 배치는 저장되지 않으며, 다음 날 같은 비교를 다시 만들어야 한다.

## 2. 범위

- **1차(이번 구현, §9의 1·2단계)**: 보드 화면, 시트 탭 띠, 시트마다 1×1 · 1×2 · 2×1 · 2×2, 칸마다 메뉴 하나와 독립 분석 Context, 칸 조건 편집과 일괄 적용·복사, 보드 지원 선언, 좁은 칸 점검. 저장은 브라우저(§7).
- **뒤로 미룸(§10)**: 서버 저장·공유, 여러 보드, 시트 복제, 칸 묶음, 서버 동시 실행 상한.
- **빠짐**:
  - 칸끼리 값을 합치는 계산(이 칸의 P95 − 저 칸의 P95). 서로 다른 시스템의 데이터를 합치는 교차 분석이라 별도 결정이다(사이트 비전 ③ 사용자 비정형 분석).
  - 메뉴를 누르면 기본으로 보드에 여는 동작(§7).
  - 본 화면 레이아웃 변경. 보드를 쓰지 않는 사람에게는 지금 화면 그대로다.
- **재개 조건 처리**: 처음 적은 다시 볼 조건 중 셸 구조 결정은 [ADR-0042](adr/0042-system-switcher-and-system-owned-rail.md)로 충족됐다. "실제 메뉴 2–3곳에서 나란히 보기 요구 확인"은 소유자 방향(2026-10-18)으로 갈음했다(사용자, 2026-10-19). 보드는 메뉴 사이 반복 UI 패턴이 아니라 Kernel·레이아웃 계약이라 06 §24의 공통화 기준이 그대로 해당하지 않는다.

## 3. 용어

[GLOSSARY](../GLOSSARY.md)의 분석 Context · 본 화면 · 분석 보드 · 시트 · 칸 · 기본 조건을 쓴다. 칸을 "패널"이라 부르지 않는다(상세 패널과 섞인다). 분석 보드는 Page Archetype(06 §12)이 아니다. 칸 안의 메뉴 화면은 자기 아키타입을 유지한다.

## 4. 화면 구조 (Decided)

- **진입**:
  - 레일 공통 도구의 `분석 보드`(메뉴 검색 아래, 모든 시스템에서 같은 자리, ADR-0042). 보드 지원 메뉴를 하나라도 열 수 있는 사용자에게만 보인다.
  - 보드 지원 메뉴의 페이지 머리 `⋯`에 `분석 보드에 열기…`. 누르면 대화상자에서 넣을 곳을 고른다: **새 시트**(1×1, 기본 선택) / 기존 시트의 빈 칸 / 기존 칸 바꾸기(바꾼다는 확인). 넣은 뒤 보드로 이동한다. 사용자가 고르기 전에는 어떤 칸도 덮어쓰지 않는다.
  - 메뉴 클릭의 기본 동작은 지금처럼 본 화면 이동이다.
- **보드 화면**: 업무 시스템 사이드바를 붙이지 않는다(홈·전역 유틸리티와 같은 취급, ADR-0028). 페이지 머리 50px에 보드 이름, 레이아웃 선택(1×1 · 1×2 · 2×1 · 2×2), 선택된 칸의 Context 바.
- **선택된 칸**: 시트에는 늘 선택된 칸이 하나 있다. 보드를 열면 첫 칸이 선택돼 있다. 칸을 누르면 선택이 옮겨 간다. Context 바는 선택된 칸의 분석 Context를 편집하고, 빈 칸이 선택되면 바는 비활성이다.
  - **표시(ADR-0051)**: 모든 칸(빈 칸 포함)에 번호 배지 `칸 N`이 늘 보인다. Context 바 앞머리·상세 머리·토스트·팝오버도 같은 번호를 쓴다. 선택된 칸은 번호 배지가 강조색이 되고, 칸 전체 높이의 왼쪽 2px 강조 막대와 머리 선택 표면(공유 selected 표면)을 가진다. 색만으로 선택을 나타내지 않는다.
  - **키보드**: 칸 머리 제목이 "칸 N 선택" 버튼이고, 칸 안으로 포커스가 들어가면(focus-within) 그 칸이 선택된다. 숫자 키 단축키는 두지 않는다.
  - **머리 동작은 먼저 선택한다**: `⋯`·`같음 N`·칩 등 칸 머리의 어떤 동작이든 열 때 그 칸을 먼저 선택한다(바가 다른 칸을 보이는 동안 다른 칸의 조건이 퍼지지 않게).
- **시트 탭 띠**: main 열 맨 아래, 높이 40px + 위 경계 1px, 본문 스크롤 밖(§8). 시트 추가(+), 이름 바꾸기(더블클릭), 끌어서 순서 바꾸기, 삭제(실행 취소 제공), `이 시트 조건을 다른 시트에 복사`. 시트는 최대 20장. 시트 탭은 ←/→로 이동하고(`role=tab`), 시트 동작은 탭 밖 메뉴로 연다(탭 안에 버튼을 넣지 않는다).
- **칸 머리(ADR-0051, 한 줄)**: 번호 배지, 업무 시스템 이름 칩, 메뉴 이름, 같은 시트의 다른 칸과 **다른 키만** `키 값` 칩(강조색), 같은 키는 `같음 N`(누르면 그 칸의 조건 전체 Popover — 정의 목록과 `Context 바에서 편집`), 동작 `⋯`(`@ap/ui` DropdownMenu): `이 조건을 시트의 모든 칸에 적용`, `본 화면에서 열기`(그 칸의 조건으로 본 화면을 연다), `바꾸기`, `복제`(같은 메뉴·같은 조건의 칸을 빈 자리에), `비우기`.
  - **넘침**: 메뉴 이름은 최소 폭을 지키고 차이 칩은 줄바꿈하지 않는다. 들어가지 않는 차이 칩은 `+N 다름` 칩 하나로 접고 누르면 같은 Popover를 연다(Context 바 넘침 칩 모양, ADR-0015). 같은 키가 0개면 `같음` 버튼을 숨기고, 칸이 하나뿐이면 차이 칩 없이 `조건 N`만 보인다.
  - **접근 이름**: `칸 2 동작`, `칸 2의 같은 조건 3개`처럼 칸 번호를 넣고 보이는 문구와 맞춘다.
- **빈 칸**: `분석 화면 넣기` — 권한 있는 시스템의 보드 지원 메뉴만 고른다.
- **레이아웃 줄이기**: 2×2 → 1×2처럼 줄여 내용이 있는 칸이 넘치면, 바꾸기 전에 "칸 N개가 비워집니다"를 확인하고(첫 포커스는 `취소`) 바꾼 뒤 토스트로 실행 취소를 준다. 빈 칸만 넘치면 확인 없이 바꾼다. 넘친 칸을 숨겨 보관하지 않는다.
- **좁은 뷰포트**: 칸 폭이 최소값 밑으로 내려가면 그리드를 세로로 쌓고 보드 본문을 스크롤한다. 저장된 배치는 바꾸지 않는다. 쌓는 경계는 뷰포트가 아니라 칸 폭 기준이다. 칸 머리 기준 하한은 340px(시안 측정)이고, 1280 + 상세 440px(main 788px)에서 2×2가 2열로 남아야 한다. 최종값은 칸 안 메뉴 본문(표·차트)이 깨지는 폭을 실제 메뉴로 재서 정한다.
- **실행 취소**: 칸 비우기·시트 삭제·레이아웃 줄이기·일괄 적용·복사는 `@ap/ui` `UndoToast`(포커스·호버 중 멈춤, Escape)로 실행 취소를 준다. 실행 취소는 그 동작이 바꾼 시트·칸만 되돌린다(토스트가 떠 있는 동안의 다른 편집은 그대로). 동작 뒤 포커스는 트리거로 돌아가고, 칸 머리는 다시 그려도 같은 요소를 유지한다.

시안: 세 안(A 신호형 · B 전부 펼침 · C 제목형)을 아티팩트로 만들어 UX 리뷰로 골랐다(사용자 요청으로 실제 앱 `?variant=` 대신, #421 코멘트). 결과는 A 머리 + C 선택 표시(ADR-0051). 배치(아래 시트 띠, 그리드)는 소유자 방향으로 고정이었다. 시안 칸 내용은 예시 데이터라, 실제 메뉴가 좁은 칸에서 어떻게 보이는지는 구현 때 확인한다.

## 5. 조건 모델 (Decided)

계약은 [06 §6.5](06_platform_ui_contract.md#65-분석-context의-범위--칸-decided-adr-0049). 보드에서 보이는 모습만 적는다.

- **칸마다 자기 분석 Context를 통째로 가진다.** 새 칸은 기본 조건을 복사해 시작한다. `분석 보드에 열기`로 넣으면 누른 화면의 조건, 보드에서 `분석 화면 넣기`로 넣으면 마지막으로 본 본 화면의 조건이다. `복제`는 원래 칸의 조건을 복사한다. 그 뒤로 칸끼리, 그리고 본 화면과 연결이 없다. 상속은 없다.
- **일괄 맞추기는 명시적 동작뿐**: `이 조건을 시트의 모든 칸에 적용`, `이 시트 조건을 다른 시트에 복사`. 한 번 복사하고 이후 연결은 남지 않는다.
- **`이 시트 조건을 다른 시트에 복사`는 위치대로 복사한다**: 원본 시트 칸 i의 조건을 대상 시트 칸 i에 넣는다. 양쪽 모두 메뉴가 있는 칸끼리만 복사하고, 짝이 없는 칸은 그대로 둔다. 비교 시트의 칸별 차이를 지우지 않기 위해서다. 메뉴와 토스트는 "칸 1–3의 조건을 '<대상>'의 같은 칸에 복사"처럼 원본·대상 칸을 적는다(코디네이터 결정 2026-10-19, UX 리뷰 지적, 되돌릴 수 있다).
- 칸 머리에 조건 요약을 늘 보이고, 같은 시트에서 칸끼리 다른 키를 강조한다.
- UX 리뷰(2026-10-18)의 "보드 조건 따름 / 이 칸만" 연결은 쓰지 않는다(소유자, 2026-10-18).
- 칸 하나는 단일 Scope다. 칸마다 서버가 권한을 다시 판정하고, 거부된 칸만 권한 상태가 된다.
- 보드에서 무엇을 해도 본 화면의 분석 Context나 마지막 화면 복원(ADR-0028)이 바뀌지 않는다.

## 6. 메뉴 쪽 요구 (Decided)

- **보드 지원 선언**: manifest `features.board: boolean`(기존 `features`의 `compare`·`annotate` 옆, 필드명 Candidate). 선언하지 않은 메뉴는 `분석 화면 넣기`·`분석 보드에 열기…`에 나오지 않는다. 1차는 분석 성격 메뉴 2–3개만 켜서 계약을 검증한다. 어느 메뉴인지는 2×2 칸 폭을 잰 뒤 구현 PR에 이유와 함께 적는다.
- **칸에는 원래 메뉴 화면이 들어간다.** 보드용 작은 화면을 따로 만들지 않는다. 화면은 자기 컨테이너 폭으로 반응해야 한다(뷰포트 기준 아님). 좁은 칸에서 깨지는 메뉴는 보드 지원을 선언하지 않는다. 메뉴 화면은 좁은 칸에서 깨지는 부분만 고친다.
- **page 상태**: 칸의 page 키(탭·정렬·페이지·드릴 단계)는 칸 상태에 산다. 메뉴는 Kernel의 page 상태 API로만 읽고 쓴다.
- **칸 안에서 다른 메뉴로 가는 링크**(드릴다운·메뉴 간 연결 `navigateTo`): 대상이 보드를 지원하면 그 칸의 화면을 대상 메뉴로 바꾸고 칸 조건을 링크가 넘긴 값으로 갱신한다. 칸 머리에 `이전 화면`을 한 단계만 둔다. 대상이 보드를 지원하지 않으면 본 화면으로 이동한다(보드 상태는 저장돼 있다).
- **상세 패널**: 보드 전체에 오른쪽 상세 슬롯 하나(ADR-0013·0047)를 칸들이 나눠 쓴다. 칸마다 드로어를 붙이지 않는다(1280에서 상세가 열리면 main 788px). 상세 머리에 어느 칸·메뉴의 상세인지 보인다. 다른 칸을 선택해도 상세는 그대로 두고, 시트를 바꾸거나 상세를 연 칸의 조건·화면이 바뀌거나 그 칸을 비우면 닫는다.
- **모듈 화면**(ADR-0038·0039): FeedbackOps·EV 모듈 화면도 호스트 포트로 Context·page 상태를 받으므로 같은 규칙으로 칸에 들어갈 수 있다. 1차 검증 대상은 아니다.

## 7. 저장·URL·조회 (Decided, 1차)

- **저장**: 브라우저 localStorage `platform:board:${userId}`(즐겨찾기·표 설정과 같은 방식). 새로고침·새 탭·다음 날에도 남는다. 서버 저장은 §10.
- **보드 수**: 사용자당 하나. 비교 묶음은 시트로 나눈다.
- **URL**: `/board?sheet=<시트 ID>`(플랫폼 소유 화면 — Registry 메뉴가 아니고, 어떤 메뉴도 `/board`나 그 아래 경로를 쓸 수 없다. 이 화면은 최근 방문·공간 마지막 화면·메뉴 사용 계측에 남지 않는다). 칸 상태(메뉴·조건·page 키)는 URL에 넣지 않는다. 새로고침하면 같은 시트로 돌아온다. 뒤로가기는 시트 전환만 되돌리고, 칸 안의 조건·page 변경은 기록에 남기지 않는다. 이 URL은 그 브라우저 안에서만 의미가 있고 공유 링크가 아니다.
- **열 수 없게 된 칸**: 저장된 칸의 메뉴가 Registry에서 빠졌거나 보드 지원이 꺼지면 "더는 보드에서 열 수 없는 화면"과 `비우기`를 보인다. 메뉴·Scope 권한을 잃으면 그 칸만 권한 상태다. 어느 경우도 자동으로 지우지 않는다.
- **조회**: 지금 보이는 시트의 칸만 마운트해 조회한다. 칸마다 기존 조회 수명주기(취소·세대)를 그대로 쓴다. 2×2면 동시 조회가 최대 4개다.
- **계측**: 칸이 열리면 그 메뉴의 사용으로 센다(`recordUsage`, 출처 `board` 표시). 보드 열기·시트 수·칸 수는 보드 사용으로 따로 센다. 이 부분은 `UsageEvent`가 메뉴 사용 모양(`menuId`·`path` 필수)이라 계약 변경 없이는 못 넣는다 — 구현하지 않고 [백로그](../.planning/backlog.md)에 둔다(#497a).
- 메뉴 클릭으로 바로 보드에 여는 방식을 쓰지 않는 이유: 지금은 화면 하나 = URL 하나라 새로고침·뒤로가기·링크 복사가 그대로 된다(06 §6.4). 기본을 보드로 바꾸면 뒤로가기가 무엇을 되돌리는지를 새로 정해야 한다.

## 8. 셸 결정에서 지금 정해 둘 것

셸 구조 ADR(#249)에 함께 적어 보드를 막지 않게 한다.

- **진입 자리**: 레일 도구 영역(메뉴 검색 아래)에 플랫폼 소유 도구 하나. 셸 안이 시스템 전환 아이콘 방식(시안 D안)이든 공간 레일 방식이든 같은 자리다.
- **하단 띠 공간**: 보드 화면에서만 main 열 맨 아래 40px + 위 경계 1px을 쓰고, 일반 화면에서는 높이 0이다. 띠는 main 열에서 끝나고 오른쪽 상세 슬롯 아래로 지나가지 않는다. 표 높이 맞춤(`tableFit`)이 본문 영역(`data-platform-page-content`)을 관찰하므로 띠는 그 영역 밖(아래)에 둔다. 사이드바 바닥 FeedbackOps 블록과 공간을 나누지 않는다(보드 화면에는 시스템 사이드바가 없다).
- **머리와 칸**: 페이지 머리 50px·Context 바 48px의 역할을 유지하고, 칸 안에 셸 머리·Context 바를 다시 넣지 않는다.
- **본 화면과의 경계**: 보드에 들어갈 때 본 화면 Context를 기본 조건으로 복사할 뿐, 이후 양방향으로 동기화하지 않는다. 보드에서 무엇을 해도 본 화면의 조건이나 마지막 화면 복원(ADR-0028)이 바뀌지 않는다.
- **전역 Context 바와의 관계**: 보드 화면의 Context 바는 지금 고른 칸의 조건을 편집한다. 셸 ADR은 Context 바를 "현재 칸의 Context 편집기"로 적어 두어, 보드가 생겨도 바의 의미가 바뀌지 않게 한다(본 화면은 칸이 하나).
- **Context를 읽는 길은 Kernel 훅 하나**: 지금 메뉴 코드는 URL을 직접 읽지 않고 Kernel 훅(`usePlatform`의 전역 Context·`pageParam`·`setPage`)만 쓴다(2026-10-18 확인). 이것을 메뉴·모듈 규칙으로 유지한다. 깨지면 칸 범위 Context를 Kernel 한 곳에서 바꿀 수 없다.

## 11. 백엔드에 생기는 일

- **보드 저장소**: 보드·시트·레이아웃·칸별 메뉴 ID·칸 조건·page 상태를 사용자별 문서로 저장한다. 공유하면 소유자·공유 대상·감사 기록이 필요하다.
- **쓰기 포트**: 지금 `PlatformAdapter`는 읽기 중심이다(쓰기는 주석 등 일부). 보드 저장은 새 쓰기 포트와 서버 저장소 소유자 결정이 필요하다.
- **동시 조회 부하**: 2×2 시트는 한 화면 질의가 네 배다. 시트를 바꿀 때 보이지 않는 시트의 칸은 조회하지 않는다(화면에 보이는 시트만 마운트).
- **시스템마다 다른 서버**: 칸 하나는 플랫폼 마트, 다른 칸은 FeedbackOps·EV 서버를 부른다. 모듈이 자기 서버를 부르는 구조(ADR-0038) 그대로면 보드는 배치만 하고 데이터를 합치지 않는다.
