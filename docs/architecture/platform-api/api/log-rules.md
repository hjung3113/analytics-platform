# Log Rules

Index and global rules: [03-api-contracts.md](../03-api-contracts.md). This file is the normative contract for **nodes R-a, R-b and R-d** (#1491, #1492, #1494): the token-submitted validation catalog report, the `log_rules` storage behind it, the catalog reads and the spec coverage reads. Design and decisions: `docs/design/features/log-rules/README.md` §2–§5.2, §8 and ADR-0122. The R-e screen (#1495) reads these seven declarations; its UI contract is design §6.4. Not here (later nodes): the consumers of `RuleCoveragePort` (Gate, Round, Datasets; R-f), any call from the platform to the Validator, any rule editing. The wire contract is `@ap/contract-schemas` `validation-catalog-report` `v0` (provisional until the Validator is surveyed).

The platform receives the Validator's report as a **read-only snapshot**. It stores identifiers, short display text, the support level and the declared targets, and nothing else: there is no column for a rule body, condition, threshold, parameter, script or sample log.

## Report

```text
POST /api/v1/validation-catalog/report
Authorization: Bearer <service token with scope validation.catalog.report>
Content-Type: application/json
{ sourceSystem, validatorVersion,
  ruleSets: [{ ruleSetKey, revision, resultRef?, status, supersedes?,
    rules: [{ ruleKey, title, summary, support, scope?, requiredDefault?,
      targets?: [{ format, target, requirementIds?: [string] }] }] }] }
→ 200 { reportId, outcome: "accepted", replayed, current }
→ 422 validation.failed  detail: { fields: [{ path, code }], report_id }
→ 401 auth.token_invalid | 403 permission.denied | 429 rate_limited.actor
```

- **Transport and permission.** The route sets `config.tokenCallable` and `config.tokenMutation` (own mutation-sized token bucket, 10/min). Capability `validation.catalog.report`: **token-scope-only** (see 05). A cookie session — Admin included — is `403 permission.denied` (`detail.capability`); a token without the scope, or whose owning Actor (system Actor, or the issuer of a personal token) holds no current workspace-wide grant of the capability, is the same 403. Effective right = owner's grant ∩ token scopes. Service tokens are issued by an Admin only (ADR-0116). Order of judgment: rate limit → token gate → capability → body.
- **Body size is judged before parsing**: more than 2 MB (2 × 1024 × 1024 bytes) is refused `too_large` and recorded. The transport reads up to 8 MB so that an oversize report can be recorded; beyond 8 MB the transport refuses the body before the handler (Fastify's `413` is remapped by the root error handler to `422 validation.malformed_request`) and nothing is recorded.
- **Closed fields.** An unknown key at any level — top, RuleSet, Rule, `scope`, target — is `unknown_field` (`path` names the key). `scope` keys: `logTypes[]`, `processes[]`, `modelIds[]`, `softwareRange`, `inputFormats[]` (each list ≤ 50 items, each item ≤ 200 characters; the key set is provisional, design D2).
- **Identifiers** (`sourceSystem`, `validatorVersion`, `ruleSetKey`, `revision`, `resultRef`, `supersedes`, `ruleKey`): 1–200 characters, no leading or trailing whitespace, no control character; otherwise `invalid_identifier`. Compared byte for byte: no case folding, no normalization. `support` ∈ `supported|partial|unsupported|unknown` and `status` ∈ `active|retired`, else `invalid_value`. `resultRef` defaults to `revision` (stored resolved).
- **Limits** (`too_large`; design D7, first values): RuleSets 50, Rules 5,000 in the whole report, `targets` 20 per Rule, `requirementIds` 50 per target, title 120, summary 300, `target` 500, `format` 40 characters.
- **Duplicates** (`duplicate_key`): the same `ruleSetKey` + `revision`; the same `ruleKey` inside one Revision; the same effective `resultRef` for two Revisions of one RuleSet.
- **Free text** — title, summary, `target`, `format`, `requirementIds`, `scope` strings, and every identifier — is refused, never rewritten: a control character (tab and newline included) is `control_character`; a secret pattern is `secret_pattern`. The patterns (`log-rules/domain/secret-patterns.ts`, unit-tested): this platform's API token format found anywhere in the text, a PEM private-key header, an AWS access key id (`AKIA` + 16), `Bearer` + a 20+ character token-like value, and `password|passwd|secret|token|api key` followed by `=` or `:` and a value. False positives are accepted on purpose.
- **Error codes** (`detail.fields[].code`): `unknown_field`, `invalid_identifier`, `invalid_value`, `invalid_json`, `duplicate_key`, `too_large`, `secret_pattern`, `control_character`. The first one is the recorded reason. At most 50 fields are listed.

## Idempotency and supersession

- `report_digest` = SHA-256 of the **canonical form** of an accepted report: object keys sorted, RuleSets ordered by `(ruleSetKey, revision)`, Rules by `ruleKey`, `resultRef` resolved; target order is kept (it is the declaration order). Re-sending the same snapshot — in any key or Rule order — answers `200` with the same `reportId`, `replayed: true`, and writes nothing (no row, no audit). `current` is `false` when a newer report of the source has superseded it since (the platform does not re-activate an older snapshot; send a changed report instead).
- A **different** digest from the same `sourceSystem` is a new full snapshot: in one transaction the previous accepted report gets `superseded_at` / `superseded_by_report_id` (never deleted) and the new rows are inserted. A partial unique index leaves exactly one current accepted report per `(workspace, source_system)`.
- One advisory lock per workspace (`pg_advisory_xact_lock`) serializes the replay lookup and the write, so parallel identical submissions make one report and parallel different ones leave exactly one current.
- A **rejected** report is recorded: `outcome = 'rejected'`, `reject_reason`, the reporter Actor, a digest of the raw body bytes under its own domain prefix (`log_rules.catalog_report.rejected.v0\n` + body), so a rejected body can never occupy the digest of a valid snapshot, and — only if it passes the same identifier, control-character and secret checks itself — `source_system`. Its content is not stored. The same rejected body again answers the same `422` with the same `report_id` and writes nothing.

## Catalog reads (R-b, #1492)

Five reads over `POST /api/v1/menu-query`, declared by `log-rules/catalog-endpoints.ts` in the same shape as `logLifecycle.*`: owning menu `log-rules` (the existing planned menu, `/log/rules`, group `logRules`; no menu, manifest or screen is added here), permission `platform:view`, `requiresScope: false`, no Context, the workspace is the session Actor's and never a param. A param the endpoint cannot honour (unknown key, unknown sort or filter field, value outside its set, page size over 200) is an `error` outcome with a message, never an empty page. The dispatch outcome set has no `not_found`: an unknown id, or an id that exists only in another workspace, answers `ok` with `data: null` (a list: `rows: []`, `total: 0`); nothing is `403`. The reads write nothing and hold no rule body: only identifiers, short text, support levels and declared targets, verbatim.

**The current catalog.** The accepted, not superseded reports of the workspace (one per `source_system`). A rejected report, and the content of a superseded one, never appears in any read. A RuleSet is shown through its Revisions in those reports. Revisions are ordered by the Validator's `supersedes` (a Revision follows the one it supersedes; a Revision that supersedes nothing, or something not in the snapshot, starts a chain; chains and siblings by revision string, compared exactly). The **current Revision** of a RuleSet is its `active` Revision that no other `active` Revision supersedes; with several such heads (`ambiguousCurrent: true`) the last in order wins; with none (all retired, or active Revisions that only supersede each other in a cycle; a Revision naming itself does not supersede itself) the RuleSet has no current Revision. A `ruleSetKey` named by two current reports is shown from the most recently reported one (one Validator is expected). `Rules` lists exactly the Rules of the current Revisions.

| Endpoint id | Params | Result |
| --- | --- | --- |
| `logRules.ruleSets` | `q` (substring of `ruleSetKey`), `page`, `pageSize` (default 50, max 200), `sorting` (`ruleSetKey` default, `sourceSystem`, `revisionCount`, `ruleCount`, `reportedAt`), `filters` (ADR-0105: `ruleSetKey`, `sourceSystem`; `in`/`notIn`, exact text) | `{ rows, total }`; row `{ ruleSetKey, sourceSystem, validatorVersion, lastReportedAt, revisionCount, currentRevision: { revision, resultRef, supersedes } \| null, ambiguousCurrent, supportCounts: { supported, partial, unsupported, unknown, total } }` (counts of the current Revision's Rules; zeros without one). Ties are broken by `ruleSetKey` |
| `logRules.ruleSetDetail` | `ruleSetKey` | `null` or `{ ruleSetKey, sourceSystem, validatorVersion, lastReportedAt, currentRevision, ambiguousCurrent, revisions[] }`; each Revision in order `{ revision, resultRef, status, retired, supersedes, isCurrent, ruleCount, supportCounts, previousRevision, changes }`. `changes` = `{ added[], removed[], supportChanged[{ ruleKey, from, to }], addedCount, removedCount, supportChangedCount, truncated }` against `previousRevision` (the Revision it `supersedes` when that is in the snapshot), computed on read from `rule`; each list is cut at 500 (`truncated`), the counts are complete. A Revision with no predecessor has `previousRevision: null` and `changes: null` (no change is claimed against nothing). A retired Revision is listed with `retired: true` |
| `logRules.rules` | `q` (substring of `ruleKey`, `title` or `summary`, case-insensitive, `%`/`_` literal), `targetQ` (substring of any declared target text, case-insensitive, matched on the stored text, never parsed), `page`, `pageSize`, `sorting` (`ruleSetKey` default, `ruleKey`, `title`, `support` in the order supported, partial, unsupported, unknown, `revision`, `targetCount`, `requirementIdCount`), `filters`: `support` (`in`/`notIn`: `supported`, `partial`, `unsupported`, `unknown`), `ruleSetKey` (`in`/`notIn`), `scope` and `requirementIds` (presence: `isNotEmpty` = the Rule declares a scope / declares at least one requirement id on a target, `isEmpty` = it does not) | `{ rows, total }`; row `{ ruleSetKey, revision, ruleKey, title, summary, support, scope, requiredDefault, targetCount, requirementIdCount, firstTarget: { format, target } \| null }`. Every order ends with `ruleSetKey`, `ruleKey`, row id, so pages never repeat or skip a row |
| `logRules.ruleDetail` | `ruleSetKey`, `ruleKey` (exact) | `null` or `{ ruleSetKey, ruleKey, revision, inCurrentRevision, sourceSystem, lastReportedAt, title, summary, support, scope, requiredDefault, targets[{ position, format, target, requirementIds[] }], revisions[{ revision, status, retired, isCurrent, support }] }`. The fields come from the current Revision when it carries the Rule, else from the latest Revision that does (`inCurrentRevision: false`). `targets` are in declaration order, text as stored; `requirementIds` are the declared strings only — matching them to the log-knowledge requirement keys is R-d's job, no spec is read here. `revisions` lists every Revision of the RuleSet in order, `support: null` where the Revision does not carry the Rule |
| `logRules.catalogStatus` | none | `{ received, lastReportedAt, sourceSystem, validatorVersion, sources[{ sourceSystem, validatorVersion, reportedAt }], ruleSetCount, ruleCount, requirementIdsDeclared }`. `received: false` = no accepted report: «카탈로그 미수신» (all fields empty/null, `requirementIdsDeclared: null`; not an error, and a rejected report does not change it). `sourceSystem`/`validatorVersion`/`lastReportedAt` are those of the most recently reported current report. `requirementIdsDeclared: false` = received, but no Rule of any Revision of the current catalog (retired ones included) declares a requirement id: «요구사항 ID 미선언» (`ruleCount` still counts current Revisions only) |

Filters follow the table filter model (one condition per field, AND across fields; `isEmpty`/`isNotEmpty` take no value). Sort and filter keys are allow-lists; no param value reaches SQL as an identifier. The `rules` page is three indexed queries per page (current-Revision lookup, the page, the total; workspace-first indexes; no migration): measured on a 5,000-Rule catalog with two targets per Rule, the first page took 12 ms, a deep sorted page 42 ms, a `requirementIds` filter 19 ms, a target substring search 24 ms and a text search 11 ms (local throwaway database, integration test «a large catalog»).

## Coverage (R-d, #1494)

Computed on read from the effective requirement keys of `log-knowledge` (`knowledgeLookup.listEffectiveRequirements`, R-c; keys `moduleKey` / `moduleKey/eventKey` as stored) and the Rules of the **current active** catalog (R-b «current»: accepted, not superseded reports; the active head Revision of each RuleSet; retired Revisions and older Revisions never count). Nothing is stored; no migration; no outbound call.

**Matching.** A requirement id a target declares equals a key only when the strings are identical (no case folding, trimming, prefix or module-vs-event match, no ID mapping). Ids with no matching key are not counted. A Rule naming an id on several targets counts once for it.

**State per requirement** (support of every declaring Rule):

| State | When (first match wins) |
| --- | --- |
| `no_rule` | no declaring Rule |
| `covered` | any declaring Rule is `supported` |
| `partial` | else any declaring Rule is `partial` |
| `unsupported` | else all declaring Rules are `unsupported` |
| `unknown` | else (all `unknown`, or `unsupported` mixed with `unknown`: «Validator did not say» is never turned into `unsupported`) |

The mixed-support precedence is the platform's documented choice; the design table is silent on mixes. **Open point:** design §3.3 also lists «`scope` covers the model/SW only partly» as `partial`. The v0 `scope` is a free label whose keys are not fixed (design §3.2, D2), so it is **not interpreted**: `partial` comes from `support` alone. Reopen when the Validator survey fixes the `scope` keys and the owner asks for it.

**Not computable** (`computable: false`, a distinct `reason`; never 0%, never all-`no_rule`), judged in this order: `model_unknown` (model or software version not in the workspace) → `ambiguous_key` (an effective module or event key is empty or contains `/`; `ambiguousKeys` lists them) → `no_spec` (no published model spec) → `no_catalog` (no accepted, not superseded report) → `no_requirement_ids` (no Rule of the current active Revisions declares a requirement id). `no_requirement_ids` looks at current active Revisions only; `catalogStatus.requirementIdsDeclared` looks at every Revision, so the two may differ.

**`coverageDigest`** = SHA-256 of `log_rules.coverage.v0\n` + canonical JSON (sorted keys) of `{ specPin, requirements[{ key, state, rules[[ruleSetKey, revision, ruleKey]]}], ruleSetRevisions[[ruleSetKey, revision, resultRef, revisionDigest]] }`, with requirements, rules and Revisions sorted. Same inputs → same digest regardless of input order; any change of a key, a state, a declaring Rule, the spec pin (revision id or change-set digest) or a current Revision (including a new report that changes a Revision digest) changes it. `ruleSetRevisions` is every current active Revision, not only the ones that matched. A coverage figure is configuration information, never a pass: Gate decides from rule results.

| Endpoint | Params | Result |
| --- | --- | --- |
| `logRules.coverage` | `modelId` (UUID), `softwareId?` (UUID of a version of that model), `page` (0-based), `pageSize` (1–200, default 50) | `null` for an unknown model/software or one of another workspace (`ok`, `data: null`). `{ computable:false, reason, specPin, ambiguousKeys? }` or `{ computable:true, specPin, coverageDigest, counts{ no_rule, unsupported, unknown, partial, covered, total }, ruleSetRevisions[{ ruleSetKey, revision, resultRef, revisionDigest }], rows[{ key, state, declaredCount, declaredBy[{ ruleSetKey, revision, ruleKey, support }] }], total, page, pageSize }`. `counts` and `coverageDigest` cover all requirements, `rows` is one page. Fixed order: `no_rule`, `unsupported`, `unknown`, `partial`, `covered`, ties by key (code-unit order); `declaredBy` lists at most 50 Rules (sorted), `declaredCount` is complete |
| `logRules.coverageSummary` | `modelIds` (1–50 UUIDs; duplicates folded, order kept) | `{ rows[{ modelId, computable:true, counts, coverageDigest } \| { modelId, computable:false, reason }] }`; an unknown id is a `model_unknown` row. Model-level only (no software). The catalog is read once; each model is one effective-spec read in its own transaction |

Both are `platform:view`, `requiresScope: false`, workspace = the session Actor's. **Visibility:** both reads pass the current actor to log-knowledge’s object visibility predicate. Hidden Model/SW equals unknown: single coverage returns `data: null`; summary returns `computable: false, reason: model_unknown`, without counts or digest.

**Transactions.** `coverage` reads the catalog and the spec in one transaction; the only lock is the model advisory lock inside the port, taken after the lock-free catalog reads, so concurrent coverage reads cannot deadlock. `coverageSummary` deliberately uses the pool handle per model so no model lock is held while waiting for the next. Nothing writes.

**Cost** (local throwaway database, integration test «cost»): a model of 600 requirement keys against a 5,000-Rule current catalog (10 RuleSets, two ids per Rule) computed in about 70 ms (catalog read, spec read, computation). `coverageSummary` costs one such computation per model after a single catalog read, bounded by 50 models.

**`RuleCoveragePort`** (`coverage-port.ts`, barrel `createRuleCoveragePort({ knowledgeLookup })`): `getCoverage(tx, workspaceId, modelId, softwareId | null, viewerActorId)` → `{ computable:false, reason, specPin, ambiguousKeys? }` or `{ computable:true, requirements[{ key, state }], coverageDigest, specPin, ruleSetRevisions[] }`; `resolveRuleSetRevision(tx, workspaceId, ruleSetKey, revision)` → `{ ruleSetKey, revision, resultRef, status, isCurrent, revisionDigest }` for a Revision of the current catalog whose `revision` or `resultRef` equals the string exactly, or `null` (unknown key, no match, or more than one match: never guessed). The caller verified the workspace and decides the permission; no consumer is wired in R-d (R-f).

Screen limitation (R-e, #1495): the selector accepts deep-linked `modelId`/`softwareId` UUIDs; `coverageSummary` is a summary of supplied ids, never a model-discovery list. A model-name/software-name picker remains unimplemented until a sanctioned model-list surface is available.

Not implemented: a workspace-wide model page for `coverageSummary` (it would need a model-list method on the `knowledgeLookup` port; reopen with the model-list screen integration, R-f), custom sort/filter of `coverage` rows.

## Audit

One `core.audit_log` row per accepted or rejected report, in the same transaction as the writes (none for a replay): `validation.catalog.reported` / `validation.catalog.rejected`, subject type `catalog_report`, subject id = the report id, Actor = the token's system Actor, `detail.api_token_id` added by the audit writer. Detail: accepted → `sourceSystem`, `validatorVersion`, `outcome`, `ruleSetCount`, `ruleCount`, `targetCount`, `reportDigest`, `supersededReportId`; rejected → `sourceSystem` (or null), `outcome`, `rejectReason`, `bodyBytes`, `reportDigest`. Never a rule key, title, summary or target. Both events are in the platform audit projection (`create` / `update` actions).

## Storage notes

Schema `log_rules`, migration 0106; column list and grants in 04. Every table carries `workspace_id`, composite same-workspace FKs and workspace-first indexes. **Insert-only**: `rule_set_revision`, `rule` and `rule_target` refuse UPDATE and DELETE (trigger, every role); `catalog_report` refuses DELETE and allows one change per row, current → superseded, by a column-limited grant and a guard trigger. `report_digest` is unique per workspace (accepted and rejected rows share the constraint; a rejected row's digest is over the raw bytes). `rule_set_revision.released_at` has no source in the v0 report body and stays null until a Validator reports it.

## Synthetic reporter

`tooling/scripts/log-rules-synthetic-reporter.mjs` posts a fixed catalog (3 Revisions in 2 RuleSets, one retired, one `unknown` support, targets with requirement ids) with a service token read from `LOG_RULES_REPORT_TOKEN`. Every label says «합성 fixture»; it is not evidence of an integration with the in-house Validator. It refuses a base URL or environment flagged as production, allows loopback by default, and is not part of the production assembly (the API image copies none of `tooling/`; a unit test pins this).
