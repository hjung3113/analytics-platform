# Log Knowledge

Index and global rules: [03-api-contracts.md](../03-api-contracts.md). This file is the normative contract for the log knowledge catalog reads (#1193, [ADR-0107](../../../adr/0107-log-knowledge-catalog-authority-keys-and-edit-rights.md), design [v0.6 §7.1](../../../design/features/log-knowledge-hub/design-v0.6-candidate.md)). The write actions (#1194 a) are in [Write actions](#write-actions), the item writes (#1197 w) in [Item write actions](#item-write-actions); import is #1195. The item reads (#1197 a, [ADR-0109](../../../adr/0109-log-knowledge-item-ownership-revisions-assessments.md)) are in [Item reads](#item-reads).

## Transport

The reads are menu-query endpoints: `POST /api/v1/menu-query` with `{ endpoint, context: {}, params }`. Judgment order, envelope and refusals are the Menu Dispatch engine's ([real-server-checklist §3](../../../integration/real-server-checklist.md)). The module only contributes the declarations (`modules/log-knowledge/catalog-endpoints.ts`). Owning menu id `log-knowledge-catalog`, `requiresScope: false`, no Context key.

## Permission

Declared permission `platform:view`: every active workspace session may read the catalog (the rule the Home menu uses; the hub's later read menus need it). The workspace is the session actor's; no param names it and no row of another workspace is returned.

**Object access (#1504 S-a, ADR-0124).** On top of the menu permission, a model, a SW version and an Item can be `restricted` (see [Object access](#object-access-1504-s-a-migration-0112)). Every read and write below judges the visibility of the objects it touches for the acting actor. A hidden object answers exactly like one that does not exist (same outcome, `data: null` / empty page / the `not_found` field error of a missing id, no name, no count); lists, totals, `modelCount` / `softwareCount` / `itemCount` / `modelItemCount` and the Item `links` carry visible rows only. Admin has no read bypass.

## Common params

| Param | Value | Default |
| --- | --- | --- |
| `q` | string ≤ 200 or `null`. Matches rows whose `code_key` starts with `toCodeKey(q)` (NFKC, trim, collapsed whitespace, upper case), or whose name contains `q` (case-insensitive). `%` and `_` are literals | `null` |
| `page` | integer ≥ 0 (0-based) | `0` |
| `pageSize` | integer 1–200 | `50` |
| `sorting` | up to 3 `{ id, desc }` over the endpoint's sort columns, no column twice | first column ascending |
| `filters` | the table filter model ([ADR-0105](../../../adr/0105-one-table-filter-model.md)): `{ id, op, value? }[]`, per-endpoint fields in [Filters](#filters) | none = **every row** |

There are no `status`, `vendorId`, `processId` or `modelId` params: every filter is a `filters` condition. An absent or empty `filters` answers **all rows**, active and inactive; the server does not default to active rows (the screen pins `active in [true]` itself).

Every sort ends with `id` ascending, so paging is deterministic. A param key outside the endpoint's list, a wrong type, a value out of range or a sort column outside the list is an `error` outcome (HTTP 200, `data: null`), never an empty page.

Data shape: `{ rows, total }` (`PageResult`), outcome `ok` also when `rows` is empty. Timestamps are ISO-8601 UTC strings. `version` is `row_version` as a string.

## Endpoints

| Endpoint id | Filter fields | Sort columns | Row |
| --- | --- | --- | --- |
| `logKnowledge.vendors` | `filters`: `active`, `id` | `code`, `name`, `active`, `modelCount`, `createdAt`, `updatedAt` | `id, code, name, active, version, modelCount, createdAt, updatedAt` |
| `logKnowledge.processes` | `filters`: `active`, `id` | same as vendors | same as vendors |
| `logKnowledge.models` | `filters`: `active`, `id`, `vendorId`, `processes` | `code`, `name`, `vendorName`, `active`, `softwareCount`, `createdAt`, `updatedAt` | `id, code, name, active, version, vendorId, vendorName, processes: {id, name}[], softwareCount, latestSoftwareLabel, createdAt, updatedAt` |
| `logKnowledge.softwareVersions` | `filters`: `active`, `id`, `modelId` | `versionLabel`, `name`, `releaseOrder`, `active`, `createdAt`, `updatedAt` | `id, code, versionLabel, name, active, version, modelId, releaseOrder, createdAt, updatedAt` (`code` = `versionLabel`) |

- `code` is the typed original; sorting by `code` and `versionLabel` orders by the comparison key.
- `latestSoftwareLabel` (model) is the `versionLabel` of the model's newest active software version (highest `createdAt`, ties by id); `null` when it has none.
- `modelCount` (vendor, process) and `softwareCount` (model) count active models and active software versions.
- `releaseOrder` (software, #1196 a, migration 0091) is the version's position in its model's release order, 1 = first: existing rows were numbered by `createdAt` then `id` per model, and a new row (create action, catalog import apply, any insert) takes the model's max + 1 — assigned by a `BEFORE INSERT` trigger when the inserted value is 0 (the column default), so no insert path can forget it. It is **not unique** (a later editing action will swap two orders) and is not part of the default sort, which stays `versionLabel`.
- A model in several processes appears once under a `processes` filter (EXISTS, never a join). `processes` in the row lists every mapped process, by name.

## Filters

Wire and semantics are the table filter model's (`ColumnFilter`, real-server-checklist §3 «필터 와이어 모양·연산자 화이트리스트»): one condition per field, AND across fields, `in`/`notIn` the only OR, no condition = no constraint. Fields are enums with string values (`ColumnFilterSpec`); the menu declares the same specs in `menus/log-dev/log-knowledge/src/endpoints.ts` and `catalog-menu-drift.test.ts` fails when the two differ.

| Endpoint | Field | Operators | Values | Meaning |
| --- | --- | --- | --- | --- |
| all four | `active` | `in`, `notIn` | one of `'true'`, `'false'` (`multiple: false`: one value) | `in ['true']` active rows; `notIn ['true']` inactive rows |
| all four | `id` | `in`, `notIn` | uuid strings (≤ 200); any uuid is accepted | the row's id is / is not one of the values (the drawer resolves a row by `id in [focus]`, one read) |
| `models` | `vendorId` | `in`, `notIn` | uuid strings (≤ 200); options are not enumerated, any uuid is accepted | the model's vendor is / is not one of the values |
| `models` | `processes` (`cell: 'many'`) | `in`, `notIn`, `isEmpty`, `isNotEmpty` | uuid strings (≤ 200); none for `isEmpty`/`isNotEmpty` | `in`: some mapped process is in the values; `notIn`: at least one mapped process and none in the values (unmapped models are excluded); `isEmpty`: no mapped process; `isNotEmpty`: some |
| `softwareVersions` | `modelId` | `in`, `notIn` | uuid strings (≤ 200) | the version's model is / is not one of the values |

An unknown field, an operator outside the field's list, a value of the wrong shape (not a list, empty, not `'true'`/`'false'`, not a uuid, a value on `isEmpty`), a second condition on one field or a `filters` that is not a list is an `error` outcome with a message, never an empty page. An unknown but well-formed uuid matches nothing and the page is `ok`.

## Write actions

`POST /api/v1/menu-action` with `{ action, context: {}, input, idempotencyKey, expectedVersion? }`. Judgment order, envelope, replay and the `If-Match`/key headers are the Menu Dispatch engine's ([real-server-checklist §3](../../../integration/real-server-checklist.md)). Declarations: `modules/log-knowledge/catalog-actions.ts`; owning menu id `log-knowledge-catalog`, `requiresScope: false`.

**Permission.** The actions declare the menu permission `knowledge:catalog-manage` (the one permission of the `log-knowledge-catalog` management menu, design v0.6 §2.1 «관리자 전용 카탈로그 관리»; mock registration follows [real-server-checklist §3](../../../integration/real-server-checklist.md)). The real server judges it with the capability `knowledge.catalog.manage` (workspace-scoped, ADR-0107 decision 3), and `PLATFORM_PERMISSION_TABLE` lists `knowledge:catalog-manage` in bootstrap for exactly the actors that check lets write: Admin role, or an active workspace grant of `knowledge.catalog.manage`. Judged as the capability check plus the Admin module bypass (`applyAdminModuleBypass`), so an Admin with no grant row is allowed and a User is refused (`forbidden`, no row). Judged before the transaction and again on it. The workspace is the actor's; an id of another workspace is `not_found` (target) or a `not_found` field error (reference).

| Action | `input` | Concurrency |
| --- | --- | --- |
| `logKnowledge.vendorCreate` / `processCreate` | `code`, `name` | `none` |
| `logKnowledge.modelCreate` | `vendorId`, `code`, `name`, `processIds` | `none` |
| `logKnowledge.softwareCreate` | `modelId`, `versionLabel`, `name` | `none` |
| `logKnowledge.vendorUpdate` / `processUpdate` | `id`, `code`, `name` | `version` |
| `logKnowledge.modelUpdate` | `id`, `code`, `name`, `processIds` (the full replacement set) | `version` |
| `logKnowledge.softwareUpdate` | `id`, `versionLabel`, `name` | `version` |
| `logKnowledge.<kind>SetActive` (`vendor`, `process`, `model`, `software`) | `id`, `active` | `version` |

- A model has no `vendorId` on update: the Vendor cannot change (ADR-0107 decision 2). Sending it is `invalid` `unexpected_field`.
- `version` is `row_version` as a string. Every successful write increments it and sets `updated_at`/`updated_by`; a create answers `version: "1"`. `expectedVersion` differing from the current one answers `conflict` with the current version, writing nothing.
- A successful answer's `data` is `{ id, code, name, active, version }` (`code` = `versionLabel` for software).
- `processIds` replacement adds and removes `model_process` rows (`assigned_by` = actor); the model row and its id stay. Existing mappings may stay when their process is inactive; only newly added processes must be active.
- **SetActive** to the value a row already has changes nothing: no version bump, no audit row, answer `ok` with the current version. Deactivation never cascades (ADR-0107 decision 4): children keep their own `active`; reactivation is per row. Nothing is hard-deleted.
- `code` is stored as typed; `code_key`/`version_key` are computed by the server (`toCodeKey`) and never taken from input.

**`invalid` field errors** (`fieldErrors[{ path, code }]`; a database-judged one is thrown as `MenuActionInvalidError`, the engine rolls the write back and answers `invalid`, never a 500):

| Code | When | Path |
| --- | --- | --- |
| `required` | missing, not a string/boolean/array, or blank (a software `name` may be `""`) | the field |
| `too_long` | `code`/`versionLabel` > 64, `name` > 200 (code points), `processIds` > 200 | the field |
| `malformed` | not a uuid, NUL or lone surrogate | the field, or `processIds.<i>` |
| `duplicate` | `code_key` already in its ADR-0107 scope (including a concurrent create: one wins, the other gets this); `processIds` repeats an id | `code` (`versionLabel` for software) or `processIds.<i>` |
| `not_found` | `vendorId`, `modelId` or `processIds.<i>` unknown or of another workspace | the field |
| `inactive` | the parent vendor/model or a newly mapped process is inactive | the field |

**Audit** (same transaction, non-sensitive): `knowledge.catalog.created`, `.updated`, `.deactivated`, `.reactivated`; `subject_type` `knowledge_vendor` | `knowledge_process` | `knowledge_model` | `knowledge_software`; detail `{ code, name, changes?: { field: [before, after] } }` (a model's `processIds` change as sorted id lists; `changes` is absent when nothing differed). Platform actions: created → `create`, updated and reactivated → `update`, deactivated → `retire`. The four subject types are in the `core.platform_audit_events` allowlist (migration 0081).

**`invalidates`** (read endpoints of this menu the Kernel refreshes): vendor writes → `vendors`, `models`; process → `processes`, `models`; model → `models`, `vendors`, `processes`, `softwareVersions`; software → `softwareVersions`, `models`.

## Item write actions

Five more `menu-action` writes (#1197 w, [ADR-0109](../../../adr/0109-log-knowledge-item-ownership-revisions-assessments.md)); same transport, replay and `If-Match`/key rules as [Write actions](#write-actions). Declarations: `modules/log-knowledge/item-actions.ts`, value checks `domain/item-input.ts` (zod; shared by `validate` and the handler), SQL `repositories/item-write.ts` (`knowledge.*` item tables and the item counter only). Owning menu `log-knowledge-items`, `requiresScope: false`.

**Permission.** Menu permission `knowledge:item-publish`, judged with the capability `knowledge.item.publish` (workspace-scoped, no Managed System, non-sensitive) plus `applyAdminModuleBypass` (`always`), the same pairing as `knowledge:catalog-manage` ↔ `knowledge.catalog.manage`: Admin passes with no grant, a Developer needs the grant (requestable and grantable), a User is refused at request and at grant and is `forbidden` here. Bootstrap lists `knowledge:item-publish` exactly for the users the actions accept (`platform-port/permissions.ts`, rule `item-publish`). Reads stay `platform:view`.

| Action | `input` | Concurrency | `data` |
| --- | --- | --- | --- |
| `logKnowledge.itemCreate` | exactly one of `ownerModelId` / `ownerSoftwareId`; `typeCode`, `title`, `observation?`, `expected?`, `analysisOpinion?`, `improvement?`, `evidence?` (≤ 20 pointers) | `none` | `{ id, itemNo }` |
| `logKnowledge.itemRevise` | `id`, `typeCode`, `title`, the four bodies, `evidence?`, `changeNote` (1–500) | `version` | `{ id, itemNo, revisionNo }` |
| `logKnowledge.itemAssess` | `id`, `dimension` (`verification` \| `processing`), `newState`, `rationale` (1–2000) | `version` | `{ id, itemNo }` |
| `logKnowledge.itemDerive` | `sourceItemId`, `sourceRevisionNo`, exactly one owner, `typeCode`, `title`, the four bodies (no `evidence`) | `none` | `{ id, itemNo }` |
| `logKnowledge.itemSetArchived` | `id`, `archived` | `version` | `{ id, itemNo }` |

- `version` is `row_version` as a string; every successful write that changes the item bumps it and sets `updated_at`/`updated_by`; create and derive answer `version: "1"`. `expectedVersion` differing from the current one answers `conflict` before the handler (also for a same-value SetArchived).
- **Create / Derive**: the number comes from the workspace counter (`allocateItemNo`), the item is `published`, `not_checked`, `open`, revision 1 is written with its evidence (server-assigned `ordinal` 1..n). Derive also inserts `item_link(derived_from, source = new item, target = original, source_revision_no)` pinned to the given revision, and takes no evidence. The owner never changes afterwards (`itemRevise` has no owner input).
- **Revise** appends revision `latest + 1`; evidence belongs to that revision (omitted = none) and the earlier revisions and their evidence are untouched. `latest_revision_no` moves with it.
- **Assess** inserts one `item_assessment_event` (`prior_state` = the current projection, `based_on_revision_no` = latest) and sets the dimension's projection in the same transaction.
- **SetArchived** is non-destructive. To the value the item already has: nothing changes, no bump, no audit, `ok` with the current version. An archived item refuses revise and assess.
- `EvidencePointer`: `sourceKind` (`log_file` \| `spec` \| `image` \| `validation_run` \| `other`), `sourceOwner`, `sourceRef` (non-blank, ≤ 1000), `sourceVersion?`, `contentHash?`, `locator?` (≤ 1000), `note?` (≤ 500); optional texts that are blank are stored as null. The 1000 cap is the API's (no DB CHECK). No body text is audited.

**`invalid` field errors** (value checks at step 6; the database-judged ones are thrown as `MenuActionInvalidError`, never a 500):

| Code | When | Path |
| --- | --- | --- |
| `required` | missing, wrong type or blank (`title`, `typeCode`, `changeNote`, `rationale`, `dimension`, `newState`, `archived`, evidence `sourceKind`/`sourceOwner`/`sourceRef`) | the field, or `evidence.<i>.<field>` |
| `required_one` | both or none of the two owners; neither `observation` nor `expected` has text | `owner`; `observation` |
| `too_long` | `title` > 200, a body > 20000, `changeNote` > 500, `rationale` > 2000, `evidence` > 20, evidence `note` > 500 (code points) | the field |
| `malformed` | not a uuid, unknown enum value, `sourceRevisionNo` not an integer ≥ 1, NUL or lone surrogate | the field |
| `invalid_state` | `newState` does not belong to `dimension` | `newState` |
| `not_found` | owner unknown or of another workspace; derive source item or revision unknown | `ownerModelId` / `ownerSoftwareId`; `sourceItemId` / `sourceRevisionNo` |
| `inactive` | the owner model, the owner SW, or the SW's model is inactive | `ownerModelId` / `ownerSoftwareId` |
| `archived` | revise or assess on an archived item | `id` |
| `unchanged` | `newState` equals the current state of the dimension | `newState` |

**Audit** (same transaction, non-sensitive): `knowledge.item.created`, `.revised`, `.assessed`, `.derived`, `.archived`, `.restored`; `subject_type` `knowledge_item`; detail `{ itemNo, title, revisionNo?, dimension?, priorState?, newState?, sourceItemId?, sourceRevisionNo? }`. Platform actions: created/derived → `create`, revised/assessed/restored → `update`, archived → `retire`. Migration 0083 adds `knowledge_item` and `knowledge.item.publish` to the audit projection's allowlists.

**`invalidates`**: `logKnowledge.items`, `logKnowledge.itemDetail`. **Accepted limit:** the model-side counts (`exploreModels.modelItemCount`, the `modelProfile` counts) belong to menu `log-knowledge-models`, and the engine invalidates only within an action's own menu, so those reads show a stale count until they refresh on their own (backlog, not implemented).

## Item reads

Four more menu-query endpoints (`modules/log-knowledge/item-endpoints.ts`), same transport, `platform:view`, `requiresScope: false`, no Context key; the workspace is the session actor's. Two owning menus: `log-knowledge-models` (explore, model profile) and `log-knowledge-items` (item list, item detail). The detail screens `log-knowledge-model` / `log-knowledge-item` are navHidden children that read their parent's endpoints (the engine allows `invalidates` only within an action's own menu). The menu package mirrors all four reads in `menus/log-dev/log-knowledge/src/endpoints.ts`; `catalog-menu-drift.test.ts` compares the menu declarations with the server declarations.

The dispatch outcome set has no `not_found`: an unknown or other-workspace id answers **`ok` with `data: null`**. Actors (`createdBy`, `publishedBy`, `actorId`) are returned as ids; no approved cross-module name read exists for this module yet.

| Endpoint id | Menu | Params | Data |
| --- | --- | --- | --- |
| `logKnowledge.exploreModels` | `log-knowledge-models` | the common params; filters and sort columns of `models` | the `models` row plus `modelItemCount` (published items owned directly by the model) |
| `logKnowledge.modelProfile` | `log-knowledge-models` | `modelId` (uuid) | `{ model, softwareVersions, truncated, modelItems }` or `null` |
| `logKnowledge.items` | `log-knowledge-items` | the common params | `{ rows: ItemRow[], total }` |
| `logKnowledge.itemDetail` | `log-knowledge-items` | `itemId` (uuid), optional `revisionNo` (integer ≥ 1) | `ItemDetail` or `null` (also `null` for a `revisionNo` the item does not have) |

`modelProfile` data: `model: { id, code, name, active, vendor: { id, code, name, active }, processes: { id, code, name }[], createdAt, updatedAt }`; `softwareVersions: { id, versionLabel, name, active, itemCount, updatedAt }[]` (every version, active or not, newest `createdAt` first, cut at 500 with `truncated: true`); `modelItems: { total }` (published items owned directly by the model). `itemCount` counts the version's published items.

`items`: `q` matches the latest revision's title (contains, case-insensitive) and `KI-<n>` / `KI<n>` (the item number, case-insensitive; a bare number is not parsed and only searches titles). Sort columns `itemNo`, `title`, `updatedAt`; default `updatedAt` descending. **No `publicationState` condition = published items only** (unlike the catalog reads); archived items answer only when asked. `ItemRow`: `{ id, itemNo, title, typeCode, owner: { kind: 'model' | 'software', modelId, modelName, softwareId?, versionLabel? }, verificationState, processingState, publicationState, latestRevisionNo, updatedAt }`; `title` and `typeCode` are the latest revision's.

| Field | Operators | Values | Meaning |
| --- | --- | --- | --- |
| `ownerKind` | `in`, `notIn` | `model`, `software` | model-owned / SW-owned items |
| `ownerModelId` | `in`, `notIn` | uuid strings (≤ 200) | items owned **directly** by the model; with `includeSoftware in ['true']` also items of its SW versions |
| `includeSoftware` | `in` | `'true'` or `'false'` (one value) | only widens `ownerModelId`; default false, so a profile's model-common list never shows SW items. Alone it constrains nothing |
| `ownerSoftwareId` | `in`, `notIn` | uuid strings | items owned by the SW version |
| `typeCode` | `in`, `notIn` | `anomaly`, `needs_check`, `behavior_note`, `guideline` | latest revision's type |
| `verificationState` | `in`, `notIn` | `not_checked`, `observed`, `verified`, `disputed` | |
| `processingState` | `in`, `notIn` | `open`, `under_investigation`, `resolved` | |
| `publicationState` | `in`, `notIn` | `published`, `archived` | replaces the published-only default |

`notIn` on `ownerModelId` / `ownerSoftwareId` excludes items without that owner column. Enum filters accept only the listed values (anything else is an `error` outcome).

`ItemDetail`: `item` (an `ItemRow` plus `version`, `createdBy`, `createdAt`); `revision` (the requested revision, default latest: `revisionNo, title, typeCode, observation, expected, analysisOpinion, improvement, changeNote, publishedBy, publishedAt, evidence: { ordinal, sourceKind, sourceOwner, sourceRef, sourceVersion, contentHash, locator, note }[]`); `revisions` (all, newest first: `revisionNo, title, publishedBy, publishedAt, changeNote`); `assessments` (all, newest first: `id, dimension, priorState, newState, rationale, actorId, basedOnRevisionNo, observedAt`); `links: { kind, direction: 'outgoing' | 'incoming', itemId, itemNo, title, owner, sourceRevisionNo }[]`. For `derived_from`, `outgoing` means this item was derived from `itemId` at `sourceRevisionNo` of that original; `incoming` means `itemId` was derived from this item. `related` has no revision (`null`).

## Knowledge drafts (#1198 a, migration 0101)

A human author proposes a new item or a revision of one as a **draft**; a reviewer decides later ([Review decisions](#review-decisions-1198-b): approve / reject / request changes and the atomic publish; [Agent and Validator submission](#agent-and-validator-submission-over-api-tokens-1198-c)). Node a ships the tables, the author's four writes and the two reads, all on menu `log-knowledge-items` (`modules/log-knowledge/draft-actions.ts`, `draft-endpoints.ts`; value checks `domain/draft-input.ts`, status flow `domain/draft-transitions.ts`, SQL `repositories/draft-write.ts` / `draft-read.ts`). The author's actions never write `knowledge.knowledge_item*` / `knowledge.item_*`; only an approval does ([Review decisions](#review-decisions-1198-b)). Not here: screens, search outbox (#1199). The client menu declares no draft endpoints yet, so `catalog-menu-drift.test.ts` excludes ids starting `logKnowledge.draft`.

### Tables (migration 0101)

- `knowledge.draft`: `id`, `workspace_id`, `origin` (`human` · `ai` · `validator`; derived by the server from the auth context, never from input — [Agent and Validator submission](#agent-and-validator-submission-over-api-tokens-1198-c)), `validator_source_system?` / `validator_run_id?` / `validator_finding_id?` (migration 0104: all null or all set), `proposal_type` (`create` · `revise`), `target_item_id?` / `base_revision_no?` (revise only: the item and its latest revision at draft creation), `owner_model_id?` / `owner_software_id?` (create: exactly one; revise: copied from the target item), `status`, `latest_draft_rev`, `submitter_actor_id`, `submitted_at?`, `closed_at?` / `closed_by?`, `close_reason?` (≤ 500, the withdraw reason, never audited), `row_version`, created/updated at/by. CHECKs: closed sets, create/revise pairing, owner XOR, closed columns set exactly when the status is final.
- `knowledge.draft_revision` (append-only): `workspace_id`, `draft_id`, `draft_rev_no` (1..n per draft, gapless, allocated under the draft row lock), `proposal_json`, `payload_digest` (64 lower-case hex), `schema_version` (1), `author_actor_id`, `author_auth` (`session` · `token`; set by the server from the auth context), `created_at`. Primary key `(workspace_id, draft_id, draft_rev_no)`. UPDATE and DELETE are refused by grant (`42501` for the app role) and by trigger (`23514` for every role).

- `knowledge.draft_review` (append-only, migration 0103): `id`, `workspace_id`, `draft_id` (composite FK), `reviewed_draft_rev_no`, `approved_digest?` (64 hex, set iff `approved`), `decision` (`approved` · `rejected` · `changes_requested`), `self_approval` (true only for `approved`), `rationale?` (≤ 2000, required unless `approved`), `posted_item_id?` / `posted_revision_no?` (set iff `approved`; composite FKs to `knowledge_item` / `knowledge_item_revision`, RESTRICT), `reviewer_actor_id`, `reviewed_at`. Partial unique `(workspace_id, draft_id) where decision in ('approved','rejected')`. UPDATE and DELETE are refused by grant (`42501`) and trigger (`23514`).

### Proposal and digest

`proposal` is the item input: `create` = what `itemCreate` accepts (`ownerModelId` / `ownerSoftwareId` exactly one, `typeCode`, `title`, `observation` / `expected` at least one, `analysisOpinion`, `improvement`, `evidence[]`, `subjects[]`); `revise` = what `itemRevise` accepts without `id` (the target is the draft's), with `changeNote`. The same field rules and server checks run (item input builders reused; `checkOwner`, `judgeSubjects`, target exists and not archived). Unlike the item actions, **unknown keys are refused** at the proposal, in each `evidence[i]` and each `subjects[i]` (`malformed` at the key's path), and every proposal field error is prefixed `['proposal', …]`. The owner of a create draft is fixed at creation: another owner on update is `['proposal', 'ownerModelId' | 'ownerSoftwareId'] immutable`.

The stored proposal is the **normalized** parse (trimmed text, `null` for empty optional text, `evidence: []` when none, unset owner fields absent, normalized `subjects` values; an omitted `subjects` on a revise stays absent and means "keep the previous revision's links"). `payload_digest` = SHA-256 hex of `canonicalJson` (`domain/spec-hash.ts`) of that normalized proposal: `proposalDigest(normalizeProposal(...))` in `domain/draft-input.ts`, the pure function node b compares with `approvedDigest`. The same normalized proposal always has the same digest; any content change has another.

### Status flow

Statuses: `draft`, `submitted`, `changes_requested`, `approved`, `rejected`, `withdrawn`. One table, `LEGAL_DRAFT_STATUS_PAIRS` in `domain/draft-transitions.ts`, mirrored by the guard trigger `knowledge.draft_guard` (drift test `draft-transitions.test.ts`):

| from | to | by |
| --- | --- | --- |
| `draft` | `submitted`, `withdrawn` | `draftSubmit`, `draftWithdraw` |
| `changes_requested` | `submitted`, `withdrawn` | `draftSubmit` (resubmit), `draftWithdraw` |
| `submitted` | `withdrawn` | `draftWithdraw` |
| `submitted` | `approved`, `rejected`, `changes_requested` | `draftApprove`, `draftReject`, `draftRequestChanges` ([Review decisions](#review-decisions-1198-b)) |
| `approved`, `rejected`, `withdrawn` | — | final |

The trigger also fixes the identity and proposal-shape columns, freezes a final draft, requires `row_version + 1` on every update and lets `latest_draft_rev` stay or rise by exactly 1.

### Writes (`menu-action`)

Right: capability `knowledge.draft.create` (workspace-scoped; Admin always; **Developer and User by grant**), menu permission `knowledge:draft-create`; same transport, key and replay rules as [Write actions](#write-actions). Only the draft's `submitter_actor_id` may update, submit or withdraw it. Every write answers `data: { id, status, latestDraftRev, payloadDigest }`, `invalidates: ['logKnowledge.drafts', 'logKnowledge.draftDetail']`, and runs in one transaction with its audit row.

| Action | Input | Concurrency | Effect |
| --- | --- | --- | --- |
| `logKnowledge.draftCreate` | `proposalType`, `targetItemId?` (revise: required; create: refused), `proposal` | none + `idempotencyKey` | draft `draft` at revision 1 (+ revision row); `version` `1` |
| `logKnowledge.draftUpdate` | `id`, `proposal` | `expectedVersion` | allowed in `draft`, `submitted`, `changes_requested`: appends revision `latest + 1`, status unchanged. Same digest as the latest revision: `ok` with the current version, no revision, no audit. An edit during review changes the digest (a reviewer approving the old digest gets `conflict`, or `approvedDigest: stale_digest`) |
| `logKnowledge.draftSubmit` | `id` | `expectedVersion` | `draft` / `changes_requested` → `submitted`; sets `submitted_at` (a resubmit updates it) |
| `logKnowledge.draftWithdraw` | `id`, `reason?` (≤ 500) | `expectedVersion` | `draft` / `submitted` / `changes_requested` → `withdrawn`; `closed_at`, `closed_by`, `close_reason` |

Refusals (`outcome: 'invalid'`, field errors): `proposal.*` item codes (`required`, `too_long`, `malformed`, `required_one`, `duplicate`, `model_mismatch`, `not_found`, `inactive`), `proposal.ownerModelId|ownerSoftwareId: not_found | inactive | immutable`, `targetItemId: not_found | archived` (create of a revise draft), `id: archived` (update of a revise draft whose target was archived since), `id: illegal_transition` (a move outside the table, any write on a final draft), `id: forbidden_not_author`, `reason: too_long | malformed`. The visibility and authorship check runs **before** the engine compares `expectedVersion`: a draft that is missing, another workspace's or not visible to the caller answers `not_found` (never `conflict`, never a version); a visible draft the caller did not author is `['id'] forbidden_not_author`. The capability check comes first (`forbidden`).

Audit (`core.audit_log`, `subject_type: 'knowledge_draft'`, subject id = draft id): `knowledge.draft.created` (`create`), `knowledge.draft.updated` / `knowledge.draft.submitted` (`update`), `knowledge.draft.withdrawn` (`retire`). Detail (strict): `draftId`, `proposalType`, `origin`, `targetItemId`, `draftRevNo`, `payloadDigest`, `statusBefore` (null on create), `statusAfter` — never a title, body, evidence or the withdraw reason (`packages/feature-shared/src/audit/log-knowledge-draft.ts`).

### Evidence intake (#1474 X-h)

The log explorer hands body-free evidence locations to a draft through a **service surface** (not menu actions) exported by the log-knowledge barrel: `draftEvidenceIntake({ checkService })` → `{ create(tx, actor, input), append(tx, actor, input), canIntake(tx, actor), listOwnOpen(tx, actor, { limit }) }`. The explorer calls `create` / `append` inside its own transaction, so a refusal (`MenuActionInvalidError`) rolls the whole handoff back. These writes run the same cores as `draftCreate` / `draftUpdate` (`draft-core.ts`): the capability `knowledge.draft.create` (denied → `target: forbidden`, the only form a service can throw), the owner and subject checks, the `origin` / `author_auth` derivation (a token call stores `author_auth = 'token'`), the author-only rule and the editable-status rule.

- `create { owner: { modelId } | { softwareId }, title, observation, refs, sourceOwner, origin }`: a `needs_check` draft (`proposalType: 'create'`) in status `draft`, author only; `title` and `observation` are what the person wrote in the handoff dialog and the item content rules apply (`title: required | too_long`, `observation: required_one`); an unknown or inactive owner is `target.modelId | target.softwareId: not_found | inactive`. Answer `{ draftId, version, payloadDigest }`.
- `append { draftId, expectedVersion, refs, sourceOwner, origin }`: a new revision of the caller's own, not-final draft with the pointers added, de-duplicated by `(sourceRef, locator, contentHash)` (already stored pointers win; a call that adds nothing changes and audits nothing). `expectedVersion` is the draft's row version (the `version` of the previous answer): a draft the caller cannot see is `target.draftId: not_found`, one they can see but did not author `target.draftId: forbidden_not_author` — both judged **before** the version, so a stranger learns no version — then a mismatch is `expectedVersion: conflict`, a final draft `target.draftId: illegal_transition`.
- **Pointer mapping.** Each `refs[i] = { fileRef, line, fileSha256, note?, sourceResolved, hashMismatch? }` (strict, shape judged again) becomes the proposal evidence pointer `{ sourceKind: 'log_file', sourceOwner, sourceRef: fileRef, contentHash: fileSha256 (lower-case), locator: 'line:<line>', note }`; `sourceOwner` is the Round/sample set's source owner, passed by the caller. The knowledge side has no Source, so the caller reports what it knows: `sourceResolved=false` → `refs.<i>: unresolved` (nothing written); `hashMismatch=true` → the note starts with the fixed marker `[해시 불일치]` (`[해시 불일치] <note>`, or the bare marker; cut to 500 characters) so the reviewer sees it. An item carries at most 20 pointers: more (in `create`, or in total after `append`) is `refs: too_many`; `fileRef` over 1000 characters is `refs.<i>.fileRef: too_long` (the evidence field limit).
- `listOwnOpen(tx, actor, { limit })`: read-only, rechecks `canIntake` (false → `[]`). Returns only the actor's own workspace drafts in editable statuses (`draft`, `submitted`, `changes_requested`), newest `updatedAt` first with id as the tie-break, up to `min(limit, 50)`. Rows are `{ draftId, title, ownerLabel, status, evidenceCount, version, updatedAt }`; title/count come from the latest revision, `ownerLabel` is model code and optional SW version label. No proposal body or evidence pointer is returned. No audit or entity-link side effects. The explorer consumes this barrel instead of reading `knowledge.*`.
- **Audit.** The existing `knowledge.draft.created` / `knowledge.draft.updated` rows with one optional strict detail key `handoff: { originKind: 'log_explorer', originId, refCount }` (the pointers handed in this call). No text, hash or location.

### Review decisions (#1198 b)

`modules/log-knowledge/review-actions.ts` (input `domain/review-input.ts`, SQL `repositories/draft-review.ts`), same menu and transport as the writes above. Right: **`knowledge.item.publish`** (owner answer #1198 Q2: no new capability), menu permission `knowledge:item-publish`; Admin by the module bypass. The check runs inside the transaction, so a right revoked between load and approve is `forbidden` with nothing written. A service actor (AI, Validator, token subject) never holds it, so approve/reject/request-changes are always `forbidden` for them; from the token PR on, `knowledge.item.publish` is session-only. Concurrency is `version` = the draft's `row_version` (`expectedVersion` = expectedDraftVersion). `currentVersion` locks the draft; a draft in status `draft` that the caller did not author is `not_found` (private to its author). Authorship is not required: reviewers are not authors.

| action | input | result |
| --- | --- | --- |
| `logKnowledge.draftApprove` | `id`, `approvedDigest` (64 hex), `expectedItemVersion?` (positive int: required for a `revise` draft, `malformed` for `create`), `rationale?` (≤ 2000) | `data: { draftId, reviewId, itemId, itemNo, revisionNo }`; draft `approved`, closed; invalidates drafts, draftDetail, items, itemDetail |
| `logKnowledge.draftReject` | `id`, `rationale` (required, ≤ 2000) | `data: { draftId, reviewId, status }`; draft `rejected` (final); invalidates drafts, draftDetail |
| `logKnowledge.draftRequestChanges` | `id`, `rationale` (required, ≤ 2000) | draft `changes_requested` (not final: the author edits and resubmits with the author actions) |

All three require status `submitted` (otherwise `['id'] illegal_transition`, withdrawn / approved / rejected included).

**Approve, one transaction, in this order** (any failure rolls everything back): (0) input shape incl. `expectedItemVersion` vs. the draft's type; (a) the latest revision's digest equals `approvedDigest`, else `['approvedDigest'] stale_digest` (an edit after the reviewer loaded the draft normally already fails the engine's version check with `conflict`; this is the second guard); (b) self-approval: the reviewer authored a revision with `author_auth = 'token'` → `['id'] self_approval_via_token`; authored only through the session → allowed, `self_approval = true`; (c) `create`: the owner checks and `judgeSubjects` run again against current data (owner deactivated, subject target gone since the draft → refused with the author actions' paths under `['proposal', …]`); `revise`: the target is locked; missing → `['id'] target_missing`, archived → `['id'] archived`, `row_version ≠ expectedItemVersion` → `['expectedItemVersion'] stale` (nothing written); (d) the shared publish core (`repositories/item-publish.ts`, used by `itemCreate` / `itemRevise` too) writes the item, revision, evidence and subjects (a revise without `subjects` carries the previous revision's) and the item's own `knowledge.item.created` / `revised` audit row, exactly as a direct publish; the published revision's author is the reviewer, provenance is the review row; (e) the `draft_review` row; (f) the draft becomes `approved` (`closed_at`, `closed_by` = reviewer, `row_version + 1`); (g) `knowledge.draft.approved`. The published content is exactly the approved revision's stored proposal. No search outbox (owner answer Q3; search reflection is #1199).

**Replay and races.** The engine's `idempotencyKey` replay returns the original answer. A second approve with a new key on an approved draft is `['id'] illegal_transition`. Two concurrent approves serialize on the draft row lock: one wins, the other gets `conflict`; the partial unique index `draft_review_final_uq` (one `approved` / `rejected` review per draft) is the database backstop, its `23505` is mapped to `['id'] illegal_transition`. An approval is a publication decision, not a verdict that the knowledge is technically correct.

**Evidence access revoked.** Not applicable until evidence carries an ACL: evidence is a pointer list with no access control in the platform today, so there is nothing to recheck at approval (reopen: an evidence-ACL issue; `.planning/backlog.md`).

Audit (`subject_type: 'knowledge_draft'`): `knowledge.draft.approved` (`retire`; detail `draftId`, `reviewId`, `draftRevNo`, `approvedDigest`, `itemId`, `revisionNo`, `selfApproval`, `origin`), `knowledge.draft.rejected` (`retire`) and `knowledge.draft.changes_requested` (`update`) (detail `draftId`, `reviewId`, `draftRevNo`, `payloadDigest`, `origin`). The rationale text is never in the audit detail.

Refusal codes: `id: illegal_transition | self_approval_via_token | target_missing | archived`, `approvedDigest: required | malformed | stale_digest`, `expectedItemVersion: required | malformed | stale`, `rationale: required | too_long | malformed`, `proposal.*` (owner / subjects judged again).

### Reads (`menu-query`, `platform:view`)

Row visibility is decided in SQL: the **author** sees their drafts in every status; a holder of `knowledge.item.publish` (Admin by the module bypass) also sees every draft whose status is not `draft` (a not-yet-submitted draft is private to its author); nobody else sees any draft.

- `logKnowledge.drafts` — params `q`, `page`, `pageSize`, `sorting`, `filters` ([Common params](#common-params), ADR-0105). `q`: `ILIKE` on the latest revision's title. Filters: `status`, `origin`, `proposalType` (`in` / `notIn` over their closed sets), `ownerModelId` (`in` / `notIn`; matches `coalesce(owner_model_id, the SW version's model)`). Sorts: `updatedAt` (default, desc), `submittedAt` (`NULLS LAST`), `createdAt`. Row: `{ id, origin, proposalType, targetItemId, baseRevisionNo, ownerModelId, ownerSoftwareId, title, status, latestDraftRev, submitterActorId, postedItemId, submittedAt, updatedAt, createdAt }` (`postedItemId` is null unless the draft is approved); never the proposal.
- `logKnowledge.draftDetail` — `paramKeys: ['draftId']`. A draft the caller may not see (or unknown / other workspace) answers `ok` with `data: null`. Otherwise `{ draft, revisions, reviews, targetItemVersion, proposal }`: `draft` is the row shape plus `version`, `closeReason`, `closedAt`, `closedBy`, `createdBy`; `revisions` is `{ revNo, payloadDigest, authorActorId, createdAt }` newest first; `reviews` is `{ id, decision, reviewedDraftRevNo, approvedDigest, selfApproval, rationale, postedItemId, postedRevisionNo, reviewerActorId, reviewedAt }` newest first (the rationale is visible to whoever can see the draft); `targetItemVersion` is the target's current `row_version` when the viewer holds `knowledge.item.publish`, the draft is `submitted`, `revise`, and the target exists (the `expectedItemVersion` to send), else `null`; `proposal` is the latest revision's stored proposal.

### Agent and Validator submission over API tokens (#1198 c)

**As-built shape (replaces the design §6.6 route candidate `/api/v1/knowledge/agent/drafts`).** There is no separate agent route. An AI agent or a Validator calls the same `logKnowledge.draftCreate` / `draftUpdate` / `draftSubmit` / `draftWithdraw` menu actions through `POST /api/v1/menu-action` with a Bearer API token ([ADR-0116](../../../adr/0116-platform-api-tokens-personal-and-service.md), [auth.md](auth.md)): one service, one set of rules, one audit trail, and the token core already supplies authentication, scope ∩ permission, the 10/min token bucket and the token id in the audit detail. The token needs the scope `knowledge.draft.create` (and `workspace.read` for the two reads) and its actor must hold `knowledge.draft.create`. `duplicateCandidates` / `reviewUrl` answers need search (#1199) and are not built.

- **Identity comes from the server only.** `draft_revision.author_auth` is `token` when the request authenticated with a token, else `session`, on every revision (create and update). `origin` at create: session → `human`; token of an `actor_type = 'system'` actor → `validator` when the input carries `validatorRef`, else `ai`; personal token of a human actor → `human` (provenance stays human; `author_auth = 'token'` is what the approval rule in [Review decisions](#review-decisions-1198-b) reads). The pure rule is `deriveOrigin(authKind, actorType, hasValidatorRef)` in `domain/draft-input.ts`. No input field sets `origin`, `author_auth`, an actor id or a timestamp (unknown keys are refused).
- **`validatorRef`** (`draftCreate` only, optional): `{ sourceSystem, runId, findingId }`, a strict object, each part trimmed, non-empty, at most 200 characters, no control characters (`required` / `too_long` / `malformed` at `['validatorRef', part]`). Allowed only for a token call of a system actor; a session or a personal token gets `['validatorRef'] not_allowed`. Stored on `knowledge.draft`; the partial unique index `draft_validator_ref_uq (workspace_id, validator_source_system, validator_run_id, validator_finding_id) WHERE validator_source_system IS NOT NULL` allows one draft per finding per workspace. A resend of a ref answers its existing draft only to that draft's author; a hidden owner/target/posted Item first answers `['validatorRef'] not_found`; otherwise any other caller gets `['validatorRef'] taken` and learns nothing else about the draft (no id, status, digest or version).
- **Replay.** A repeat with the same ref (any idempotency key, any payload) answers `ok` with the existing draft's `data` (`id`, `status`, `latestDraftRev`, `payloadDigest`) and its current `version`: no new draft, revision or audit row. The insert is `ON CONFLICT … DO NOTHING`, so a racing create falls back to reading the winner without aborting the transaction.
- **No approval path.** A token subject never reviews or publishes: `knowledge.item.publish` is session-only, so `draftApprove` / `draftReject` / `draftRequestChanges` / `itemCreate` / `itemRevise` with a token answer `200 { outcome: 'forbidden' }` and write `api_token.session_required_denied`. A system actor only touches its own drafts (the author rule) and, holding no review right through a token, sees only its own drafts in the reads.
- **Retention.** No retention job: drafts and revisions are append-only and kept; withdrawn and rejected drafts stay as history. Token lifetime (expiry, revoke) is the token core's.

| --- | --- | --- |

`logKnowledge.specCoverage` (R-f, #1496; menu `log-knowledge-models`, `platform:view`, params `modelId`, optional `softwareId`): the 명세 커버리지 summary for the spec screen badge, from the log-rules `RuleCoveragePort` (injected as a structural type; no import of log-rules). A draft's content is never returned.

`SpecRevisionHeader`: `{ id, revisionNo, state: 'draft' | 'published' | 'rejected', publishedAt, publishedBy, contentSha256, eventCount, version }` (`version` = `row_version`, the `expectedVersion` of a draft write). Storage (`knowledge` schema, all keyed by `workspace_id`, composite same-workspace FKs, `ON DELETE RESTRICT`): `model_spec_revision` (`(workspace_id, model_id, revision_no)` unique; `state` in `draft|published|rejected`; `schema_version`; `content_sha256` null until published, 64 lowercase hex; `source_doc_ref` jsonb `{docLabel, docVersion, link?}`, closed keys; a published row must carry hash, `published_by` and `published_at`), `spec_module` (`(workspace_id, spec_rev_id, module_key)` unique; the parent must be a module of the same revision), `spec_event` (`(…, module_id, event_key)` unique; the module must be of the same revision; `fields_json` a jsonb array, its v1 shape is validated by the write node; `detail_doc_ref` is free text, a pointer into the source document), `spec_event_relation` (both events of the same revision; no self relation). The `spec_sw_change` table is not created yet (node c).

**Grants (migrations 0091 and 0092, ADR-0109 style).** `platform_app` holds `SELECT` and `INSERT` on the four tables, no `DELETE` anywhere, and on `model_spec_revision` a column-limited `UPDATE (state, content_sha256, published_by, published_at, row_version, reject_reason, source_doc_ref)`; `model_id`, `revision_no` and every other column are not updatable. The grant is wide enough for a draft save and the `draft → published | rejected` transition, so the wall is a trigger, not the grant: `BEFORE UPDATE` on `model_spec_revision` refuses (`23514`) any update unless `OLD.state = 'draft'`, refuses a change of an identity column, and for a draft that stays a draft requires a higher `row_version`. A published or rejected revision therefore never changes again. A `BEFORE INSERT` trigger on `spec_module`, `spec_event` and `spec_event_relation` refuses (`23514`) a row whose revision is not a `draft`; it reads the revision `FOR SHARE`, so an insert and a publish cannot interleave (a publish waits for an open insert, a later insert sees the sealed state). A partial unique index allows one open draft per model.

## Model spec write actions

#1196 b1, migration 0092. Four `menu-action` writes on menu `log-knowledge-models` (`modules/log-knowledge/spec-actions.ts`; value checks `domain/spec-input.ts`, TSV parser `domain/spec-tsv.ts` (b2), canonical hash `domain/spec-hash.ts`, SQL `repositories/spec-write.ts`); same transport, replay and `If-Match`/key rules as [Write actions](#write-actions). Permission `knowledge:spec-publish`, judged with the workspace-scoped capability `knowledge.spec.publish` (Admin always; Developer by request; a User is refused on request, approval and direct grant — `supported-scope-policy.ts`). Self-publish is allowed and audited (#1198 revisits). `requiresScope: false`; the workspace is the session actor's. Input is structured rows **or** TSV text ([TSV text input](#tsv-text-input-1196-b2), node b2): both converge into the same rows before validation; nothing is a file attachment. Menu mirror: `specActionSpecs` in `menus/log-dev/log-knowledge/src/endpoints.ts` (mock actions registered with node d), compared by `catalog-menu-drift.test.ts`.

| Action | Concurrency | Input | Answer `data` |
| --- | --- | --- | --- |
| `specDraftCreate` | `none` | `modelId`, `sourceDocRef: { docLabel, docVersion, link? }` | `{ revisionId, version }` |
| `specDraftSave` | `version` (`revisionId`) | `revisionId`, `mode: 'append' \| 'replace'`, optional `sourceDocRef`, and **exactly one of** `modules[]`/`events[]`/`relations[]` (a non-empty array counts as rows) or `text` + `format: 'tsv' \| 'paste'` | `{ revisionId, version, counts }` (`revisionId` is the **new** draft after a `replace`) |
| `specPublish` | `version` | `revisionId` | `{ outcome: 'published', revisionId, contentSha256 }` or `{ outcome: 'unchanged', revisionId: <existing published id> }` |
| `specReject` | `version` | `revisionId`, `reason` (1–500 chars) | `{ revisionId }` |

Rows: `modules[]` `{ name, parentModule? }`; `events[]` `{ module, name, fields?, triggerRule?, detailDocRef? }`; `relations[]` `{ sourceModule, sourceEvent, predicate, targetModule, targetEvent, ruleRef? }` (the TSV columns are the snake_case names of these fields, [TSV text input](#tsv-text-input-1196-b2)). `fields[]` is the closed `fields_json` v1: `{ name, type: string|int|float|bool|enum|timestamp, unit?, allowedValues?, description }`; an unknown key or type is refused. A reference (`parentModule`, `module`, relation ends) is a name or key, resolved with `toCodeKey`.

- **Keys and normalisation (at save).** Names are NFC, trimmed, inner whitespace collapsed. `module_key` = `toCodeKey(name)`, unique per revision; `event_key` = `toCodeKey(name)`, unique **per module** (the unique index is `(workspace_id, spec_rev_id, module_id, event_key)`), so `(module_key, event_key)` is unique per revision. Relation edges are unique per `(source, predicate, target)` — against the draft as well as within the call, judged before insertion so the unique index never surfaces; a self relation is refused.
- **`specDraftCreate`.** Unknown or other-workspace model → field error `modelId:not_found`; an open draft exists → `modelId:draft_exists`. `revision_no` = max + 1, `row_version` 1. Serialised per workspace + model by `pg_advisory_xact_lock`, so parallel first creates leave one draft.
- **`specDraftSave`.** `append` adds rows; `replace` rejects the draft (`reject_reason = 'replaced'`) and creates a new draft with the call's rows in the same transaction, because the four tables are append-only; the draft's `source_doc_ref` carries over unless the call sets one. A call carries exactly one of rows or `text` (an empty array is not rows): both or neither → `input:rows_or_text`; `text` without `format` → `format:required`; `format` without `text` → `text:required`. A `text` call is parsed by [TSV text input](#tsv-text-input-1196-b2) and then takes this same path: the same rows, the same errors, the same hash as the equivalent structured call. Rows are inserted in dependency order (modules by parent depth, then events, then relations). A reference must point to a row already in the draft or anywhere in the same call (row order within a call is free), otherwise a row-numbered field error `modules.<i>.parentModule`, `events.<i>.module`, `relations.<i>.sourceEvent|targetEvent` with `not_found` (for a `text` call these keep the line and column of the offending cell); a module cycle is `cycle`; a duplicate qualified key is `duplicate` (against the draft or the call), and so is a repeated relation edge: `relations.<i>.predicate:duplicate` for an edge the draft already stores or the call already holds. Caps per call: ≤ 2,000 rows in total and ≤ 512 KiB — the serialized body for a rows call, the text itself for a `text` call (the JSON envelope would inflate every tab) — → `invalid` `input:too_large` (larger specs stream in several calls). The answer is small because replay records are capped at 128 KiB.
- **`specPublish`.** An empty draft is `invalid` (`revisionId:empty`). The canonical hash (design §15.5) of the stored rows is compared with the latest published revision of the model: equal → `ok` with `outcome: 'unchanged'`, the draft becomes `rejected` with reason `unchanged` in the same transaction (no orphan draft blocks the next create) and no revision is created, even when only `docVersion` differs; otherwise the draft is sealed (`state = 'published'`, `content_sha256`, `published_by`, `published_at`).
- **`specReject`.** Draft → `rejected` with `reason`. Who and when of a reject are in the audit row only (`published_*` stay `NULL`, the published check requires it).
- **State and version.** `currentVersion` locks the revision row `FOR UPDATE` and answers `row_version` for a draft; for a published or rejected revision it answers `<state>:<fresh uuid>`, a new value per call that no client can hold — a token returned in an earlier conflict cannot be sent back as `expectedVersion` — so the engine answers `conflict` (a write to a sealed revision, with or without any current version). Unknown or other-workspace revision → `not_found`. A stale version → `conflict` with the current version.
- **Audit.** One `core.audit_log` row per write in the same transaction, subject type `knowledge_model_spec`, subject id = revision id, body-free detail (`packages/feature-shared/src/audit/log-knowledge-spec.ts`): `knowledge.spec.draft_saved` (`mode: create|append|replace`, `input: rows|tsv|paste` on a save — the provenance only, never the text; counts added, `replacedRevisionId`), `knowledge.spec.published` (`outcome`, `contentSha256`, counts, `existingRevisionId`), `knowledge.spec.rejected` (`reasonLength`; the text is not copied). The projection `core.platform_audit_events` (migration 0092, the 0085 body plus the subject type and the capability) lists them; `audit-actions.ts` maps the event types to `update`, `create`, `retire`.

Refusals are `invalid` field errors thrown from `handle` after the locks: `revision:none_published`, `modelId:not_found`, `softwareId:not_found`, `endsBeforeSoftwareId:not_found|not_after_start`, `targetKey:not_found|already_exists` (a replacement reports `replacement.…`), `range:overlap`, `changes:too_many` (500 open per model), `replacement:target_mismatch`, `change:already_retired`, `needsRevalidation:not_set`; value codes of `validate`: `required`, `too_long`, `malformed`, `too_large` (`change` over 16 KiB serialized), `target_mismatch` (a `change.after.name` that spells another key). An unknown or other-workspace change id is `not_found`; a stale `expectedVersion` is `conflict`.

- **Key grammar.** Each segment (module key, event key, field name, predicate) escapes `%`, `/`, `#` as `%25`, `%2F`, `%23`; event = `module/event`, field = `module/event#field`, relation = `sourceModule/sourceEvent#predicate#targetModule/targetEvent`. Built and parsed only in `domain/spec-target-key.ts`.
- **Basis and locking.** `based_on_rev_no` is the CURRENT published revision number at write time, server-set. Supplied UUIDs (`modelId`, `softwareId`, `endsBeforeSoftwareId`, `changeId`, replacement ids) are accepted in any spelling and canonicalised to lower-case before the lock key and every lookup — the DB answers lower-case ids, and the lock key hashes the text. `specChangeAdd`, the retire replacement path and `specPublish` take one model-scoped `pg_advisory_xact_lock(hashtextextended('spec-change:<ws>:<model>', 0))`; order everywhere: revision row, advisory lock, change rows. `currentVersion` of retire/confirm reads the row unlocked for `model_id`, takes the lock, then `SELECT … FOR UPDATE`. This serialises concurrent adds (so `range:overlap` cannot be passed twice) and a publish against an add.
- **Retire.** Sets `retired_at`, `retired_by`, clears `needs_revalidation`; with a `replacement` the new row is inserted first (the overlap check excludes the row being retired) and the old row's `retired_by_change_id` points at it (the table guard also rejects a pointer at another target or the row itself). Open = `retired_at is null`.
- **Publish flag step.** Inside the same transaction as `specPublish` (after the seal): the touched keys of the new revision against the previous published one (`domain/spec-diff.ts`) set `needs_revalidation = true`, `revalidation_rev_no = <new revision_no>`, `row_version + 1` on every open change of the model on those keys, in one set-based `UPDATE` (chunks of 500). The publish answer and replay record are unchanged; the audit detail gains `flagged` (count).
- **Reads.** `logKnowledge.specChanges` — `modelId`, optional `softwareId` (changes whose range contains that version), `needsRevalidation` (boolean), `status` (`open` default, `retired`, `all`), `page` (0-based), `pageSize` (1–200); data `{ rows, total }`, order `(created_at desc, id)`; a row carries the change fields, `softwareLabel`, `endsBeforeLabel` and `version` (`row_version`). `logKnowledge.modelSpec` with `softwareId`: unknown or other-model version → `data: null`; no applicable change → the model spec as before plus `effective: false`; otherwise `{ revision, effective: true, softwareId, modules, events, relations, stale, removed }` where every entry has `origin` (`revision|change`), `changed: [{ changeId, changeKind, targetKind, targetKey }]` and `needsRevalidation`; change-added entries have `id: null` and are identified by `moduleKey` / `eventKey` (+ `moduleKey`). Without `softwareId` the answer is unchanged (no `effective` key). The range `[start, end)` is judged on the CURRENT `release_order` when read; apply order `(start order, created_at, id)`, sorted in SQL at the timestamp's full precision; two added changes for one field compose by field key (one keyed field, the later change wins, both marked).
- **Audit.** Subject type `knowledge_model_spec` (no projection change), subject id = the change id; `knowledge.spec.change_added` (`modelId, changeId, softwareId, endsBeforeSoftwareId, targetKind, changeKind, basedOnRevNo, replacesChangeId?`), `change_retired` (`modelId, changeId, replacementChangeId?`), `change_confirmed` (`modelId, changeId, revalidationRevNo?`). Never `note`, `change_json` or `target_key`.
- **Table walls.** The runtime role holds `SELECT, INSERT` and `UPDATE (needs_revalidation, revalidation_rev_no, retired_at, retired_by, retired_by_change_id, row_version)`; no `DELETE`. `knowledge.spec_sw_change_guard` (BEFORE UPDATE) rejects any other column change, any `row_version` step other than +1, a `retired_by_change_id` that is the row itself or a row of another target, and any change of a retired row.

## Object access (#1504 S-a, migration 0112)

Design: `docs/design/features/log-knowledge-search/README.md` §3.4; decision: [ADR-0124](../../../adr/0124-knowledge-search-evaluates-acl-at-query-time-and-reads-display-live.md). No screen yet (the menu `log-knowledge-access` has no UI; the search screen is node S-f).

**Storage.** `access_mode` (`internal` default | `restricted`) on `equipment_model`, `software_version` and `knowledge_item`; `knowledge.object_access_rule` (`rule_id`, `target_kind` `model|software|item`, `target_id`, `grantee_kind` = `actor`, `grantee_id`, `effect` `allow|deny`, `valid_until?`, `created_by/at`, `revoked_at/by`): a rule is revoked, never deleted. Existing rows stay `internal`.

**The rule (one place).** `domain/access-visibility.ts` (pure) and `repositories/access-visibility.ts` (the SQL expressions every statement uses). An object is visible to an actor iff **no active deny** names the actor on any level of its chain Model → SW version → Item (as far as the object goes) **and** every level is `internal` or holds an **active allow** for the actor. So a restricted parent hides all descendants, a child's allow never lifts a parent's restriction, and a deny beats an allow. A rule counts while it is not revoked and `valid_until` is null or in the future. There is no Admin or service-actor shortcut: a service actor needs explicit allow rules like anyone. The rules are read in the request's own statement, so a revoke or a mode change shows with the next request.

**Where it applies.** Reads: `vendors` / `processes` counts, `models`, `softwareVersions`, `exploreModels`, `modelProfile`, `items`, `itemDetail` (all revisions, links), `modelSpec` (also with `softwareId`), `modelSpecRevisions`, `specDraft`, `specChanges` (a change starting at a hidden SW is not listed, a hidden end version shows neither id nor label, and a hidden replacement change has `retiredByChangeId: null`; a hidden SW filter behaves like an unknown id), `specSubjectItems`, `conceptMappings`, `conceptSuggestions` (the scan and the candidate names), `drafts` / `draftDetail` (a draft of a hidden owner, target Item or approved posted Item is hidden even from its author), `importDetail`, CSV reports and apply progress (a job with any hidden staged target, mapped/result target or SW parent is missing as a whole, including raw names/codes, states and counts). Writes: Item create / revise / assess / derive / archive, draft create / update / submit / withdraw / approve / reject / request-changes, model and SW create / update / set-active, spec draft and SW change writes, concept propose / confirm / reject, import plan and resolve (the catalog snapshot leaves hidden models and SW versions out, so a row naming one is planned as new) all treat a hidden object as missing. Known limit: a unique code key is still enforced by the database, so creating a model or SW version whose code equals a hidden one answers `duplicate`.

**Read port.** `knowledgeLookup.getModel / getSoftware / getEffectiveSpecPin / listEffectiveRequirements` require the trailing `viewerActorId`; a model or SW version hidden from that actor answers like a missing one (`null`, `model_unknown`). Both coverage endpoints, `RuleCoveragePort` and lifecycle reads/commands pass the current actor, including workers and explorer ports. Lifecycle hierarchy paths/targets/child flags, lists, totals, SW sorting counts, history references, attachment parents and Entity Links use the same knowledge predicate.

**Access-management recipient.** See the Admin-only recipient policy in [Permission policy](../05-permission-policy.md).

**Replay and locking.** Matched command replays rejudge the input and created/posted objects before returning stored ids or versions; they never repeat the write. Validator-ref replays also rejudge the stored draft before authorship/response. Item writes lock the owner chain and then the Item, and rejudge in a new statement after the row lock; owner creation checks rejudge after SHARE locks. Mode changes and rule add/revoke lock the target UPDATE, serializing against these locks. Rule expiry uses statement time rather than transaction start time. The access-management capability exception is preserved.

**Import disclosure choice.** Hide the whole job when any staged target or parent is hidden, so filtering/paging cannot expose an omitted row count or raw cells. The raw cells use the validation normalizer and name fallback before disclosure, including before the first validation. Unmapped raw input stays private to its uploader until its references can be judged. This conservative, reversible projection keeps JSON, CSV, progress and replay on one gate. Applying a new SW independently rechecks its parent after locking it inside the row transaction; hidden and missing both fail with `parent_missing` and no catalog/audit/identity write.

**Audit projection (migration 0113).** The general `core.platform_audit_events` projection has no viewer argument, so it excludes knowledge subjects and lifecycle project/round/request subjects (including round Entity Link events). Source events remain in `core.audit_log`. A future caller-aware projection can restore visible events. C7 (duplicate/taken hidden-code confirmation) and C12 (consecutive Item numbers plus visible totals disclose hidden count) remain **not implemented pending owner decision**, recorded in [the search backlog](../../../design/features/log-knowledge-search/README.md#9-미구현-목록-다시-여는-조건).

**Capability and endpoints.** Capability `knowledge.access.manage` (menu permission `knowledge:access-manage`): workspace-scoped, **sensitive**, `adminModuleBypass: 'always'`, **session-only** (ADR-0116 decision 4: never a token call), refused for a User recipient (`supported-scope-policy.ts`), kept out of the platform audit projection. Managing is judged by the capability, not by visibility: a manager reaches a target they cannot see, and may grant themselves access (audited). Menu `log-knowledge-access` (not mirrored by the log-knowledge menu package):

## Read port: effective requirement keys (#1493, log-rules R-c)

No HTTP endpoint. A barrel read port for other modules (first consumer: log-rules, node R-d), next to `getModel`, `getSoftware` and `getEffectiveSpecPin` on `knowledgeLookup` (`modules/log-knowledge/knowledge-lookup.ts`; design `docs/design/features/log-rules/README.md` §3.3, §4).

`knowledgeLookup.listEffectiveRequirements(tx, workspaceId, modelId, softwareId | null, viewerActorId)` answers `{ state, specPin, requirements }`:

| `state` | When | `specPin` / `requirements` |
| --- | --- | --- |
| `ok` | the model has a published model spec revision | the pin and the keys of the effective spec |
| `no_spec` | the model has no published revision (a draft does not count); never an empty `ok` | `null` / `[]` |
| `model_unknown` | the model is not in the workspace, or `softwareId` is not a version of that model | `null` / `[]` |
| `ambiguous_key` | a module or event key of the effective spec is empty or contains `/` | the pin / `[]`, plus `ambiguousKeys: string[]` (the offending keys, `module/event` for an event) |

- **Effective spec.** The latest published revision plus the open changes applicable to `softwareId` in apply order, the same resolution as `getEffectiveSpecPin` and `modelSpec` with `softwareId` (`applySpecChanges`); `null` = the revision as is. A stale change is not applied; a removed module does not remove its events (no cascade, as in the spec reads).
- **Key format.** A requirement is `{ key, kind: 'module' | 'event', moduleKey, eventKey? }`; `key` = `moduleKey` for a module, `moduleKey/eventKey` for an event, the stored stable keys as they are (no case folding, no trimming). `domain/requirement-key.ts` holds `requirementKey` and `parseRequirementKey`. Order: all modules, then all events, each in the effective spec's order (revision order: key ascending; entries added by a change come last in application order). The result is deterministic.
- **`/` in a key.** Write validation does not forbid it (`toCodeKey` keeps `/`, and an NFKC fullwidth solidus becomes `/`; a change can add `A/C%2FD`), so `a/b/c` would be ambiguous. The port refuses with `ambiguous_key` instead of returning a key that cannot be parsed back.
- **Snapshot.** The model advisory lock `getEffectiveSpecPin` takes is held before the revision and the changes are read, and the pin is computed from those same rows: the pin and the keys always describe one effective spec (integration test with a change committed while the read waits on the lock). The lock is taken first, before the requested software's release order is read, so a concurrent reorder cannot pair an order of one moment with the change list of another. A pool-backed `Db` passed by a caller is wrapped in one transaction of the port's own (the lock is a transaction lock); a transaction handle is used as is.
- **Scope.** Every statement filters by `workspace_id`; reads `knowledge.*` only; writes nothing; one pass over the revision's modules and events plus one change query (no per-key query).
- **ACL.** The port takes a caller-verified workspace and decides no permission; the caller owns the entry permission. Object access (#1504, [Object access](#object-access-1504-s-a-migration-0112)) requires the trailing `viewerActorId`: a model or SW version hidden from that actor answers `model_unknown`. Every caller passes the current viewer.

### Concept mapping (node e)

| Action | Concurrency | Input | Answer `data` |
| --- | --- | --- | --- |

One `confirmed` `equivalent` per `(model, target_key)` (`target:already_confirmed` on confirm; DB partial unique too).
- **Confirm** needs `proposed` (`mapping:already_confirmed|already_rejected`) and the target still in the current revision. **Reject** takes `proposed` or `confirmed` (`mapping:already_rejected` otherwise) and stores the reason. A rejected row is final.

## TSV text input (#1196 b2)

`specDraftSave` with `text` (a string) and `format: 'tsv' | 'paste'` — `tsv` is the content of a TSV-formatted `.txt` the screen read (the file itself is never stored), `paste` is pasted text. Both run the same pure parser (`domain/spec-tsv.ts`, `parseSpecTsv`); `format` is provenance only, recorded in the audit detail. Everything after parsing is the structured path of [Model spec write actions](#model-spec-write-actions): same normalisation, same planning, same `content_sha256` (an acceptance test asserts text and rows parity), same caps wall, same capability.

- **Format.** UTF-8 text; a leading BOM is ignored; line endings `\n`, `\r\n` or a lone `\r`; blank lines are skipped. One header row is required — exact column names (after trim), free order, any subset, `kind` mandatory. No quoting or escaping: a cell cannot contain a tab or a newline (the JSON of `fields_json` must be compact one-line). A line with more cells than the header → error; fewer → the missing cells are empty; trailing empty cells are fine.
- **Columns** (all optional in the header except `kind`; there is no `name` column — the `module`/`event` column carries the entity's display name): `kind` (`module|event|relation`), `module`, `parent_module`, `event`, `trigger_rule`, `detail_doc_ref`, `fields_json`, `source_module`, `source_event`, `predicate`, `target_module`, `target_event`, `rule_ref`.
  - `kind=module`: `module` (the module name, key from `toCodeKey`), optional `parent_module` (a module name).
  - `kind=event`: `module` (owning module), `event` (the event name), optional `trigger_rule`, `detail_doc_ref`, `fields_json` (a JSON array of the closed `fields_json` v1; anything else, including non-array JSON, is `malformed`).
  - `kind=relation`: `source_module`, `source_event`, `predicate`, `target_module`, `target_event`, optional `rule_ref`.
  - A non-empty cell of a column the row's `kind` does not use → error (silent ignoring would hide mistakes).
- **Errors** are row-numbered by the line in the submitted text (the header is line 1) with the column name: path `['text', 'line N', 'column <name>']`, e.g. `text:line 7:column predicate:unknown_value`. Codes: `required` (missing/blank value, no `kind` column, empty text), `too_long`, `malformed` (bad `fields_json`, NUL/lone surrogate), `unknown_column`, `duplicate_column` (header, naming the header — an unknown header cell is echoed only as its first 40 characters plus `…`, control characters stripped), `unknown_value` (a `kind` cell outside the three), `unexpected_value` (a cell of another kind's column), `too_many_cells` (path `['text', 'line N']`), and the structured codes of a bad cell (`not_found`, …). Planning errors of the text (duplicate keys, dangling references, cycles) come back on the same line/column paths. Parse errors and planning errors share one bounded summary (#1196): at most 20 line errors are reported; more are summarised by a trailing `text:more_errors:<total>` marker whose code is the numeric total (e.g. `text:more_errors:25`). Other cell contents are never echoed (a FieldError carries no payload).
- **Caps**: ≤ 512 KiB of text and ≤ 2,000 data rows per call → `invalid` `input:too_large` (the text is not echoed back); both are judged before the text is parsed — an over-cap call never reaches cell, schema or JSON work, and envelope/contract refusals (rows/text, `format`) are answered without running the parser. Streaming = several calls, each with its own header row; `mode` and the version CAS behave exactly as for rows.

Worked example:

```tsv
kind	module	parent_module	event	trigger_rule	detail_doc_ref	fields_json	source_module	source_event	predicate	target_module	target_event	rule_ref
module	Spindle
module	Spindle Motor	Spindle
event	Spindle		Start	on start		[{"name":"speed","type":"float","unit":"rpm","description":"RPM at start"}]
event	Spindle Motor		Stop			
relation							Spindle	Start	precedes	Spindle Motor	Stop	§4.2
```

## Catalog import staging (#1195 a, migration 0087)

Steps ①–③ of design v0.6 §6.2 (④–⑤ follow in the next section). Nothing in ①–③ writes vendor, process, model, software, `model_process`, `external_identity_map` or `core.audit_log`; the runtime role holds SELECT/INSERT/UPDATE (no DELETE) on `catalog_import_job`, `catalog_import_row` and `catalog_import_resolution`.

**Upload** `POST /api/v1/log-knowledge/imports` — multipart with one `file` part and an `entityType` field (`vendor|process|model|software`); headers: session cookie, `x-csrf-token`, `Idempotency-Key` (UUIDv4). Order: session (401/403) → CSRF (403 `csrf.invalid`) → key → `knowledge.catalog.import` (Admin bypass; 403 `permission.denied`; judged before an idempotent replay and again in the transaction) → file. `201 {jobId, rowCount, status:'uploaded'}`. The request hash covers `entityType`, file name, size and sha256; the same key with another request is `409 conflict.idempotency_key_reuse`. The file bytes are not stored. File refusals answer `{code, message}` and create no job: `413 file_too_large` (> 5 MB); `400` `too_many_rows` (> 5,000 data rows), `too_many_columns` (> 50), `invalid_headers` (blank or duplicate header), `unsupported_type` (type is decided by content — zip signature = XLSX, otherwise text — and the extension must agree), `encoding` (CSV must be UTF-8, BOM stripped), `sheet_count` (XLSX needs exactly one sheet), `empty`, `unreadable` (ragged CSV, corrupt XLSX), `invalid_entity_type`; `503 busy` when two parses are already running.

Cells are kept as strings in `raw_json` (`{<header>: <string>}`, dates as ISO). A formula, merged or non-plain cell (XLSX) is stored as `''` and recorded in the immutable `parse_errors` (`formula|merged|unsupported_cell`); formulas are never evaluated.

**Actions** (menu `log-knowledge-catalog`, `concurrency:'version'` on the job's `row_version`; answers carry ids and counts, never rows):

- `logKnowledge.importMap` `{jobId, mapping:{<field>:<header>}}` — fields per entity: vendor `vendor_code, vendor_name`; process `process_code, process_name`; model `vendor_code, model_code, model_name` (+ optional `process_codes`, split on `;` or `,`; the names shape `vendor_name, model_name` (+ `process_names`, `vendor_code`, `model_code`) and the upload's own mapping: §Catalog import by names); software `vendor_code, model_code, version_key` (+ optional `version_name`). Field errors under `mapping.<field>`: `required`, `unknown_field`, `unknown_header`, `duplicate_source`; `jobId:state` when the job is past `review_required`. Stores `mapping_json`, status `mapped`, bumps `plan_version`, resets normalized data, errors, plan state and targets; `parse_errors` is never touched. Answer `{jobId, status, planVersion}`.
- `logKnowledge.importValidate` `{jobId}` (job `mapped|validated|review_required`) — per row: `normalized_json`, `validation_errors` (the catalog write codes under the file's field names, `parent_missing`, `parent_inactive`, `process_missing`, `process_inactive`, `duplicate_in_file`, plus the row's `parse_errors`) and `plan_state` `error|new|unchanged|update|conflict`. Lookup scope is `(workspace, resolved vendor, code_key)` for a model and `(resolved model, version_key)` for a software version: a code present only under another vendor is `new`, a vendor move is never inferred. An existing inactive row is `conflict` (it keeps its key); an update is a differing name (or, when `process_codes` is mapped, a differing process set). Existing rows carry `target_id` and `target_version`. Status `validated` without `error`/`conflict` rows, else `review_required`; bumps `plan_version`. Answer `{jobId, status, planVersion, counts:{pending,new,unchanged,update,conflict,error}}`.

**Read** `logKnowledge.importDetail` `{jobId, page, pageSize, sorting?, filters?}` — menu right `platform:view`, handler also requires `knowledge.catalog.import` (`forbidden` outcome). Filters `planState` and `applyStatus` (`in|notIn`; `notIn` keeps rows with no apply status yet), sort id `rowNo`. `ok` data `{job, rows, total, applyCounts}`, a row is `{rowNo, raw, normalized, errors, planState, targetId, targetVersion, resolution, mapTargetId, applyStatus, applyError, resultTargetId}` (`resolution` shows only a resolution written for the job's current validation); `applyCounts` is `{applied, unchanged, skipped, excluded, unresolved, conflict, failed, remaining}`. An unknown or other-workspace job answers outcome `error`, `data:null`, message `not_found` (the same for both).

## Catalog import resolve and apply (#1195 b, migration 0088)

Steps ④–⑤ of design v0.6 §6.2. Right `knowledge.catalog.import` (Admin bypass) on every entry point; the apply route re-checks it inside each transaction that writes.

**Resolve** `logKnowledge.importResolve` `{jobId, resolutions:[{rowNo, resolution, mapTargetId?}]}` (≤ 500; job `validated|review_required`; `concurrency:'version'`). `skip` on any row; `map` on a `new` or `conflict` row to an **active** row of the job's entity in the same scope (same vendor for a model, same model for a software version; `scope`/`inactive`/`not_found` under `resolutions.<i>.mapTargetId`); `create` only on `new` rows (also the default). `abort` is not offered (`invalid`). A `map` stores the target's current `row_version` as `expected_target_version`. The call bumps `row_version` and `plan_version` but not the validation generation; a later `importMap` or `importValidate` increments `catalog_import_job.validation_generation`, which makes every earlier resolution stale (`catalog_import_resolution.based_on_validation`). Answer `{jobId, status, planVersion, resolved}`.

**Cancel** `logKnowledge.importCancel` `{jobId}` — any status before `applying` → `cancelled`.

**Apply** `POST /api/v1/log-knowledge/imports/:jobId/apply` body `{expectedPlanVersion}` — session, CSRF, capability; no `Idempotency-Key`: it is a resumable state machine and every answer is the current progress `{jobId, status, planVersion, remaining, counts}` (`counts`: `applied, unchanged, skipped, excluded, unresolved, conflict, failed, remaining`). Errors: `404 {code:'not_found'}` (unknown or other workspace), `409 {code:'conflict', reason:'plan_version'|'state'}`, `400 invalid`, `503 {code:'busy'}` with `Retry-After: 5` (both per-process apply slots taken; nothing was started).
- The first call (job `validated|review_required`, `plan_version == expectedPlanVersion`) seals in one transaction: `plan_hash` per row = sha256 of the canonical JSON `{rowNo, normalized, planState, targetId, targetVersion, resolution, mapTargetId, expectedTargetVersion}`; `sealed_plan_hash` = sha256 of the row hashes in `row_no` order; rows that never write get their final status (`excluded` for `error` — even with a skip —, `skipped`, `unchanged`, `unresolved` for a `conflict` without a map); status `applying`, `apply_pass = 1`. Map/validate/resolve/cancel then refuse (`jobId:state`).
- Rows run in `row_no` order, one transaction each: job `FOR SHARE`, hash recomputed against the stored `plan_hash` (mismatch → `failed plan_changed`), row `FOR UPDATE`, skip when already final (exactly once). `new` creates (parent re-checked: `failed parent_missing|parent_inactive|process_missing|process_inactive`; key taken, also by a concurrent insert → `conflict taken`). `update`/`map` lock the target: `row_version != expected` → `conflict stale_target`; a target that no longer exists → `conflict target_missing`; inactive → `conflict inactive_target`; they change the name (a software name only if `version_name` is mapped) and a model's process set (only if `process_codes` is mapped; new assignments must be active) and never the code or `active`. `map` also writes `external_identity_map` (`catalog_import`, entity, canonical JSON array key, `accepted`) when none exists for the key; an existing row for another target → `conflict identity_conflict`. An unexpected error rolls the row back and marks it `failed unexpected` in its own transaction.
- One runner per job: a session-scoped advisory lock (workspace + job) is held for the whole call; a concurrent caller answers progress and starts nothing.
- Time budget `IMPORT_APPLY_BUDGET_MS` (15,000): at least one eligible row per call, then no new row after the budget; the answer is `status:'applying'` and the client calls again. A pass attempts each eligible row at most once (`apply_pass`); when none is left the job becomes `completed` (no `failed`/`conflict` row) or `partial_failure` with `applied_at`. A call on `partial_failure` starts a new pass over the `failed` rows only; `conflict` rows are final.
- Audit, same transaction as the write: `knowledge.catalog.created|updated` with `detail.source = {importJobId, rowNo}`; `knowledge.catalog.identity_mapped` (subject = target; `{sourceSystem, sourceType, externalKey, source}`).

**Report** `GET /api/v1/log-knowledge/imports/:jobId/report.csv` — session and capability; unknown or other-workspace job → 404. UTF-8 BOM, CRLF, RFC 4180 quoting, every cell guarded against formula injection (prefix `'` before `= + - @ TAB CR`). Columns `row_no, plan_state, resolution, apply_status, apply_error, result_target_id`, then the stored (trimmed) upload headers in stored order with the stored raw values. `Content-Disposition: attachment` (RFC 5987 file name).

## Catalog import by names (#1195 b2, no migration)

The owner's import is a one-time bulk load of a **names-only model sheet** (ADR-0107 decision 2 supplement). Four steps: upload → validation result → rows that need a decision (only when conflicts exist) → apply result. No mapping step. Vendor, process and software uploads keep working as before and are server-only (not offered by the UI; `.planning/backlog.md`).

**Headers (`entityType=model`).** Compared after trim and NFKC: vendor (설비사) `설비사명 | 설비사 | 메이커명 | 메이커 | 제조사 | vendor_name` (the last four are older names, still accepted); model `모델명 | 모델 | model_name`; processes (optional) `공정명 | 공정 | process_names`. The old `vendor_code`, `model_code`, `process_codes` stay accepted as optional columns; a non-blank code cell wins over the name for that row's key. Other columns are ignored. A `vendor_code`/`model_code` column also satisfies the maker/model requirement (code-only API sheets).

**Auto mapping.** The upload recognizes the headers, stores `mapping_json` itself (`{vendor_name, model_name, process_names, …}` → header text) and answers `{jobId, rowCount, status:'mapped'}`; `importValidate` runs without `importMap`. If no header is recognized at all (an API client's own headers) the job stays `uploaded` and waits for `importMap`. `importMap` remains for that case and for fixing headers: a mapping that names `vendor_name` is judged as the names shape (`vendor_name`, `model_name` required; code columns and `process_names`/`process_codes` optional), any other model mapping as the code shape (`vendor_code`, `model_code`, `model_name` required).

**File-level failures** (HTTP 400, no job): `missing_header` (`detail.headers` = the expected names missing, `설비사명` and/or `모델명`) and `duplicate_header` (`detail.headers` = the header texts that resolve to one field: identical or alias-equivalent). A blank header is still `invalid_headers`; other entities still refuse identical headers as `invalid_headers`.

**Process names** split on `,` only; each trimmed, empties dropped, deduplicated by key (a repeat of the same name after normalization is one process, not an error). The codes of a process column (`process_codes`) split on `;` or `,` as before.

**Match rule** (maker, process, model): the row with this `code_key` (the code cell, else the name); else `toCodeKey(name)` against both the existing `code_key` and `toCodeKey(existing name)`. Two different rows → `conflict` with the reason in `errors[]`: `ambiguous_name` (the model itself; resolved by the existing model `map`/`skip`), `ambiguous_parent` (a maker or process) or `parent_inactive` (an existing inactive maker/process named by name, ADR-0107 never duplicates it); the latter two are cleared by `skip` only: `importResolve` refuses a `map` on them (`not_allowed`). A maker or process given only as a code that does not exist stays an error (`parent_missing`, `process_missing`, `process_inactive`, `parent_inactive`) as before.

**Parents in the same plan.** A model row whose maker (or process) given by name does not exist plans `new` (or `update` for an existing model that gains a process) and lists `creates: {vendor?: <name>, processes: [<name>…]}` — stored in `normalized.creates` (sealed with the row) and returned as `creates` on each `importDetail` row (`null` when none). Every row that depends on a missing parent lists it; the apply creates it once, on the first row that needs it. A model row that needs a new parent is never `unchanged`.

**Apply.** Inside the row's own transaction: judge every parent first (nothing is written before a refusal), then create the maker, the model, the processes and the links. Each parent is insert-if-absent on its unique key, then read (`DuplicateCatalogKeyError` → re-lookup), so a replay or a competing runner never makes a second row; each created row writes `knowledge.catalog.created` with `detail.source = {importJobId, rowNo}`. Failure codes at apply time: `ambiguous_parent`, `parent_missing`, `parent_inactive`, `process_missing`, `process_inactive` (`failed`), key taken (`conflict taken`).

**Codes.** A row created without a code gets `code` = its name (original text) and `code_key` = `toCodeKey(name)`; a derived code over `CODE_MAX` (64 code points) is a row error `too_long` on the name column (`vendor_name`, `model_name`, `process_names`), never truncated. Catalog create (`vendorCreate`, `processCreate`, `modelCreate`) accepts a missing or blank `code` the same way (overlong → `code: too_long`); update and `softwareCreate` keep requiring one.

### Storage invariants (migration 0082)

Five tables plus the number counter, every key composite with `workspace_id`. An item has exactly one of `owner_model_id` / `owner_software_id` (CHECK, composite FK, `ON DELETE RESTRICT`); `platform_app` may UPDATE only `latest_revision_no, publication_state, verification_state, processing_state, row_version, updated_by, updated_at`. Revisions, evidence, assessment events and links are SELECT/INSERT only for `platform_app`. `item_no` comes from `item_counter` through one atomic upsert (`repositories/item-number.ts`). ## Catalog import by menu actions: paste and apply (#1195 b3, no migration)

A menu reaches the server only through `useMenuFetch` and menu actions, so the import wizard cannot call the multipart upload, `POST …/apply` or `GET …/report.csv`; those stay API-only (their request and response shapes are unchanged; the apply route gains the 503 `busy` admission answer listed in its Errors). Two menu actions (menu `log-knowledge-catalog`, right `knowledge.catalog.import` with the Admin bypass, judged before replay and again on the transaction; both `concurrency:'none'`, both invalidate `logKnowledge.importDetail`) cover the wizard. The result step shows rows and `applyStatus` from `importDetail` (paged: default 50, max 200) and exports them from the table.

**Paste** `logKnowledge.importPaste` `{text: string, sourceName?: string}` — model sheets only (`entity_type 'model'`).
- `text` is what the user pasted from Excel or the contents of a CSV the browser read. At most **256 KiB** of UTF-8 and **1,000 data rows** (the upload keeps 5 MB and 5,000); the other limits (50 columns) are the upload's.
- Delimiter: **tab** when the first non-empty line contains a tab, else **comma**. A leading BOM is dropped. It goes through the upload's CSV parser (one parser, an explicit delimiter and row limit), whatever `sourceName` or its extension says; `sourceName` only names the job.
- Header recognition and file-level refusals are the upload's (names-only model sheet, aliases, `missing_header`, `duplicate_header`, `invalid_headers`, `empty`, `too_many_columns`, `unreadable`, `too_many_rows`, `file_too_large`; invalid UTF-8 cannot occur in a string).
- Stored like a CSV upload: `file_type 'csv'`; `file_name` = `sourceName` with control characters and `/ \` turned into `_` (≤ 255), else `붙여넣기.tsv` (tab) or `붙여넣기.csv`; `file_size` = UTF-8 byte length; `file_sha256` = sha256 of the UTF-8 text. Staging only: the catalog is untouched.
- Answer `ok` `{jobId, rowCount, status: 'mapped'|'uploaded'}` (`mapped` when the headers were recognized).
- **Refusal** = `invalid`, no job created, field errors in the existing `{path, code}` shape: `{path:['text'], code:<refusal code>}`, plus one `{path:['text','headers',<header text>], code}` per header the refusal names (the missing expected names for `missing_header`, the colliding header texts for `duplicate_header`). Input shape errors: `{path:['text'], code:'required'}` (not a string), `{path:['sourceName'], code:'invalid'}`.
- One process parses at most **2** pastes/uploads at a time (slots shared with the upload route). With none free the answer is `invalid` `{path:['text'], code:'busy'}`; it is not recorded, so the client retries with the same key shortly.

**Apply** `logKnowledge.importApply` `{jobId, expectedPlanVersion}` (positive integer) runs the same `runApply` as the route. The answer is always `ok` (the engine returns only `ok` data from a handler) with a discriminant:
- `{outcome:'progress', jobId, status, planVersion, remaining, counts}` — as the route's progress;
- `{outcome:'not_found'}` — unknown job or another workspace's;
- `{outcome:'conflict', reason:'plan_version'|'state'}` — as the route's 409;
- `{outcome:'busy'}` — no apply slot free (two runs per process, shared with the route; the route answers 503 `busy` with `Retry-After`), or the runner pool gave no connection within its acquire timeout. Nothing waits on the command pool while the outer transaction is open.

*How `runApply` runs inside the handler.* The engine's transaction holds a command-pool connection, the `(actor, key)` advisory xact lock and the idempotency record, and nothing of the job (no `currentVersion`). `runApply` runs on a **separate runner pool** (`createApplyRunnerPool`, `max` = the two apply slots, built in `server.ts` like the self-approval pool, inheriting the command pool's runtime time budgets): command connections can all be held by one action and its same-key followers parked on its lock, and a runner waiting on the command pool would then wait on connections only the lock holder can free (or, with `DB_POOL_MAX=1`, on its own). One pinned runner connection holds the session advisory lock (workspace + job) and runs the seal, every per-row transaction and the contention progress read. Its acquire timeout is a third of the apply budget (500 ms–5 s) and its statement timeout is the budget (at least 1 s). It never reads or writes the idempotency table or locks the job row from the outer transaction, so it cannot wait on either. The apply route holds no outer connection, so it keeps the command pool (single-connection regression in `import-apply.integration.test.ts`). The time budget bounds the call (`IMPORT_APPLY_BUDGET_MS`, 15 s).

*Protocol.* Each progress step is a fresh action call with a fresh idempotency key; the client stops at `completed` or `partial_failure`, and a later deliberate call retries the `failed` rows. A retry of an unknown or error result resends its key; a **replay returns the earlier recorded answer** (an earlier progress, or an earlier `busy`), starts no apply and creates nothing, so the client moves on with a fresh key for the next step, and also for a retry after `busy`. Rows commit outside the action record: if the record does not commit (a crash after the rows), the same key re-runs the apply, and the seal plus per-row idempotency (node b, b2) create no catalog, parent, identity or audit row twice.
