# 지식 검색은 접근 권한을 조회 때 현재 규칙으로 판정하고, 표시 값은 최신 Revision에서 그때 읽는다

상태: **Decided (2026-11-08, 소유자 답 반영 — 추천대로).** 결정자: 소유자(2026-11-08). 초안: 설계 레인, 근거 [#1199](https://github.com/hjung3113/analytics-platform/issues/1199), 설계 [`log-knowledge-search`](../design/features/log-knowledge-search/README.md) §3.2·§4.

## 배경

통합 검색은 권한 없는 Item을 결과·미리보기·자동완성·건수 어디에도 내보내면 안 되고, 권한 회수는 즉시 반영돼야 한다(#1199 수용 기준). 검색 색인은 outbox로 비동기 갱신되므로 색인에 권한이나 본문을 복사해 두면 갱신 전까지 옛 값이 나간다.

## 결정

1. **색인은 접근 권한을 담지 않는다.** 가시성 판정(Model → SW → Item 거절 우선 상속, 규칙, 팀·역할 현재 projection)은 **요청마다 같은 SQL 안에서 현재 규칙 테이블로** 한다. 후보 생성 뒤 따로 거르는 경로, 판정 없는 자동완성·건수 경로를 만들지 않는다.
2. **화면에 나가는 값은 통과한 행에서 그 순간 읽는다**: 제목·발췌는 최신 Revision에서, 발행·확인·처리 상태는 Item 행의 현재 값에서. 색인은 후보를 찾는 데만 쓰고 발췌를 저장하지 않는다. 색인이 늦으면 순위가 낡을 뿐 옛 본문이 나가지 않는다.
3. **정확한 총 건수를 주지 않는다.** `hasMore`와 상한 표시(같은 판정을 거쳐 센 값)만 쓴다. 가려진 건수는 말하지 않는다.
4. 판정 비용이 목표(p95 300ms 가설)를 못 맞추면 색인 열을 **후보를 좁히는 힌트**로만 쓸 수 있고, 최종 판정은 항상 live다. 그 변경은 이 ADR을 개정한다.

## 대안과 버리는 이유

- **색인에 `restricted`·허용 주체를 복사하고 색인 쪽에서 거르기:** 빠르지만 규칙 변경과 색인 갱신 사이 구간에 회수된 Item이 나간다. «즉시 반영·fail-closed» 수용 기준과 맞지 않는다. 기각(4의 힌트 용도만 허용).
- **ACL 구간(사용자 집합)별 색인 분할:** 팀·규칙 조합이 늘면 색인 수가 폭증하고 규칙 변경마다 재색인이 필요하다. 기각.
- **후보를 넉넉히 뽑은 뒤 응용 코드에서 거르기:** 페이지·건수·정렬이 거르는 양에 따라 흔들리고 한 경로라도 빠지면 유출된다. 기각.

## 결과

- 검색 SQL이 규칙 테이블을 매번 조인한다. 비용은 설계 §6의 부하·`EXPLAIN` 보고로 잰다.
- 색인 어댑터(`SearchPort`)는 권한을 몰라도 되므로 어댑터를 바꿔도 권한 경계가 같다.
- 시험: 권한 회수 직후 같은 질의·자동완성·건수·관련 Item 링크에서 사라짐, 상위 제한 + 하위 허용 우회 실패, 색인 지연 중 옛 본문 미노출, 서비스 Actor 검색 범위.

## 남은 위험 (소유자 수용, 2026-11-09, #1504)

- **중복 코드 응답:** Model/SW 생성·변경에서 이미 있는 코드와 충돌하면 `duplicate`/`taken`이 나가 숨은 객체의 코드 존재를 알 수 있다. 코드 유일성을 지키려면 충돌 사실을 알려야 하므로 허용하고 기록한다. 다시 여는 조건: 코드를 접근 범위별 네임스페이스로 나누는 결정.
- **연속 Item 번호:** 번호(`KI-n`)가 workspace 연속이라 보이는 번호의 최댓값과 보이는 총건수로 숨은 Item 개수를 역산할 수 있다. 번호를 유지하고 남은 위험으로 둔다. 다시 여는 조건: 비연속 표시 번호 도입(ADR-0109 `KI-n` 사용처 동반 변경).
- **숨은 SW 버전에서 시작한 변경의 유효값(#1880):** 보이는 SW 버전의 유효 명세(`modelSpec` + `softwareId`)는 숨은 버전에서 시작해 그 버전까지 이어지는 변경도 모두 적용한다. 응답에서 그 변경의 `changeId`·`changed` 표시·`stale`·`removed` 항목은 빼지만, 적용된 값(바뀐 이름·규칙·필드, 추가·삭제된 항목, `origin: 'change'`, `effective: true`)은 남아 그런 변경이 있다는 사실은 추론할 수 있다. 유효값과 핀(`changeSetDigest`)이 보는 사람에 따라 달라지면 같은 버전의 명세와 검증 고정점이 사람마다 갈리므로 허용하고 기록한다. 다시 여는 조건: 유효 명세를 보는 사람별로 계산하고 핀을 사람별로 나누는 결정.
