# ADR-0126 — 상세 패널 크게 보기: 같은 패널을 본문 영역으로 펼친다

- 상태: Decided (2026-11-07, 소유자 A안 컨펌, #1459)
- 보완: [ADR-0013](0013-detail-panel-shell-docked-slot.md)
- 계약: [공통 컴포넌트 §13](../contract/components.md#detaildrawer--docked-shell-slot-decided-adr-0013), [Kernel §6.4](../contract/kernel.md)

## 배경

오른쪽 상세 슬롯은 목록과 함께 읽기에는 맞지만 긴 입력·편집에는 좁다. 소유자는 모든 상세 서랍과 VOC 작성에 같은 크게 보기를 요청했고 [실제 앱 A안](https://claude.ai/artifact/VXAQYfQFJevzeyeLWk6GSQ)을 컨펌했다. 입력·리치 에디터·스크롤을 유지하면서 사이드바와 페이지 머리는 계속 사용할 수 있어야 한다.

## 결정과 이유

- **같은 패널을 본문 영역으로 펼친다.** 기본 도킹 배치는 유지한다. 펼친 패널은 실제 페이지 머리 아래 본문 영역을 덮고 읽기 폭은 48rem, 하단 저장·전송 영역은 고정한다. 뷰포트 전체 모달은 사이드바·머리를 막고, 별도 상세 페이지 이동은 작성 상태 보존을 어렵게 하므로 택하지 않았다. 기존 `전체 화면` 목적지 이동과 «상세 패널 크게 보기»는 다른 기능이다.
- **한 제공자가 상태를 소유한다.** `@ap/ui`의 기존 `DetailPanelSlotProvider`를 controlled로도 사용하며 셸이 Kernel 주소 상태를 연결한다. portal·내용 등록과 VOC가 같은 컨트롤·읽기 폭·Escape 규칙을 쓴다. 열려 있는 새 등록자는 크게 보기를 이어받는다. 기존의 등록자 키 변경마다 초기화하는 규칙은 이 결정으로 대체한다. 닫힘·비움·일시 정지는 끝낸다.
- **URL은 표현 상태만 기억한다.** 플랫폼 예약 키 `expand=1`은 메뉴 page key와 구분한다. 새로고침 뒤 늦게 등록되는 상세도 복원하므로 비어 있는 초기 슬롯은 키를 지우지 않는다. 조회 초안·저장된 뷰·공유·메뉴 간 전달에는 들어가지 않는다. 보드와 보드 칸 소유 상세는 메모리만 쓴다. 세부 경계는 Kernel 계약이 소유한다.
- **내용을 다시 마운트하지 않는다.** 같은 DOM 서브트리의 배치만 바꿔 입력·편집기·스크롤을 지킨다. 크게 보기 버튼은 같은 노드에 남고, Escape로 줄이면 그 버튼으로 포커스를 돌린다. 주소 복원 자체는 포커스를 옮기지 않는다.
- **Escape는 열린 팝업, 크게 보기 해제, 기존 닫기 순서다.** 닫기 버튼은 바로 기존 닫기 경로를 부른다. 미저장 가드([ADR-0115](0115-kernel-navigation-guard-for-unsaved-edits.md))의 의미는 바꾸지 않는다. 크게 보기의 주소 쓰기는 `replace`다. 덮인 본문만 `PlatformPage`가 `inert`로 만들고 머리·레일·사이드바에는 포커스 trap을 두지 않는다.

## 결과

메뉴별 옵션·구현은 필요 없다. SDK 토글의 접근 이름은 호스트 번역으로 전달하고 기존 기능 화면의 무인자 호출은 호환한다. 단위 테스트는 상태·노드 보존·URL 경계·가드를 검증하며 실제 앱 1440×900 캡처와 접근성·배치 검토는 별도 출하 게이트다.


## 개정 — 폭별 배치

Decided (2026-11-08, #1530). 소유자는 [실제 앱 제안 A](https://claude.ai/artifact/GDW6BGBLWgLQkH2LL7TtcP)를 컨펌했다. 메뉴가 탭별 `regions`의 본문·속성·대화를 선언하고 SDK `DetailDrawer`가 배치한다. 선언하지 않은 내용과 footer의 48rem 읽기 폭·DOM·포커스 동작은 유지한다. 새 선언의 정확한 API·폭·스크롤·접근성 계약은 [공통 컴포넌트 §13](../contract/components.md#detaildrawer--docked-shell-slot-decided-adr-0013)이 소유한다.

- 좁으면 본문 → 속성 → 대화를 하나의 스크롤에서 읽는다. 패널 자체가 960px 이상이면 본문·대화는 왼쪽, 18rem 속성은 오른쪽에 놓는다. 선언한 본문은 가운데 읽기 폭으로 제한하지 않고 제목의 왼쪽 선에 맞춘다. 뷰포트 폭이나 펼침 여부로 열 수를 추정하지 않는다.
- DOM 순서는 모든 폭에서 본문 → 속성 → 대화다. Grid가 넓은 배치의 속성을 오른쪽 두 행에 걸쳐 놓고, 속성은 sticky인 독립 스크롤 영역이 된다. 본문·대화의 바깥 스크롤과 속성의 안쪽 스크롤을 함께 쓰므로 재부모화·복제·ResizeObserver가 필요 없다. 넓을 때 Tab은 왼쪽 본문 → 오른쪽 속성 → 왼쪽 대화로 움직인다. 양쪽 스크롤 영역은 번역된 접근 이름·`role="region"`·`tabIndex={0}`·inset focus-visible ring으로 식별한다. DOM 순서와 보조기술의 읽기 순서를 지키기 위해 열별 DOM 그룹으로 바꾸지 않는다.
- `body`는 필수다. `properties`가 없으면 오른쪽 열을 예약하지 않고 전체 폭 한 열을 쓴다. 로딩·실패·권한 제한도 각 영역의 내용이며, 전체 상태는 본문만 선언할 수 있다. 접기·추가 breakpoint·열 크기 조절은 두지 않는다.
- 첫 소비자는 VOC 처리함 상세다. 작성기는 대화 아래, 후속 조치·연결·유사 VOC는 본문 뒤, 다음 동작 footer와 확인 대화상자는 스크롤 바깥에 유지한다. 상세를 나누어도 같은 컨트롤러와 미전송 초안 가드를 쓴다.
- 대안 B(핵심 속성을 먼저 보이고 「속성 더 보기」로 나머지를 여는 방식)는 채택하지 않았다. 소유자는 속성을 숨기거나 메뉴마다 핵심 속성을 선별하는 정책보다 모든 선언을 같은 폭별 배치로 읽는 A를 골랐다.
