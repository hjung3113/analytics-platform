# 메뉴 활용률 이벤트는 식별 필드만 수집하고, 조회조건 값은 넣지 않는다

상태: **Decided (2026-10-05)**.
- 결정자: 사용자 — 에이전트 추천(#75의 (a))을 따랐다("나머지도 니추천대로 진행"). 2026-09-22 grilling의 "수집 필드에 조회조건·필터값까지 포함"을 대체한다.

정책의 원본은 [05 메뉴 활용률 계측](../overview/roadmap-and-open-questions.md#메뉴-활용률-계측-decided--v1-범위-포함-2026-09-22-grilling-round-2), 포트는 `adapter.recordUsage`(entry/dwell)·`usageSummary`(`packages/contracts/src/adapter/adapter.ts`)다. 이 ADR은 결정과 이유만 둔다.

활용률 계측은 Kernel 관측 범위로 v1에 들어갔고(#43), 보존 기간은 무제한이다. URL과 전역 Context에는 Lot id, PPID, 자유 텍스트 검색어 `q` 같은 값이 들어 있다. 조회조건 값을 이벤트에 넣으면 서버가 이 값을 영구히 쌓는다. 활용률의 목적(어느 메뉴가 얼마나, 어떻게 쓰이는지)은 식별 필드로 채워진다.

## 결정

- 활용률 이벤트는 식별 필드만 보낸다: `menuId`, `spaceId`, 경로 패턴, 시각, 탭 `sessionId`, `dwellMs`. #43 구현이 이미 이 범위다.
- 조회조건·필터 **값**은 넣지 않는다.
- 필터 사용 신호가 필요해지면 page 키 **이름**만(값 제외) 더하는 추가형 확장으로 한다.

## Considered Options

- **(a, 채택) v1은 조회조건 제외**: 보존 무제한 정책과 충돌하지 않고, 지금 구현과 같다. 필터 사용 분석은 키 이름 확장으로 나중에 더할 수 있다.
- **(b) 조회조건 값 포함**: 메뉴별 필터 사용 패턴을 바로 볼 수 있지만, 어떤 키·값까지 넣을지와 값의 보존·마스킹 정책을 함께 정해야 한다. 보존 무제한 아래에서는 Lot id·자유 텍스트가 영구 저장된다.

## 결과

- 05 "메뉴 활용률 계측"의 수집 필드 문구를 이 결정으로 좁힌다. #75는 닫는다.
- 보충(#605): 화면 이동 경로 `via`(닫힌 집합)·`fromMenuId`(메뉴 id 또는 null; 메뉴 id 모양은 Registry의 id 규칙(`createRegistry`가 받는 비어 있지 않고 공백·`? # & /`가 없는 문자열)에 `=`·제어 문자 금지와 80 code point 상한을 더한 `/^[^\s?#&/=\p{C}]{1,80}$/u`이며 경로·URL·`key=value`·제어 문자·빈 문자열은 거부한다. 트레이드오프: `=`를 포함한 Registry id는 `fromMenuId`로 쓸 수 없다)는 `entry`에만 붙는 식별·출처 필드다. 보드 칸 `entry`는 `via`로 `paneOpen`(칸의 첫 화면)·`paneReplace`(같은 칸의 다음 화면)와 `fromMenuId`(같은 칸이 바로 앞에 보인 메뉴 id, 열릴 때는 null)를 싣는다 — 여전히 식별 필드뿐이다. 조회 조건·page 값·경로는 여전히 보내지 않으므로 이 결정은 그대로다.
- 키 이름 확장이 필요해지면 새 이슈로 다루고, 이벤트 스키마에 필드를 더하는 추가형 변경으로 한다.
