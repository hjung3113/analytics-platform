# 플랫폼 API 토큰: 개인·서비스 토큰으로 기존 업무 API를 호출한다

상태: **Decided (2026-11-07, v0.30.0 구현 착수 — 소유자 답 반영, 서비스 토큰 발급 주체는 관리자만).** 결정자: 소유자(2026-11-07). 초안: 설계 레인, 근거 [#1419](https://github.com/hjung3113/analytics-platform/issues/1419). 결정마다 소유자 답을 «소유자 2026-11-07»로 표시한다.

## 배경

사내 스크립트·검증 도구·AI가 로그 지식 조회와 검증 결과 저장 같은 기존 업무 API를 부르려 한다. 지금 `apps/platform-api`에는 사람 로그인 세션 외 호출 수단이 없다(`actor_type=system`인 Actor는 대화형 세션을 받지 못한다). 첫 소비자는 검증 요청 큐 작업자([ADR-0117](0117-validation-request-queue-claim-lease-heartbeat.md))다. 사내 계약이 바뀔 수 있어 틀을 `v0`로 먼저 둔다.

## 결정

1. **호출자 종류를 구분하지 않는다**(소유자 2026-11-07, #1419 방향 확정). 사람 스크립트인지 AI인지 보지 않고 토큰에 붙은 권한만 본다. AI 전용 경로를 만들지 않고 기존 업무 API를 토큰으로도 부를 수 있게 연다.
2. **두 종류.** 개인 토큰은 발급자의 Actor로 동작하고 유효 권한 = **발급자의 현재 권한 ∩ 고른 scope**다. 발급자 권한이 줄거나 비활성화되면 다음 호출부터 반영된다(발급 시점 권한을 복사하지 않는다). 서비스 토큰은 관리자가 발급하고 `actor_type=system` Actor에 귀속하며, 권한은 그 Actor에 부여된 것 ∩ scope다.
3. **저장·표시.** 발급 응답에서 한 번만 값을 보여 주고 서버는 해시만 저장한다(고엔트로피 난수 + SHA-256; 비밀번호용 느린 해시는 쓰지 않는다 — 조회 키로 쓰이는 긴 난수라서). 접두사(식별용 앞 8자)·마지막 사용 시각·폐기·감사를 둔다.
3a. **만료는 발급자가 고른다. 무기한도 허용한다**(소유자 2026-11-07; 추천 «만료 필수»와 다름). `expires_at`은 비어 있을 수 있다. 무기한이 위험을 키우므로 보완책을 계약으로 둔다: (ⅰ) 목록에 마지막 사용 시각·마지막 사용 주소 요약을 항상 보인다; (ⅱ) **미사용 경고** — 마지막 사용(없으면 발급)에서 30일(설정값) 지나면 목록에 경고를 보이고 발급자·관리자에게 알림; 자동 비활성화는 하지 않는다(소유자 답에 없음, 필요하면 다시 연다); (ⅲ) 즉시 폐기 — 발급자와 관리자가 한 번의 동작으로 폐기하고 다음 호출부터 거절; (ⅳ) 관리자 목록에서 «무기한 토큰» 필터; (ⅴ) 개인 토큰은 발급자 권한과의 교집합이라 발급자가 비활성화되면 만료와 무관하게 죽는다. 서비스 토큰 발급은 관리자만(팀장 가정, 소유자 확인은 다음 세션).
4. **고위험 동작은 토큰으로 못 한다**(소유자 2026-11-07). 발행·승인·Gate 결정·권한 부여·토큰 발급/폐기는 사람 로그인 세션 전용이다. 서버가 capability의 `sensitive`/세션 전용 표시로 거절한다(`permission.session_required`). 이렇게 하면 #1198 «승인은 사람»이 호출자 종류와 무관하게 지켜진다.
5. **인증 원천은 플랫폼 발급 토큰이다**(소유자 2026-11-07). 사내 SSO(#150)와 독립이고, SSO 기계 계정으로 바꾸게 될 때 같은 Actor·scope 모델 위에 인증 방식만 갈아 끼운다.
6. **scope는 기존 capability 단위 + 굵은 묶음 별칭이다.** 토큰은 capability 이름 목록을 가진다. 화면은 «조회»·«기록»·«검증 작업자» 같은 묶음을 보여 주되 서버에는 capability로 풀어 저장한다. 묶음은 UI 편의라 계약을 늘리지 않는다.
7. **잠정 `v0`.** 토큰 헤더 형식(`Authorization: Bearer ap_<prefix>_<secret>`)과 오류 코드는 `@ap/contract-schemas`에 `v0`로 낸다. 형식은 호환 없이 바뀔 수 있다고 문서에 적는다.
8. **비율·남용.** 토큰별 속도 제한을 둔다. 실패 인증은 기존 IP 버킷에 합산한다.

## 대안과 버리는 이유

- **SSO 기계 계정만:** 발급·폐기 주기가 SSO 운영 몫이라 팀 단위로 빨리 열 수 없고 #150에 묶인다. 같은 모델 위에 나중에 추가 가능해 지금은 버린다.
- **AI 전용 경로·AI 전용 권한:** 호출자를 구분하는 순간 «AI만 막는» 규칙이 새고 업무 API가 둘이 된다. 토큰 권한만 보는 쪽이 하나다.
- **고위험 동작 허용(범위 제한):** 토큰 유출이 곧 승인 유출이다. 사람 세션 전용이 감사에서도 단순하다. 비용: 자동화가 승인까지 못 간다 — 의도된 것.
- **발급 시점 권한 복사:** 발급자 권한이 줄어도 토큰이 살아 있다. 교집합을 매 호출 계산하는 비용이 작아 선택하지 않는다.
- **만료 필수(추천이었음):** 소유자가 발급자 선택·무기한 허용을 골랐다(2026-11-07). 만료 없는 토큰의 유출 위험은 결정 3a의 보완책으로 줄인다.
- **JWT(자체 서명):** 폐기·권한 축소의 즉시 반영이 어렵다. 서버 조회형 불투명 토큰으로 간다.

- 소유 문서: `docs/architecture/platform-api/api/auth.md`(토큰 호출 인증 순서), `05-permission-policy.md`(세션 전용 capability, 교집합 규칙, 감사 동사), `04-database-and-migrations.md`(`core.api_tokens`: `id, workspace_id, actor_id, kind, name, prefix, secret_hash, scopes, expires_at, last_used_at, revoked_at, created_by`). 구현 노드는 [log-lifecycle §7](../design/features/log-lifecycle/README.md) a·b.
- 토큰 관리 화면(개인 목록·발급·폐기, 관리자 서비스 토큰)은 새 화면이라 시안 컨펌 대상이다.
- 감사: 발급·폐기·거절된 고위험 시도·인증 실패를 기록하고, 토큰 호출의 쓰기에는 토큰 ID를 세부에 둔다.
- 소유 문서의 `core.api_tokens.expires_at`은 nullable이다.
- 구현: 노드 a [#1442](https://github.com/hjung3113/analytics-platform/issues/1442)(PR #1456). 미사용 토큰 알림(3a ⅱ)과 발급자 비활성화 반영(3a ⅴ, `core.actors`에 활성 칼럼 없음)은 구현 안 함 — [backlog](../../.planning/backlog.md)에 다시 여는 조건과 함께 있다.
- 열린 것: 서비스 토큰 발급 주체 확인(관리자만으로 가정), 미사용 경고 일수(30일 시작값), 사내 보안 검토에서 무기한 허용이 막힐 경우.
