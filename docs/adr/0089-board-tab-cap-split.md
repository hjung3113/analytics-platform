# 보드 시트의 칸(탭) 수 상한과 표시 그룹 수 상한을 나눈다

- Status: Decided (2026-10-27)
- Decider: 코디네이터(이슈 #893 설계 보강 §6과 plan review P11), 되돌릴 수 있다.
- Scope: [#893](https://github.com/hjung3113/analytics-platform/issues/893) 노드 893e. 관련: [ADR-0067](0067-dockview-layout-engine-board-v2.md)(저장 모델 V2·dock 렌더러). 계약 본문은 [docs/16](../design/analysis-board.md) §4·§7.

## 맥락

시트의 칸 수 `MAX_PANES = 4`는 두 가지를 한꺼번에 막았다. 칸(탭)의 합계와 화면에 나뉘어 보이는 영역(그룹) 수다. 묶음 `+`(893a)로 한 그룹에 탭을 더할 수 있게 되자, 4개 영역을 유지한 채 한 영역에 5번째 탭을 두고 싶은 요구가 이 두 한도를 나눠야 풀린다.

## 결정

- 상수를 둘로 나눈다. `MAX_TABS = 8`(시트당 칸 합계), `MAX_GROUPS = 4`(표시 그룹 수). `MAX_PANES = 4`는 "`v:2` 호환 상한"으로 이름과 역할을 남긴다.
- 그룹 수는 트리에서 계산한다(`groupsOf(tree).length`). 새 그룹을 만드는 모든 경로를 막는다: `칸 추가`는 그룹이 4개이면 선택된 칸의 그룹에 탭으로 더하고(`addPaneInGroup`), 나누기 메뉴는 꺼지며 이유를 보이고, 끌기 등으로 5번째 그룹이 되는 트리는 `setTree`가 거절하고, 저장 검증(`parseBoard`)도 그룹 5개 이상을 거절한다. `칸 닫기` 되돌리기가 칸을 옆에 붙일 때도 그룹이 4개이면 탭으로 넣는다.
- 저장은 같은 키(`platform:board:v2:${userId}`)에 값의 `v`만 올린다. 어느 시트라도 칸이 4개를 넘으면 `v:3`, 아니면 `v:2`. 읽기 검증은 `v:2`는 시트당 ≤4, `v:3`은 ≤8, 둘 다 그룹 ≤4이고 위반은 손상(`corrupt-backup`)이다. `isNewer`는 `v > 3`이다.
- 5칸 이상 시트가 있는 보드는 브라우저 설정이 `grid`여도 dock으로 열고 한 번 알린다. `기본 배치`는 5칸 이상이면 4개 그룹의 2×2 뒤에 나머지를 마지막 그룹의 탭으로 둔다. `normalizeSheet`는 더 이상 칸을 자르지 않는다. 격자 레이아웃 전환 모델 연산(`setLayout`)은 5칸 이상 시트를 바꾸지 않는다(격자는 5칸 이상에서 쓰이지 않는다).

## 대안

- **상한만 올리기(`MAX_PANES`를 8로, 그룹 상한 없음)**: 2×2 전제인 격자·기본 배치·좁은 폭 쌓기·읽기 순서가 5개 이상 영역에서 검증되지 않는다. 기각.
- **`v:2` 유지(값의 `v`를 올리지 않음)**: 이전 빌드가 5칸 값을 "손상"으로 격리하고 새 보드로 덮어 쓰는 경로가 열린다. 보호가 약해진다. 기각.
- **분리 저장(5칸 이상 보드를 다른 키에)**: 키 둘의 일관성·백업·이행 규칙이 늘고 사용자가 보드 둘을 갖게 된다. 기각.
- **grid 렌더러를 5칸 이상으로 확장**: 격자 모양 전체(열·행 비율·`gridMemory`)를 다시 설계해야 한다. 이번 범위 밖이며 `.planning/backlog.md`에 둔다.

## 8의 근거와 측정

8은 이 노드의 첫 값이다(되돌릴 수 있다). 근거는 조회 비용이다. dock이 모든 탭을 마운트해 두므로(`renderer: 'always'`) 동시 조회의 최대는 마운트된 칸 수이고, 이는 시트당 최대 8이다(전에는 2×2의 4). 측정 방법: `BoardDock.test.tsx`의 E7이 서로 다른 조건의 조회 칸 4개와 조회 없는 칸 3개 시트(7칸)를 마운트해 어댑터 `menuQuery` 호출 수를 센다. 값: 마운트 때 4회(조회 칸마다 첫 조회 1회), `칸 추가`로 8번째 칸을 더한 뒤에도 4회(추가 탭이 다른 칸의 재조회를 만들지 않는다). 20·50·무제한은 약속하지 않는다. 더 올리려면 실제 서버 부하를 측정한 새 결정이 필요하다.

## 이전 빌드와의 호환, 롤백

이 변경 이전 빌드의 `isNewer`는 `v > 2`였다(`boardStore.ts`). 그 빌드는 `v:3` 값을 읽으면 손상으로 격리하지 않고 `storageNotice: 'newer'`·읽기 전용으로 새 보드를 열며 그 키를 쓰지 않는다(`loadBoard`/`saveBoard`의 기존 동작). 그래서 5칸 이상 보드가 이전 빌드에서 지워지거나 덮이지 않는다. 롤백은 둘이다: (1) 사용자가 칸을 4개 이하로 줄이면 다음 저장부터 `v:2`로 내려가 이전 빌드가 다시 읽는다. (2) 이 빌드 자체를 되돌리면 `v:3` 값은 이전 빌드에서 읽기 전용이라 데이터는 남는다. 이전 빌드의 실제 실행은 수동 확인이 불가해 `boardCap.test.ts`가 `v>3`는 `newer`, `v:2`에 5칸은 `corrupt`로 두는 경계를 고정하는 것으로 대신한다.

## 되돌리기

`MAX_TABS`를 4로 되돌리면 이전 동작이다(저장된 `v:3` 값은 읽기 검증이 거절해 손상 격리된다 — 되돌리기 전에 칸을 줄이게 안내해야 한다).
