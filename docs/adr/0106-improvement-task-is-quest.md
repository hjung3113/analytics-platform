# 과제(Quest)는 개선 실행 시스템의 객체다: 개선 아이템·효과 확인·이름

상태: **Decided (2026-11-02)**, 결정 2와 결정 5의 마지막 문장은 아래 「개정」(2026-11-04, 소유자, #1303)이, 결정 1과 결정 3은 「개정 2」(2026-11-04, 소유자, #1323)가 바꿨다. Quest는 BRAVO가 발행한 이상 현상이고, 개선 아이템은 플랫폼 DB에 두며, 개선 실행 업무 시스템은 접었다.
- 결정자: 사용자 — 2026-11-02, [#1241](https://github.com/hjung3113/analytics-platform/issues/1241). 소유자가 Claude Design에서 만든 소개 발표 v2(`site/presentation/intro.html`)에 새로 나온 개념을 코디네이터가 하나씩 물었고, 다섯 질문 모두 추천안 또는 사용자 수정안으로 정했다.

## 배경

발표 v2는 「BRAVO가 발행한 Quest 하나를 따라가 MARS에서 구간을 좁히고 CLAS에서 원인을 추론한 뒤, Quest 아래 개선 아이템을 남기고 조치 전후를 비교해 닫는다」는 흐름을 보인다. 레포에는 Quest가 없었고, 비슷한 객체로 Finding(VOC·설문 근거), Task(Managed System 내부 실행 작업), 개선 실행 시스템의 `과제·실적`([ADR-0065](0065-log-dev-and-improvement-spaces-work-queue-first.md))이 있었다.

## 결정

1. **Quest = 개선 실행의 `과제`.** **개정 2(2026-11-04): 아래 「개정 2」 절이 대체한다.** 새 객체를 만들지 않는다. Finding·Task와는 다른 객체다. 이유: 개선 실행 시스템의 첫 화면이 이미 「내 과제」이고, Finding·Task는 데이터로 찾은 현상과 성격이 다르다.
2. **소유는 개선 실행 시스템.** **개정(2026-11-04): 아래 「개정」 절이 대체한다.** BRAVO·MARS·CLAS는 과제를 만드는 출처이며, 과제에는 출처(시스템·지표·기간·공정·설비)가 자동으로 붙는다. 이유: 업무 시스템은 다른 시스템의 객체를 흡수하지 않는다(GLOSSARY 「업무 시스템」).
3. **개선 아이템은 과제 아래의 일반 업무 객체다.** **개정 2(2026-11-04): 저장 위치는 아래 「개정 2」 절이 대체한다.** 추론한 문제·조치·조치일·상태를 담고, 저장·이력은 개선 실행 서버가 갖는다. 「엑셀처럼 편집」(여러 칸 선택·붙여넣기·채우기)은 [#540](https://github.com/hjung3113/analytics-platform/issues/540)에서 만들 범용 편집형 표 SDK 조각을 쓴다. 이유: 개선 아이템을 #540의 자산·발행(버전 발행·권한별 발행) 모델에 묶지 않고, 편집형 표는 다른 메뉴도 쓰는 범용 조각이 된다.
4. **효과 확인은 SDK 범용 「기준일 전후 비교」 조각이다.** 기준 시각과 앞뒤 구간 길이를 받아 분석 Context의 전·후 두 기간을 만들고 차트 계약 Compare 상호작용에 얹는다. 과제 화면은 조치일만 넘긴다. 이유: 도메인을 모르는 범용 조각은 소비자 수와 관계없이 SDK에 둔다([ADR-0052](0052-rich-content-stays-in-the-sdk.md)). 구현은 [#1243](https://github.com/hjung3113/analytics-platform/issues/1243), 계약은 [chart.md §16](../contract/chart.md) `beforeAfterPeriods`.
5. **이름은 둘 다 쓴다.** 화면·문서 표기는 `과제(Quest)`이고, 짧게는 `과제` 또는 `Quest` 어느 쪽도 같은 객체를 뜻한다. 발표 자료는 고치지 않는다(사용자) — 발표의 「BRAVO가 발행」은 결정 2에 따라 「BRAVO 지표에서 시작」으로 읽는다.

## 다른 안

- Quest를 새 객체로 둔다 — 과제와의 차이를 정의할 근거가 없어 버렸다.
- Quest를 BRAVO가 소유하고 개선 실행은 읽기만 한다 — MARS·CLAS에서 찾은 현상이 다른 길을 타고, 시스템 경계 원칙과 어긋나 버렸다.
- 개선 아이템 목록을 #540의 관리형 데이터 테이블 하나로 둔다 — 이력·버전은 공짜지만 과제–아이템 관계·상태 흐름을 자산 허브가 표현해야 해서 버렸다.
- 효과 확인을 과제 화면 전용으로 만든다 — 다른 메뉴가 쓰려면 다시 SDK로 옮겨야 해서 버렸다.
- 이름을 하나(`과제` 또는 `Quest`)로 통일한다 — 사용자가 둘 다 쓰기로 했다.

## 개정 (2026-11-04, #1303): Quest는 BRAVO가 발행한 이상 현상이다

- 결정자: 소유자 — 2026-11-04, [#1303](https://github.com/hjung3113/analytics-platform/issues/1303) §2-2 항목 5(소유자가 확인한 사실: Quest는 BRAVO가 만드는 현상). 팀장이 [#1320](https://github.com/hjung3113/analytics-platform/issues/1320)에서 다시 물어 확정했다.
- 결정 2를 바꾼다. Quest는 BRAVO가 발행한 이상 현상이다. BRAVO는 출처가 아니라 발행하는 쪽이고, MARS·CLAS는 그 원인을 분석하는 화면이다. 이유: 소유자가 확인한 업무 사실이고, 발표 자료(`site/presentation/intro.html` v0.26.1)도 같은 정의를 쓴다.
- 결정 5의 마지막 문장(발표의 「BRAVO가 발행」을 「BRAVO 지표에서 시작」으로 읽는다)을 지운다. 이름 병용(`과제(Quest)`)은 그대로다.
- 그대로인 것: 개선 아이템은 Quest 아래 기록하는 문제·조치이고 예정이다. 편집형 표 조각(#540)과 효과 확인 조각(#1243)도 그대로다.
- 열린 것(「개정 2」에서 닫음): Quest가 개선 실행 시스템의 `과제`와 같은 객체인지(결정 1), 개선 아이템을 어디에 저장하는지(결정 3).

## 개정 2 (2026-11-04, #1323): 개선 아이템은 플랫폼 DB, 개선 실행 공간은 접는다

- 결정자: 소유자 — 2026-11-04, [#1323](https://github.com/hjung3113/analytics-platform/issues/1323). 팀장 추천안을 받아들였다(「니 추천대로」, 「어차피 임의로 만들어 둔 거고 실제 구현된 건 없다」).
- 결정 1을 바꾼다. Quest는 개선 실행 시스템의 `과제`가 아니다. 개선 실행 시스템은 화면·서버·데이터 없이 메뉴 자리만 등록된 공간이었고, 사내에 같은 시스템이 없다. 그 공간은 접는다([ADR-0065](0065-log-dev-and-improvement-spaces-work-queue-first.md) 개정).
- 결정 3의 저장 위치를 바꾼다. 개선 아이템은 플랫폼 DB에 두는 플랫폼 기능이다(VOC·공지와 같은 층, 발표 자료 v0.26.1과 같다). Quest는 BRAVO가 소유하고, 개선 아이템은 Quest를 ID로만 가리킨다(다른 시스템 객체를 흡수하지 않음). 이유: 개선 아이템은 MARS·CLAS 화면에서 만들어 BRAVO의 Quest에 붙는, 시스템을 가로지르는 기록이다. 그런 기록의 권한·감사·이력은 이미 플랫폼 DB가 맡는다. 서버를 새로 세우거나, 읽기 전용 어댑터로 붙는 BRAVO의 기존 DB에 쓰기 테이블을 더하는 것보다 일이 적다.
- 개선 실행 공간이 맡으려던 일: 효과 검증은 `효과 확인`(#1243), 설비별 적용 이력은 개선 아이템 이력이 맡는다. `내 과제` 같은 담당자 첫 화면은 Quest 화면을 설계할 때 정한다.
- 그대로인 것: 편집형 표 조각(#540), 기준일 전후 비교 조각(#1243), 이름 병용 `과제(Quest)`. 개선 아이템의 플랫폼 API·DB와 읽기·쓰기 a/b는 이후 구현됐다(#1353·#1355).
- 운영: 옛 버전을 돌린 DB에는 「개선 실행」 Managed System이 활성으로 남아 선택 목록에 보인다. 마이그레이션은 없고, 업그레이드 뒤 업무 흐름 설정 › 시스템에서 보관한다(사내 배포는 아직 없다; [업그레이드 절차](../architecture/platform-api/release/backup-restore-upgrade.md)).
- 다른 안: 개선 실행 서버를 따로 둔다 — 그 시스템이 없어 서버 하나를 새로 세우는 셈이라 버렸다. BRAVO 서버에 둔다 — Quest와 한곳이지만 기존 MSSQL에 쓰기 경로를 새로 내야 해서 버렸다.

## 개정 3 (2026-11-05, #1328): 직속 목록과 A안 상태 흐름

- 결정자: 소유자 — [#1328](https://github.com/hjung3113/analytics-platform/issues/1328), 2026-11-05. A안의 표 위 저장된 보기 탭·본문/상태+이력 분할·Context 우선 만들기 서랍을 채택하고 B안의 「효과 확인 대기」 힌트를 조치 완료 줄에 더한다.
- 담당자 첫 화면은 직속 `개선 아이템` 목록의 `내 담당` 보기다. 조치 완료도 효과 확인 전까지 남고 효과 확인됨·취소만 빠진다. 읽기는 로그인 전원, 쓰기는 capability `improvement.manage`; User 담당자의 본인 건 예외는 두지 않는다. 이유: 조치 완료와 효과 확인을 구분하면서 기존 플랫폼 권한 경계를 따른다.
- 다른 안의 전체 레이아웃은 채택하지 않고 효과 대기 힌트만 가져온다. 빈 결과의 필터/검색/만들기 유지, 분석 기간 양끝 KST, `과제(Quest)` 표기, 온전한 `담당` 머리글은 선택안의 필수 보완이다. 상세 규칙의 원본은 [개선 아이템 화면 계약](../design/features/improvement-items.md)이다.

## 결과

- GLOSSARY에 `과제(Quest)`·`개선 아이템`·`효과 확인`·`PI`(Process Innovation)를 올린다.
- 개선 아이템은 플랫폼 기능이고 DB·API와 읽기·쓰기 a/b는 구현됐다(#1353·#1355); Quest 화면은 BRAVO가 사내에서 만든다(루트 `AGENTS.md`). 소비자 화면·Quest 연결 등 후속 범위는 #1328과 보드를 따른다. 플랫폼 몫 조각 가운데 편집형 표(#540)는 미구현이고 기준일 전후 비교 조각(#1243)은 `beforeAfterPeriods`로 구현됐다(#1341).
- [ADR-0065](0065-log-dev-and-improvement-spaces-work-queue-first.md)를 보충한다(개선 실행의 `과제`가 발표의 Quest).
