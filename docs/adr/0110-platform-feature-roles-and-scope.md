# 플랫폼 기능은 역할로 세 자리에 나누고, VOC 공개 열람은 시스템 단위 부여를 따르며, 업무 시스템은 피드백 추적 대상을 스스로 등록한다

상태: **Decided (2026-11-03)**.
- 결정자: 소유자 — 2026-11-03. 소유자가 직접 정한 것: VOC 열람은 「전체 공개」가 아니라 플랫폼 부여 범위를 따른다, 이번 릴리스는 시스템 단위 부여(Site·room은 다음), 「플랫폼」 시스템 VOC는 로그인 전원 공개, 공간 이름 `업무 흐름`, 화면 용어 `시스템`·`Task`, 셀프 등록을 이번 릴리스에 하고 앱 빌드 산출물을 서버가 읽는다, 「플랫폼」 시스템을 늘 둔다, FAQ는 자리만, 06 계약 변경 승인. 배치 표의 세부(기능별 자리, 경로 `/flow/<id>`, 상세 방식)는 팀장이 정했고 소유자가 계획 검토로 승인했다. 되돌릴 수 있다.
- 세부 권한 규칙은 소유자가 따로 전체를 정리한다. 이 ADR은 그 전까지의 규칙이다.
- 이슈: [#1287](https://github.com/hjung3113/analytics-platform/issues/1287)(배치·용어), [#1288](https://github.com/hjung3113/analytics-platform/issues/1288)(VOC 공개 열람), [#1289](https://github.com/hjung3113/analytics-platform/issues/1289)(셀프 등록), [#1290](https://github.com/hjung3113/analytics-platform/issues/1290)(공지·FAQ), [#1291](https://github.com/hjung3113/analytics-platform/issues/1291)(이관 화면 틀·UI).

## 배경

FeedbackOps 기능을 플랫폼에 합친 뒤([ADR-0097](0097-platform-features-and-role-based-names.md)) 운영 화면은 모두 `운영 콘솔` 공간 하나에 들어갔다([ADR-0100](0100-feature-navigation-and-independent-access.md) 결정 2·4). 그 결과 세 가지가 섞였다.

- 담당자의 실무(VOC 처리·Finding·Task·설문 운영)와 관리자의 플랫폼 관리(권한·감사)가 한 공간에 있다. 홈 런처에서도 이 공간은 `플랫폼 관리` 묶음에 있다.
- `기능 관리` 섹션(Managed System·Analytics Area·권한 요청 검토·부여 목록·기능 설정)은 이름과 달리 플랫폼 자체가 아니라 기능의 추적 대상과 정책을 관리한다. [ADR-0068](0068-permission-scope-and-business-system-link.md) 결정 3은 Managed System Registry·기본값·공간 연결·Analytics Area를 피드백 운영 설정에, 권한 승인만 운영 콘솔에 두기로 했는데, ADR-0100이 두 자리를 한 섹션에 모았다.
- 일반 사용자는 본인 VOC만 본다([권한표](../product/features/09-permission-access.md#capability-matrix)). 사용자용 VOC·설문 화면은 `내 활동`에 흩어져 있고 `공지`는 화면 없이 홈 링크만 있다.

업무 시스템(Space, 앱 `menus.ts`의 정적 선언)과 Managed System(코어 서버 DB)의 연결은 ADR-0068이 서버 연결 표로 정했지만 지금은 `apps/platform-web/src/feature-systems.ts`의 정적 표다.

## 결정

### 1. 역할 셋, 자리 셋

| 자리 | 누구 | 하는 일 |
| --- | --- | --- |
| **플랫폼 직속** (공간 없는 전역 그룹) | 로그인 전원 | 알리고, 찾아보고, 응답한다 |
| **업무 흐름** (공간 id `flow`) | 담당자(Developer, 부여 범위 안)와 Admin | 들어온 피드백을 판단하고 실행으로 넘기고 효과를 확인한다 |
| **운영 콘솔** | Admin | 누가 무엇을 할 수 있는지, 플랫폼을 어떻게 돌릴지 정한다 |

업무 흐름은 제품 이름이 아니라 역할(담당자의 처리 흐름)로 묶은 공간이라, ADR-0097의 「피드백 운영 업무 시스템을 만들지 않는다」와 부딪히지 않는다. 사용자 화면은 이 공간 밖에 둔다.

### 2. 기능별 자리

| 기능 | 자리 |
| --- | --- |
| VOC 등록 | 직속 `VOC`(레일 `+` 유지) |
| VOC 목록 | 직속 `VOC`: 결정 3의 범위 안 VOC 공개 부분. 필터 `전체 / 내가 등록한`이 `내 VOC`를 흡수 |
| VOC 상세 | 직속 주소 하나(공개 부분). 처리 권한자에게는 `업무 흐름에서 처리` 링크를 둔다. 내부 부분은 업무 흐름 화면에서만 그린다 — 공개·운영 상세를 한 화면에 합치면 누출 표면이 커진다 |
| VOC 처리함·분류·반복 VOC(지금 `수신함`·`Triage`·`Clusters`) | 업무 흐름 |

| 대시보드(처리 대기) | 업무 흐름 첫 화면 |

| 권한 요청 검토·부여 목록 | 운영 콘솔(부여 체계는 ADR-0068 결정 2로 이미 하나) |
| 업무 시스템과 시스템 연결 상태 | 운영 콘솔(읽기) |
| 권한·역할 조회·감사·사용 현황·Registry | 운영 콘솔 |

- 업무 흐름 메뉴의 정규 경로는 `/flow/<메뉴 id>`다. 사내 적용 전이므로 ADR-0097대로 옛 `/operations/<id>` 별칭·리다이렉트를 두지 않는다.
- 역할별로 보이는 것: 사용자는 홈·직속·내 활동. 담당자는 여기에 업무 흐름. Admin은 여기에 운영 콘솔.
- 메뉴 라벨 중 `분류`·`근거`·`반복 VOC`·`VOC 처리함`과 직속 그룹 이름(가칭 `소통`)은 **Candidate**다 — 시안 컨펌에서 정한다.

### 3. VOC 공개 열람은 시스템 단위 부여를 따른다

- 새 capability `voc.read_public`(VOC 공개 부분 열람)을 둔다. 부여 범위는 기존 Managed System 범위다. 화면에서 업무 시스템과 Managed System은 같은 `시스템`이고(결정 6) 셀프 등록으로 1:1이 되므로, 이것이 시스템 단위 부여다.
- 판정 원천은 VOC의 기존 시스템 열(`primary_managed_system_id`) 하나다. 분류에서 시스템을 옮기면 열람 범위도 따라 옮겨진다. VOC에 업무 시스템·Site 열을 따로 두지 않는다.
- 보이는 것: 본인 VOC, 기존 운영 범위, `voc.read_public`을 받은 시스템의 VOC 공개 부분. **「플랫폼」 시스템 VOC의 공개 부분은 로그인 전원에게 보인다.**
- 공개 부분은 허용 필드만 담는 응답 형식(제목·본문·신고자용 상태·담당자 답변·공개 첨부). 신고자 답글과 그 첨부는 지금처럼 신고자와 처리 권한자에게만 보이고 공개 부분에 넣지 않는다(기존 대화·첨부 계약, 2026-11-03 결정)이고, 운영 조회와 다른 경로로 준다. 내부 부분(내부 메모와 그 첨부·분류 상태·심각도·담당 배정·Cluster·연결된 Finding/Task)은 지금처럼 처리 권한에만 보인다. 같은 가시성 판정을 쓰는 모든 읽기 경로(첨부·대화·유사 VOC·알림·nav 개수)에 누출 테스트를 둔다.
- 부여는 기존 권한 요청·승인·부여 목록 흐름으로 한다. 새 쓰기 경로를 만들지 않는다.
- 범위 종류 `space`·`site`·`site_room`(ADR-0068 결정 2의 `scope_kind`)은 이번에 만들지 않는다. 지금 판정은 시스템 지정 없는 부여를 workspace 전체로 읽으므로, 새 종류는 그 해석을 모두 바꾸는 변경과 함께 들어와야 한다. Site·room 단위는 [#98](https://github.com/hjung3113/analytics-platform/issues/98)(부여 원천)과 실서버 Site 범위가 생긴 뒤 다음 단계로 한다(`.planning/backlog.md`).

### 4. 커스텀 범위는 따로 만들지 않는다

권한 경계는 결정 3의 부여 단위뿐이다. 여러 시스템·Area·태그를 묶어 보는 것은 저장된 보기(06 §21)이며 권한이 아니다. 경계를 하나 더 만들면 서버 판정과 누출 테스트가 두 벌이 된다.

### 5. 업무 시스템이 시스템을 스스로 등록한다

- 업무 시스템 선언(`SpaceDef`)에 선택 필드 `feedbackTracking`을 둔다. 기본은 꺼짐이라 기존 소비자는 바뀌지 않는다.
- 앱 빌드가 선언된 업무 시스템 목록을 파일로 내고, 코어 서버가 시작할 때 그 파일을 읽어 켜진 업무 시스템마다 같은 키(`external_key = space:<id>`)의 Managed System과 공간 연결을 만들거나 그대로 둔다(멱등). 서버는 앱 manifest를 import하지 않는다.
- `feature-systems.ts`의 정적 표는 이 등록과 기능 API 조회로 대체된다. Kernel 슬롯 계약과 `/bootstrap`은 바꾸지 않는다(Kernel은 기능 식별자를 알지 않는다).
- **「플랫폼」 시스템을 늘 하나 둔다.** 업무 시스템이 아니므로 공간 연결이 없고, 서버가 고정 키로 만든다. 셸·홈·공지·내 활동 같은 공간 없는 화면에서 등록한 VOC의 기본 시스템이고, 보관할 수 없다.
- 플랫폼 밖 사내 시스템(예: Tableau·Power BI)은 업무 흐름 `설정`에서 손으로 등록하고 `플랫폼 밖` 표시를 단다.
- ADR-0068 결정 1의 불변식(연결은 기본값과 이동에만 쓰이고 권한을 주지 않는다)은 그대로다.

### 6. 화면 용어

- 화면에서는 업무 시스템과 Managed System을 모두 **시스템**이라 부른다. 코드·API·문서의 `Space`·`Managed System` 구분과 두 레지스트리는 그대로다. 사이드바 `목록 범위`는 `시스템`으로 바꾼다.
- 기능 Task는 화면에서도 **Task**다. 개선 실행의 `과제`를 영어로 Task라 쓰지 않는 규칙은 유지한다. Task 상태 값은 화면 문구만 한국어로 바꾼다.

## 대안

- **지금 배치 유지(운영 콘솔 하나):** 담당자 실무와 플랫폼 관리가 섞이고 `기능 관리` 이름 문제가 남는다.
- **기능마다 직속 메뉴, 새 공간 없음:** 담당자 화면 20여 개가 전원 사이드바에 권한 숨김으로 섞여 역할별 진입이 흐려진다.
- **VOC 전체 공개:** 소유자가 거절했다.
- **업무 시스템·Site 범위 종류를 이번에 구현:** 기존 판정의 「NULL = workspace」 해석을 전부 바꿔야 하고, 쓰기 경로와 실서버 Site 범위가 없어 시드로만 부여할 수 있다.
- **VOC에 업무 시스템 열을 따로 둠:** 시스템 열과 판정 원천이 둘이 되어, 분류로 시스템을 옮긴 뒤 옛 공간 사람에게 계속 보인다.
- **셀프 등록 전달:** 운영 콘솔 동기화 버튼(자동이 아님), 서버가 앱 manifest import(경계 위반).
- **시스템 목록을 `/bootstrap`에 실음:** Kernel이 기능 식별자를 알게 된다.
