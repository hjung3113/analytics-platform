# 시간 도메인 병합은 배포 소유 Site 전체 보증으로 증명한다

상태: **Decided (2026-11-18, 소유자 결정 #2544)**.

여러 설비를 한 시간축에 합치는 조회(`mergeTimeDomain`)는 서버 소유 증명이 있을 때만 허용한다([kernel §6.3](../contract/kernel.md)). 코어 서버(`menu-dispatch`)는 판정 순서의 7단계에서 이를 판정하지만, 증명을 어디서 받을지는 정해지지 않았다. 국내 Site는 Site 안 모든 설비가 같은 시간 기준으로 기록한다.

## 결정

- 증명은 배포가 선언 묶음에 적는 Site 전체 보증 `timeDomainAssertions: [{ site, timeDomainId, validFrom, validTo }]`이다. 한 행은 «이 Site의 모든 설비가 `[validFrom, validTo)` 동안 `timeDomainId` 한 기준으로 기록된다»는 뜻이고, 그 Site 모든 설비의 §6.3 최소 assertion을 같은 값으로 낸 것과 같다.
- 코어는 기동 때 행을 한 번 검증하고(달력 시각, 증가하는 창, 같은 Site의 겹침 없음, `scopeCatalog` 안의 Site) 데이터로 든다. 요청은 `scopeId` Site의 창만 쓰고, 덮임·단일 도메인 규칙은 §6.3 그대로다. 7단계는 원천을 읽지 않으므로 마감 시간·공급원 실패 경로가 없다.
- `mergeTimeDomain` 선언은 Scope resolver, 유효한 보증, `requiresScope`, 적용 시간이 모두 있을 때만 등록한다. 빈 목록은 없음과 같다.
- 보증을 새 설비·원천 변경·창 갱신에 맞게 유지하는 것은 배포의 책임이다. 개별 설비의 시계 틀어짐은 원천 데이터 품질로 범위 밖이다.
- §6.3의 설비별 최소 계약 문구는 유지한다. 설비별 증명 경로는 지금 만들지 않는다. 다시 여는 조건: 한 Site 안에 시간 기준이 다른 설비가 생기는 배포.

## 검토한 대안

- 설비별 assertion 공급원: 최소 계약 그대로지만 코어가 요청마다 실제 조회 설비 목록을 알아야 하고, 국내 Site에서는 같은 값을 설비 수만큼 반복할 뿐이다.
- 배포가 주입하는 비동기 증명 포트: 무엇이든 담을 수 있지만 요청마다 원천 호출·마감 시간·실패 처리가 붙고, 포트의 답을 다시 검사하는 규칙이 코어와 배포에 나뉜다. 정적 선언이면 기동 때 한 번 검증으로 끝난다.

판정 순서·선언 표기·기동 거부 문구는 [실서버 체크리스트 §3](../integration/real-server-checklist.md#3-menuquery-판정-순서)이 원본이다.
