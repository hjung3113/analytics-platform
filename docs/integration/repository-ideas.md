# 기존 프로젝트 활용 아이디어 모음

작성일: 2026-09-22. 상태: **브레인스토밍 / Candidate**.

관련 아이디어를 넓게 모아두고 나중에 한 번에 비교·정리하기 위한 문서다. 아래 항목은 채택 결정, 구현 요구사항, 일정 또는 저장소 추가 승인이 아니다. 플랫폼 전역 계약은 계속 [06](../06_platform_ui_contract.md)이 소유한다.

## 배경과 현재 방향

- FeedbackOps를 `products/feedbackops/` 서브모듈로 연결했다. 원본 개발을 유지하고 검토한 커밋으로 갱신한다. 현재 구조와 절차는 [저장소 연결 문서](repository-layout.md)를 따른다.
- 같은 체크아웃에서 기존 구현을 참고하며 플랫폼 설계를 구체화하고, 공통 계약과 책임 범위를 확정한 뒤 통합 구현을 진행한다.
- 플랫폼과 FeedbackOps 사이에서 인증·사용자·Scope·권한·메뉴·URL·Context·셸·공통 UI·감사·알림의 소유권을 먼저 정한다. 기존 구현을 활용할 수 있는 부분까지 새로 만들지는 않는다.
- 단일 Git 저장소, 단일 패키지 workspace, 단일 서버·DB·배포는 별개의 결정이다. 현재 서브모듈 연결만으로 후자들이 결정된 것은 아니다.
- `vocpage`는 FeedbackOps로 대체된 이전 제품이다. 별도 VOC 제품으로 살리기보다, FeedbackOps에 없는 유용한 부분이 실제로 확인될 때만 선별해 가져올 수 있다. 이 방향은 사용자 의견이며, 특정 기능의 채택은 아직 미정이다.

## 조사 근거와 한계

[Luna Max 상세 조사 보고서](../../.agents/reports/repository-integration-candidates-luna.md)에 저장소별 커밋·코드·문서 근거와 전체 후보 목록을 보존한다. 조사 당시 원격 목록은 49개였으며, fork 3개를 제외한 소유 저장소 46개를 대상으로 관련성을 분류했다. 본인 작성 여부는 소유권 외에 origin·커밋 작성자 등의 근거를 함께 살폈다. 전체 소스를 전수 검토한 것은 아니다.

후속 검토에서 원격 목록, `vocpage` 알림·승인 트랜잭션, `jira-voc-nexus` 재처리·근거 없는 경우의 동작을 직접 확인했다. 후보들의 빌드·실서비스·외부 연결은 실행 검증하지 않았다. 구현 존재와 운영 적용 가능성을 구분한다.

첫 조사에서 `vocpage`를 프로토타입 위주로 평가한 부분은 정정됐다. 실제 backend/frontend 구현이 존재한다. 원격 목록에서 별도 `voc-bot` 이름의 저장소는 찾지 못했으며, 사용자가 말한 봇의 정확한 저장소 정체는 아직 확정되지 않았다.

## 함께 생각해볼 사용자 흐름

### 분석에서 개선 작업으로 이어지는 흐름

분석 이상 발견 → 설비·Lot·기간·지표 버전과 조회 링크를 담은 VOC → Finding/Task → 조치 후 같은 조건으로 분석 복귀. 기존 URL은 조회조건의 재현이지 동일 숫자의 재현을 보장하지 않는다. Task 완료와 VOC 해결 또는 실제 효과 확인도 각각 구분한다.

### 숫자에서 원문 근거로 이동

집계 결과 → occurrence → 관련 원본 로그/설정 파일. FileGateway는 파일 접근 후보이고 ProjectGraph는 변환 계보 후보다. 두 도구의 근거 성격은 다르며, 링크가 존재한다는 이유만으로 원문 열람 권한을 주지 않는다.

### 외부 VOC의 자동 정리

외부 이벤트 접수 → 이벤트 ID/내용 지문으로 재처리·충돌 판정 → 권한 범위 내 근거 검색 → 고객 답변/개발 조치 초안 → 필요시 사람 검토 → 게시. 이 흐름은 아이디어이며 Jira 연결이나 자동 게시가 이미 구현됐다는 뜻이 아니다. `jira-voc-nexus`의 로컬 proposal/replay 규칙을 참고할 수 있다.

### 공통 알림

담당자 배정·댓글·상태 변경 같은 업무 이벤트와 공통 알림 보관·읽음·노출 책임을 분리할 수 있을지 검토한다. `vocpage`의 수신자 선택, 자기 행동 알림 제외, 반복 억제는 비교 대상이다. 기존 5분 억제 값을 플랫폼 기본값으로 채택하지 않으며, 동시성·전달 보장·권한 변화·딥링크 동작은 별도 검증이 필요하다.

### 로그 검증 업무와 개선 업무 연결

모델/로그 규칙 검증 → 실패 근거 → 결함/VOC 또는 작업 연결 → 수정 후 재검증. 검증 회차와 FeedbackOps 업무 상태의 소유자를 구분하고, 동일 결함을 두 시스템에서 중복 관리할지 여부부터 정한다.

## agent 계열에서 참고할 원칙

제품 runtime으로 넣을 필요성은 현재 확인되지 않았다. 아래 원칙만 필요할 때 참고한다.

- `feedbackops-workflow`: 검증 결과를 특정 소스 버전·내용 해시에 연결하고 오래된 결과를 현재 완료 근거로 쓰지 않는 방식.
- `general-ai-harness`: 작업 전에 계약을 고정하고 실행 주체가 결과물 해시·실행 결과를 별도 기록하는 방식.
- `lifetimeworkflow`: 기계가 만든 제안과 사람이 승인한 기준을 구분하는 방식.
- `agent-platform`, `thin-agent-harness`, `agent-migration-pipeline` 등: 개발 도구/워크플로우로 별도 유지하는 것을 기본 검토안으로 둔다. 제품 권한과 에이전트 실행 권한을 같은 모델로 강제하지 않는다.

이 원칙 때문에 새 승인 엔진·증거 프레임워크를 미리 만들지는 않는다. 실제 메뉴에서 요구가 확인되면 기존 공통 계약과 비교한다.

## 나중에 한 번에 정리할 질문

1. FeedbackOps에서 가져올 공통 기반과 업무 내부에 남길 것은 무엇인가?
2. 단순 참고, 일부 코드 재사용, 서비스 연동, 정식 편입 중 각 후보의 목적은 무엇인가?
3. 사용자·Scope·Managed System·설비 접근 권한을 어떻게 연결할 것인가?
4. 원문 파일·변환 계보·검증 회차가 실제 제품 범위에 필요한가?
5. `vocpage`와 `system-survey`에서 FeedbackOps가 아직 제공하지 않는 가치가 있는가?
6. 외부 VOC 봇의 정확한 원본은 무엇이고, ingress·검색·초안·게시 중 어느 기능이 필요한가?
7. 알림·검토·감사 중 플랫폼 공통 책임과 업무 책임은 어디까지인가?
8. 어떤 최소 사용자 흐름으로 통합 계약을 검증할 것인가?

정리 시 각 항목을 채택/참고 유지/보류/제외로 분류하고, 채택한 내용만 해당 소유 문서와 결정 상태 문서에 반영한다. 그전까지 이 문서는 아이디어를 추가로 모으는 공간으로 유지한다.
