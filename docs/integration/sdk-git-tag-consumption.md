# SDK 소비 조건·변경 기록과 과거 git 태그 시험

> 현행 SDK 배포·외부 소비 계약은 [ADR-0056](../adr/0056-sdk-release-github-release-tarballs.md)의 빌드된 Release tarball과 정확 버전 peer다. 아래 시험 조건·결과는 2026-10-19의 git 태그 소스 소비 조사(#458)이며 현행 설치 절차가 아니다. 이 문서의 소비 조건·변경 기록은 계속 유지한다.

## 시험 조건

저장소 밖 임시 소비자(pnpm 11.1.1, Vite 8, Tailwind 4.3.3 + `@tailwindcss/vite`, TypeScript 5.9, React 19.3)가 이 저장소를 로컬 `file://` 클론의 태그로 받았다. 의존성 선언은 `"@ap/ui": "git+<저장소>#<태그>&path:/packages/sdk/ui"`다. 실제 원격(사설 GitHub, 사내 git 서버)과 소비자 개발 서버·테스트는 시험하지 않았다.

## 결과

| 확인 | 결과 | 소비자 조건 |
| --- | --- | --- |
| 하위 경로 패키지가 풀리는가 | 된다. `@ap/ui`의 `dependencies`에 `@ap/*`·`workspace:` 항목이 없어(`@ap/eslint-config`·`@ap/tsconfig`는 devDependencies) 다른 패키지를 끌어오지 않는다. 서브모듈은 받지 않는다 | `@ap/ui`가 `@ap/*` 런타임 의존을 갖게 되면 이 결과를 다시 확인한다 |
| TS 소스 export(`./src/index.ts`)로 빌드되는가 | 된다. Vite가 `node_modules`의 `.ts`·`.tsx`를 그대로 변환한다 | — |
| 소비자 `tsc --noEmit` | `@ap/ui` 소스가 `process.env.NODE_ENV`를 쓰므로(`components/Button.tsx`) 소비자 tsconfig에 `@types/node`가 필요하다. 그 밖의 오류는 없었다 | 소비자 `types`에 `node` 포함. 소스를 `tsc`가 통과시킬 `strict` 수준(`@ap/tsconfig/base.json`)이 소비자에도 필요한지는 미확인 |

| `@tiptap/*` 버전 | **소비자가 고정해야 한다.** 잠금 없는 소비자는 starter-kit의 확장이 3.32.0으로 떠서 `@tiptap/core` 3.23.5와 어긋나 빌드가 `MISSING_EXPORT`로 실패한다 | 소비자에 `@tiptap/*` 24개 `overrides`를 3.23.5로(이 저장소 `pnpm-workspace.yaml`의 22개 + `@tiptap/core`·`@tiptap/pm`; 이 workspace는 core·pm을 직접 의존으로 풀지만 외부 소비자는 그렇지 않아 빠지면 3.32.0으로 뜨고 `pnpm peers check`가 경고한다). 기능은 #642부터 루트 workspace라 이 저장소의 `overrides`를 그대로 쓴다 |
| `@formkit/auto-animate` 패치 | 소비자가 같은 `patchedDependencies`를 가져야 한다(패치가 `@ap/ui`와 함께 오지 않는다). 기능은 #642부터 루트 workspace라 루트 `patchedDependencies`를 쓴다 | 패치 파일 내용이 `@ap/ui`와 같은지 전환 때 대조 |

테마 이름은 `@ap/ui/theme`의 `ThemeColorToken`·`THEME_COLOR_TOKENS`·`readColorToken`으로 소비하고, 도구는 `@ap/ui/theme-tokens.json`의 `color` 이름 목록을 읽는다. CSS는 계속 `rgb(var(--…))`로 쓰며, 제품 쪽 매핑 검사는 JSON 이름 목록과 대조한다. `$value.hex`는 매핑 키로 쓰지 않는다.

`sdk-v0.8.0`부터 `@ap/components`의 `token(name)`과 `ChartSeries.color`는 `string` 대신 `ThemeColorToken`을 받는다(ADR-0055). 런타임 문자열을 넘기는 호출자는 `isThemeColorToken(name)`으로 좁힌 뒤 부르거나, 자기 데이터 모델에 `ThemeColorToken`을 쓴다. 폐기 예고 없이 바꾼 이유: `@ap/components`를 저장소 밖에서 받는 소비자가 아직 없고(기능·EV는 `@ap/ui`만 받는다, 2026-10-20 확인), 값과 출력 형식(`rgb(r,g,b)`)은 그대로다. 저장소 밖 소비자가 생긴 뒤의 같은 변경은 ADR-0044의 한 릴리스 예고를 따른다.

## 변경 기록

팀장은 SDK 태그를 낼 때 `pnpm sdk:schemas --version X.Y.Z --out <empty-or-absent-schemas-dir>`로 자산을 만들고 `gh release upload sdk-vX.Y.Z <schemas-dir>/contract-schemas-X.Y.Z.tgz <schemas-dir>/SHA256SUMS-schemas`로 함께 올린다. [릴리스 순서](../../.agents/conductor/LANES.md#lead)를 따른다.

| `sdk-v0.8.0` | components | `token()`·`ChartSeries.color` → `ThemeColorToken` | `isThemeColorToken`으로 좁힌다 (ADR-0055) |

## Release tarball로 받기 (ADR-0056)

`@ap/ui` 말고 `@ap/kernel`·`@ap/components`·`@ap/shell`·`@ap/contracts`까지 받는 소비자(EV `platform-adapter`, 사내 메뉴)는 git 태그 `path:` 대신 **GitHub Release의 tarball**을 쓴다. 이유와 대안은 [ADR-0056](../adr/0056-sdk-release-github-release-tarballs.md)이다: 네 패키지는 서로를 `workspace:*`로 의존해 git `path:`로는 풀리지 않는다. 묶음 태그 `sdk-vX.Y.Z`마다 Release에 `ap-contracts-X.Y.Z.tgz`·`ap-kernel-…`·`ap-ui-…`·`ap-components-…`·`ap-shell-…`와 `SHA256SUMS`가 붙는다. 다섯 패키지는 같은 버전이고, tarball 안의 형제(`@ap/*`)는 그 버전과 정확히 같은 `peerDependencies`다(#806). 그래서 소비자는 쓰는 패키지의 형제까지 직접 의존한다: `kernel` → `contracts`, `components` → `kernel`·`ui`·`contracts`, `shell` → `components`·`kernel`·`ui`·`contracts`. 하나를 빠뜨리면 pnpm이 그 peer를 npm 레지스트리에서 이름으로 찾는다(지금은 404로 설치 실패). 모든 `@ap/*` URL은 같은 `sdk-vX.Y.Z`를 가리켜야 한다: 하나만 올리면 pnpm 기본값은 peer 불일치를 경고만 하고 설치를 끝내니, `pnpm-workspace.yaml`에 `strictPeerDependencies: true`를 둔다(소비 검사도 이 값으로 설치한다). 내용은 ESM JS·`.d.ts`·CSS·`theme-tokens.json`뿐이라(TS 소스·tsconfig·테스트 없음) 소비자는 SDK 때문에 `@types/node`나 JSX 설정을 맞출 필요가 없다. 번들러(Vite·Vitest·webpack 계열) 소비자를 전제로 하며, `@ap/contracts`만 Node ESM에서도 그대로 읽힌다.

`package.json` (쓰는 패키지와 그 형제를 적는다. 아래는 다섯 모두를 쓰는 예):

```json
{
  "dependencies": {
    "@ap/contracts": "https://github.com/hjung3113/analytics-platform/releases/download/sdk-vX.Y.Z/ap-contracts-X.Y.Z.tgz",
    "@ap/kernel": "https://github.com/hjung3113/analytics-platform/releases/download/sdk-vX.Y.Z/ap-kernel-X.Y.Z.tgz",
    "@ap/ui": "https://github.com/hjung3113/analytics-platform/releases/download/sdk-vX.Y.Z/ap-ui-X.Y.Z.tgz",
    "@ap/components": "https://github.com/hjung3113/analytics-platform/releases/download/sdk-vX.Y.Z/ap-components-X.Y.Z.tgz",
    "@ap/shell": "https://github.com/hjung3113/analytics-platform/releases/download/sdk-vX.Y.Z/ap-shell-X.Y.Z.tgz",
    "react": "^19.3.0",
    "react-dom": "^19.3.0"
  }
}
```

`pnpm-workspace.yaml` — 아래 소비자 조건을 건다(`strictPeerDependencies: true` 포함). `@ap/*` `overrides`는 두지 않는다. `sdk-v0.14.0`까지의 tarball은 형제를 `dependencies`로 실어, 그대로 URL `overrides`를 걸면 pnpm 기본값 `blockExoticSubdeps`가 `ERR_PNPM_EXOTIC_SUBDEP`로 막는다(#806). 그 판을 `@ap/contracts`·`@ap/ui` 말고도 받아야 하면 다음 릴리스로 올린다:

```yaml
strictPeerDependencies: true
overrides:
  "@tiptap/core": 3.23.5
  "@tiptap/pm": 3.23.5
  # … 나머지 @tiptap/* 22개도 3.23.5로 (이 저장소 pnpm-workspace.yaml의 overrides 22개 + core·pm = 24개)
patchedDependencies:
  "@formkit/auto-animate@0.10.0": patches/@formkit__auto-animate@0.10.0.patch
```

남는 소비자 조건:

- `@tiptap/*` 24개(이 저장소 22개 + `@tiptap/core`·`@tiptap/pm`) `overrides`를 3.23.5로 고정하고 `@formkit/auto-animate@0.10.0` 패치를 갖는다(위 표와 같은 이유; tarball이 이 둘을 대신 해 주지 않는다).
- React 19: `react`·`react-dom`은 SDK 패키지의 peer다. 소비자가 한 벌만 설치한다(Provider·Context 짝이 한 사본이어야 한다). `@ap/kernel`도 한 벌이어야 하는데, 형제가 peer라 소비자의 직접 의존 한 벌로 풀린다.
- CSS: `@import "tailwindcss"` 다음에 `@ap/ui/styles.css`, `@ap/components/styles.css`, `@ap/shell/styles.css` 순서로 import한다. 각 파일의 `@source`가 tarball 안 `dist`를 스캔한다.
- `@ap/components/testing`은 `vitest`를 import한다(`vitest`는 선택 peer). 그 진입점을 쓰는 소비자만 `vitest`를 설치하면 된다. `@ap/kernel/testing`은 `vitest`가 필요 없다.
- 체크섬은 `SHA256SUMS`로 확인한다.

CI가 매 PR마다 같은 다섯 tarball을 만들고(`pnpm sdk:pack`), 깨끗한 임시 소비자가 그것을 `127.0.0.1` HTTP로 서빙받아 위 조건 그대로(URL 직접 의존, `@ap/*` overrides 없음, `blockExoticSubdeps: true`, `strictPeerDependencies: true`) 받아 `tsc --noEmit`(`@types/node` 없음)·Vite 빌드·CSS 클래스 생성·Vitest까지 통과해야 병합된다(`pnpm sdk:consumer-check`). 기존 `@ap/ui` git 태그 `path:` 경로(위 시험 결과)는 그대로 동작한다. tarball로 옮길지는 소비자(기능) 판단이다.

## 결론과 남은 것

- git 태그 의존성은 **된다**. 결정(레지스트리 없이 태그)을 다시 열 이유는 시험에서 나오지 않았다.
- 소비자 조건은 둘이다: `@types/node`, 그리고 `@tiptap/*` overrides와 auto-animate 패치를 소비자가 이미 갖거나 갖추는 것. 둘 다 기능 전환 작업의 수용 기준에 넣는다.
- 소비 묶음(#466, `sdk-v0.2.0`): 기능의 얇은 재수출에 맞춰 `@ap/ui`가 `@ap/feature-ui`의 공개 이름 전부(`DetailPanelSlotContext` 제외)를 내보내고, shadcn 탭은 `TabsListBase`·`TabsTriggerBase`로, CSS는 `@ap/ui/styles/{tokens,semantic,theme,compat}.css`와 스캔용 `@ap/ui/styles/sources.css`로 받을 수 있다. `sdk-v0.1.0`에는 이 이름과 경로가 없다.
- 실제 전환 결과(FeedbackOps#1289, 1번 묶음): 소비자가 `@ap/ui`의 의존 범위(`^`)대로 받으면 radix가 새 버전으로 떠 동작이 바뀐다(Radix Tabs 1.2.x: 마우스다운에 `focus()`가 더해져 자동 활성화가 `onValueChange`를 두 번 부른다). 동작을 그대로 두려면 소비자가 `pnpm.overrides`로 radix·`lucide-react`를 이전 값에 고정한다. `@ap/ui`의 `react`·`react-dom` peer(`^19.3.0`)는 FeedbackOps(19.0.0)에서 경고를 낸다 — SDK 쪽 항목(#470).
- 시험하지 않은 것(전환 전 확인): 소비자 개발 서버·테스트, 사내 git 서버 접근(GitHub의 이 저장소는 공개라 인증이 필요 없다. 사내에서 GitHub에 닿는지 또는 사내 미러가 필요한지는 [#151](https://github.com/hjung3113/analytics-platform/issues/151)·[#232](https://github.com/hjung3113/analytics-platform/issues/232)와 함께 확인), 의존 `@ap/ui` 버전이 둘 이상일 때의 React Context 중복.
- 현재 다섯 SDK 패키지는 ADR-0056에 따라 빌드된 release tarball로 배포한다. tarball은 `dist`의 ESM JavaScript·`.d.ts`·CSS·JSON을 담으므로 소비자 번들러가 TypeScript 소스를 변환하도록 설정할 필요가 없다.

- React 하한(#470, 2026-10-19 결정, 되돌릴 수 있다): `@ap/ui`의 `react`/`react-dom` peer는 `^19.0.0`이다. SDK 자체 테스트는 19.3으로 돌고, 19.0.0에서는 소비자 기능이 1~3번 묶음(#1289·#1291·#1295·#1299·#1304·#1307) 동안 단위 테스트와 시각 하네스 145/145를 통과시켜 확인했다. 그 사이에 19.0 미만에서 깨지는 API를 SDK가 쓰면 이 범위를 올리고 소비자 조건으로 기록한다.
