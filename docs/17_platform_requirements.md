## 1. 왜 플랫폼인가

분석 화면 하나는 팀 혼자 만들어도 잘 만들 수 있다. 그런데 아래 일들은 **화면과 화면 사이에서** 깨진다. 화면 하나를 아무리 잘 만들어도 생기지 않는다.

- **옮겨 갈 때 깨진다.** 지표 화면에서 설비 화면으로 가면 기간·공정·설비를 다시 고른다. 동료에게 본 화면을 넘기려면 캡처를 붙이고 조건을 설명한다. 원인 설비까지 내려갔다가 돌아오면 처음 조건이 사라져 있다.
- **화면이 여러 개일 때만 생긴다.** 화면마다 표 정렬, 필터, 차트 확대, 내보내기 쓰는 법이 다르다. 빈 표가 "0건"인지 "조회 실패"인지 화면마다 다르게 보인다.
- **운영하는 사람이 화면 수만큼 일한다.** 권한 부여·회수, 변경 이력 확인, 어느 화면이 쓰이는지 파악을 화면마다 따로 한다.

플랫폼은 이것들을 지킬 수 있는 유일한 자리다. 그래서 각 팀은 **업무 화면만** 만들고, 화면 사이의 일은 플랫폼이 맡는다. 개발 비용이 줄어드는 것(같은 기능을 화면 수만큼 만들지 않는다)은 결과이고, 목적은 위 세 가지가 깨지지 않는 것이다.

## 2. 대표 장면 — 이상을 보고, 원인을 찾고, 알리고, 고쳐졌는지 확인한다

기능을 나열하기보다 분석 한 건을 끝까지 따라간다. 화면은 견본 메뉴로 보이지만, 단계마다 기대는 것은 메뉴가 아니라 플랫폼 기능이다(실제 메뉴는 사내에서 새로 만든다). BI 도구나 팀별 화면에서는 이 흐름이 중간에 끊긴다.

| 단계 | 사용자가 하는 일 | 기대는 요구 | 지금 |
| --- | --- | --- | --- |
| 1 | 어느 업무 시스템의 분석 화면에서 지표가 튄 구간을 본다. 이 숫자가 잠정인지, 데이터가 언제까지 들어왔는지 같이 본다 | R1.1, R2.1–R2.3 | 동작 |
| 2 | 원인 설비까지 내려가 상세를 연다. 처음 화면으로 돌아오면 조건이 그대로다 | R1.3, R3.1–R3.3 | 동작 |
| 3 | 지난달과 이번 달을 같은 차트에서 비교하고, 판단을 차트 주석으로 남긴다 | R3.2, R3.4 | 동작 |
| 4 | 그 화면에서 바로 VOC를 낸다. 그 업무 시스템으로 좁혀 열리고, 지금 화면 주소가 같이 간다 | R5.1 | 링크까지 동작. VOC 처리 화면은 FeedbackOps(별도 제품) |
| 5 | FeedbackOps에서 개선 Task로 이어지고, 담당자는 Task의 링크로 같은 화면·같은 조건에 돌아온다 | R5.2 | 링크 계약 동작. 실제 연결은 사내 SSO 뒤(#150) |
| 6 | 개선 뒤 같은 지표를 이전 기간과 비교해 효과를 확인한다. 분석 보드에 개선 전·후를 나란히 둔다 | R3.2, R4.1 | 비교는 동작, 분석 보드는 진행 중 |
| 7 | 운영자는 누가 무엇을 바꿨는지 변경 감사에서 확인한다 | R6.2 | 동작 |

한 문장으로: **보는 데서 끝나지 않고, 고쳐졌는지 확인하는 데까지 이어지는 곳.**

### 3.9 SDK — 다른 저장소의 앱이 플랫폼에 올라오는 계약

SDK는 플랫폼에 올릴 앱이 지키는 **계약**이면서, 앱이 자기 프레임워크 없이 쓸 수 있는 **하나의 플랫폼 프레임워크**다. 플랫폼이 소유하고, 의존은 SDK ← 제품 한 방향이다. 앱을 플랫폼 밖에서 따로 돌리는 것은 그 앱의 책임이다([ADR-0043](adr/0043-platform-sdk-is-the-app-contract-and-unified-framework.md)).

## 4. 판단 기준 — 이 플랫폼이라서 되는 것

요구를 고르고 우선순위를 정할 때 쓰는 기준이다. 사이트·발표에서 다른 제품과 직접 비교하는 문구로 쓰지 않고, 기능 설명의 근거로만 쓴다(사용자 2026-10-20).

- **업무 맥락이 기본이다.** 사이트·공정·설비 그룹·EquipmentID·Lot·Recipe가 처음부터 조건이고, 지표에서 설비·실행 단위까지 내려간다(R1.1, R1.3). 범용 대시보드 도구로는 화면마다 이 맥락을 다시 만들어야 한다.
- **화면 사이에서 깨지지 않는다.** 팀별로 따로 만든 화면에서는 R1·R3·R6이 화면 수만큼 따로 생긴다. 여기서는 한 번만 있다.
- **숫자의 상태와 정의가 따라온다.** 신뢰 표시(R2.1), 지표 정의 버전(R2.4), 같은 조건 같은 숫자(R2.6)는 수작업 집계로는 지켜지지 않는다.
- **보는 데서 끝나지 않는다.** VOC·개선·감사로 이어진다(R5, R6.2).
- **약한 곳도 기준이다.** 자유도는 아직 수작업이 더 크다(R4.3 결정 대기). 분석 보드(R4.1)가 그 사이를 일부 메운다. 이 점을 감추는 문구를 쓰지 않는다.

## 5. 기존 시스템을 옮길 때

기존 시스템(예: CLAS)을 가진 팀이 옮기면 무엇이 남고 무엇이 없어지는지.

| | 기존 시스템이 계속 가진 것 | 플랫폼이 대신 맡는 것(팀이 더는 만들지 않는 것) |
| --- | --- | --- |
| 화면 | 업무 화면의 내용(지표 계산 표시, 업무 흐름, 업무 객체) | 화면 틀·사이드바·전환기·검색, 표·차트·상세 패널·필터·상태 화면 |
| 조건·주소 | 그 화면만 쓰는 조건 | 분석 조건 유지, 주소 계약, 화면 사이 링크, 드릴다운 복귀 |
| 권한·운영 | 업무 규칙에 따른 쓰기 판정 | 로그인 연결, 시스템·화면·조회 범위 권한, 감사, 활용률, 화면 오류 격리 |
| 서버 | 도메인 API와 데이터 | 조회 선언 검사, 상태 분류, 적합성 묶음(서버 구현은 팀이 고른다) |

옮기는 길은 둘이다.

1. **플랫폼 저장소 안 화면으로** — 메뉴 생성기로 패키지를 만들고 화면을 옮긴다. 지금 된다([사내 적용 가이드](integration/in-house-rollout.md)).
2. **자기 저장소에 둔 채 SDK로 올리기** — manifest와 화면을 내고 플랫폼이 등록한다. 계약 1판(등록 검사·화면 렌더·호스트 포트)이 동작하고 계약 검사용 고정 모듈로 검증했다. 첫 외부 소비자는 equipment-visualization이다(#332 뒤).

FeedbackOps는 화면을 옮기지 않고 업무 시스템마다 진입 링크로 붙는다([ADR-0027](adr/0027-feedbackops-stays-standalone-entry-links.md)). 플랫폼 셸 안에 올릴지는 [ADR-0038](adr/0038-host-module-contract-and-feedbackops-mounting.md)(Proposed)이 정한다.

## 6. 도입 근거로 보일 수 있는 것과 아직 없는 것

**지금 보일 수 있는 것**

- mock 서버 위에서 §2 대표 장면의 1–3·6(비교)·7단계가 끝까지 동작하는 데모.
- §3의 "동작" 요구마다 계약 문서·테스트·E2E가 있다. 숫자(릴리스 수, 테스트 선언 수 등)는 사이트 원장이 재서 적는다.
- FeedbackOps가 이미 SDK UI를 받아 쓴다(R9.1): 다른 저장소가 SDK를 실제로 소비한 증거.

**아직 없는 것(숨기지 않는다)**

- **효과 숫자가 없다.** 도입 전 기준선(#233)이 없어 "빨라진다"를 말할 수 없다. 숫자 대신 동작으로 말한다("다시 고르지 않는다", "같은 숫자를 본다"). 무엇을 잴지만 적는다.
- **실데이터가 없다.** 실서버·SSO·배포 환경이 사내 답 대기다(§7). 장점은 아직 "구조로 보장된 약속"이다.
- **사용자가 직접 만드는 분석은 아직 없다**(R4.3 결정 대기). 비전으로만 둔다.

## 8. 하지 않는 것

지금 하지 않기로 한 것과 그 이유. 다시 열 조건은 근거 문서에 있다.

- **승인 워크플로우** — 감사와 버전 관리로 대부분 대체한다. 규제 요구가 나오면 다시 본다([00](00_overview.md)).
- **범용 알림 규칙 엔진** — 적재 중단·집계 실패 같은 운영 알림부터. 공정 이상 알림은 지표·임계값이 검증된 뒤([00](00_overview.md)).
- **스케줄 리포트, 외부 BI 연동** — mart·view를 SQL로 질의할 수 있게 문서화하면 나중에 붙이기 쉽다([00](00_overview.md)).
- **자유 SQL·코드를 받는 지표 식** — 감사할 수 없고 주입 위험이 있다. 제약된 식부터([00](00_overview.md)).
- **자유 배치 위젯 빌더·대시보드 빌더** — 분석 보드(R4.1)는 위젯 빌더가 아니라 기존 화면을 칸에 담는다. 위젯 빌더는 실제 화면 2–3곳에서 반복이 확인될 때([06 §14](06_platform_ui_contract.md#14-platform-component-promotion-rule)).
- **운영 중 설치·원격 로딩 플러그인** — 코드 안 선언형 등록부터([06 §5](06_platform_ui_contract.md#5-menu-extension-contract), R7.4).
- **원문 로그·설정 파일 drill-through** — 파서 view/mart 조회로 충분하다. 내부 개발자 메뉴가 필요해지면 다시 본다([05](05_roadmap_and_open_questions.md)).
- **칸끼리 값을 합치는 교차 계산** — 서로 다른 시스템의 데이터를 합치는 분석이라 별도 결정이다([16 §2](16_analysis_board.md#2-범위)).
- **앱을 플랫폼 밖에서 따로 돌리는 호스트** — 각 제품의 책임이다([ADR-0043](adr/0043-platform-sdk-is-the-app-contract-and-unified-framework.md)).
