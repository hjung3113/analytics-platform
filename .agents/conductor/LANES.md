# Flows (lane) and Lead

These are the assignment rules for multiple Claude sessions working in this repository at the same time. Each session owns one flow and handles its issues according to [`PROFILE.md`](PROFILE.md); the lead session handles assignments, conflicts, and releases across flows. The flow table, owned paths, ports, and release owners are repository rules. Handoffs between sessions (Run messages and terminal input), flow-session lifecycle, and lead recovery are temporary rules until the engine provides workflow steps ([conductor-engine#124](https://github.com/hjung3113/conductor-engine/issues/124)).

## Request classification

Before adding a `lane:*` label to a new request (issue, review follow-up, or request from a product session), the lead decides who owns it. The source of the criteria is the root [`AGENTS.md`](../../AGENTS.md), “이 레포의 목적” (heading in root `AGENTS.md`) (the SDK provides generic components, promotion criteria, and what to do when a common contract conflicts); this section maps those criteria to flows and tasks. Do not split tools, CI, and documentation structure (`lane:arch`), introduction pages (`lane:site`), or operations and ancillary requests (`lane:ops`).

Evaluate the following in order; the first match classifies the request (or that part of it).

1. **Kernel responsibility:** Does it fit the list in 06 [§4](../../docs/contract/kernel.md#4-platform-kernel-responsibilities) (shell, Registry, global Context, URL, permissions and Scope, Audit, instrumentation, etc.) or Kernel runtime responsibilities ([`packages/sdk/kernel/AGENTS.md`](../../packages/sdk/kernel/AGENTS.md): query lifecycle, caching, deduplication, etc.)? Contracts and runtime (`packages/sdk/{contracts,kernel,shell}`) belong to `lane:sdk`; work connecting those contracts to the app (assembly, mock, real adapter, server conformance) belongs to `lane:platform`. Do not wait for a consumer count. Decisions to change the 06 contract belong to the owner (§Flow sessions).
2. **SDK component:** Can differences between menus (hierarchy, number of steps, row names, drilldown interaction, business wording, permissions) be declared by the menu, leaving a component that other menus can use as-is ([ADR-0052](../../docs/adr/0052-rich-content-stays-in-the-sdk.md) inclusion criteria)? If so, it belongs to `lane:sdk` and stays in the SDK regardless of consumer count. Check domain terms in the request against [`GLOSSARY.md`](../../GLOSSARY.md); do not put them in the component name or API.
   - **SDK operations:** If the work concerns SDK distribution or quality itself (tarball, dependency pinning, performance, test stability, public API snapshot), rather than a specific feature, classify it here and use `lane:sdk` (#806, #706, #741).
3. **Menu responsibility:** The remaining work is the menu’s business meaning (numbers, CRUD, state transitions, chart settings specific to that menu, and forms unique to it — 06 §4 “What Kernel Does Not Own,” §13 Domain Component). If a menu request conflicts with a common contract, it still belongs to the menu: align the menu with the contract (root `AGENTS.md`). The menu’s location determines who owns it.
   - **Sample menus** (`menus/*`, excluding bridge menus): `lane:platform`. Change a sample only as much as needed to validate the platform contract it covers. Do not assign requests that only polish the screen.
   - **Product menus:** FeedbackOps bridge menus belong to `lane:fo`; the EV host module belongs to `lane:ev`. The product owns the business meaning ([ADR-0043](../../docs/adr/0043-platform-sdk-is-the-app-contract-and-unified-framework.md)).
   - **In-house menus** (actual menus built outside this repository): Do not build them here. If the request arrives as an issue, comment with the relevant step from §5 of the [in-house menu development guide](../../docs/integration/in-house-rollout.md) and the SDK components to use, then close it as not planned. If it arrives in conversation, answer with guidance and do not open an issue. If the guide lacks an assembly method, update the guide (`lane:platform`, M4).

- **Mixed requests:** Split by classification. Put Kernel work and SDK components in a `lane:sdk` issue; put menu declarations and screens in the relevant menu flow’s issue, after the SDK issue. For an in-house menu request, keep only the SDK component as an issue and describe the menu part to the consumer in that issue. For example, HW Time’s equipment → equipment-module → action drill consists of two SDK components (“drill through menu-declared steps” and “category row for a horizontal bar”) plus the HW Time step declaration (#541). Keep a sample-menu change in the same PR if the first consumer is a sample that validates the component, or if the requested sample-menu change is small (such as one link).
- **Promotion candidates:** The root `AGENTS.md` is the source for promotion criteria; the lead counts consumers of patterns that arise in menus. If a pattern does not qualify under item 2 (it mixes business meaning or its form differs by menu) but may appear in other menus, record `Not implemented — <pattern> SDK promotion` in `backlog.md`, with current consumers (menus and issues) and the reopening condition (2–3 actual consumers). If the same pattern comes up again, add its consumers to that line. When the condition is met, file a `lane:sdk` issue. Count sample, product, and in-house menus as consumers.
- **When flow and classification differ:** The default is the flow that owns the path being changed (§Flows table). Another flow (for example, a product flow) handles it only when the lead assigns it there. Flows follow path ownership; classification determines the source document, promotion criteria, and owner responsibilities. A product flow may take Kernel or SDK work for its own product. The same applies when an SDK component needs to change a consumer file owned by another flow. In both cases, send the start message in §Shared paths; the lead sets the order. Divide bugs by confirmed cause, not by where the symptom appears.
- **Names:** Requests phrased as “platform role” usually concern Kernel responsibility. `lane:platform` covers app assembly, mock, adapters, and sample menus; it is not Kernel ([`GLOSSARY.md`](../../GLOSSARY.md), `Kernel`).

## Machine resources (16 GB)

The number of concurrent workers and flow sessions is determined by machine capacity, not fixed. `bash .agents/conductor/scripts/capacity.sh` prints one line (`green|yellow|red workers=<1-7> lanes=<2-4> start=<yes|no> … why=…`), and callers use this script from any flow worktree. When `AP_MAIN` is set, the previous swap record is stored at `$AP_MAIN/.review/capacity.last`. These limits apply machine-wide to every Claude session working on this repository (including fo and ev sessions whose cwd is outside AP and user-started sessions) and every flow's workers.

| Stage | Condition (all / any) | Workers | Flow sessions | New starts |
| --- | --- | ---: | ---: | --- |
| green | Free ≥ 25% | 7 | 4 | yes |
| yellow | 20% ≤ free < 25%; also use when memory measurement fails | 3 | 3 | yes |
| red | Free < 20% | 1 | 2 | no |

- **Stage criteria (owner decision):** Determine the stage only from free-memory percentage: green ≥ 25%, red < 20%, and yellow between them (#965). If memory measurement fails, use yellow. Keep swap, load, and kernel pressure as reference values in the output only. These limits prevent adding workers and heavy stages when load is already high. Since blocking new starts does not reduce swap already accumulated by out-of-flow sessions, the lead's check in §Flow sessions surfaces those sessions. Review this table after `capacity.last` records and timeout incidents accumulate. The green-stage worker cap of 7 is recorded in #1018.
- **Red:** `workers` and `lanes` do not authorize new slots; `start=no`. `lanes=2` is the target count when the lead closes flows in `대기` (waiting); `workers=1` is reference only. If `start=no`, rerun after 5 minutes; if it is still `no`, send the blocked report in this exact format: `<흐름>: 막힘 #n capacity <단계> why=<why>`. (`막힘` = blocked.) In yellow, if lower-numbered slots are held by other workers and only higher-numbered slots are free, wait; this is intended.
- **Workers:** Before launching each implementation worker or reviewer, run `capacity.sh` and claim a slot only when `start=yes`. A slot is `$AP_MAIN/.review/worker-slot-N` (`N` runs from 1 through the printed `workers` value, up to 7; try in order, and if all attempts fail, no slot is available). Acquire it using the lock procedure below. Release it as soon as the worker finishes. Before launching a reviewer after implementation, release the slot, run `capacity.sh` again, and claim a slot again; do not hold a slot between stages. If `start=no` or all slots are held, do not launch a worker (including a reviewer) without a slot. While waiting, do host verification or documentation work; if no other work is available, send a blocked report in the format above, including the `capacity.sh` stage and `why`.
- **Claimed resources are not taken away:** If the stage drops (for example, green to red), let workers already running and their claimed slots and `heavy.lock` finish. Block only new claims. A worker holding `worker-slot-3` when `workers` drops below 3 keeps it until it finishes.
- **Heavy stages:** Only one `heavy.lock` may be held machine-wide, regardless of allowed worker count. If `start=no` (red), do not start a new heavy stage or try to acquire `heavy.lock`. Focused E2E and package-level checks do not use this lock.
- **Flow sessions:** At each scheduled check and mailbox event, the lead checks `lanes` from `capacity.sh`. If the current number of sessions (`orca terminal list` flow sessions plus user-started sessions) is below `lanes` and a flow has work, start it. If there are too many, close flows in `대기` state first; do not close user-started sessions, and notify the owner. Do not terminate an active flow session when the stage drops: it takes no new assignments and closes after finishing. Before starting a session, run `capacity.sh` and confirm `start=yes`. At yellow or below, include the top memory processes and elapsed time in the check report using `ps -eo rss,etime,command | grep -E 'claude|codex|ChatGPT' | sort -rn | head`. If a session is at least one day old and not in the flow table, tell the owner to close it; the lead does not close it.
- **Heavy stages run one at a time machine-wide:** root `pnpm test`, `pnpm build`, `probe.ts`, and FeedbackOps integration. Do not run all of `pnpm e2e` locally; run it under the same lock only to reproduce a CI failure (#959). Preview and ego-browser work (UX review and capture) uses `browser.lock`, not `heavy.lock` (#945).

  Only a session whose `mkdir` succeeds may start:

  `mkdir "$AP_MAIN/.review/heavy.lock" && echo "$ORCA_TERMINAL_HANDLE" > "$AP_MAIN/.review/heavy.lock/owner"`

  Immediately write `since` (`date -u +%FT%TZ`) and `purpose` (the stage and waiting PID, e.g. `762p2 UX review, pid 41234`) in the same directory. The PID is `pid` from `$WAVE_STATE/<name>.json`. For an Orca terminal worker with no PID, write `terminal <handle>`; for a host check run directly, write `foreground`. If relaunching a worker (for example, quota fallback), update `purpose` first. The same applies to `worker-slot-*`; after launching the worker, update `purpose` when its PID is known.

  Release only when `owner` is your own handle: `[ "$(cat …/owner)" = "$ORCA_TERMINAL_HANDLE" ] && trash …/heavy.lock`. Use `trash`, not `rm`; the `owner` file prevents `rmdir`. This is the acquisition and release procedure for `heavy.lock`, `browser.lock`, `worker-slot-N`, and `merge.lock`; change only the directory name. The recommended wrapper is `bash .agents/conductor/scripts/with-lock.sh <lock> "<purpose>" -- <command…>` (#1018): it acquires the lock using the same procedure, releases it with `mv` + `trash` only if the owner matches, and exits without running the command with code 75 and one line if the lock is already held. The lock follows the child process lifetime: the child runs in a new process group, and TERM, INT, and HUP go to the whole group, including grandchildren; only SIGKILL can leave a lock behind. For SIGKILL, the end of `purpose` contains `, pid <wrapper PID>, pgid <child group>`; `lock-audit.sh` reports `held` if any child-group process is alive, and `done-pid-dead` only when both wrapper and child group are dead. The wrapper also writes a `token` file; release requires both `owner` and `token` to match, so a subagent or background command with the same handle cannot release a lock newly claimed by another session. If neither `ORCA_TERMINAL_HANDLE` nor `WITH_LOCK_OWNER` is set, it exits 2. A lock acquired with direct `mkdir` has no `token` and release checks only `owner`. The direct `mkdir` procedure is still valid; the lead's stale-lock release (see "Stale lock check") is the only exception. To avoid a release race, owner or lead releases with `mv <lock> <lock>.released-$$ && trash <lock>.released-$$`. If the rename fails, another session already released or claimed it; do not touch it. If acquisition fails, wait and work on something else. Focused E2E (`-g`) and package-level checks do not use a lock.

- **`browser.lock` (#945):** Preview servers, ego-browser, and capture stages (including UX review) acquire `$AP_MAIN/.review/browser.lock` using the same procedure (`mkdir`, `owner`, `since`, `purpose`, release with `mv` + `trash`). There is one machine-wide lock so people take turns using the single ego-browser (Ego Lite). It may be held at the same time as `heavy.lock`, allowing browser work while another flow runs root tests or build. If one session holds both, acquire `browser.lock` first, then `heavy.lock`; this fixed order prevents deadlock. Preview Vite uses CPU and memory, so if `capacity.sh` returns `start=no` (red), do not start a browser stage.
- **"Locks follow the heavy process":** Tie the lock to the heavy process (worker or preview server). As soon as the worker finishes, whether successfully, with `error_max_turns`, quota exhaustion, or a crash, stop the preview server and release the lock and slot before reading results. Wait for worker completion only with `worker-wait.sh`; it checks both sentinel PID liveness and the time limit, and always pass `--kill-on-timeout`. Exit codes `10`, `11`, and `12` mean the worker finished and get the same handling. Code `13` (capacity) means the worker stopped: in the `with-lock.sh` pattern below, `worker-wait` ends and releases the slot on 13; send `continue` to the terminal, reclaim the slot, and run `worker-wait` again. Do not write a direct wait that watches only a sentinel; a reviewer may die without writing one and the wait would never end (#932).

  Tie the slot to the worker lifetime like this (`run_in_background`):

  `bash .agents/conductor/scripts/with-lock.sh worker-slot-N "<node> <role>" -- bash -c '<start-worker> && bash ~/.agents/skills/orca-dispatch-recipes/scripts/worker-wait.sh … --kill-on-timeout'`

  The slot is released when the worker finishes or the background command stops. `worker-wait.sh` is in `orca-dispatch-recipes`, not `$ENGINE`. Inside the single-quoted `bash -c`, only exported variables are visible, so export values such as `$WAVE_STATE` and the worker name first. If this command exits 13, the slot is already released: send `continue`, reclaim the slot with the same command shape, and run `worker-wait` again; without `continue`, it immediately returns 13 again.
- **"30-minute lock audit" (owner decision):** Every 30 minutes, separately from the two-hour scheduled check, the lead runs `.agents/conductor/scripts/lock-audit.sh` (it does not release locks) and finds locks whose verdict is `done-*` or `owner-gone`. Re-create `CronCreate` when the lead session changes. Completion evidence is one of:
  1. The PR in `purpose` is merged or closed (`gh pr view <n> --json state`).
  2. The worker PID in `purpose` is dead (verify with `ps` under "Stale lock check").
  3. `purpose` is `ship` and no `ship-pr.sh` process exists (`pgrep -fl ship-pr`).
  4. The PID in the worker state JSON has exited. For `worker-slot-*` and `heavy.lock`, `purpose` may not include a PID or PR; `lock-audit.sh` uses its first token (e.g. `1011b FIX2`) to find `$AP_MAIN/.review/wave/state-*/W-<name>*.json` and check `pid` (#1018).

  The fallback is conservative: if `purpose` contains `foreground` or `terminal`, do not use it. Exclude JSON files started more than 120 seconds before `since`. If the first and second tokens do not narrow the result to one candidate, mark `done-pid-dead` only when all candidates are dead. If there is a second token but no candidate name matches it (only JSON for other roles), the verdict is `held`; exception: if the second token is `impl` and a `W-<name>.json` exists. When uncertain, use `held`. If a lock is found, do not wait for the 30- or 90-minute thresholds; immediately follow step 2 of "Stale lock check" (notify the owner, then the lead releases it after 10 minutes). A flow session releases its slot as soon as its worker or `ship-pr.sh` ends, whatever the result.
- **"Stale lock check" (owner decision, #932):** Whenever a mailbox event wakes `check --wait`, without waiting for the two-hour check, the lead checks `since` and `purpose` for `heavy.lock`, `browser.lock`, `worker-slot-*`, and `merge.lock`. During the scheduled check, also compare `owner` handles with `orca terminal list`; the lead uses `trash` to release a lock. Release the first applicable case:
  1. The directory has had no `owner` for over 5 minutes, or its handle is already closed: release it immediately.
  2. `since` is over 30 minutes old and the PID in `purpose` is dead. Check with `ps -o command= -p <PID>`: there is no PID, or the process (such as `claude -p`, `codex exec`, or `vite`) does not match `purpose`. Do not rely only on `kill -0` because PIDs can be reused. Immediately message the owner's flow: `[팀장] <잠금> 풀어라: <purpose>` (`[팀장]` = [lead]; `풀어라` = release). If that terminal is not `tui-idle`, start the 10-minute timer when it becomes idle. If there is no `<흐름>: 풀음 <잠금 이름>` (`풀음` = released) within 10 minutes, the lead releases the lock. If the owner replies `<흐름>: 유지 <잠금> <근거>` (`유지` = keep; e.g. `유지 worker-slot-2 FINAL reviewer terminal term_C is still running`), do not release it; verify the evidence and have the owner update `purpose`. Count 10 minutes with `check --wait --timeout-ms 600000`. If the owner already released it, leave it alone; do not touch a lock newly claimed during release. If a preview server from the same flow remains, ask them to stop it. If there is no owner, use `app-preview.py status` to find that flow's label, then `stop <label>`. If ownership is unclear, do not force it; report it. If neither the owner nor the lead session exists, release it directly only for case 1 (the owner handle is absent from `orca terminal list`), and record it in the flow report.
  3. `purpose` is missing or the PID is unknown: if `since` is over 90 minutes old, run `pgrep -fl 'vitest|playwright|turbo|ship-pr|claude -p'` and `lsof -a -p <PID> -d cwd`. Check whether a process has a cwd under the owner's flow worktree (the `LEAD.md` table); do not count preview `vite`. If none is running, follow case 2 (ask the owner, then release). After releasing, record what was released and why in the flow report. A `merge.lock` whose `purpose` is `ship` is stale only if `ship-pr.sh` has exceeded its CI timeout. The same applies when the owner is alive but the PID is dead; a running preview `vite` does not prove the owner is alive. If `since` and `purpose` are missing (user-started sessions or locks from before this rule), report them as missing and apply only cases 1 and 3. The 90-minute threshold allows a long local check to finish. The flow-session limit is the table in "Machine resources (16 GB)".

## Flow sessions

Flow-session terminals are not visible to the owner. Send any step where the global conductor skill asks the owner something to the lead as a message.

- **Start:** Read the task file. Merge authority is the owner's authority stated in the task file (form, date). Do not ask again or use `AskUserQuestion`; nobody is there to answer, so the flow would stop.
- **Owner decisions:** Send prototype approval (Artifact link), a decision that changes the 06 contract, test deletion, 3 or more new menu screens, or a global tool update to the lead as `<flow>: 질문 #n` (question). Pause that issue and continue with other assignments. Make and record all other decisions yourself according to the skill's Decisions.
- **Report blockers:** If an issue is blocked because a lock or slot could not be secured, wait. If it clears within 5 minutes, do not send; otherwise send immediately after that wait: `<flow>: 막힘 #n <lock name>, owner <owner>, since <time>, purpose <purpose>` (blocked). On the same wake after receiving the blocked message, the lead checks the `purpose` PID for that lock and, following step ② above, tells the owner to release it or releases it directly, then replies to the flow with the outcome (first response: immediately on receipt; do not wait for the next routine check). If a blocked flow fails to acquire the lock, retry once after 5 minutes; if the second attempt also fails, send the message. If `since` or `purpose` is missing, write `none`.
- **Between assignments:** When one issue is complete, start the next issue immediately in the order listed in issue comments. If the next issue's files do not overlap and a capacity slot is available, start it in parallel (PROFILE §Launch). When all assignments are complete, send `<flow>: 대기` (waiting) and do not start anything until a new assignment arrives.
- **Wait for predecessor PR:** A flow does not wait for lead notification that a predecessor PR merged. If the predecessor is a PR, the flow itself runs `until s=$(gh pr view <n> --json state -q .state); [ "$s" != OPEN ]; do sleep 60; done; echo "$s"` with `timeout <limit>` using `run_in_background` (a foreground `sleep` blocks, so it must run in the background; `gh pr view` runs once and exits, and `gh pr checks --watch` exits when checks finish, not when the PR is merged, so neither command waits for a merge). Start only when `MERGED`, and announce with `<flow>: `착수` (start)` (lead notification is supplementary). If `CLOSED` (not merged) or the timeout is exceeded, do not start; ask the lead with `<flow>: `질문` #n`. Send the earlier `대기` message only when there is no predecessor to wait on and no issue to assign.
- **Handoff:** When the terminal status line's `ctx:` exceeds 60%, hand off during a quiet period after completing an issue. Flow sessions cannot see the status line in the model, so after each assignment check with `orca terminal read --terminal "$ORCA_TERMINAL_HANDLE" --screen | grep -o 'ctx:[0-9]*%'`; the lead also reads `ctx:` from each flow terminal during routine checks and instructs a `교대` (handoff) if it exceeds 60% (the receiving session finishes its in-progress issue, then sends `<flow>: `교대``). If it exceeds 75%, write the in-progress work to `HANDOFF.md` and hand off immediately, even mid-issue. `ctx%` takes priority; the skill's token limit is secondary. Do the same when nearing the skill's Session hygiene limit. A handoff means recording the in-progress work and any held locks, slots, preview label, and `$WAVE_STATE` worker name in `HANDOFF.md` at the flow worktree root, then sending `<flow>: `교대`` (the new session's first action is to rerun `worker-wait.sh`; if `with-lock.sh` tied the slot to the worker's lifetime, the background command ends during handoff and releases the slot too, so the new session reacquires the slot and takes over the worker). The lead enters `/clear`, then sends "Re-read the task file and continue from HANDOFF.md."
- **Merge:** Merges happen one at a time across the whole machine; CI runs concurrently (root `AGENTS.md`). For ordinary PRs, hold `merge.lock` only for the **short interval just before merge**.
  - **Ordinary PR:** Since `ship-pr.sh` runs CI and merge in one step, use the four-step workaround until the engine supports `--merge-lock` and `--release` ([conductor-engine#150](https://github.com/hjung3113/conductor-engine/issues/150)). Wait for CI outside `merge.lock`.
    - **(a) Create:** Run `ship-pr.sh --branch … --base main --title … --body-file …` without `--ci`, `--merge`, `--issue`, `--worktree`, or `--archive-review`. If `--merge` is left in, the ruleset rejects it because required checks are pending (exit 2); if `--issue` is left in, it closes the issue before merge.
    - **(b) Wait:** Run `gh pr checks <n> --watch --fail-fast` in the background with a time limit (run it again if it finishes before checks are registered). When it finishes, verify with `gh pr checks <n> --json name,bucket` that every check passed.
    - **(c) Merge:** Run check ② and merge inside the **same `merge.lock`** (this closes the gap where a shared-path PR could merge between the check and merge). First, outside the lock, check ①: the latest push CI on `main` is not failing. Then `export` the variables (`bash -c` inside single quotes sees only exported variables) and run one command: `export PRN=<n> BR=<branch> SHA=<sha>; bash .agents/conductor/scripts/with-lock.sh merge.lock "$PRN merge" -- bash -c 'git fetch -q origin main && if git diff --name-only "$(git merge-base origin/main "$BR")" origin/main | grep -qE "^(tooling/sdk/api/|package\.json$|packages/(contracts|kernel|components|shell)/package\.json$|pnpm-lock\.yaml$|turbo\.json$|\.github/workflows/|apps/platform-e2e/)"; then echo REBASE-NEEDED; exit 3; fi; gh pr merge "$PRN" --squash --match-head-commit "$SHA"'` (the same workaround for `gh pr merge` as PROFILE §Traps). If changes on `main` touch any of the five branches, do not merge; exit with code 3 (`REBASE-NEEDED`) and release the lock, then rebase and restart from (b) (rebasing creates a new head, so CI must be awaited again; do not put rebase under `merge.lock`). If exit code 75 means the lock is held (usually while a shared-path PR runs CI), rerun all of (c) from its checks; do not merely repeat the same `with-lock.sh` command. The "retry once after 5 minutes" in the blocker report also means rerun all of (c). If merge is rejected due to a conflict, restart from (a) without a lock.
    - **(d) Aftercare:** Wait for the merged commit's push run (`gh run list --branch main --event push --limit 1`) to finish (if red, follow the `main 깨짐` (main broken) procedure below), verify the issue is closed, archive `.review/` to `$WAVE_BRIEFS/<n>/`, clean up the worktree and terminal, delete the remote branch, and run `plan-graph.py mark` if this is a graph. If a semantic conflict between two PRs that passed CI at the same time lands on `main`, push CI catches it; follow the `main 깨짐` procedure below.
  - **Shared-path PR (only the five branches in §Shared paths above):** Run the entire `ship-pr.sh` process (rebase → CI → merge) under `merge.lock` (`with-lock.sh merge.lock "<purpose> ship" -- <ship-pr.sh …>`). This prevents semantic conflicts between these PRs during CI. Documentation rows, `menus.ts`, 06 contract docs, and the FO bridge list are excluded.
  - **Release lock (shared-path PR):** If `ship-pr.sh` exits with rebase conflict (20), CI failure (21), or CI timeout (22), release `merge.lock` **before fixing or re-verifying**. Acquire it again when shipping after the fix. Running `ship-pr.sh` inside `with-lock.sh` releases the lock when the process exits.
  - After merge, if `main` CI fails, send `<flow>: main 깨짐` (main broken) and fix it. The lead pauses merges by other flows meanwhile.
- **Full E2E (only to reproduce a CI failure):** Notify the lead in one line at the start and end.
- **Duplicate check before filing:** Before opening a new issue (intermittent test failure, trap, follow-up), flow sessions check open and recently closed issues with `gh issue list --state all --limit 20 --search "<keyword, test name, file>"`. If the cause is the same, do not open a new issue; add a comment to the existing issue instead (`.planning/README.md` line cleanup is the lead's responsibility).
