# 플랫폼 구축 병렬 리서치 지시서

작성: 2026-09-22. 요청 모델: GPT-5.6 Luna / reasoning max. 상태: 조사 및 제안; 채택·구현 승인 아님.

## 목적

메뉴를 늘리는 대신 Platform Kernel을 가장 적은 불필요한 구현으로 견고하게 만들 방법을 찾는다. 기능·성능·운영·오픈소스·기존 자산 재사용을 함께 비교하고, 기존 문서에 무엇을 유지/보강/대체/보류하면 좋은지 구체적으로 제안한다. 인기 라이브러리 목록이 아니라 이 저장소의 계약을 만족하는 선택 근거가 결과물이다.

## 모든 조사자의 필수 작업

1. 현재 cwd와 Git 상태를 확인한다. AGENTS.md, docs/INDEX.md, docs/00_overview.md, docs/05_roadmap_and_open_questions.md, docs/06_platform_ui_contract.md를 읽는다. 06은 전체를 분할해서 읽고 담당 영역은 상세 검토한다. 관련 01/02/03/04/07, DESIGN.md, PLATFORM_REQUIREMENTS.md, integration 문서를 추가로 확인한다. 과거 보고서는 탐색 단서이며 현행 계약이나 구현 증거를 대신하지 않는다.
2. 공식 문서·공식 저장소·LICENSE·릴리스/지원 정책 같은 1차 출처를 웹으로 현재 확인한다. 검색에 내부 코드·비공개 URL·고유 데이터는 보내지 않고 일반 기술 질의만 쓴다. 출처 링크, 확인일, 적용 버전/에디션을 기록한다. 유료 경계·임베딩 제한·라이선스가 불명확하면 확인 불가로 남긴다. 성능 광고를 실측으로 쓰지 않는다.
3. 재사용 주장은 실제 코드의 경로와 심볼, 현재 커밋을 근거로 한다. 존재/로컬 검증/실서비스 검증을 구분한다. 서브모듈 및 다른 로컬 저장소는 읽기만 한다. 하위 AGENTS.md를 따른다. 파일이 없으면 과거 보고서를 근거로 구현 존재를 단정하지 않는다.
4. 각 주요 선택에서 직접 최소 구현, 작은 OSS 라이브러리, 완제품/기존 자산 재사용을 비교한다. 제품 전체 교체와 일부 기능 채택은 별개다. 3~5개의 실질 후보에 집중하고 채택 불필요한 이유도 기록한다.
5. 팀 언어·데이터량·동시성·배포·SSO 등이 Open이므로 단일 수치/기술을 확정하지 않는다. 가정별 선택 분기와 결정을 바꾸는 증거를 제시한다.

## 지켜야 할 경계

- 기존 계약을 조용히 바꾸지 않는다. Decided/Candidate/Open/Deferred를 구별한다. 바꾸는 것이 낫다면 정확한 충돌·편익·마이그레이션 영향과 별도 결정 필요성을 명시한다.
- naive wall-clock, half-open 구간, 시간역 병합 서버 검증, URL의 권한 비증명, 매 요청 Scope 검증, 계산 완료 세대와 원천 watermark의 구분을 보존한다.
- 범용 플러그인/위젯/승인/알림 엔진, 저장된 뷰, 외부 BI는 현재 제외/Deferred 상태를 먼저 확인한다. 조사할 수 있지만 도입을 확정하지 않는다.
- FeedbackOps는 독립 제품이다. 플랫폼 계약을 소급 강제하거나 shared/ui를 자동으로 플랫폼 공용이라고 간주하지 않는다.
- 소스·공식 설계 문서·의존성·서브모듈 참조 수정, 설치, 서버 실행, 마이그레이션, commit/push, 외부 게시 금지. 지정 보고서 하나만 작성한다. 리서치용 공개 웹 읽기는 요청 범위다.
- 실제 부하 테스트나 POC를 실행하지 않았다면 검증 계획으로만 표시한다. 보안·라이선스 법률 적합성을 확정하는 표현을 피한다.

## 보고서 형식 (한국어)

1. 핵심 권고 5개 이내와 현재 가장 먼저 피해야 할 실패.
2. 현행 상태: 문서 계약 / 구현 존재 / 미확인 사항을 분리하고 경로·절·커밋을 제시.
3. 후보 비교표: 문제, 후보/버전·에디션, 계약 적합/공백, 라이선스·유료 경계, 운영/통합/이탈 비용, 권고(유지/보강/대체후보/참고/보류/제외), 근거.
4. 항목별 적용 카드(가치 있는 6~10개): ID, 사용자/운영 문제, 현재 근거, 제안, 자체 소유할 책임, 재사용 경계, 실패 모드, 최소 검증과 합격/탈락 기준, 우선순위 및 선행 조건, 반영 대상 문서·절과 추가/수정할 문안 요지, 확신도.
5. 추천 최소 조합과 대안: 선택이 바뀌는 조건, 지금 도입하지 않을 것, 작은 수직 검증 흐름. 수치 목표는 측정 전 가정이라고 표시.
6. 충돌/중복/미결 질문: 사용자에게 필요한 질문은 최대 5개, 답이 없을 때 가능한 판단 범위 포함.
7. 출처 목록과 검증 한계. 각 중요 사실 가까이에 링크/코드 근거도 배치.

## 병렬 담당과 출력 소유권

- A: 플랫폼 기능·프론트엔드·OSS 대체 가능성 → `01-kernel-frontend.md`. Router/URL codec/공개 스키마, Query 캐시·취소·세대, 테이블·차트·접근성, 메뉴 확장·관측 가능한 상태, BI/admin framework 재사용 경계. FeedbackOps UI는 읽어도 인증/업무 통합 상세는 C에게 맡긴다.
- B: 데이터 계약·성능·백엔드·운영 → `02-data-performance-operations.md`. PostgreSQL view/mart/재집계, 원자적 세대 공개·chart/table/CSV 일치, 조회량·취소·내보내기, 관측성·복구·계약 테스트, SQL-first와 작업 실행 도구, 규모별 확장 분기. 인증 구현 비교는 C에게 맡긴다.
- C: 기존 구현 재사용·인증/권한·제품 통합 → `03-reuse-security-integration.md`. FeedbackOps 실제 코드 중심으로 사용자/SSO/권한/Scope/Audit/알림/업무 흐름 소유권, 원본 로그·계보 서비스 연계, build-vs-reuse-vs-adapt. 필요시 OSS 인증/정책/업무 제품을 비교하되 새 엔진 도입 필요부터 판단한다.
