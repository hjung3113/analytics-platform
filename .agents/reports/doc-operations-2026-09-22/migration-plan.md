# 단계별 이행 계획과 첫 작업 지시서

모든 단계는 후속 작업 제안이며 아직 적용하지 않았다. 본 패키지의 권고가 제품 결정을 승인하지 않는다. 현재→목표는 operating-model §2, 보존할 의미는 current-map과 대표 검증에 있다.

## 첫 번째 작업: M1의 구체적 패치 범위

담당 에이전트는 아래 지시로 시작할 수 있다. commit/push 권한은 별도 세션 지시에 따른다.

1. `git status --short`, HEAD와 AGENTS/INDEX를 읽는다. source-snapshot과 달라진 대상이 있으면 해당 본문만 재검토한다. FeedbackOps 내부/참조는 쓰지 않는다.
2. 대상 파일은 `docs/INDEX.md`, `docs/03_backend_stack.md`, `docs/04_frontend_ui_ux.md`, `docs/07_app_shell_wireframe.md` 네 개다. 첫 patch에서 06/DESIGN/05 본문 이관을 하지 않는다.
3. INDEX에서 `../DESIGN.md`=시각 token/render 원본(전역 행동·접근성은06), `../PLATFORM_REQUIREMENTS.md`=파생 작업·제안 목록, `../HANDOFF.md`=세션 배경으로 실제 상대 경로를 링크한다. 메뉴 구현은 06 관련 계약→02→07/해당 화면→04 후보 순서로 안내한다.
4. 03 '시간 계약'의 원천 wall-clock 설명은 유지한다. 'Phase 0에서 ... 결정' 목록을 확정 메커니즘의 06 §6.3 참조와 실제 TZ/다중 사업장 날짜 Open 입력으로 분리한다. UTC 분석 API 영구 금지 같은 새 의미를 추가하지 않는다.
5. 04의 '구체 URL API·버전·잘못된 값 ... Open 결정 해결' 문장은 메커니즘 원본 06 §6.4 / 공개 필드·artifact Candidate를 나눠 참조한다. 라이브러리 채택하지 않는다.
6. 07 §6의 문장 샘플: “URL에서 복원된 요청 Context와 목적지 객체 ID를 구분해 표시한다(전역 계약 §6.1). 직렬화·충돌 메커니즘은 전역 계약 §6.4를 소비하며, 공개 필드명·enum의 Candidate 상태는 원본을 따른다.” §8의 올바른 혼합 상태는 그대로 둔다.
7. diff를 검토해 바뀐 것은 경로/상태 안내뿐인지 확인한다. 숫자·권한·URL·시간 의미·기술 선택 변경이 발견되면 patch를 분리하고 결정 근거를 요청한다.
8. 링크 대상 존재·기존 제목 유지·07 §7 시나리오 표의 원본 참조·`git diff --check`와 V1/V2 문서 워크스루를 수행한다. 01/02의 남은 Phase 표현 등 이번에 정정하지 않은 범위도 기록한다. runtime 없으므로 runtime test를 꾸며내지 않는다. 변경 4개 파일, 보존한 예외, 미결/미실행을 보고한다.

### M1 수용 기준

신규 작업자가 INDEX에서 DESIGN과 06의 경계를 발견한다. 03/04/07을 읽어 이미 확정된 URL/시간 메커니즘을 다시 Open으로 오해하지 않는다. 실제 TZ와 Scope hierarchy·상속·복수 선택·소속 규칙은 Open, 공개 필드명·구현 형식은 Candidate/미채택 상태를 유지한다. 단일 요청 scopeId와 서버 재검증은 Decided로 보존한다. 기존 문서 링크와 외부 사본/서브모듈은 유지된다. 이 결과는 문서 안내 정정이지 제품 구현 시작 승인이 아니다.

## 이관 전 반드시 할 의미 보존 매핑

본문을 옮기는 M4는 전체 파일 삭제/정리 작업으로 수행하지 않는다. 예를 들어 05 지연완료 절은 (필수 H 설정 없음→자동 시작 안 함), (창 안 자동), (창 밖 식별/조회 후보), (`autoRefreshClosed` 의미), (다른 재계산 트리거), (R 소유/naive/정밀도/첫 세대 전 공급), (`[R-H,R)`), (원천 멈춤), (R 부재 예외), (override/horizon 미구현≠영구 금지), (근거 링크)를 별도 행으로 old→new 대응한다. 새 위치를 먼저 읽고 원래 의미가 모두 회수되는지 역대조한 뒤 옛 위치는 안내만 남긴다.

후속 작업에서 새로운 사용자 결정이 생기면 기존 제안과 충돌 여부를 기록하고 목표 구조를 수정한다. 이 계획 자체를 불변 계약으로 취급하지 않는다.
