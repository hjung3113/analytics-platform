## 논점 1 — 05 3열 확장 vs 원본 인접 관계 vs INDEX 행렬

**root-r2 반박에 대한 응답.** "설계 상태와 증거가 같은 행에서 독립적으로 늙는다"는 지적을 수용한다. 반례가 정확하다: 시간 메커니즘 Decided + TZ 공급자 미구현 + decoder만 검증됨은 결정 1건에 대해 서로 다른 속도로 노화하는 상태이고, '증거 있음' 한 칸은 이를 표현하지 못한다. 증거의 자연 단위는 결정이 아니라 산출물이다. **자기 수정: 05에서 `증거` 열을 철회한다.** 증거는 작업 기록(commit+경로, 검증이면 명령+결과+기준 source revision)이 소유하고, 05 행은 그 기록으로의 링크도 지금은 두지 않는다(코드 부재 시 링크 대상이 없으므로 열 자체가 위조 유혹을 만든다). 구현 착수 시점에 작업 기록 문서의 위치를 정하고 그때 링크를 논한다.

**소비자 열은 방어한다.** 변경 작업 중 에이전트가 실제로 여는 파일은 원본 섹션과 05 행이다. 소비자 목록을 원본 섹션 인접에 두면(root의 대안) 계약 문서 본문에 운영 레지스트리 데이터가 섞이고, 매 문서가 자기 소비자 목록을 자가 보고해야 한다(등록 누락 시 침묵). Grok의 INDEX 권위 행렬은 발견에는 좋지만 변경 시 열리지 않고, "지금 섹션 상태" 열을 포함한 대형 표는 Grok 자신이 실패 모드 1로 인정한 "제4 원본" 위험이 있다. **절충 수정안: 05 행 = 상태 토큰 + 결정명(명사구) + 원본 좌표 + 근거 링크 + 소비자 목록. INDEX = 소유권·역할·경로만(상태·소비자 열 없음).** 여기서 "추가 수동 원본"은 상태 토큰 하나뿐이고 이는 원본 섹션 제목과 같은 어휘 토큰의 반복이지 규칙 서술이 아니다. 내 R1이 유지하려했던 05 요약 문구(규칙 재서술에 가까웠음)도 축소한다 — 결정명 수준, 규칙 문장 금지.

**05의 R/H 소유 보존.** 세 안이 수렴했다: 지금 05 "지연 완료 허용 시간" 절이 R/H 메커니즘의 상세 원본이고 06 §6.3이 인용한다(재확인: 06 원문 "정의는 `05_roadmap_and_open_questions.md`의 '지연 완료 허용 시간' 참조"). 내 R1 샘플이 원본 열에 06 §6.3과 05 절을 병기한 것을 유지하되, Grok의 **쌍 잠금** 규칙을 채택해 명시한다: 이 쌍은 하나의 작업에서만 함께 수정한다. 05→06/01 이관은 문서 OS 설치의 선결 조건이 아니며, URL/시간/지연완료를 실제로 다시 여는 작업이 올 때 별도 변경으로 수행한다(root-r2와 동의).

## 논점 2 — 안정 ID/anchor vs 섹션 번호

**자기 수정: `06§6.3-time` 형태 좌표 ID를 철회한다.** 실패 사례로 자체 검증: (a) 섹션 분할 — §6.3이 둘로 나뉘면 좌표 ID의 소속을 사람이 배정해야 한다. ID 체계가 사람 판정을 요구하면 ID의 이득(기계 안정성)이 없다. (b) 부분 발췌 이동 — 규칙 하나가 §6.3→§6.4로 옮겨가면 좌표 ID와 semantic anchor가 똑같이 깨지고, 탐지 가능한 수단은 규칙 키워드 grep뿐이다. (c) 리네임 — heading 개명은 좌표 ID에 무영향이지만, 현행 참조 관습은 §번호 prose("06 §6.3")라 번호가 이미 사실상의 키다.

**채택하는 대안:** 초기에는 현행 prose 참조를 그대로 쓴다. 섹션 번호 재부여를 금지로 만들지 않고 **변경 이벤트**로 정의한다 — 재부려면 소비자 문서의 §인용을 구조 검사로 일괄 탐지해 같은 작업에서 갱신. semantic anchor는 고위험 계약(지금이면 06 §6.1–§6.4, §19)을 **실제로 처음 변경할 때** 해당 섹션에만 선택 도입하고 구 anchor는 alias로 남긴다(root 안). 전 문서 metadata·frontmatter 강제는 불필요 — 동의하며, 이는 내 R1 구조 검사 (5)(Status 헤더 부재 탐지)도 "경고 후보" 이상으로 쓰지 않는다는 뜻으로 수정한다.

## 논점 3 — 충돌 처리: 두 규칙 모두 폐기

**자기 수정: "행 단위 마지막 갱신 승리"를 철회한다.** 인덱스 행 병합의 타이브레이커로 보였지만 root 반례가 옳다: 집합 키 중복 제거 구현과 단일 `scopeId` 중복 거부 수정이 각각 올바르게 반영된 뒤, 잘못된 공통 요약 "중복 키 모두 오류"가 마지막 기록이면 그 요약이 원본 06 §6.1의 두 구분(집합=중복 제거, 단일값=같은 값이어도 형식 오류 — 원문 재확인)을 지워버린다. 승인 없이 의미를 바꾸는 규칙이다.

**Grok의 "더 구체적인 금지/예외 임시 우선"도 반대한다.** root-r2 반례에 동의하고 원문으로 보강한다: "R 부재 시 분석 전면 금지"에 가까운 연구 문구가 아무리 구체적이어도, 06 §6.3 원문의 명시적 허용 예외("R이 아직 없는 경우… `defaultRangeTo`가 독립적으로 유효하면 그대로 자동 물질화하고, 자동 재집계만 보류한다"; §6.4 "단일 설비 naive 조회는 계속 허용… 전면 금지하지는 않는다")보다 우선할 수 없다. 구체성은 권위가 아니며, 구체적인 잘못된 요약이 구체적인 올바른 예외를 이기는 역전이 이 규칙의 예측 결과다.

**채택:** 권위를 판정할 수 없으면 현행 승인 baseline 유지 + 새 의미 변경만 보류 + 조정은 신규 review 문서에 판정자 명시로 기록. 과거 근거 문서를 갱신해 정정하는 대신 후속 기록을 남긴다(root "감사 반복 방지" 논점 수용).

**관계 표 완전성에 대한 반박(요청된 예).** FE 에이전트가 `04` 라우팅 행에 "집합 키는 반복 키 직렬화, 카디널리티 1 키 중복은 오류"를 올바르게 쓰는 동안, BE 에이전트가 장차의 API 문서에 "요청 파라미터는 단일 값만, 콤마 결합 허용"을 쓰면: 서로 다른 파일이므로 Git conflict가 없고, 두 문서 모두 링크·§인용 구조 검사를 통과하며, 둘 다 05 행을 건드리지 않아 나의(폐기된) 행 승리 규칙은 아예 발동하지 않는다. 이것은 같은 결정의 충돌이 아니라 원본(06 §6.1 "콤마 결합은… 채택하지 않는다")으로부터의 **독립 이탈 2건**이다. Grok의 쓰기 잠금도 막지 못한다(잠금은 원본 파일 하나에만 걸린다). 방어는 3층뿐: (a) 소비자의 규칙 재서술 금지·포인터 의무, (b) 재서술이 불가피하면 원본의 예외 조건을 누락 없이 옮기는 의무, (c) 키워드 구조 탐지("콤마", "equipmentIds=" 등이 06/reviews 밖에 나타나면 후보 지명). 결론: **관계 표(소비자 목록)는 완전성 장치가 아니라 탐색 비용 절감 장치다.** 완전성은 보장할 수 없고(신규 소비자 파일은 등록 없이 생긴다) 그렇게 광고해서는 안 된다. root가 R1에서 이미 인정한 한계("수동 영향 표는 소비자 증가로 stale해질 수 있다")를 공식 명세로 채택하자.

## 논점 4 — REQUIREMENTS 체크박스와 HANDOFF 역사

**자기 수정.** 내 R1 "체크박스 갱신 유지"는 결정 반영([x])과 미완료 작업([ ])이 같은 기호를 공유하는 문제를 방치했다 — 체크박스는 본질적으로 완료/미완료(delivery 성격) 부호이므로, 이 파일 안에서 결정 상태와 delivery가 계속 섞인다. Grok 지적에 동의. 다만 즉시 파일 재구조는 비용이 크고 이 파일의 지위는 비권위 통합 요약이므로, **최소안**: 머리에 "§0 `[x]`는 결정의 문서 반영 완료, 이후 `[ ]`는 미완료 작업이며 구현 완료가 아니다" 한 줄 + 각 행이 05 행 또는 원본 절을 가리키게 변경. `[N/3]` 재집계는 중단(동의). 구현 단계 진입 시 이 파일 전체가 실제 백로그로 대체될 수 있음을 그때 결정한다.

**HANDOFF 문장 제거(Grok) vs 역사 보존(root) — root 편을 든다.** HANDOFF는 스스로 "기록이며 Git 상태의 대체물이 아니다"라고 선언한 세션 기록이다. "05와 REQUIREMENTS에 함께 반영" 문장의 운영 효력은 새 운영 안내가 반영 위치를 지정하는 순간 소멸하고, 문장을 지워서 얻는 이득은 그것뿐인데 비용은 "이중 갱신 관례가 왜 존재했는지"라는 감사 흔적의 소거다. 이익 < 비용. 대체 주석("본 운영 문장은 2026-09-22 안내로 대체됨")은 본문 삭제가 아니므로 허용한다.

## 논점 5 — 기계 검사의 한계 (자기 과장 정정)

내 R1 "소유권 위반은 구조 검사에서 반려 사유"는 과장이었다. **위반의 판정은 시맨틱이고, 구조 검사는 후보 지명만 한다.** 정확한 경계:

- 기계 가능(리터럴 일치·존재 검사): 상대경로·파일 존재; 타 문서의 "§N.M" 인용이 06에 대응하는 헤딩 존재; 06 머리말 섹션 상태 목록 ↔ 섹션 제목 상태 태그 일치(둘 다 리터럴); 소비자 문서의 상태박힌 문구 패턴("§6.4의 Open 결정", "Phase 0에서 결정한다" — 재확인된 실제 stale 문구들) 탐지(Grok 금지 패턴, 채택); docs 신규 파일의 Status 헤더 부재 탐지.
- 기계 불가(사람·모델 리뷰): 재서술이 예외를 보존하는지(논점 3의 콤마 사례 — "콤마"라는 단어가 없는 패러프레이즈는 grep을 통과한다), 요약의 진부화, 소유권 배정의 정당성, `[N/3]`과 원문의 실제 대응, 06↔DESIGN 숫자·의미 동기화.

grep은 오탐·미탐을 모두 내므로 산출물은 "경고 목록"이지 판정이 아니다. 이 문장을 규칙에 명시한다.

## 논점 6 — 06 §6.3 원문 대조와 분리 샘플

원문 재확인으로 확보한 예외 목록: (1) R 부재 시 `defaultRangeTo` 독립 유효하면 자동 물질화 지속·자동 재집계만 보류; (2) 단일 설비(또는 동일 wall-clock 확인 집합)는 TZ 미확인이어도 naive 조회 허용, §6.4도 전면 금지 안 함; (3) 실제 TZ 값·Δ·H는 Open; (4) 병합 가드 위반은 `time_domain_unverified`/`time_domain_mismatch` → `outcome=error`이며 경고 후 병합으로 위장 금지.

**독립 sample-time-contract.md 반대.** 이 예외들은 요약·발췌에서 가장 먼저 소실되는 부분이다(root R1의 실패 모드: 검색 발췌가 §6.3 예외를 잃으면 "TZ 미정 = 전면 차단"으로 오독). 시간 계약의 요약 사본은 이미 05 행·grilling §3·`03`·`07` §8에 4개 존재하며, 5번째 독립 파일은 예외 소실 위험만 추가한다. 대안: 시범 샘플이 필요하면 **05 행 형태**로 예외를 명사로 열거한다("R 부재 시 독립 물질화 예외 / 단일 설비 naive 조회 허용 / Δ·TZ 값 Open / 병합 가드 error 결과") — 규칙 논리의 재서술이 아니라 원본으로의 안내표. 규칙 원본은 06 §6.3 한 곳으로 둔다. root의 "defaultRangeTo 1개 샘플로 원본/파생/영향 trace"는 trace 기록이 계약 사본이 아니라는 조건에서 동의한다. 덧붙여 `DESIGN.md` "Date preset meaning" 항목이 이미 올바른 형태의 선례다 — 프리셋 의미를 결정하지 않고 "use server defaultRangeTo… retain §6.3 explicit half-open URL ranges"로 원본을 가리킨다(재확인).

## 논점 7 — 채택 승인 주체 3층

(1) **제품 채택**(라이브러리·스택·메뉴 신설·integration 후보 편입·지표/시간/권한 정책의 값 확정) = 사람 승인 필수. 모델 합의·다수결 불가 — 06 머리말 "독립 초안끼리 일치해도 승인으로 간주하지 않는다", research README "모델 간 동의는 실행 검증이나 제품 결정과 구분"이 이미 규범이다. (2) **명시적 위임된 엔지니어링 결정** = 위임 범위 내에서 에이전트가 실행하고 근거를 기록한다. 실존하는 위임 사례: HANDOFF의 사용자 지시("넓게 모아두고 나중에 한 번에 정리")가 수집·정리 권한을 위임했다. 원본이 명확한 stale 정정(예: `04` "계약 문서의 Open 결정을 해결한 뒤 구현" ↔ 06 §6.4 Decided — 재확인된 불일치)도 정정 방향이 유일할 때 문서 정합 위임으로 처리 가능하다.
