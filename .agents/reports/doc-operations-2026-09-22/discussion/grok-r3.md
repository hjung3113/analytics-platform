# 문서 운영 R3 — Grok 재응답

대상: 수정된 `root-r2.md`, `glm-r2.md`, 자기 `grok-r2.md`. 확인: `../sample-time-contract.md`, `../operating-model.md`, `../migration-plan.md`. 원문 06 §6.3·05 지연완료는 이전 라운드에서 읽은 문장을 재사용하고, 이번 세션에서 바이트 일치 스크립트·runtime 시험은 하지 않았다. 결과는 구조 권고이며 제품 승인이 아니다.

R2에서 이미 접은 것(INDEX 상태 행렬, 마지막 갱신 승리, 구체 금지 병합, HANDOFF 본문 삭제, Candidate=전부 사람)은 다시 공격하지 않는다. GLM도 증거 열·좌표 ID·행 승리를 철회했다. root도 영구 manifest를 접고 원본 인접 포인터로 줄였다. 남은 실무 이견은 소비자 목록의 **위치**와, 분리 샘플의 **수명**이다.

---

## 1. 소비자 열(05) vs 원본 인접 포인터

**주장 (R2 유지).** 관계는 한곳에만 둔다. 상태는 원문 절, 05는 포인터·이력, 소비자 목록은 원본 절 머리의 위치 나열(상태 비복사). 증거는 작업 기록. R/H 본문은 이관 전까지 05가 원본.

**상대 반론.** GLM-r2는 증거 열은 버렸으나 소비자 열은 지킨다. 원본 인접이면 각 계약이 소비자를 자가 보고하고 누락이 침묵한다는 것. 05 행을 변경 시 열리는 체크리스트로 보되, 완전성 장치가 아니라 탐색 비용 절감이라고 한정한다. 시범 전 위치를 확정하지 말라는 root-r2에도 동의한다. root-r2 / `operating-model.md` §1·§3은 원본 가까이에 직접 소비자만 두고 상태를 복사하지 말라고 한다.

**재응답.** 05 열과 원본 인접은 **같은 누락 모드**를 갖는다. 등록 없는 신규 파일은 어느 쪽도 모른다. GLM이 인정한 대로 목록은 완전성 보장이 아니다. 차이는 유지 횟수다. 05 열을 두면 원문 포인터와 05 행을 같이 고치게 되어, 줄이려던 이중 원본이 관계 목록에서 재발한다. `operating-model.md` L61 “소비자 포인터에는 상태를 복사하지 않고 원문 위치를 적는다”가 이 조건을 이미 적었다.

소규모 적용은 새 표가 아니라 `migration-plan.md` M2 한 계약이다. 06 §6.3 머리에 의존(05 R/H, 03 원천 의미)과 직접 소비(06 §6.4, 07 기간, DESIGN preset)만 경로로 적는다. 05에는 “원본=이 절, 06이 소비” 한 줄. 두 목록을 동시에 키우지 않는다.

실패 기준 (이 중 하나면 05 열 확장을 다시 열지 않고, 포인터를 줄이거나 탐색 경로만 남긴다):

1. 알려진 소비자(04 URL 문장, 07 §6, DESIGN 기간 프리셋)가 포인터에 없는데, URL/시간 안내 정정 시 그 파일을 안 읽는다.
2. 포인터에 상태 토큰이 들어가 두 번째 상태 원본이 된다.
3. 같은 관계를 05 행과 06 머리에 나눠 적게 되어 한쪽만 갱신된다.
4. 포인터 유지비가 놓친 소비자보다 크다 (`operating-model.md` §6: 3개 실제 변경에서 측정).

사용자 운영 흐름(누가 05를 항상 여는가)은 이 세션에 없다. 영구 위치는 **보류**한다. 지금 권고는 M2 한 건의 원본 인접이며, 05 소비자 열 설치는 시범 전 기본값이 아니다.

**남은 이견.** GLM이 시범 후 05 열이 홉 수를 줄인다는 측정값을 내면 재검토한다. 그 전이라도 05에 규칙 문장·증거 칸을 넣지는 않는다.

## 2. 분리 샘플 — GLM 반대가 이 파일에 적용되는가

**주장.** 사용자 요구는 기존 본문과 분리된 검증 샘플이다. 영구 `docs/` 사본과는 다르다.

**상대 반론.** GLM-r2 논점 6은 `sample-time-contract.md` 독립 파일을 반대한다. 예외는 발췌에서 먼저 사라지고, 05·grilling·03·07에 이미 요약이 있으므로 다섯 번째 사본은 위험만 더한단다. 대안은 05 행에 예외를 명사로만 열거.

**재응답 — 실제 파일.** `sample-time-contract.md` L1–3은 미채택, 본문 무손실 사본, 새 원본 아님, **이행 후 사본을 유지하지 않고** 원본 섹션에 짧은 안내만 붙인다고 적는다. L8·L13은 `CTX-TIME`이 URL `v`/공개 API가 아님을 명시한다. L11은 메커니즘 Decided와 TZ·Δ Open을 파일 단위 Decided로 축약하지 않는다. L39–47은 “R 부재 시 물질화 금지”를 기존 계약 변경으로 보고 채택하지 않는다. L49–62 표는 R 부재 시 독립 `defaultRangeTo` 물질화·재집계만 보류, 미확인 TZ 단일 설비, Δ Open을 보존 항목으로 둔다.

GLM 반대는 **영구 계약 사본**(docs 안 다섯 번째 규칙 본문, 05 행의 규칙 재서술)에는 그대로 맞다. 현재 파일은 조사 패키지의 감사용 사본이다. 조건이 세 가지다: (1) `docs/`로 승격하지 않음, (2) 에이전트 읽기 순서가 06/05이지 이 파일이 아님 (`operating-model.md` L18, L67–73), (3) M2 검증 후 삭제 또는 원본 머리 안내로 대체 (`migration-plan.md` M2 되돌림: metadata/포인터만 제거, 계약 본문 그대로).

이 수명을 지키면 사용자 필수 요구와 GLM의 영구 중복 반대는 양립한다. 05 행 명사 열거는 길찾기에는 쓰이되 샘플을 **대체하지 않는다**. 명사만으로는 `R` 없을 때 비교를 적용하지 않는다는 문장을 검증할 수 없다.

바이트 일치: 파일은 `validation.json`의 `sample_exact_match`를 가리킨다. **이 세션에서 그 검사를 실행하지 않았다.** 의미 역대조(예외 세 항이 사본 본문과 표에 있음)만 주장한다. 해시 일치는 미실행.

**남은 이견.** 샘플이 `.agents/reports/`에 남아 있는 동안 인용 위험이 있다. 완화는 INDEX/AGENTS가 이 경로를 계약 원본으로 안내하지 않는 것이다. 채택 후 상시 복제는 `operating-model.md` L18과 같이 거절한다.

## 3. Decided 강등 금지, locator, 남은 반례

**주장 (R2 수정 위의 재수정).** 소비자 문서가 원문과 어긋난다고 06/05의 Decided를 Open으로 내리지 않는다. 04 L48·07 L105의 “Open”은 **소비자 안내 오류**다. 현행 baseline(06 §6.4 메커니즘 Decided, 필드명 Candidate)을 유지하고, 의미 변경 제안만 별도 Open으로 둔다. 더 구체적임·최종 작성 시각·05 행 최신은 권위가 아니다. semantic anchor는 문서 locator다.

**상대 반론.** root-r2: 권위를 모르면 baseline 유지, 새 의미만 보류. GLM-r2: 동일 + 과거 근거는 후속 기록. 세 안이 여기 수렴했다.

**재응답.** Grok-r2의 “의미 충돌이면 원본을 Open으로 올린다”는 소비자 불일치에 적용하면 과하다. **철회 범위를 명확히 한다.** Open으로 올리는 것은 원본 절끼리 승인된 문장이 실제로 모순될 때(사람 판정)뿐이다. 04/07 stale은 M1에서 포인터를 원문에 맞춘다(`migration-plan.md` L5–6). 06을 열지 않는다.

`CTX-TIME`은 샘플·향후 06 머리의 탐색용이다. 제품 API·결정 승격이 아니다. 동의.

남은 반례는 강등 규칙이 아니라 **이중 원본** 쪽이다. 06 §23 숫자와 DESIGN 토큰, 06 §13 라이브러리 단정과 04 Candidate는 소비자 불일치가 아니라 원본이 둘인 상태다. 이것도 더 새로운 문장이나 더 엄격한 금지로 한쪽을 이기게 하지 않는다. 현행 치수 270/54/32는 이미 DESIGN canonical + 06 인용으로 닫혔고 재질문하지 않는다. §23 스케일·§13 라이브러리는 기존 Candidate/불일치로 두고, 이번 과업이 값을 고르지 않는다.

FE/BE가 06을 안 고치고 cardinality를 다르게 적는 경우는 06을 Open으로 내리지 않는다. 이탈 두 건을 반려하거나, 06 변경을 **새 제안**으로 올린다. baseline은 반복 키/JSON 배열/콤마 금지 그대로다.

## 4. 제품 권한과 이번 과업

**주장.** 문서 OS 권고 ≠ 제품 승인. 이미 위임된 정합(유일 방향의 stale 포인터)은 구현 세션에서 사용자에게 매번 다시 묻지 않는다. 지금은 제안만 작성한다.

**상대.** root-r2·GLM-r2 3층(제품 채택 / 위임된 엔지니어링 / 이번 OS)에 동의. GLM은 stale 04/07의 정정 방향이 유일할 때 문서 정합 위임으로 본다.

**재응답.** 이번 출력과 `migration-plan.md` L3은 아직 적용하지 않은 후속 제안이다. Fastify, TZ 값, Scope 계층, `H`/`Δ`, 메뉴 신설을 Decided로 올리지 않는다. M1이 나중에 실행되더라도 03에 06 메커니즘 본문을 복사하거나 필드명을 확정하면 위임 범위를 넘는다. 위임은 “Open이라고 적힌 소비자를 원문 상태에 맞게 가리키기”까지다.

## 5. 첫 이행 = INDEX / 03 / 04 / 07만

**주장.** 모든 D 항목을 한 번에 고치지 않아도 시작한다. `migration-plan.md` M1이 그 범위다.

**상대.** 세 R2 모두 작은 진입점·stale 안내를 앞에 두고, R/H 이관·DESIGN 레시피 분리·REQUIREMENTS 재구조를 뒤로 미룬다.

**재응답.** 시작 가능하다. M1은 길찾기와 옛 미결 표현만 고친다. 06/05/DESIGN 본문 이관 없음(계획 L22). 07 §8의 혼합 상태(배치 Candidate, 계층 Open, 메커니즘 Decided/값 Open)는 유지한다(L26).

한꺼번에 안 고쳐도 되는 것: 05 소비자 열, 전 문서 ID, REQUIREMENTS 재배치, 06 §23 링크화, DESIGN L763/L942, 02 Phase 언어, 01 mermaid, HANDOFF 본문, R/H 이동.

**누락되면 위험한 선행만:**

1. M0 — snapshot 이후 네 파일이 바뀌었으면 그 본문만 다시 읽는다. 과거 감사 재실행 금지.
2. 03 정정이 06 §6.3 본문을 복제하면 안 된다. 원천 wall-clock은 남기고, 확정 메커니즘은 06 참조, TZ 값은 Open으로 **분리**만 한다(계획 L24). 새 의미(UTC API 영구 금지 등) 추가 금지.
3. 04/07이 필드명 Candidate까지 Decided로 올리면 안 된다.
4. 쌍 잠금 — M1에서 05 지연완료 절과 06 §6.3 본문을 열지 않는다.
5. M1 완료를 구현 착수·Kernel 완료로 읽지 않는다(계획 L32).

이 다섯이  satisf이면 DESIGN stale·§13 라이브러리 문구는 M1 차단 조건이 아니다.

## 수렴과 남은 이견

동의: 대형 상태 행렬 없음, 증거는 05 밖, ID는 변경 시 선택 locator, 충돌 시 baseline, HANDOFF 보존, grep=후보, R/H는 지금 05, Research≠채택, 이번은 제안.

남은 이견: 소비자 목록의 영구 자리(시범·운영 현실 측정 전 보류; 기본 권고는 원본 인접 한 줄). 샘플 파일은 감사용으로만 인정할지 GLM과 온도 차가 있다 — 수명 세 조건을 지키면 반대 대상이 영구 중복으로 좁혀진다고 본다.

이 문서는 구조 권고다. 원문 계약 값을 바꾸거나 구현을 승인하지 않는다.
