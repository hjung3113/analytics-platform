# GLM R3 — 반론 후 재응답

작성: 2026-09-22. 읽은 것: `root-r3.md`, `grok-r2.md`, `root-r2.md`(R2 시 이미), 세 아티팩트 `../sample-time-contract.md`·`../operating-model.md`·`../migration-plan.md` 전문. 원문 재대조: `06` §6.3(샘플 사본과 문단별 대조), `03` "시간 계약" 4개 결정 후보, `docs/INDEX.md` 역할 표. `validation.json`은 열지 않았다. R1/R2는 수정하지 않고 이 파일만 쓴다.

## 1. 소비자 포인터 위치 — 원본 인접을 조건부 수용

**주장(R2):** 소비자 목록은 05 행. **반론(root-r3/Grok R2):** 고위험 원본 섹션 말미의 짧은 비규범 참조 블록이며 계약 본문 오염이 아니다. 05 전 항목 소비자 명단은 실측 없는 포괄 그래프로 오해된다.

**재응답(수정):** 원본 인접을 시범 배치로 수용한다. 결정적 이유는 내 R2 논거가 스스로를 반례로 만든다는 것이다 — "변경 작업 중 에이전트가 여는 파일은 원본 섹션과 05 행"이라 했지만, 실제 순서는 원본이 먼저이며 05는 원본을 다 읽은 뒤에나 열린다. 원본 인접 블록은 변경이 일어나는 바로 그 지점에서 읽힌다. 오염 우려도 실체가 약하다: 06 머리말이 이미 상태·소유권 같은 운영 선언을 계약 문서 안에 담고 있으므로, 섹션 말미의 "직접 소비: …" 한 줄은 새로운 오염 부류가 아니라 기존 관행의 연장이다(operating-model §3의 최소 안내 예가 정확히 이 형태).

**조건과 실패 기준(이견 보류 해제, M6 데이터로 최종 확정):**

- 조건 1: 포인터는 정확히 한 곳(원본 인접)에만 존재. 05행과의 이중 유지 금지.
- 조건 2: M2 시범은 06 §6.3 단일 계약에 한함(전 섹션 일괄 적용 아님).
- F1 목록 부패 — M6의 3개 실제 변경 중 2회 이상 원본 변경 시 포인터 목록이 미갱신으로 남으면 05행 복귀를 재검한다.
- F2 발견 실패 — 변경 담당이 목록을 읽지 않아 소비자를 놓쳐도, 그 원인이 위치가 아니라 등록·리뷰 게이트 결함이면 위치 이동으로 해결하지 않는다(위치 교체가 가짜 해법).
- F3 이중 유지 적발 — 같은 관계가 두 곳에 있으면 측정 없이 즉시 한쪽 삭제.
- F4 원본 diff 오염 — 계약 문장 변경과 안내 블록 변경이 같은 커밋에서 뒤섞여 리뷰 비용이 커지면 안내 블록을 섹션 말미 고정 영역으로 격리하는 규칙을 추가한다.

**남은 이견:** 없음(조건부 수용). 사용자의 운영 현실을 모르는 상태에서 최종 판정을 내리지 않는다 — ROUND3이 허용한 보류를 M6 측정 시점으로 이연한 형태다.

## 2. 분리 샘플 — 반대 철회, 검증 산출물로 수용

**주장(R2):** 독립 `sample-time-contract.md` 반대. **반론(root-r3):** 사용자가 이번 단계의 분리 샘플을 필수 요구했고, 현 사본은 날짜·원본·상태·수명이 드러난 검증 산출물이며 유지 대상 계약으로 라우팅하지 않는다.

**재응답(수정):** 실제 파일을 읽고 반대를 철회한다. 내 반대는 (a) 규칙을 요약·재서술하며 예외를 잃는 사본, (b) 수명 선언 없이 상설화되는 다섯 번째 원본에 대한 것이었다. 실제 샘플은 이중 어느 쪽도 아니다: 본문 무손실 사본(재서술 부재) + "미채택 제안" 표지 + "이행 후에는 이런 사본을 유지하지 않는다"(수명) + "현재 계약은 원문 링크로 확인"(현행 라우팅). `CTX-TIME`이 URL `v`·metricVersion과 무관한 문서 locator라고 못박은 점(L8, L13)도 논점 3의 anchor 비권위 원칙과 일치한다.

내 검증 범위를 정확히: 샘플의 원문 사본 구간을 `06` §6.3 원문과 문단 단위로 대조했다(서두, 구간 경계, 날짜-only, TZ 미확인, 병합 가드, `defaultRangeTo` 2문단, 근거 링크 문장) — 차이를 발견하지 못했다. byte-exact 여부는 `validation.json`을 열지 않았으므로 주장하지 않는다. 역대조 표의 10개 단위도 원문에서 확인한 예외(R 부재 독립 물질화·재집계만 보류, 단일 설비 naive 조회, Δ/TZ 값 Open, 병합 가드 error 결과)와 일치한다.

**잔여 위험 기록(구조 결함 아님):** 사본은 원문 변경을 따라가지 않으므로, M0 재확인에서 원본 §6.3이 snapshot 이후 바뀌었다면 사본이 "snapshot 시점 실험 증거"로만 쓰이는지 육안 확인이 필요하다. 이는 운용 체크포인트일 뿐 샘플 구조를 바꿀 이유는 아니다.

**남은 이견:** 없음. "영구 중복 금지"는 유지하되, 그 대상은 요약 사본이지 감사용 byte 사본이 아님을 확정한다.

## 3. 강등 금지·baseline·anchor — 동의, 남은 반례 1.5건

**동의:** 소비자 불일치만으로 Decided를 Open으로 강등하지 않는다. 현행 baseline 보존 + 새 의미 변경은 별도 Open. 구체성·최종 작성 시각은 권위가 아니다. semantic anchor는 문서 locator이며 제품 API·승격이 아니다(Grok R2 철회와 일치).

**남은 반례 1 — "강등 금지"를 "재동기 지연"으로 읽으면 안 된다.** `07` §6의 "§6.4의 Open 결정" 문장은 원본(06 §6.4 Decided)·05 표·07 §8 표의 삼중 교차로 stale가 확정된 문장이다. 이를 원본 상태로 되돌리는 M1 정정은 의미 변경이 아니라 정렬이며, 위임된 문서 정정의 범주다. 규칙 문장 제안: **"강등 금지 = 새 승인 없이 원본의 의미를 여는 것의 금지. 원본 상태로의 재동기는 허용되고, 이를 미루면 소비자 오독 비용이 계속 발생한다."** 강등 금지를 stale 방치의 근거로 인용하는 사례를 차단하는 문장이다.

**남은 반례 0.5 — 원본 문서 내부 모순에서는 baseline이 둘 이상이다.** DESIGN Navigation 문단 vs 같은 파일의 정정 문단, `07` §6 본문 vs §8 표가 실례다. 판정 규칙 제안: 소유 문서의 **선언된 상태**(06 머리말/§9 Decided, 07 §8 표)와 일치하는 쪽이 baseline이고 나머지는 정정 후보다. 이 판정 자체는 사람 영역이며, 자동화 대상이 아니다.

**anchor 부가 1줄:** alias는 이전 위치만 가리키고 상태를 갖지 않는다. alias에 상태·설명이 붙기 시작하면 alias 자체가 두 번째 원본이 된다.

## 4. 권한 구분 — R2 3층과 아티팩트 정합 확인

운영모델 §5 "모델 동의는 제품 승인 아님", 이행계획 머리 "이 패키지의 권고가 제품 결정을 승인하지 않는다", M1 수용 기준 "문서 안내 정정이지 구현 시작 승인 아님" — 내 R2 3층(제품 채택=사람 승인 / 명시 위임된 문서 정정=실행 / 이번 과업=제안만)과 모순 없음을 확인했다.

추가로 M1 항목 4의 실현 가능성을 원문으로 검증했다: `03` "시간 계약"의 4개 결정 후보 중 경계 의미(half-open)·UTC 임의 변환 금지·미확인 TZ fallback은 06 §6.3에서 메커니즘 Decided이고, 실제 TZ 값·다중 사업장 "같은 날짜"는 여전히 Open이다. M1의 분리("확정 메커니즘의 06 §6.3 참조 + 실제 TZ/다중 사업장 날짜 Open 입력")는 이 지도를 정확히 반영하므로 의미 보존적이다. "UTC 분석 API 영구 금지 같은 새 의미를 추가하지 않는다"는 경계 문장도 06 §6.3의 원문 예외("별도 UTC 분석 API 자체를 영구 금지하는 것은 아니다")와 정합한다.

**남은 이견:** 없음.

## 5. 첫 이행 4파일 — 시작 가능, 선행 조건 3건

**시작 가능하다.** M1의 정정 대상 네 곳은 모두 이번 토론에서 원문 대조로 이미 확정된 결함이다: INDEX 역할 표의 "개별 프론트엔드 메뉴 구현 → 04 먼저"(재확인: 현행 표가 실제로 04를 첫 문서로 둔다. AGENTS/06 §29의 Platform-first와 역행), `03` Phase 0 목록, `04` "Open 결정을 해결한 뒤 구현", `07` §6 "§6.4의 Open 결정". D 항목 전부를 한 번에 고치지 않아도 이 네 곳은 서로 독립적으로 유효하다.

**선행 조건(누락 위험만, 범위 확장 아님):**

1. **M0 생략 금지.** 이 패키지 작성 중에도 원본은 움직였다(INDEX 등의 수정 시각). snapshot HEAD `2d6fe5a…` 이후 네 파일에 다른 변경이 쌓였으면 M1 문구가 충돌하거나 이미 고쳐진 항목을 다시 연다. M1 지시 1이 이미 이를 요구하므로 실행에서 건너뛰지 않는 것으로 충분하다.
2. **부분 정규화 상태의 기록.** M1은 `01`("Phase 0에서 필드별 원천 소유자… 구분")·`02`(Phase 1~4 배치 문구)의 Phase 언어를 남긴다. 그래서 M1 수용 기준("03/04/07을 읽어 오해하지 않는다")은 01/02 독자를 커버하지 않는다. 블로커는 아니며 M3/M4로 이월되는 항목임을 M1 결과 보고에 한 줄 남기라.
3. **07 §7 표 무결성 확인 포함.** §6만 고치고 §8 표는 동봉 금지(지시됨)가 옳다. 반대편 위험은 §6 문장 교체가 §7 시나리오 표의 "원본 계약" 열 §참조에 영향을 주지 않는지 링크 검사 범위에 넣는 것이다(§7 표는 현재 옳으므로 건드리지 않는 것이 결론, 확인만).

M1 지시 8("변경 4파일, 보존한 예외, 미결/미실행을 보고")은 수행하지 않은 검증을 완료라고 쓰지 않는 원칙과 정합하며 그대로 유지한다.

**남은 이견:** 없음.
