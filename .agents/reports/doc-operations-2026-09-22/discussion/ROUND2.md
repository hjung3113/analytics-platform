# R2 상호 반박 — 공통 지시

R1 3개가 모두 완료됐다. 같은 디렉터리 root-r1.md, grok-r1.md, glm-r1.md를 읽고 각 제안의 실제 주장과 반례를 대조하라. 원본은 같은 source-snapshot이며 변경되지 않았다. R1을 고치지 말고 자신의 *-r2.md만 작성한다. 권장 구조를 강요하지 않는다.

필수: 상대 주장별 근거/반례/동의 또는 반대/자기 수정안/남은 이견. 아래 논점과 5 대표 작업을 구체적으로 검토. 2000~4000자 이상 필요한 만큼 쓰되 반복 원문 복사는 피한다. 주요 이견에는 이후 R3 재응답 기회가 있다.

1. 05에 source+소비자+구현 증거를 모두 넣는 GLM안 vs root의 원본 인접 관계+작업 evidence vs Grok INDEX 행렬. 어느 방식이 상태·관계·증거의 추가 수동 원본을 덜 만드는가? 05 현재 R/H 소유를 어떻게 보존하는가?
2. 안정 ID/anchor 선택 도입 vs 섹션 번호 동결. 리네임·일부 발췌·section 분할 실패 예로 검증. 전 문서 metadata 강제는 필요하지 않을 수 있다.
3. GLM R1 '행 단위 마지막 갱신 승리'와 Grok R1 '둘 다 원본처럼 보이면 더 구체적인 금지/예외 임시 우선'은 승인 없이 의미를 바꾸는 위험이 없는가? root 또한 관계 표가 완전하다고 보장할 수 있는가? Git conflict 없는 서로 다른 파일의 FE/BE cardinality 변경으로 반박하라.
4. REQUIREMENTS checkbox는 결정 완료와 delivery를 섞는다. GLM의 checkbox 갱신 유지로 구분 가능한가? Grok의 역사 HANDOFF 문장 제거는 원본 역사 보존보다 이점이 큰가?
5. 소유권 오류/재정의/상태 일치는 기계적으로 어디까지 확인 가능한가? grep heuristic을 의미 검증이라고 과장하지 말라.
6. 실제 원문 06 §6.3: R 부재 시 독립 defaultRangeTo 물질화 허용·자동 재집계만 보류; 미확인 TZ 단일 설비 조회 허용; 실제 TZ/Δ Open. 신규 sample-time-contract.md(분리 proposal)를 원문과 비교 가능. 필요한 경우 원문을 직접 읽어 예외 소실을 확인.
7. Candidate→채택은 모두 사람 신규 승인만 허용하는가, 아니면 이미 명시적으로 위임된 엔지니어링 결정 권한도 존중해야 하는가? 이번 문서 OS 권고가 제품 승인으로 바뀌지 않아야 한다.

이번 출력은 문서 운영 제안 평가다. 원문·제품·submodule·다른 산출물 수정 금지. 05/INDEX/원본 관계 위치 선호에 관해 대안을 스스로 제시해도 된다.
