# 주 에이전트 독립안 R1

상태: 문서 운영 제안. Grok/GLM 신규 독립안 열람 전 작성. 기준: 공통 BRIEF와 source-snapshot. 주 에이전트의 실제 모델은 세션이 공개한 GPT-6 계열이며 구체 배포 모델/effort는 별도 증거 없이 단정하지 않는다.

## 문제와 보존 경계

원문 확인: AGENTS, INDEX, README/HANDOFF, 00–05, 06 §1–11/15–19/21–31, 07, PLATFORM_REQUIREMENTS 전체; DESIGN 토큰 이름 검색 및 Overview/Sources/Layout/Navigation/Shared interaction/Open Decisions 본문. 전체 DESIGN 토큰 값 검증, 외부 소스 실행/최신성 확인은 아직 하지 않음.

- INDEX의 역할 표에서 개별 메뉴 구현은 04부터 읽는다. AGENTS/06 §29의 Platform Done 우선과 실제 독서 순서가 어긋날 수 있다. 06 관련 계약→02 선택 도메인→07/화면 spec→04 후보 순서가 더 안전하다. 전체 06 매번 정독은 과하다.
- 03 '시간 계약'은 half-open·미확인 TZ 처리를 Phase 0 결정 대상으로 남겼지만 06 §6.3은 확정. 04 '정보구조·Context·딥링크'는 버전/잘못된 값 처리를 Open 해결 후 구현이라 기술하지만 06 §6.4에서 메커니즘 확정. 상태 요약이 원문보다 뒤처졌다.
- 05는 결정 색인이라고 선언하지만 폴링/DB 접근/지연완료 R,H 정책의 유일한 상세 원문을 실제 소유한다. 즉시 옮기면 06 §6.3의 R 링크까지 잃는다. 현재 권위를 먼저 명시하고 나중에 정확한 단위로 이관해야 한다.
- 06 문서 Draft와 하위 Decided/Candidate가 혼재하는 것은 오류 자체가 아니다. 다만 검색 발췌가 §6.3 첫 단락/예외를 잃으면 TZ 미정=전체 분석 차단으로 오해한다. 섹션 시작에 상태·원본·전제 연결이 필요하다.
- DESIGN Navigation의 여섯 스크린샷 그룹은 06 §9 일곱 그룹과 다르면서 'matching'이라고 한다. 뒤 Open Decisions는 불일치를 인정한다. 따라서 숨겨진 신규 IA가 아니라 문서 내부의 이미 인정된 잘못된 요약. 구체 수치 270/54/32는 해결됐으므로 다시 묻지 않는다.
- REQUIREMENTS §0 [x]는 결정 반영, 이후 [ ]는 구현/제안/검증 작업 혼합. [3/3] '신뢰도가 가장 높다'는 출처 개수와 계약 권위를 혼동시킨다. §3 지표 쌍 요약은 06 §6.1의 명시적 초기화 경로 예외를 잃기 쉽다.
- PLATFORM_REQUIREMENTS의 전역 '결정 전 구현 금지'는 06 §6.4의 단일 설비 naive 조회 허용과 함께 읽어야 한다. blocker는 작업별이어야 한다.

장점: INDEX·문서 책임 선언·Decided != 구현 완료·Research 경계·독립 upstream 보존·외부 snapshot manifest·금지사항과 상세 반례가 이미 있다. 이를 깨는 대규모 재분류 불필요.

## 구조 제안과 대안

권고: 기존 파일 유지. INDEX에 역할/작업 경로와 원본 책임 표를 보강. 원본 섹션 중 실제 변경하는 계약만 안정 anchor/짧은 contract ID를 부여(모든 문장 ID 금지). 05는 결정/질문 레지스터로 수렴하되 현재 세 상세 정책은 이관 전까지 현 원본임을 명시. DESIGN은 시각 값·render interaction; 의미/권한/시간은 06 링크. REQUIREMENTS는 파생 작업 후보 목록으로 축소하고 출처·분류·blocker·증거를 명확히 한다.

내용을 또 다른 규칙 원본으로 복제하지 않는 최소 운영 표: 계약 식별자/현재 원본 위치/직접 소비자/관련 질문/구현 증거 위치. 초기에는 5개 대표 사례에 해당하는 행만 수동 작성. INDEX는 길찾기, 표는 영향 관계, 05는 결정 상태, 작업 기록은 구현/검증 증거를 각각 소유한다. 상태를 네 곳에 복제하지 않는다. 상태는 원문에서 읽고 표에는 포인터만 둘 수 있다.

대안: 06을 identity-url/time/permission/state/menu로 분할. 지금 즉시 시행하면 §번호 인용이 많이 깨지고 URL·시간·Scope 한 계약이 여러 파일로 흩어진다. 독립 변경 빈도/검색 실패가 시범 후 입증될 때만 선택.

## 운영

설계 상태(Decided/Candidate/Open/Deferred)와 delivery(미구현/진행/구현 증거 있음/검증 증거 있음)는 독립. 구현 증거는 commit+path, 검증은 command+result+기준 source revision. 코드 없음은 플랫폼 자체 미구현으로 쓰고 FeedbackOps 코드를 증거로 전용하지 않는다.

원본 변경→직접 소비자 검토→문자열/별칭 검색으로 누락 탐지→영향 여부/이유 기록→의미 검토→링크·anchor·상태표 일치 검사. '내용 변경 없음' 소비자도 검토한 기준 hash를 남길 수 있다. 매 변경마다 전체 파일 hash 때문에 모든 후속 작업을 무효화하지 않고 해당 섹션 diff로 판정한다. 생성 인덱스는 필요가 확인될 때만: 생성기를 도입하면 출력 수동 수정 금지와 재생성 검사 필수. 지금 RAG 도입 불필요.

멀티 에이전트: 파일 소유권만으로 부족. 계약 ID/변경 전 revision/소비자 작업을 선언하고 같은 계약 의미 변경은 단일 담당이 조정. 원문이 바뀌면 영향받은 검증만 다시 수행. 코드가 계약과 다르면 코드를 사실 증거로 기록하되 승인된 계약 자동 덮어쓰기 금지.

## 검증 가설

1. 새 설비관리 consumer: 06 §4–6/8/17/19/28–29 + 02 설비관리 + 01 마스터 소유권. field owner 미결은 쓰기만 막고 전체 Shell 설계를 막지 않는다.
2. defaultRangeTo: 06 §6.3→05 지연완료 R/H→03 시간/04 요약/07 시나리오/DESIGN 기간 프리셋/REQUIREMENTS. R 부재 때 독립 기본 기간 물질화 가능이라는 예외를 보존하는 sample.
3. integration 후보: candidate 원본→05 결정 증거→06/01/03 해당 원본 수정→candidate에 결과 링크. 채택돼도 code completion 아님.
4. visual vs behavior: DESIGN table-density 32/compact 25/터치44와 06 §15/19 상태 의미 분리. DESIGN 수치 변경은 render 시험, 의미 변경은 응답 계약 시험.
5. 동시 변경: client와 server가 public field명 별도 확정하는 충돌을 공통 계약 변경 선언에서 잡는다. 단순 Git conflict 없음이 안전 증거 아님.

## 자기 제안 실패 조건·질문

수동 영향 표는 소비자 증가로 stale해질 수 있다. 5사례에서 누락 소비자/탐색 횟수/갱신 부담을 기록하고 필요할 때만 자동 참조 추출. ID가 원문과 분리되면 또 다른 registry가 된다. 원문 inline ID + 포인터 방식 유지. 모든 Open을 레지스터로 이관하면 의미 전제를 잃을 수 있으므로 상세 질문은 인접 원문, 05는 요약 경로.

인터뷰: 최우선 대표 consumer와 승인자/운영 담당; Scope 현실·timeDomain assertion 제공 주체; SSO/배포/팀 역량; 운영 수치 산정의 SLO와 데이터량. 기술 형식 선택은 팀 제약 확인 후 조사, 사용자에게 코드 생성 도구를 즉시 고르게 하지 않는다. 이미 확정된 단일 scope·naive·270/54/32를 재질문하지 않는다.

이행: (1) 상태·진입점 오독만 고치는 작은 patch (2) defaultRangeTo 1개 sample에서 원문/파생/영향 trace (3) 05 정책을 원문 완전성 표로 이관, 기존 anchor forwarding 유지 (4) 코드 생길 때 증거 연결 (5) 실제 분할 필요 재평가. 각 단계 독립 revert; 역사 파일은 본문 수정 대신 현재 문서로 안내하는 sidecar/index 사용.
