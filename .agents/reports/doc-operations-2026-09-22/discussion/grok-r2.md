# 문서 운영 R2 — Grok 반박

R1을 고치지 않는다. 원문·제품·서브모듈은 그대로다. 대조 대상: `root-r1.md`, `glm-r1.md`, 자기 `grok-r1.md`. `sample-time-contract.md`는 미채택 시범으로만 읽었다. 다른 참가자 R2는 열지 않음.

세 안은 큰 재분류를 거절하고 06 권위·섹션 혼합 상태·Research≠채택·R/H를 05에 당분간 두는 점에서는 같다. 갈리는 것은 **상태·관계·증거를 어디에 적으면 두 번째 원본이 되지 않는가**, 그리고 **승인 없이 의미를 닫는 규칙**이다.

## 1. 05 슈퍼인덱스 vs 원본 인접 vs INDEX 행렬

**GLM 안 A:** 05 표에 근거·소비자·증거 열을 더하고, 그 행이 갱신 체크리스트가 된다. 지연완료 소비자를 01 mart·02 재집계 행·03 DB 각주로 재확인했다고 한다.

**root:** 계약 ID/원본 위치/직접 소비자/질문/구현 증거는 *최소 운영 표*로 두되, 상태는 원문에서 읽고 표에는 포인터만. 작업 기록이 구현/검증 증거를 소유. 05의 세 상세 정책은 이관 전까지 현 원본. 초기에는 5사례 행만.

**Grok R1:** INDEX에 권위 행렬+영향 표, 05는 상태 한 줄+포인터. 예외로 R/H 본문은 지금 05가 원본.

**반례 — 추가 수동 원본.** GLM 소비자 열은 작성 즉시 불완전하다. 같은 주제의 실제 소비는 07 L105/L136(시간 Open/Decided 혼재), 04 L48(URL Open stale), DESIGN L808–813(기간 URL 재서술), 06 §6.3 자체(`defaultRangeTo`↔`R` 결합), REQUIREMENTS Q3–4에도 있다. GLM T2는 07 §7·03만 적었다. 빠진 소비자를 나중에 발견하면 05 행을 고치게 되고, **원문과 05 행이 동시에 맞는 목록**이 된다. 그것은 P1이 비판한 복제와 같다. 요약 문구를 유지하면(GLM §2.1) 실패 사례 1(자기 고백)이 기본 경로다.

Grok INDEX 행렬은 더 나쁘다. R1 §3.1은 주제마다 상태(D/C/O)를 행렬에 복사한다. 07 L105 stale을 행렬이 “06 Decided”로 적으면 발견에는 도움이 되지만, 행렬이 세 번째 상태 원본이 된다. R1 §7 실패 1이 바로 이것이다. **철회:** 전 주제 권위 행렬을 INDEX 상설 원본으로 두지 않는다. INDEX는 역할·파일 책임·5사례 영향 포인터만.

root의 “상태는 원문, 표는 포인터, 증거는 작업 기록”이 복제를 가장 덜 만든다. 다만 root도 “5사례 행만”이 커지면 GLM과 같은 표가 된다. 자기 실패 조건(stale 영향 표)이 이미 그 점을 말한다.

**R/H 보존.** 세 안 모두 지금 05 지연완료 절이 `R`/`H`/`lateArrivalAutoHorizon` 상세 원문이고, 06 §6.3 L256이 그 정의를 인용한다는 사실에 동의한다. 즉시 01로 옮기면 06 링크가 빈다(Grok·root). GLM은 05를 “인덱스로 완성”하면서도 샘플 행에 원본을 `06 §6.3` **과** `05 지연완료 절` 둘 다 적는다 — 예외를 숨기지 않은 점은 맞다. 그러나 05 표를 인덱스로 키우면 에이전트가 **표 요약만** 읽고 05 본문 알고리즘(`R` 없으면 자동 재집계만 보류, 창 밖은 정정 후보)을 건너뛴다.

**수정안:** 05 머리말에 한 줄만 추가하는 수준이 이관보다 싸다. “결정 색인. 예외: 지연완료·실시간성·파서 DB 접근 절은 이관 전까지 정책 본문 원본이며 06 §6.3이 이를 소비한다.” 소비자 목록은 05에 상설 열로 넣지 말고, 그 절 머리 또는 06 §6.3 머리에 “직접 소비자: …” 한 줄을 **원본 인접**으로 둔다. 증거 열은 코드가 생기기 전 05에 만들지 않는다. 공란 열이 ‘미구현 증명’처럼 읽히거나, 반대로 채워지며 설계 Decided와 섞인다.

남은 이견: GLM은 구현 착수 예고 전이면 안 B(INDEX만)로 충분하다고 했다. 동의. 안 A의 05 확장은 착수 신호가 와도 **소비자·증거를 05에 넣는 형태로는** 반대한다.

## 2. 안정 ID vs 섹션 번호 동결

**root:** 실제로 바꾸는 계약에만 짧은 ID/anchor. 모든 문장 ID 금지. inline ID + 포인터.

**GLM:** 행 ID `06§6.3-time` 형태, 신규 넘버링 발명 안 함. 실패로 리네임에 약함 → 섹션 번호 재부여 금지. 그 금지가 06 분할을 막는다고 자기 비판.

**Grok R1:** 전 문서 metadata·ID 의무화 거절. 경로+절 번호.

**리네임.** `04`의 옛 “딥링크 절”은 파일은 그대로인데 절이 사라졌다. ID가 그 절에 붙어 있지 않으면 검색어가 죽는다(현재 `rg` “딥링크 절” 0건). 반대로 ID 레지스트리만 살리고 원문 제목을 바꾸면 root가 경고한 “ID가 원문과 분리된 또 다른 registry”가 된다.

**일부 발췌.** 에이전트가 06 §6.3 첫 단락만 가져가면 TZ 미정=전체 분석 차단으로 읽힌다(root). ID가 있어도 발췌 범위를 강제하지 않으면 예외(`R` 부재 시 독립 `defaultRangeTo`, 미확인 TZ 단일 설비)가 빠진다. 필요한 것은 ID가 아니라 **절 머리의 혼합 상태 한 줄**과 “이 절을 중간에서 자르지 말 것”.

**섹션 분할.** 06을 identity/url/time/…로 나누는 대안을 root는 지금 거절한다. GLM ID `06§6.3-time`은 분할 후 거짓 좌표가 된다. 번호 동결은 분할을 사실상 금지한다 — GLM 실패 2. Grok의 경로+§ 인용도 같다.

**수정안:** 전 문서 frontmatter 강제 불필요(세 안 일치). 안정 장치는 (1) 06 절 번호 재배열을 기본 금지, (2) **실제로 반복 인용되는 소절**에만 ATX 제목 아래 수동 HTML anchor 또는 이미 유일한 제목(`### 6.3 시간 계약 …`)을 링크 타깃으로 쓴다. 새 식별자 공간(`CTX-TIME`, `D-late`)은 시범 샘플·토론용이며 공개 API/`v`/metricVersion과 섞지 않는다(`sample-time-contract.md` L8, L13가 이미 그렇게 적음). 05 행 ID를 계약 ID로 승격하지 않는다.

남은 이견: root의 선택적 contract ID가 “5사례 표의 키”가 되면 결국 레지스터다. 원문 제목이 키이고 표는 그 제목을 인용해야 한다.

## 3. 무승인 의미 변경 — 마지막 갱신 / 구체적 금지 / 관계 표

질문 3의 반례는 Git이 침묵하는 **서로 다른 파일의 FE/BE cardinality**다.

원문 06 §6.1: 컬렉션은 URL 반복 키, JSON은 배열, **콤마 결합 채택하지 않음**. 공개 계약은 Kernel 소유, 클라이언트 라우터와 서버 검증이 같은 산출물을 소비.

시나리오: 04 에이전트가 TanStack Router 예시에서 `equipmentIds=A,B`를 적고, 01/03 에이전트가 쿼리 매핑에서 콤마 split을 적는다. 06은 안 건드린다. Git conflict 없음. GLM “05 행 마지막 갱신 승리”는 둘 다 05를 안 고치면 **승리가 없다**. 한 쪽만 05에 “직렬화 세부는 구현 중”을 쓰면 그 행이 이기고, 06의 콤마 금지가 조용히 진다. Grok R1 “둘 다 원본처럼 보이면 더 구체적인 금지/예외를 임시 우선”은, 04/01이 원본처럼 보이지 않으면 작동하지 않고, 반대로 06과 04가 둘 다 원본처럼 보이면 **04의 더 긴 예시가 이긴다**. 어느 쪽이든 승인 없이 공개 cardinality가 바뀐다.

root “관계 표가 같은 계약 의미 변경을 단일 담당이 조정”은 방향은 맞다. 보장은 없다. 표에 04·01이 06 §6.1 소비자로 없으면 탐지 실패. 완전하다고 주장하는 표는 없다(root 자기 실패: 누락 소비자).

**철회:** Grok R1 §5.4.5의 “구체적 금지 임시 우선”을 병합 규칙으로 쓰지 않는다. 리뷰 힌트(“금지/예외 문장을 먼저 읽어라”)로는 남긴다. 의미 충돌은 원본 절을 Open으로 올리거나 사람/지정 코디네이터가 고친다. GLM 마지막 갱신 승리는 **토론 산출물 디렉터리**에는 맞지만(참가자별 파일 격리) 권위 문서 05 행에는 반대한다.

**수정 규칙:** 공개 필드 cardinality·이름·카디널리티를 바꾸는 작업은 06 §6.1을 먼저 연다. 04/01만의 커밋은 구조적으로 통과해도 시맨틱 반려. Git 무충돌은 안전 증거가 아니다(root 검증 가설 5 — 동의).

## 4. REQUIREMENTS 체크박스와 HANDOFF

세 안 모두 `[x]` §0는 결정 반영, 이후 `[ ]`는 작업/제안 혼합, `[3/3]`은 권위가 아님에 동의한다.

**GLM:** Open→Decided 때 REQUIREMENTS 체크박스도 갱신(HANDOFF 관례 승격). 재합성하지 않고 체크만.

구분 가능한가? **부분만.** §0의 `[x]` 두 줄은 “문서 충돌 해소”라 결정 완료에 가깝다. §1 이후 `[ ]` Must는 구현 작업이다. 같은 `[ ]` 문법에 신규 제안 메뉴(사용자 디렉터리 등)와 이미 Decided인 Data Trust 물질화가 섞여 있다. 체크를 유지하면 에이전트가 `[x]`를 delivery로 읽거나, 미체크를 Open으로 읽는다. GLM이 05에 설계/증거 열을 나눠도 REQUIREMENTS가 세 번째 상태를 유지하면 섞임은 남는다.

**Grok R1**은 HANDOFF L67 “05와 REQUIREMENTS를 함께 반영”을 **제거**하자 했다.

**반례 — 역사 보존.** HANDOFF는 2026-09-22 세션 기록이다(자기 선언: Git 대체 아님). 본문 삭제 권고는 당시 운영 관례의 증거를 지운다. root의 sidecar/현재 문서로 안내가 낫다.

**수정안:** HANDOFF 문장은 남긴다. INDEX 또는 AGENTS에 **현재** 규칙: “결정 상태는 05(+원본 절). REQUIREMENTS는 파생 작업 목록이며 체크는 delivery 후보일 뿐 Decided가 아니다. 신규 결정을 REQUIREMENTS Open 목록에 이중 기록하지 않는다.” HANDOFF 머리 또는 해당 문단 옆에 “당시 관례. 현행은 INDEX …”를 다는 쪽이 삭제보다 이점이 크다. REQUIREMENTS 체크 갱신 의무는 승격하지 않는다.

## 5. 기계 검사가 하는 일 / 하지 않는 일

과장하지 않기. 동의하는 구조 층:

- 상대 경로 존재, 06 `§6.3` 문자열이 06 제목에 존재.
- 05 표가 가리키는 파일명 존재(절 존재는 제목 grep 정도).
- 헤더에 Research/Candidate가 없는 신규 `docs/**` 탐지(GLM 구조 5) — 휴리스틱, 오탐 있음(`repository-layout.md`는 운영 원본).
- `equipmentIds=` 콤마 패턴, “§6.4의 Open 결정” 같은 **금지 구 목록** — 알려진 stale 문장 탐지.

의미 검증이 **아닌** 것:

- “원본 외 정의 지점”(GLM 구조 4). 인용과 재정의는 산문에서만 갈린다. 03의 wall-clock 원천 의미는 정의가 맞고, 같은 파일의 Phase 0 목록은 재정의에 가깝다. grep은 둘을 못 가른다.
- 05 소비자 열 완전성. 없는 행을 증명할 수 없다.
- 06 Draft 머리 vs 절 Decided 일치. 혼합이 정상이다.
- DESIGN L763 “matching §9” vs L640 정정. 같은 파일 내부 모순.
- FE/BE cardinality 드리프트(§3).

Grok R1 §5.3이 구조/의미를 나눈 것은 유지한다. GLM이 구조 검사에 “소유권 위반 반려”를 넣은 것은 과하다. 소유권 위반 판정은 시맨틱 리뷰다. 구조 통과를 시맨틱 적합이라고 하지 말라는 GLM 본문 마지막 문장과는 그 표가 충돌한다.

## 6. 06 §6.3 예외와 `sample-time-contract.md`

원문(06 L242–258, 05 지연완료 절)에서 이번 논점이 요구한 세 예외:

1. `R`이 아직 없으면 `defaultRangeTo` 비교를 적용하지 않고, 독립적으로 유효하면 **자동 물질화**. 자동 재집계만 보류.
2. TZ 미확인이어도 단일 설비(또는 동일 wall-clock 확인 집합) naive 조회 허용. 전체 분석 금지가 아님.
3. 실제 TZ 값·Δ는 Open.

샘플 파일은 §6.3 본문을 사본으로 붙이고, 역대조 표 L61에 `R` 없으면 독립 to 물질화·재집계만 보류를 적었으며, “R 부재 시 물질화 금지”는 동작 변경이라 채택하지 않는다고 명시했다. 미확인 TZ·Δ Open도 사본에 있다. **이 사본 구간에서 세 예외는 소실되지 않았다.**

그러나 운영 평가:

- 사본 자체가 세 번째 원본이다. 파일이 “이행 후 사본을 유지하지 않는다”(L3)고 한 문장이 핵심이다. 유지하는 순간 GLM P1이 재발한다.
- 05 `R`/`H` **알고리즘 본문**은 사본하지 않고 포인터만 둔다 — 맞다. 샘플만 읽고 창 밖 정정 후보·`lateArrivalAutoHorizon` 필수 설정을 놓칠 수 있다. 발췌 실패는 ID가 아니라 절 경계 문제.
- GitHub slug 링크(L9)는 렌더러 의존. 자기 고백대로 제목 문자열이 실제 찾기 수단이다.
- `CTX-TIME`은 샘플 식별자이지 계약 승격이 아니다(L8, L13). 문서 OS가 이 ID를 06에 넣으면 제품 승인으로 미끄러진다.

Grok R1 샘플 A/B(07 L105, DESIGN Navigation)는 사본이 아니라 소비자 문장 치환이라 예외 소실 면에서는 더 작다. 시간 계약 시험에는 root 샘플이 더 직접적이다. **둘 다 채택이 아니다.**

## 7. Candidate 채택과 위임된 엔지니어링 권한

Grok R1 §5.1 “Candidate 채택은 사람 결정 후”는 **너무 넓다. 수정한다.**

이미 문서가 위임한 것(신규 제품 Open이 아님):

- 06 §5: 필드명·TS 타입·등록 방식은 **구현 설계에서 구체화**.
- 06 §6.1: 공개 계약 형식(OpenAPI/JSON Schema/codegen)은 Candidate — 형식 선택은 구현 시점 엔지니어링, 의미(반복 키 vs 콤마)는 이미 Decided.
- 06 §6.4: 필드명·enum 문자열 Candidate.
- 04/03 스택 표: Candidate. 팀 제약 확인 후 고르는 것은 root가 말한 “사용자에게 생성 도구를 즉시 고르게 하지 않는다”와 같다. 다만 Fastify를 SYNTHESIS 동의로 Decided로 올리는 것은 위임 밖.
- 와이어프레임 스킬: 설계 단계는 문서 리뷰로 종료, Design System은 **구현 요청이 있을 때**.

사람 신규 승인이 필요한 것: Decided 의미 변경, Open domain(TZ 값, Scope 계층, `H`/`Δ`), Research 후보의 계약 승격, 신규 최상위 메뉴, 06 Kernel 경계 변경, FeedbackOps 편입.

문서 OS 권고(INDEX 한 줄, stale 포인터 수정, 05 예외 명시)를 제품 승인으로 읽지 않는다. 270/54/32·단일 `scopeId`·naive wall-clock은 이미 닫혔고 재질문하지 않는다(root — 동의).

## 다섯 과제에 다시 비추기

1. **새 메뉴→Kernel.** 세 안 모두 06 §5/§28–29가 원본. root가 지적한 INDEX “개별 메뉴 구현은 04부터”(INDEX 역할 표)는 AGENTS/06 §29와 어긋난다 — INDEX 보강이 행렬보다 우선. field owner Open이 쓰기만 막고 Shell을 막지 않는다는 root 가설에 동의. GLM 05 행 1홉 단축은 소비자 열이 완전할 때만 성립하며, 지금은 아니다.

2. **URL/Context/시간.** 원본 잠금은 06 §6 + (R/H에 한해) 05 본문. 05에 소비자 열을 키우면 T2 체크리스트처럼 보이지만 FE/BE cardinality(§3)와 07/04 stale을 못 닫는다. 원본 인접 한 줄 + 알려진 stale 구 grep이 더 작다. `sample-time-contract.md`는 예외 보존 시험에는 통과, 상설 파일로는 실패.

3. **Candidate 채택/defer.** 조사 문서 헤더 유지, 05에 사람 승격만 기록. 위임된 구현 세부는 06이 이미 열어 둔 범위에서 엔지니어링이 진행한다(§7). 모델 `[3/3]` 금지 — 세 안 동의.

4. **DESIGN 시각 vs 행동.** 값=DESIGN, 행동=06, 2026-09-21 패턴. §23 숫자 이중 원본은 OS가 값을 고르지 않고 링크화 이슈만(Grok·GLM). shadow 허용 범위 불일치는 여전히 Open으로 둔다.

5. **동시 편집.** 토론 파일 격리(GLM) + 권위 문서 순차(세 안). 마지막 갱신 승리와 구체 금지 우선은 쓰지 않음. 공개 계약 의미는 06을 같은 작업에서 연다. Git 무충돌 ≠ 안전.

## 위치 선호 (대안, 강제 아님)

1. 원본 절이 상태·예외·(필요 시) 직접 소비자 한 줄을 가진다. 05 지연완료 절은 그 원본으로 **명시**하고 당장 옮기지 않는다.
2. 05 요약 표는 포인터+날짜. 열을 소비자/증거로 확장하지 않는다.
3. INDEX는 역할 표 수정(04-first 제거, DESIGN/REQUIREMENTS/HANDOFF 한 줄)과 5사례 영향 포인터. 전 주제 상태 복사 행렬은 두지 않는다.
4. 구현 증거는 코드가 생기는 작업 기록에만. 지금 05에 공란 열 만들지 않음.
5. 선택적 anchor는 자주 깨지는 소절 제목에만. 계약 ID 레지스트리 없음.

R1에서 철회·수정한 것: INDEX 상설 권위 행렬, 구체 금지 임시 병합, HANDOFF 본문 삭제, Candidate=전부 사람 승인. 유지: 파일 유지, R/H 05 잔류, 섹션 혼합 상태, Research≠채택, 구조≠의미 검사, 제품 결정을 OS가 닫지 않음.

원본 재확인 잔여: 06 §23↔DESIGN 숫자 전수, 파서 `docs/23` 부재, 07 L105 의도 vs 실수. 샘플 사본의 바이트 일치는 이 세션에서 `validation.json`을 열지 않아 주장하지 않음. 의미 역대조는 원문 §6.3과 샘플 L19–35를 직접 읽은 범위다.
