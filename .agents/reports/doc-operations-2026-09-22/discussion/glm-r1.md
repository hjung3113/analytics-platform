## 1. 근거 기반 문제 진단, 강점/경계

### 1.1 문제

**P1 — 결정 상태가 여러 곳에 걸쳐 있고 05의 "인덱스 소유" 선언과 실제가 다르다.**
`docs/INDEX.md` "문서 소유권과 tooling 경계"와 `05` 머리말은 05가 결정 상태 추적을 소유한다고 선언한다. 실제로는 (a) 05의 요약 표, (b) 06 본문 인라인 괄호 표기(`§6.1 (Decided)`, `§6.3 (Decided; TZ 값은 Open domain decision)` 등), (c) 06 머리말의 섹션 단위 상태 선언, (d) 근거 리뷰 문서(`reviews/…grilling.md` §10이 자신이 무엇을 06/05에 반영했는지 별도로 기록), (e) `07` §8의 자체 상태표가 같은 결정을 각자 서술한다. 지연완료 메커니즘 하나가 `06 §6.3`(`defaultRangeTo`·`R`), `05` "지연 완료 허용 시간" 절, grilling §6.3, 그리고 소비 서술인 `01` mart 재계산 트리거 절·`02` 플랫폼 코어 "재집계(지연 완료) 정책" 행·`03` DB 표의 watermark 각주까지 6곳에 걸쳐 있다(각각 재확인 읽음). 05 표의 "원본 / 다음 판단" 열이 이미 원본을 가리키므로 구조는 있으나, 요약 문구 자체가 복제라 어느 한 곳만 갱신되면 조용히 어긋난다.

**P2 — 갱신 부담이 관례와 사람 기억에 있다.**
`HANDOFF.md` 마지막 문단이 그 증거다: "각 결정이 날 때마다 `docs/05`(결정 상태 추적)와 `PLATFORM_REQUIREMENTS.md`(체크박스)에 함께 반영한다." 즉 결정 1건에 최소 3–5개 파일 동시 갱신이 필요한데, 그 대상 목록을 계산하는 방법은 어디에도 명세화돼 있지 않다. grep 가능한 구조는 있으나(문서 수가 적어 가능) 절차 문서가 없다.

**P3 — 발견성 구멍: INDEX 소유권 서술에 DESIGN.md와 PLATFORM_REQUIREMENTS.md가 없다.**
재확인: 현재 `docs/INDEX.md` 전문에 `DESIGN.md`·`PLATFORM_REQUIREMENTS.md`에 대한 언급이 없다(docstructure-grok의 동일 지적이 현재에도 참). 그런데 `06` 머리말은 "실제 값의 단일 원본은 `DESIGN.md`다"라고 선언하고, `PLATFORM_REQUIREMENTS.md` §0은 2026-09-21 치수 충돌 결정(`[x]` 2건)의 체크 기록을 가진다. 시각 값의 canonical과 요구사항 체크리스트라는 실질적 권위 문서 2개가 진입점 색인에서 빠져 있다. `HANDOFF.md`도 INDEX·README·AGENTS 어디에서도 링크되지 않아 색인 경로로는 발견되지 않는다(README·AGENTS 재확인).

**P4 — "설계 상태"와 "전달/검증 상태"를 구분하는 어휘는 있으나 증거를 붙일 자리가 없다.**
`05` "Decided는 설계 계약의 상태이며 구현 완료를 뜻하지 않는다", `06` §29 Platform Done이 완료의 두 층을 정의한다. 다만 Platform Done을 **입증한 기록**(테스트·계약 스냅샷 결과·화면 검증)이 어느 문서 어느 컬럼에 남는지 정의한 곳은 없다. 코드가 없는 지금은 공란이어도 되지만, 구현 시작 즉시 이 자리가 필요해진다(§9 T1/T2에서 구체화).

**P5 — 리서치↔계약 계층 구분은 잘돼 있으나, 규칙이 산문에만 존재한다.**
`repository-ideas.md`(브레인스토밍/Candidate), `component-contract-candidates.md`(Research/Candidate, "채택 결정…이 아니다"), research README("모델 간 동의는 실행 검증이나 제품 결정과 구분"), SYNTHESIS §7("이미 적용했다는 뜻이 아니다") — 지위 선언은 모두 각 파일 헤더에 있다(각각 재확인). 강점이지만, "research→후보→소유 문서 반영"의 이동 조건(언제 누가 무엇을 바꿔야 하는가)을 한 곳에 모아 둔 문서는 없다. `.agents/reports/*`가 스냅샷이므로 재작성하지 않는다는 규칙도 docstructure-grok 부록 안에만 있고 레포 지침에는 없다.

**P6 — 섹션 단위 혼합 상태의 표기 관례가 불균일하다.**
좋은 사례: `06 §6.3` 제목 "(Decided; TZ 값·다중 사업장 같은 날짜는 Open domain decision)", `05` "지연 완료 허용 시간 (Decided — 정책 메커니즘; 구체 숫자는 Open Questions 유지)". 한 결정 안에 메커니즘/값이 갈리는 상태를 섹션 단위로 보존하는 패턴이 이미 확립돼 있다. 반면 `07` 헤더는 "상태: 설계 산출물"이라는 별도 어휘를 쓰고, `DESIGN.md`는 Open Decisions 절만 있을 뿐 문서 단위 상태 선언이 없다(Overview는 스테이지 산출물임을 서술). 상태 어휘의 정의(각 상태가 무엇을 보증/보증하지 않는지)는 06 머리말이 사실상 담당하지만, 문서 유형별(계약/와이어프레임/토큰/요구사항/리서치) 상태 표기 위치·형식 규칙은 존재하지 않는다.

**P7 — 같은 주제의 숫자/규칙이 문서 3층(계약↔토큰↔요구사항)에 걸쳐 있다.**
04/06/DESIGN의 UI 삼중 정의는 docstructure 감사들의 공통 지적이다. 2026-09-21에 치수(270/54/32)는 "DESIGN canonical + 06 인용" 패턴으로 해소됐다(`06 §7` Baseline "Decided — `DESIGN.md` canonical과 일치", `§15` "Decided — `DESIGN.md` `table-density` 토큰과 일치", `05` 표 갱신 행, `PLATFORM_REQUIREMENTS.md` §0 `[x]` 2건 — 모두 재확인 읽음). 즉 해결 패턴(값의 단일 원본 + 다른 문서는 인용)이 한 번 증명됐는데, 이 패턴을 언제 적용할지의 규칙화는 안 됐다. `06 §23` 토큰 스케일은 여전 Candidate로 남고(06 머리말 선언), `PLATFORM_REQUIREMENTS.md` 디자인 요소 첫 행이 그 공백을 요구로 지적한다.

## 3. 소유권, 섹션 단위 상태 vs 전달 증거, 원본/요약/예시 관계

- **소유권 배분(현행 유지 + INDEX 승격)**: 행동/구조 계약=06, 시각 값=DESIGN, 후보·리서치=04/research/integration, 상태=05, 화면 소비=07, 요구사항 통합=PLATFORM_REQUIREMENTS(비권위), 근거=reviews, 스냅샷=.agents/reports. 이 배분 자체는 06 머리말·INDEX·docstructure 감사가 일치하므로 바꾸지 않는다.
- **섹션 단위 설계 상태**: "메커니즘 Decided + 값 Open" 혼합(`06 §6.3`, `05` 지연완료)을 상태의 기본 단위로 유지한다. 상태는 문서 단위가 아니라 섹션·결정 단위로 기록되어야 하며, 그 원본은 각 계약 문서 자신(06은 머리말 선언, 07은 §8 표)이다. 05는 그것들의 인덱스지 두 번째 원본이 아니다.
- **설계 상태 vs 전달 증거**: 같은 결정 행에서 두 상태를 다른 열로 분리한다. `증거` 열은 지금 전부 "—(미구현, 런타임 부재)"로 시작하고, 구현 후에만 계약 스냅샷 테스트 결과·Platform Done 체크(06 §29)·화면 검증 링크로 채운다. "Decided ≠ 구현 완료"를 열 구조로 강제하는 효과가 있다.
- **원본/요약/예시 관계**: 값·규칙의 원본은 계약 문서 섹션; 요약(05 표, INDEX 설명)은 포인터+한 줄; 예시(07 §7 시나리오 표, DESIGN reference-dashboard 레시피)는 원본 계약의 소비 시연이며 "문서 대조용이며 런타임 테스트 통과 기록이 아니다"(07 §7 각주 — 재확인) 같은 비권위 고백을 유지한다. 예시가 규칙을 재정의하지 않는다는 07의 서술 패턴("전역 규칙을 이 문서에서 재정의하지 않고")을 다른 소비 문서에도 적용한다.

## 4. 최소 발견/색인/변경영향 방법과 유지비

- **발견**: INDEX 역할 표(사람) + INDEX 소유권 표(에이전트)의 2개 표가 전부. 신규 파일이 생길 때마다 소유권 표에 1행 추가. 문서 20~30개 수준에서는 자동 색인 생성·RAG·링크 검사기가 필요 없다(문서 수가 인지 비용보다 낮다).
- **변경영향 산출**: 05 행의 `원본/근거/소비자` 열이 갱신 대상 목록 그 자체가 된다. 예: 지연완료 행 → 원본 `06 §6.3`·`05` 절, 근거 grilling §6.3, 소비자 `01` mart 재계산 트리거 절·`02` 재집계 정책 행·`03` DB 표 — 실제로 이 소비 3곳이 지연완료를 서술하고 있음을 재확인했다(`07`에는 지연완료 직접 서술 없음). grep(`defaultRangeTo|lateArrivalAutoHorizon`)이 백업 역할을 하나, 05 행이 1차 답을 준다.
- **유지비**: 결정 1건 갱신 시 (a) 원본 섹션, (b) 05 행, (c) 필요시 근거 문서 추가 — 관례(HANDOFF 마지막 문단)와 동일한 2~3곳이며, 소비자 갱신은 05 열이 알려주므로 잊힘이 줄어든다. 신규 결정 등록은 05 1행 + 원본 섹션 상태 표기. 인덱스의 구조 검사(§5)는 스크립트 없이 grep 몇 종으로 수행 가능하다.

**리뷰 트리거**: 06 §4–§6, §8–§9, §11, §17, §19(Decided 섹션 — 06 머리말) 변경 시 §28 Platform Governance 체크리스트 + 07 §7식 문서 대조 표. 소유권 위반(04에 계약 본문, DESIGN에 행동 규칙, 07의 계약 재정의)은 구조 검사에서 반려 사유.

**재생성 트리거**: 없음이 원칙. INDEX 두 표는 수동. PLATFORM_REQUIREMENTS는 재합성하지 않고 체크박스만 갱신(부록이 "원본 대조 권장"으로 자신의 한계를 이미 고백). 스냅샷 보고서는 재작성 금지 — 이 규칙을 감사 부록에서 AGENTS/INDEX로 승격.

**부재 코드 처리**: `증거` 열의 기본값 "—(미구현)"을 허용하고, "설계 Decided"와 "전달 미확인"을 열로 분리(§3). 문서 대조 표(07 §7)의 "런타임 테스트 통과 기록이 아니다" 고백 패턴을 증거가 생기기 전까지의 표준 표기로 쓴다. 증거 없는 "구현됨" 표기를 구조 검사 금지 항목에 둔다.

**시맨틱 vs 구조 검사**

- 구조(grep·스크립트 가능): (1) 링크/파일 존재, (2) 06 머리말 섹션 상태 목록 ↔ 본문 섹션 제목 상태 일치, (3) 05 표가 인용하는 문서·섹션 실존, (4) 규칙 키워드(`defaultRangeTo`, `metricId`+`metricVersion`, 270px 등)의 원본 외 정의 지점 탐지(인용 아닌 재정의 탐지), (5) 헤더 상태 문장(Research/Candidate 등) 없는 신규 docs 파일 탐지.
- 시맨틱(사람·모델 리뷰만): 규칙 모순, 상태 승격의 정당성(근거 없는 Open→Decided), 소유권 경계 위반의 판정, 요약 문구와 원본의 의미 일치. grilling/grill-duel 절차(reviews 선례)가 이 층을 담당한다. 구조 검사 통과가 시맨틱 적합을 의미하지 않는다.

**다중 에이전트 충돌**: 실제 이미 운영 중인 패턴을 규칙화한다 — 병렬 산출은 `discussion/`·`reports/` 디렉터리의 참가자별 파일로 격리(오늘 component-contract-candidates 3개 r1 병렬 작성, 이번 doc-operations 다수 참가가 증거; 디렉터리 리스팅 확인). 권위 문서(06·05·DESIGN 값)의 병합은 단일 코디네이터가 순차 커밋한다. 충돌 판정: (a) 같은 섹션 동시 변경 금지, (b) 서로 다른 문서에서 같은 결정 변경 시 05 행이 조정 지점(행 단위 마지막 갱신 승리 + 근거 링크 보존), (c) 참가자 간 불일치는 합의로 못박지 않고 SYNTHESIS §10 "코디네이터 판정" 선례에 따라 판정자를 명시해 기록한다. 모델 합의를 제품 결정으로 승격하지 않는다는 research README 원칙을 그대로 적용.

## 7. 내 제안(안 A)의 실패 사례

1. **05 표의 요약 문구가 stale 이중 원본화** — 가장 유력한 실패. 완화: 원본 우선 한 줄 명시 + 구조 검사 (4)로 재정의 탐지. 그러나 요약 자체의 진부화는 시맨틱 검사 없이는 못 잡는다.
2. **원본 좌표 ID가 리네임에 약함** — 06 섹션 번호 재부여(현재 관례상 없음)나 문서 이동 시 ID 전부 무효. 완화: 섹션 번호 재부여 금지를 규칙화하되, 이 금지가 장차 06 분할을 막는 비용이 된다.
3. **갱신 트리거 표의 완전성 환상** — 표에 없는 신규 문서 유형(예: 구현 산출물, ADR)이 생기면 트리거 누락. 신규 파일 헤더 상태 문장 강제(구조 검사 5)로 부분 방어.
4. **코디네이터 병목** — 권위 문서 순차 커밋 규칙이 참가자 많을 때 지연. 수용: 결정 빈도가 낮은 지금은 병목이 아니고, 결정 빈도가 올라가면 그때 분할 필요 신호다.
5. **INDEX 소유권 표의 행 낭비** — 문서 30개를 넘으면 1행씩 느는 표가 읽기 부담. 그 시점에 자동 생성 재검토(지금은 하지 않음).
6. **안 A조차 당장은 과잉일 수 있음** — 구현 착수 시점이 멀면 안 B가 충분. 이 보고서는 안 A를 권하지만 시점 조건을 명시한다: 구현·프로토타입 착수 예고 전이면 안 B로 시작해 05 열 확장만 나중에.

## 8. 우선순위화된 인터뷰 vs 조사, 마이그레이션/롤백

**인터뷰 필요(사람 도메인 입력, 구현 전 필수)**: ① 사업장별 원천 TZ 실제 값·"같은 날짜" 의미(05 Open, §6.3 전제) ② Scope 계층·복수 Scope·설비 소속(§6.2) ③ 백엔드 언어·SSO·배포·규모(05 Open 5항) ④ 지연완료 숫자(H·Δ·horizon) ⑤ VOC 담당 조직·필드 소유권(HANDOFF 11) ⑥ CJK/다크모드/보조기술 실수요(PLATFORM_REQUIREMENTS, HANDOFF 15).

**조사 필요(에이전트가 초안 가능, 결정은 사람)**: ① Menu Registry 스키마 후보 2–3종 비교 초안 ② §19→배지 매핑표 초안 ③ z-index 스택 초안 ④ component-contract-candidates 후보 1–3의 기존 06/01/03 정합성 대조 ⑤ URL 공개 스키마 산출 형식 비교. 모두 "후보 제안"으로 내고 05에 Open/Candidate로 등록.

**마이그레이션(독립 커밋 3개, 본문 이동 없음 → 참조 깨짐 없음)**: (1) INDEX 소유권 표 추가 + 스냅샷 재작성 금지 규칙 승격. (2) 05 표에 근거/소비자/증거 열 추가(기존 행 채우기, 미확인은 "—"로 두고 위조 금지). (3) 갱신 트리거 절 문서화. **롤백**: 각 단계는 표/절 삭제만으로 되돌린다. (2)의 열 제거 시 행과 기존 요약은 그대로 남으므로 정보 손실 없음.

## 9. 다섯 실제 과제로 검증

- **T1 새 메뉴가 Kernel 소비**: 경로 AGENTS→INDEX→06 §5/§12/§28–29는 지금도 작동한다. 안 A 추가분: 05에서 "Menu Registry/Context/URL" Decided 행의 원본·소비자 열로 이동 경로가 1홉 단축. 남는 갭은 콘텐츠(§6-1 레지스트리 스키마 미정)이지 구조 아님.

- **T4 DESIGN 시각 vs 전역 행동**: 2026-09-21 치수 해소가 선례 패턴("값은 DESIGN canonical, 계약 문서는 인용")이다. 안 A는 이 패턴을 트리거 표의 "치수·토큰 충돌" 행으로 일반화한다. §23 전체 인용 전환 여부는 콘텐츠 결정이므로 제안하지 않는다(문서 OS는 패턴만 소유).
