# 목표 문서 운영 모델

표기: 아래 REQUIREMENTS는 실제 루트 `PLATFORM_REQUIREMENTS.md`의 약칭이다.

상태: 미채택 권고. 제품 선택이나 구현 승인이 아니다. 기존 경로를 우선 보존하고, 대표 작업에서 필요가 확인된 연결만 추가한다. 토론 최종 판정은 discussion/DECISIONS.md를 함께 본다.

## 1. 필요한 기능과 가장 작은 수단

| 필요한 기능 | 첫 적용 수단 | 지금 도입하지 않을 것 / 재평가 조건 |
|---|---|---|
| 시작점·원본 찾기 | INDEX 작업별 읽기 경로 + 책임 표 + 현재 계약/후보/역사 경계 | 별도 포털; 문서량 자체가 아니라 반복 탐색 실패 때 검토 |
| 발췌에서 상태·전제로 복귀 | 고위험 원본 섹션에 짧은 식별자·상태·직접 의존·미결 포인터 | 모든 문장 ID/모든 파일 frontmatter 강제 |
| 용어/별칭 | INDEX의 작은 용어→원문 위치 표. 정의 자체는 복제 안 함 | 독립 용어사전으로 정의 재작성 |
| 변경 영향 | 원본 가까이에 직접 소비자/관련 계약 포인터, 변경 기록에 실제 검색·검토 결과 | 완전 dependency graph라 주장하는 수동 manifest |
| 문서/코드/검증 구분 | 작업별 기존 PR/이슈/로컬 변경 기록의 evidence 표 | 별도 글로벌 delivery 대장, 제품 상태와 문서 검토 상태 혼합 |
| 오래된 요약 발견 | source section diff + 참조/별칭 검색 + 검토 완료/불필요 이유 | 파일 수정시각이 최신이면 자동 유효로 판정 |
| 구조 검사 | 로컬 path/anchor/ID 중복·필수 포인터 검사; 생성물이 생길 때 재생성 diff | 링크 성공=의미 일치, RAG 도입을 성과로 간주 |

처음에는 Markdown, Git diff, rg로 충분하다. 이 패키지의 source-snapshot은 **이번 조사 기준 동결용**이며 매번 수작업으로 갱신할 영구 운영 manifest가 아니다. sample 또한 검증용 사본이다. 조사 시점의 역사 증거로 보존할 수 있지만, 채택 후 변경을 동기화하는 상시 복제 원본으로 운영하지 않는다.

## 2. 목표 책임과 이동 판단

05의 폴링·DB 접근·R/H 세 메커니즘은 **현재 05가 원본**이다. 후속 이관을 하게 되면 데이터 운영 정책은 01로, 기술 선택의 비교 근거는 03으로 두는 권고다. 이관 완료 증거 전에는 01을 해당 메커니즘의 현행 원본이라고 표시하지 않는다. 06 §6.3의 R 소비 참조를 같은 작은 변경에서 갱신한다.

06 §4/§15/§19/§26은 Kernel의 token 소비 책임, 플랫폼 최소 기준·상태 의미·접근성 행동을 유지한다. DESIGN의 focus/render 표현을 바꿔 visible focus나 focus trap 의무를 바꿀 수 없다. 시각값의 편집 원본은 DESIGN이지만 06의 Decided 최소 기준에 영향을 주는 변경은 양쪽 계약 검토 대상이다.

DESIGN reference dashboard 분리는 독립 변경이 필요할 때 한 파일로 시행할 수 있다. 처음부터 모든 컴포넌트별 파일을 만들지 않는다. recipe를 분리해도 공통 token은 DESIGN에 유지하고, Candidate 업무 가정과 시각 예시 수치를 보존한다.

## 3. 상태와 authority — 세 축

1. **정보 종류:** 계약 / 근거·배경 / 후보 / 예시 / 질문 / 과거 기록. 예시가 구체적이라는 이유로 계약이 되지 않는다.
2. **설계 결정:** Decided / Candidate / Open / Deferred. 세부 문단 상태가 파일 표지보다 우선한다. Decided 변경은 승인 근거와 대체 원문을 연결한다. 과거 기록/대체됨은 유효성 표시이며 기존 설계 상태 네 가지를 임의로 합치지 않는다.
3. **실행 증거:** 미구현 / 진행 중 / 구현 근거 있음 / 검증 근거 있음. 검증은 무엇·어떤 revision·어떤 환경·결과인지 함께 적는다. 일부 검증을 전체 Verified로 축약하지 않는다.

권위와 최신성은 별개다. 승인된 원본이 기준이며, 최신 연구는 후보다. 구현이 원문과 다르면 실제 동작을 증거로 남긴 뒤 (a) 구현 결함 수정 또는 (b) 명시적 계약 변경을 선택한다. 구현이 먼저 존재한다는 이유로 계약을 자동 바꾸지 않는다.

원본 섹션의 최소 안내 예:

```text
참조: CTX-TIME (문서 탐색용)
범위/상태: 시간 메커니즘 Decided; TZ 실제 값·영업일·Δ Open
의존: 05 지연완료 R/H; 03 원천 시간 의미
직접 소비: 06 URL; 07 기간 입력; DESIGN preset
미결: 해당 원문 질문/05 포인터
```

이 안내는 새로운 전역 필수 frontmatter가 아니다. 소비자 포인터에는 상태를 복사하지 않고 원문 위치를 적는다. 05의 상태 요약을 당장 제거할 수 없으면 파생 요약으로 명시하고 원문 변경과 함께 검토한다. 완전한 기계 생성 상태표가 필요해질 때만 원문 annotation을 단일 입력으로 추출한다.

구현 기록에는 예를 들어 `CTX-TIME / source revision / 코드 없음 / 문서 대조만 수행 / runtime 미검증 / 다음 필요한 입력`을 적는다. 존재하지 않는 코드 경로나 fake issue ID를 미리 만들지 않는다. 담당은 `데이터 담당 — 사람 미지정`으로 쓸 수 있고 지정 요청을 다음 행동으로 둔다.

## 4. 탐색 경로와 용어

첫 작업: AGENTS→INDEX에서 작업을 고르고 아래 묶음을 읽는다. 판단 대상 원문과 중요한 예외를 직접 읽는 것이 종료 조건이다. 보고서 요약은 길찾기 보조다.

| 작업 | 최소 읽기 묶음 | 필요할 때 추가 |
|---|---|---|
| 새 메뉴 준비 | 06 §4–6/8/17/18–19/26/28–29 → 02 해당 도메인 | 01 데이터/해당 화면 spec/DESIGN/04 후보 |
| URL·시간 변경 | 06 §6.1–6.4/11/18–19 → 05 R/H → 01 mart | 03 원천 시간, 07, DESIGN preset, history 반례 |
| 시각 변경 | DESIGN 해당 token/render section → 06 관련 행동 | 07 배치, reference recipe, CJK/접근성 증거 |
| 연구 채택 | 해당 후보 본문·근거·게이트 → 소유 계약(상태·증거 소비 시 06 §18–19) → 05 | upstream pinned source, 기술 비교·실측 |
| 검토·구현 완료 판단 | 변경 계약 원문 → task 코드/테스트 evidence → 06 §28–29 | 미결 blocker와 검증 범위 |

용어 포인터 예: `defaultRangeTo/기본 조회 상한→06 §6.3`, `R/원천 진행 경계·H/자동 창 길이→05 지연완료`, `timeDomain/assertion→06 §6.3`, `scopeId/요청 범위→06 §6.2`, `table-density/행 밀도→DESIGN`, `confirmed→06 §19 또는 integration 후보1의 별개 confidence/conclusion 경로`. confirmed를 범용 '검증 완료'로 합치지 않는다.

검색은 현재 권위 문서부터 시작하고 research/reviews/references/.agents/reports는 분리한다. rg 결과 한 줄만으로 상태를 판정하지 않고 해당 섹션의 상태/전제/예외까지 읽는다. 이후 검색 도구를 만들면 발췌마다 source path+stable section+revision+종류/범위+상태 원문 링크를 붙인다. 상태 문맥 없이 작은 chunk만 반환하는 RAG는 채택하지 않는다.

안정 참조: 첫 수정 계약에 명시적 anchor를 추가하고 기존 제목/경로를 유지한다. 제목 변경 시 기존 anchor alias를 남긴다. 이동 시 원래 위치에 새 원본으로 가는 안내만 남기고 본문 이중 유지 금지. 과거 기록의 당시 인용은 보존하고 현행 route를 제공한다. `#L55-L65` 같은 host line fragment는 일반 Markdown heading과 달라 실제 소비 환경에서 검증한다. 이동 전 `rg`로 backtick 파일명·§번호·token 이름도 찾는다.

## 5. 동기화·변경 영향 절차

**제안 → 검토 → 반영 → 검증**은 다른 완료 조건을 가진다.

| 단계 | 해야 할 일 | 완료 증거 |
|---|---|---|
| 제안 | 원본 revision/계약 범위, 명료화·근거보강·새 결정 분류, 유지할 예외, 소비자/질문/코드 현황 기록 | 실제 diff 또는 구체 문안, 반례, scoped blocker |
| 검토 | 원문 담당·소비자 담당이 의미/호환/권한·실패 조건 대조, 후보 채택에는 근거 필요 | 승인/보류/반대 이유와 책임자. 모델 동의는 제품 승인 아님 |
| 반영 | 원본 먼저, 파생 링크/요약/05 상태·task evidence 함께 갱신. 분리 저장해도 하나의 추적 가능한 변경 묶음 | 반영 revision, 변경한 것과 보존한 것 |
| 검증 | 구조 검사 + 원문/예외 대조 + 존재하는 관련 구현 테스트. 없는 runtime은 미검증 표시 | 명령·실결과·source/code revision·미수행 검증·후속 담당 |

변경 담당은 다음 목록을 실제로 채운다: `변경한 계약 → 영향 후보 → 확인 결과(수정/재검증/영향 없음+이유) → 남은 blocker`. 관계 표는 직접 관계의 출발점이며 완전성 보장이 아니다. 원문에서 소비자가 새로 발견되면 이 목록과 원본 포인터를 함께 보강한다.

| 원본 변화 | 반드시 검토할 소비자/산출물 | 재생성·검증 |
|---|---|---|
| 06 URL/cardinality/지원 Context | FE codec·서버 validator·Registry 선언·07·REQUIREMENTS·관련 adapters | 공통 schema 채택 이후 생성 client/types; 현재는 문서 반례 대조 |
| 06 시간 + 05 R/H | 01 데이터·03 설명·07 기간 입력·DESIGN preset·integration adapter | boundary/precision/R 부재 벡터; runtime 없으면 예정만 |
| 06 §19 의미 | API/status source·적용 kind 선언·DESIGN render·04/07 요약 | payload 완전성·unknown/empty/원인 구분 검증 |
| DESIGN 시각 값 | 06 인용·07 배치·token binding·render evidence | generator 도입 시 CSS/types 재생성; 현재 토큰 값 대조 |
| 01 upstream 소비 계약 | 지원 revision/fixture·view/mart·API·Data Trust·03 | dump 기반 계약 회귀(현재 미실행) |
| 후보 채택/보류 | 05 결정 경로·대상 계약·REQUIREMENTS·원 후보의 결과 링크 | 채택 근거/예외·비범위 보존; 연구 이력의 본문을 현재형으로 소급 수정 안 함 |

현재 수동: 제품 Markdown, 결정 기록, 작업 evidence. 현재 자동 생성으로 확인된 플랫폼 계약/codegen 산출물 없음. source-snapshot/sample-source/validation은 이번 조사용 파생 산출물이다. 미래 생성 도입 시 반드시 입력 원본/생성 명령/버전/수동 편집 금지/재생성 diff를 기록한다.

새 코드가 없으면 '미구현'으로 표시하되 문서 readiness와 혼동하지 않는다. **설계 준비 완료**는 해당 slice의 입력·출력·불변식·실패/권한/시간·수용 기준을 결정/제한할 수 있다는 뜻이다. **구현 착수 승인**과 **구현/검증 완료**는 별도다. 미결 질문이 기능 일부만 막으면 그 범위만 차단하고 나머지 계획은 계속한다.

## 6. 병렬 변경과 검사 한계

작업 시작 시 `원본 revision + 계약 범위 + 쓰기 파일 + 소비 계약`을 공유한다. 같은 파일이 아니어도 FE/BE가 같은 public field의 의미를 바꾸면 충돌이다. 기존 담당 변경을 덮어쓰지 말고 한 담당이 계약 변경을 조정한 뒤 소비자가 새 revision을 확인한다. 기준 source hash 변경은 경고이지 자동 폐기 판정이 아니다. 바뀐 섹션과 연결된 검증만 재실행한다.

자동 검사 가능: 링크 경로/명시 anchor 존재, ID 중복, 선언한 의존 대상 존재, generated diff, source drift, source와 sample 동일성. 사람/LLM 판단 필요: 상태 범위·예외 보존·동음이의어·권한/시간 의미·실제 소비자 누락·승인 근거 적합성. link check가 semantic approval을 대체하지 않는다.

적용 후 3개 실제 변경에서 잘못 찾은 원본·놓친 소비자·불필요하게 읽은 문서·갱신 누락·유지 비용을 기록한다. 개선되지 않으면 추가 메타데이터를 늘리는 대신 경로/중복 본문부터 줄인다. 자동 graph/RAG는 그 이후에도 비교 선택지일 뿐 의무가 아니다.
