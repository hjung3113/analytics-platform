# @ap/feature-bridge

Runtime of the feature bridge (ADR-0071, ADR-0081). A consumer-side package, not an SDK (absent from `SDK_PACKAGES`). Bridge menus (`@ap/menu-my-activity` and feature menus `platform/{dashboard,voc,findings,tasks,integration,surveys,feature-admin}`) and app files import the package root. Only the app `main.tsx` imports the slot and API subpaths (`./feature-api`, `./*-slot`).

## Rules

- Import only `@ap/feature-screens/global-screens/core` from the root and from slot files (outside `src/pages/`). Pulling the full entry into permanently loaded code puts feature screens in the main bundle (ADR-0071 decision 1). The full entry `@ap/feature-screens/global-screens` is imported only from `src/pages/`, which slots open lazily on first use.
- Do not re-export screens. Bridge menus import the exact feature entry directly.
- Keep session singletons in this package only. No other package creates `featureQueryClient` or a session.
- Put slot and page tests in the menu package that uses the slot, not here: they need the menu's manifest, registry and fixtures, and `packages/*` cannot import menus. Examples: `@ap/menu-my-activity` (`src/notifications-slot.test.tsx`, `voc-compose-slot.test.tsx`, `home-todo-slot.test.tsx`, `src/feature/test-support.tsx`), `@ap/menu-dashboard` (`scope-control-slot.test.tsx`, `scope-control-page.test.tsx`), `@ap/menu-voc` (`nav-counts.test.tsx`). Tests here run without a menu (route tables, links, UUID, entry graph, `FeatureScreenPage`). The registry and `mountAt` harness (`./testing`) live here; test bodies live in the menu.
- Keep one `managedSystem` read/write rule: `src/feature/list-scope.ts` (`useListScope`), shared by the sidebar picker and the page-owned `ListScope` (root export, lazy) that 내 Task draws in its filter area.
- Keep one UUID check: `UUID_PATTERN`, `isUuid` (`src/feature/uuid.ts`, root export). `VOC_ID`, `SURVEY_ID` and route-table `detailPath.pattern` derive from it.
- `src/feature-entry-graph.test.ts` pins the import graph of the feature entries the bridge reaches and the `/core`-only rule for permanently loaded modules.

## Sidebar slots (Kernel slot values; imported by app `main.tsx` only)

- `src/operator-menus.ts` is the one place the slots (`scope-control`, `nav-counts`, `saved-views`) decide by space and **current menu**. Only operator menus of the 업무 흐름 space (`flow`) that declare `managedSystem` and sit in an allow-listed group mount anything. Platform administration (groups `admin`, `access` of `operations`) and global 내 Task mount nothing, so no operator session, query or scope UI starts there.
- `For(spaceId('flow'), currentMenu)` of `scope-control` and `nav-counts` returns one module-level component; creating one per call would remount the sidebar.
- `src/scope-control.tsx` (slot `scopeControl`, sidebar `시스템`, ADR-0081): in mock it draws a disabled `전체` placeholder itself; only in a ready session it opens `src/pages/ScopeControl.tsx` (lazy). That page draws the picker `disabled` when the menu group is `flowSettings` (ADR-0081 d4; judge by group, never by a menu-id list).
- `src/nav-counts.tsx` (slot `navCounts`, sidebar count badges): the component calls `children` in the same place in mock, loading, error and ready states, so the sidebar list does not remount. It reads feature `fetchNavCounts` with `useQuery` for the current `managedSystem` (`['nav-counts', managedSystem]` in `featureQueryClient`, `undefined` for no scope). Feature screens' observers share the query, so `invalidateNavCounts` refreshes once and the query cancels when the scope is left. An omitted key shows no badge; 0 shows 0. The count badge `surveys.all` goes to `survey-management`.
- `src/saved-views.tsx` (slot `spaceNavSection`, sidebar `저장된 보기`): `Body` is one module-level component. In mock or before the session is ready it draws only a muted line (`실서버 필요`) and sends no request. In a ready session it opens `src/pages/SavedViews.tsx` (lazy): list `['saved-views','voc']`, apply, delete (with focus recovery), and the save form in the inbox and Triage. Apply finds the menu the saved `view` points to through `operatorHostLinks.targetOf` and clears keys it does not carry and `managedSystem`. Failures go to the Kernel toast.
- `src/access-request-slot.tsx` (slot `accessRequest`, the blocked-place request entry, ADR-0154 decision 6): `Pending` reads the user's open requests (`fetchPermissionRequestsMine`, `permissionRequestsMineKey` in `featureQueryClient`, the key the home `내 할 일` shares and the dialog invalidates on submit) and decides with the one matcher `isPendingFor` (`src/feature/access-request-match.ts`: a site place is pending for an open request on the site or any room of it; a room place for its site or that room only). `statusHref` is 내 활동 › 권한 요청. `pending` is null in mock, before the session is ready, while loading and after an error. `Dialog` opens `src/pages/AccessRequest.tsx` (lazy, from the first open) with feature `RequestAccessButton` in controlled mode. A `permission` target gets `pending: null`, no link and no dialog (place (a) is node 1844f1c). The app passes the slot only with a feature API.
- `src/notifications-slot.tsx`, `voc-compose-slot.tsx`, `home-todo-slot.tsx` open their pages lazily. The notification `Recent` also opens `src/pages/RecentInbox.tsx` (lazy, screen entry `global-screens/inbox-panel`) so the panel is not in the start chunk; bell and badge stay in place through `useUnreadNotificationCount` from `/core`, and Suspense is inside the panel only.

## Host seam and route tables

- `src/feature-api.ts`: `setFeatureApi`/`featureApi`, the feature API slot the app injects. It imports nothing from the feature.
- `src/feature/session.ts`: `featureQueryClient` is the one feature QueryClient (ADR-0071 decision 5; separate from the Kernel's internal query client, ADR-0086) and `useFeatureSession` (session generation). On a feature 401 it calls `snapshotSessionDrafts(userId)` before retiring the subtree, and a new generation calls `beginSessionDraftOwner(userId)` (form drafts kept across a session expiry, ADR-0071 decision 5, #1887; registry in feature `lib/session-draft`, reached through `/core`).
- `src/feature/FeatureBridge.tsx` is the host seam. It leaves out the unbounded notification time (`Infinity`) so the Kernel default applies. `links.tsx`, `survey-links.tsx`, `voc-links.tsx` hold the feature path → platform menu link maps.
- `src/feature/operator-links.ts`: `operatorHostLinks` merges all feature path → platform menu link tables in declaration order (VOC, Findings, Tasks, integration, my VOC, surveys, admin) for bridge menus and the dashboard (ADR-0071 decision 10). Each table's allowed targets and rejection conditions are in that file and the route files below.
- Route tables (`operatorRoute`) map feature paths to platform menu paths and all hang on `operatorHostLinks`: `voc-routes.ts`, `task-routes.ts` (seven tables: Task Request, board, Milestone, list, my Task, two list aliases), `finding-routes.ts`, `integration-routes.ts` (four: dashboard, Evidence, coverage, links), `survey-routes.ts`, `admin-routes.ts`.
  - Surveys (`surveysRoute`, `surveyChildTarget`, `surveyOperatorTargets`; hidden screens `surveyBuilderRoute`, `surveyResultsRoute`, `surveyFollowUpRoute`): read the path parameter `:surveyId` from `route.params`, not as a page key; only follow-up carries `focus` as a page key.
  - Admin (`adminOperatorTargets`: managed systems, analysis areas, permission requests, permission grants, settings): settings maps `#coverage` to `section` through `operatorRoute`'s `hash`. Do not link an `/admin/…` path with no mapping or a fragment other than `#coverage`.
  - Coverage `설정` (`/admin/settings#coverage`), permission-request notifications and recovery-source links go to this menu.
- `src/feature/RejectedPage.tsx` (root export): the shared rejection screen for a wrong address value (`값 지우기`). Every bridge-menu operations screen (all that use `FeatureScreenPage`, and `dashboard`) uses the same wording (ADR-0071 decision 9).
- `src/feature/FeatureScreenPage.tsx` (root export) is the operations-screen page frame. Not used by `dashboard`, whose frame differs.
  - Check address values (`route.rejectedKey`); on rejection render `RejectedPage`, mount neither `children` nor `detail`, and send no request. The value check `isValid` (`isVocSearchValueValid` etc.) imports screen entries, so each menu passes it as a prop.
  - Otherwise render `PlatformPage layout="fill" bodyInset="none"` (body to the edge; the screen's `ListShell` draws its own inner padding), a header `primaryAction` slot (`data-feature-primary-action`; the screen gets it from the seam's `usePrimaryActionTarget` and draws one primary button through the `HostPrimaryAction` portal; with no target — standalone or gated screens — the screen toolbar stays as is, ADR-0081 decision 5), `FeatureBridge` (`operatorHostLinks`), the screen area and the `detail` drawer.
- `src/feature/FeatureDetailDrawer.tsx` (root export; `.fo-detail-body` style in `src/styles.css`): wraps feature detail `DetailParts` into the shell detail slot `DetailDrawer`. Bridge menus (`fo-voc`, `tasks`) use it inside `FeatureBridge`.

## Test harness (`./testing`, test-only, not a root export)

`createFeatureMenuHarness({ manifests, homeMenuId, group, detailSlot })` → `{ registry, mountAt(url, { registry?, extra? }) }`. A bridge menu's `test-support.tsx` calls it with its own manifests. It accepts a `permissions` option (default `platform:view`, `features:access`); a menu the session has no permission for is not drawn as a shell. It uses `@ap/kernel/testing` and `@testing-library/react`, so lint allows `kernel/testing` in `src/testing.tsx` only.
