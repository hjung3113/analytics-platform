04 · 분석 흐름

어떤 화면을 만들든 이 흐름이 이어집니다

본다 → 내려간다 → 비교한다 → 알린다 → 확인한다. 화면마다 따로 만들지 않아도 플랫폼이 각 단계를 보장합니다.

근거

L65 · L82 · 1~3·5단계는 예시 데이터로 동작합니다. 4단계의 VOC 처리 화면은 별도 제품이고 실제 연결은 사내 SSO 뒤입니다. 캡처는 견본 화면이며 권장 설계가 아닙니다.

  1. 1본다 — 숫자 옆에 갱신 시각 · 커버리지 · 지표 버전이 붙고, 0건 · 권한 없음 · 오류가 서로 다르게 보입니다.

  2. 2내려간다 — 원인 쪽으로 내려가도 처음 조건 그대로이고, 돌아오면 출발한 자리입니다.

  3. 3비교한다 — 이전 기간을 같은 시간 축에 이어 그려 비교하고, 판단을 주석으로 남깁니다.

  4. 4알린다 — 보던 화면 그대로 링크로 알립니다. 받는 사람의 권한으로 다시 확인합니다. 개선 과제로 잇는 연결은 사내 SSO 뒤입니다.

  5. 5확인한다 — 고친 뒤 같은 조건으로 이전 기간과 비교하고, 바뀐 것은 공용 감사에 남습니다.

위험과 완화

위험완화
개발 · 유지 인력 의존미산정입니다. 결정이 필요합니다.
실데이터로 검증하지 않았다적합성 묶음이 실서버도 같은 계약을 지키는지 검사합니다. 시범 범위에서 먼저 확인합니다.
SSO 일정이 정해지지 않았다서버 연결부만 바꾸는 구조라 화면 코드는 고치지 않습니다. 실서버에서는 아직 검증하지 않았습니다.
사용자 조합 분석이 결정되지 않았다분석 보드(설계 확정 · 구현 전)가 이미 있는 화면을 칸에 담아 일부를 먼저 메웁니다.
기존 시스템 이전을 시작하지 않았다두 길(저장소 안 화면 · SDK 모듈)로 화면 단위로 하나씩 옮깁니다. SDK 길은 고정 모듈로만 검증했고 외부 앱 연결은 대기입니다. 첫 시범 이전은 CLAS 화면 하나입니다(제안).
보안 · 망분리 심사(#151)앱은 외부 네트워크를 부르지 않는 것을 요구로 두었습니다(R10.4). 사내 환경 확인과 심사는 #151의 답을 기다립니다.
FeedbackOps 의존별도 제품이며 플랫폼은 링크로만 연결합니다(ADR-0027 · ADR-0045). 처리 화면의 일정은 FeedbackOps 쪽에 있습니다.
