## Details

### C1 — permission grant reason chain parallel to `canSubmit`
Evidence: `canSubmit` (lines 530-544) and `submitBlockedReason` (545-570) list the same predicates twice in different shapes. I traced every term: `sessionReady`, `optionsUnconfirmed`, `selectedCandidate`/length mismatch/`scopeReady`, `overLimit`, `preflightBlocked`, `selfGrantForbidden`, `selfPolicyUnconfirmed`, `reasonReady`, `expirationReady`/`expirationInvalid`, `selfEnvelopeReady`, governance, `pending` — each has a reason, and when all are false the chain ends at `undefined`, so a reason is never shown while the button is enabled. Correct today. The risk is next month: the issue's defect (disabled with no reason) comes back the first time someone adds a `canSubmit` term and forgets the chain, and the ternary is a read-twice line (addendum Readability). Order nit: the chain puts `selfEnvelope` before governance, but the DOM renders the governance checkbox (l.860) above the envelope fields (l.890/904), so it is not quite "in the order the form is filled". 
Fix: extract `function directGrantBlockedReason(s): string | undefined` with early `if … return` lines (the `CreateSurveyDialog.tsx:224-237` shape), swap governance above selfEnvelope, and set `const canSubmit = submitBlockedReason === undefined`. Same in `WorkspaceSettingsScreen.tsx:270`: `canSave = dirtyKeys.length > 0 && saveBlockedReason === undefined` (the bar is hidden when nothing is dirty, so no reason is needed for that term). Existing tests cover it unchanged.

### C2 — notice server errors survive edits
Evidence: `set` (l.90-93) calls `local.clearError(field)` and `setFailure(null)` but leaves `serverErrors`. After a server rejection of «종료 일시», editing it removes the banner but keeps the field error and `aria-invalid`; the managed-systems dialog in the same PR clears `serverSlugError` on edit, so the two forms disagree. A stale server error on an earlier field would also win the next local-invalid focus (`querySelector('[aria-invalid="true"]')` is DOM order).
Fix: in `set`, also `setServerErrors(prev => { const next = { ...prev }; for (const k of keys) delete next[k]; return next; })`. Extend the existing server-rejection test (Notices.test.tsx ~l.219) with: change «종료 일시» → `aria-invalid` gone.
