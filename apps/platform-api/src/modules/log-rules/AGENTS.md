# log-rules module

Owns the validation rule catalog the external Validator reports over a service token. Design: `docs/design/features/log-rules/README.md` (ADR-0122); API: `docs/architecture/platform-api/api/log-rules.md`.
The `RuleCoveragePort` is consumed by log-lifecycle (Round attempt RuleSet link), log-datasets (rule-id check), log-knowledge (spec badge) and the picker options. Contract E2E: `apps/platform-e2e/tests-real/log-rules.admin.real.spec.ts` (synthetic fixture, run on the host, not in CI).

## Invariants

- The only write is `POST /api/v1/validation-catalog/report`, token-only: capability `validation.catalog.report` is `tokenOnly` (a session is denied `token_required` before any grant is read) and has no Admin bypass; the token owner's own grant ∩ the token scopes decides. Never add a session path, a menu action or a human capability for it.
- No column, field or log line holds a rule body, condition, threshold, parameter or script. Every object in the report is closed (`unknown_field`); a new accepted key needs the contract schema, the table column, the limits and the doc in one change.
- Free text is refused, never rewritten (`control_character` — C0/DEL/C1 controls and ill-formed Unicode such as a lone surrogate, plus invalid UTF-8 bytes as `invalid_json` —, `secret_pattern`); a refused report is recorded with its reason and **no content**, and the audit row never carries rule text or targets.
- Order of judgment in `domain/report.ts`: byte size before parse → JSON → closed shape and limits → control characters → secrets → duplicates. Keep the size check first.
- One transaction per report behind the per-workspace advisory lock (`lockReports`): replay lookup by digest, supersession of the previous report of the same source (marker first, the deferred FK points at the new row), snapshot rows, audit row. A replay writes nothing.
- Rows are insert-only (trigger on every role); the only UPDATE is the supersede marker. Test teardown disables the triggers with the migrate role; production code never does.
- `result_ref` is stored resolved (`resultRef ?? revision`); matching of an attempt's `rule_set_revision` to it, and the `ambiguous` rule, belong to the read nodes (design §2 identification contract). Identifiers are compared exactly.
- The synthetic reporter (`tooling/scripts/log-rules-synthetic-reporter.mjs`) is test/dev only; no `src/` file may import it.
- Catalog reads (`logRules.ruleSets|ruleSetDetail|rules|ruleDetail|catalogStatus`) are menu-dispatch declarations on the existing `log-rules` menu id (`menu.ts`): `platform:view`, `requiresScope: false`, workspace = the session Actor's; unknown or other-workspace id → `ok` with `data: null` / an empty page, never 403. They write nothing and return no rule body.
- «Current catalog» = accepted, not superseded reports (`repositories/catalog-read.ts` `loadGroups`); a rejected or superseded report never reaches a read. Revision order, current Revision and the Revision diff are pure functions in `domain/revision-order.ts`, driven only by the reported `supersedes`.
- Sort and filter keys are allow-lists in `domain/catalog-params.ts`; every order ends with the stable keys (`ruleSetKey`, `ruleKey`, id). Targets and requirement ids are returned as stored by the catalog reads; only coverage matches them, by exact string equality with log-knowledge's requirement keys.
- Coverage (`logRules.coverage|coverageSummary`, `RuleCoveragePort`) is computed on read, never stored (`domain/coverage.ts`, pure). Exact string match only; `scope` is NOT interpreted (open point in `api/log-rules.md`), `partial` comes from `support`, mixed supports follow the documented precedence.
  - «Not computable» has distinct reasons (`model_unknown`, `ambiguous_key`, `no_spec`, `no_catalog`, `no_requirement_ids`) and is never 0%. `coverageDigest` has its own domain prefix; do not change the canonical form without bumping it.
- The spec side comes only from the log-knowledge barrel port `knowledgeLookup.listEffectiveRequirements` (injected in `server.ts`), never its tables. Lock order: catalog reads (no locks) first, then the port's single model advisory lock; a loop over models must use the pool handle so no model lock is held across iterations (`coverageSummary`).
- ACL: coverage and summary pass the current actor into the knowledge port; `RuleCoveragePort.getCoverage` requires `viewerActorId`. Hidden Model/SW answers `model_unknown`, without requirements, counts or digest.
- Port consumers get the port as a structurally typed dependency injected in `server.ts` (`createRuleCoveragePort({ knowledgeLookup })`); log-lifecycle, log-datasets and log-knowledge never import this module, which keeps the log-rules → log-knowledge dependency one-way.
  - `findRuleSetRevision` is the only lookup that tells `ambiguous` from `unknown`; link only `matched`. An unresolved Revision never blocks dataset work: `checkRuleKeys` answers `unresolved` and the caller accepts unchecked.
- `modelOptions|softwareOptions` read through `KnowledgeLookup.listModels|listSoftware` and return ids and display text only; the required viewer applies the same object visibility predicates as coverage.
