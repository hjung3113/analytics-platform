# log-datasets module

Owns the test datasets of the log domain: dataset, its immutable revisions, the candidates that become datasets, expected baselines, regression suites and suite runs, comparison, coverage, and result review labels.
Design: `docs/design/features/log-test-datasets/README.md`; API: `docs/architecture/platform-api/api/log-datasets.md`. Dataset ≠ data-collection Source; Baseline ≠ metric Baseline (`GLOSSARY.md`).

## Invariants

- `model_ids` are log-knowledge stable ids and `source_ref.roundId` a log-lifecycle id: plain uuids, no cross-schema FK and no existence check. The sample list parser and digest are log-lifecycle's (`domain/sample-manifest.ts` re-exports them); do not copy them.
- Every read and write filters by the session workspace AND by visibility: `private` is the owner's alone (`datasetVisibleTo`), so a foreign or invisible id is the same absence as a missing one. Add the predicate to any new statement that reads `dataset`.
- `dataset_revision` is immutable: DB trigger (UPDATE/DELETE refused for every role) and no grant; `seq` is `max + 1` under the dataset `FOR UPDATE` lock. A different file list is a new revision; the same digest twice in one dataset is refused.
- Availability is computed at read time from per-file check states (`domain/availability.ts`), never stored; only the latest revision is checked on read. `available` needs every file found AND its hash matched; no port, `unsupported`, aborted or an unreadable hash is `unverified`, never confirmed.
- The `SourceReadPort` is OPTIONAL (`deps.sourceRead`). Never import `log-explorer/adapters/synthetic` or `testing/` (log-explorer's production graph test fails if they enter). Do the Source IO before locking the dataset row; never keep an adapter error text.
- A candidate holds data references only: no code, command or LLM origin field; the proposer is the session actor. Approve = dataset + first revision + decision in one transaction.
- Every write is one transaction: row change and `core.audit_log` row; audit detail is body-free (`packages/feature-shared/src/audit/log-datasets.ts`): ids, tag/status names, counts, digest, lengths; never a `fileRef`, hash list or note text.
- No read or action accepts an unknown param/input key. `datasets` returns no stale field (a list-wide badge needs a Source check per dataset: backlog).
- Baselines (`expected_baseline`, append-only `baseline_event`): a draft is editable; `approved` / `superseded` never change content (guard trigger, every role).
  - Lock order is ALWAYS dataset row first (`lockDataset`, also the visibility judgment), then baselines; approve supersedes the revision's previous approved baseline first, then approves, in one transaction under that lock.
  - Approve is `dataset.baseline.approve` (sensitive, session-only, no Admin bypass); self-approval is allowed and recorded (`selfApproved`). A baseline never changes from run results; `fromAttemptId` is refused until a lifecycle read port exists.
- 기준 낡음 ("baseline staleness"; `domain/baseline-stale.ts`, `stale-read.ts`) is read-time only and asserts `stale` only from a comparison that ran: Source-owner ACL gate first; no port / denied / unreadable = `unknown`; a pinned rule set, parser or engine profile is `unknown` until an engine capability read exists.
  - The spec pin is read through the log-knowledge barrel port only. Baseline audit and event rows carry ids, counts, status names, a digest and reason LENGTH; never an expectation, exception text or evidence location.
- Suites (`regression_suite`) and runs (`suite_run`, `suite_run_item`): a run and its items are immutable (trigger, every role) and there is NO stored run state — it is derived from the item requests' states (`domain/suite-state.ts`) read through the log-lifecycle barrel port (`deps.lifecycleRequests`); never select or write a lifecycle table.
  - `suiteRun` (`dataset.suite.run`, non-sensitive, session-only, a User refused on the CURRENT role) is idempotent by (suite, actor, key), takes the per-user run lock before counting active runs (cap `SUITE_RUN_CONCURRENT_LIMIT` 3), resolves EVERY item to an approved baseline first (one bad item refuses the run), and asks the Source (ACL first, deadlines) before writing.
    - It pins revision, baseline, digests and the 기준 낡음 badge. An item of a dataset the reader cannot see is returned `restricted` without id, name or digest. Audit detail: ids, counts, state names only.
- Comparison (`domain/comparison.ts`, `comparison-endpoints.ts`, `repositories/comparison-read.ts`): computed at READ time from the run item's PINNED baseline and the latest `succeeded` attempt's rule results, read through the lifecycle barrel port `deps.lifecycleResults` on the caller's transaction (never a lifecycle table); nothing is copied or stored.
  - `not_comparable` NEVER counts as PASS; an item with no succeeded attempt is not classified. Responses carry rule ids, classifications, counts and ids only.
  - Visibility = the dataset's (a run with no visible item is the absence answer `data: null`; invisible items are `restricted`). The classification table is documented in `api/log-datasets.md`; change a cell only with its unit test and that table.
- Review labels (`suite_review_label`, action `reviewLabelAdd`): append-only (trigger, every role), `dataset.manage` + session-only + a User refused on the CURRENT role; the required ordinal identifies exactly one run item and its revision must match; the rule must exist in that item (baseline or latest result); a label NEVER changes a baseline, a result or a classification.
  - Audit `dataset.review_label_added` is body-free (ids, label name, reason LENGTH); dataset subjects stay out of the platform audit projection.
