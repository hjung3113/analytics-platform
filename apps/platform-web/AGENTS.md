# apps/platform-web — 조립 지점

플랫폼 패키지를 조립하는 앱(dev·테스트에서는 mock 어댑터를 주입한다). 메뉴 화면은 [`menus/*/*`](../../menus/AGENTS.md) 패키지가 두고, 앱은 조립 지점이다(루트 `AGENTS.md`).

## 폴더

- `src/main.tsx` — `I18nProvider` → `PlatformProvider adapter registry slots` → `AppShell` + `RouteOutlet`. 조립만 한다(FeedbackOps origin env는 `src/feedbackops-origin.ts`가 읽어 `appSlots`에 넘긴다, #60. 조립이 준 `feedbackOpsApi`(실서버 조립만, 없으면 mock)는 `@ap/fo-bridge/fo-api`에 넣는다, ADR-0071). mock·`src/dev/**`를 import하지 않는다(#153, [ADR-0009](../../docs/adr/0009-production-assembly-injection.md)) — 어댑터와 레일 도구는 `#platform-assembly`의 `createAssembly({ registry })`에서 받는다(계약 타입 `src/platform-assembly.d.ts`). `slots`는 `src/slots.ts`의 `appSlots(assembly, feedbackOpsOrigin, notificationsSlot, vocCompose, homeTodoSlot)`(`notificationsSlot`·`homeTodoSlot`은 `main.tsx`가 `@ap/fo-bridge/notifications-slot`·`/home-todo-slot`에서, `vocCompose`는 `/voc-compose-slot`의 `vocComposeSlot(managedSystemFor)`로 넣는다, #652·#655·#657)다(`contextBar`·`topBarTools`·`feedbackOps`·`plannedSpaces`와 보드 지원 메뉴 머리 `⋯`의 `boardEntry` = 셸 `OpenInBoardAction`) — `main.tsx`가 env를 한 번 읽은 origin을 메뉴 서브패스와 여기에 함께 넘기고, `feedbackOps` 슬롯은 `src/feedbackops-systems.ts`의 `feedbackOpsSlot(origin)`이 만든다(공간 → Managed System uuid 표 `FEEDBACKOPS_MANAGED_SYSTEMS`, origin이 없거나 잘못되면 항목은 `href: null` 비활성, 전체 진입은 `feedbackops:access` 권한자에게만, ADR-0045, #251). `vite.config.ts`가 mode로 경로를 고른다: dev 서버·`--mode mock`·vitest → `src/dev/mock-assembly.tsx`, `--mode real`(`pnpm dev:real`) → `src/real/http-assembly.tsx`(이 레포의 실서버 조립: `@ap/http-adapter`의 부트스트랩을 기다려 어댑터·로그인 이동·연결 실패 화면 중 하나를 돌려준다, dev server는 `scripts/real-dev-proxy.ts`로 `/api/fo/`(접두사를 떼고 FeedbackOps 경로로, ADR-0071)·`/api`·`/auth`를 이 순서로 env `AP_BACKEND_ORIGIN`(기본 `http://127.0.0.1:3011`)에 프록시, mock·DevTools 없음), 그 밖(운영) → env `AP_PLATFORM_ASSEMBLY`(실어댑터 조립, #154), 없으면 빌드 실패. `createAssembly`는 `Promise`도 돌려줄 수 있고 `{ redirect }`·`{ screen }`으로 렌더 대신 이동·안내 화면을 고를 수 있다 — `main.tsx`가 기다린 뒤 마운트한다. `@ap/http-adapter`는 `src/real/**`(와 그 테스트)만 import한다(경계 lint).
- `src/dev/mock-assembly.tsx` — mock 조립: 메뉴 mock 엔드포인트를 여기서 `export const MOCK_ENDPOINTS` 하나에 등록하고(`createMockAdapter`와 서버 적합성 테스트가 같은 목록을 읽는다) — 각 메뉴의 `@ap/menu-<g>/mock`가 내보내는 `<g>Mock` 배열을 `MOCK_ENDPOINTS`에 spread한다(#114, #126, #153). `/mock` import와 `MOCK_ENDPOINTS` spread는 `// <gen:menu-mock-imports>`·`// <gen:menu-mock-spreads>` 마커 영역으로 `pnpm gen:menu`가 쓴다(analytics mock도 같은 영역에 들어 있다) — 등록 자체는 손으로 쓰지 않고, 영역 밖 배선은 손으로 쓴다.
  `platform:mock-menu-query` performance mark는 E2E 요청 수 계수용으로 endpoint 이름만 담고 Context는 포함하지 않는다.
- `src/modules.ts` — 외부 호스트 모듈 마운트(ADR-0053, #801): EV의 `eqv`를 `mountModule`로 등록한다(`@eqv/*`는 EV 릴리스 tarball URL 의존, EV ADR-0014). 자리는 `EQV_SPACE`(CLAS)·`EQV_PREFIX`(`/clas/topview`) 두 상수 한 곳이고(임시값, 사용자가 캡처로 확정) `apps/platform-e2e/tests/eqv.spec.ts`가 경로 사본을 가진다. `menus.ts`는 레지스트리 호출에서만 `EQV_MODULE`을 합친다(`GROUPS`·`MENUS`·`PERMISSIONS`는 플랫폼 몫 그대로). 모듈 권한 `eqv:view`는 앱이 선언하지 않는다(Registry가 `<moduleId>:` 접두사로 검사, 선언하면 `eqv` 네임스페이스가 예약돼 모듈이 거부된다, ADR-0072). `modulePermissions(registry)`는 모듈 메뉴의 권한을 모아 mock 역할 어휘에 더한다.
- `src/dev/eqv-mock.ts` — EV 엔드포인트 둘(`eqv.topview-context`·`eqv.topview-events`)의 mock. `@eqv/platform-adapter/mock-data`의 합성 fixture로 답하고 `mart: false`다. 명세는 `mergeTimeDomain: false` 사본이다 — mock 세계에는 `eq-synth-01`이 없어 엔진이 `requiresScope: false` 엔드포인트마다 time-domain 평가를 합치기 때문이며 mock 전용이다(엔진 후속은 코디네이터가 별도 이슈로). `MOCK_ENDPOINTS`(생성기 소유)에는 넣지 않고 `mock-assembly.tsx`의 `MODULE_MOCK_ENDPOINTS`로 내보내며, 어댑터와 적합성 테스트가 `[...MOCK_ENDPOINTS, ...MODULE_MOCK_ENDPOINTS]`를 읽는다. `@eqv/*/mock-data`는 `src/dev/**`·`src/server-conformance.test.ts`만 import하고(lint `app` 프리셋), 운영 그래프는 `check:prod-graph`(`scripts/prod-graph.ts` `FORBIDDEN`)가 막는다. `src/style.css`는 `@ap/ui/styles.css` 바로 뒤에 `@eqv/platform-adapter/styles.css`를 가져온다(생성기 영역 밖). vitest는 `@eqv/*`를 인라인 변환한다(`vite.config.ts` `test.server.deps.inline`, 패키지가 `@ap/*` TS 원본을 import).
- `src/query-history-store.ts` — SDK 이력 포트의 현재 브라우저 로컬 구현(06 §11). 튜플 키·schema 검증·Web Locks 직렬화·20건 병합/보존을 소유하고 `main.tsx`에서 주입한다. 저장 예외는 고정 비민감 오류로 거부하며 내용은 계측에 보내지 않는다.
- `src/menus.ts` — IA 공간(`SPACES`, `satisfies readonly SpaceDef[]`로 id 리터럴 유지)·그룹(`GROUPS`, 행마다 `space`; `hideLabelWhenSingle`은 선택적 사이드바 표시 선언)·앱이 쓰는 메뉴 권한(`PERMISSIONS`)을 `groupId`·`spaceId`·`menuPermission`으로 선언하고 `createRegistry({ …, permissions: PERMISSIONS })`에 넘긴다(ADR-0072)과 `menus/*/*`의 모든 `@ap/menu-*` 패키지 `manifests` 연결(`MENUS`), `createRegistry` 호출. 화면 lazy import는 각 메뉴 패키지가 소유한다. 패키지 연결(import·spread)은 `gen:menu` 마커 영역이며 `pnpm gen:menu`가 쓴다 — `SPACES`·`GROUPS`는 손으로 쓴다.
- 메뉴 화면과 그 화면 전용 합성 데이터(`data.ts`)는 `menus/<space>/<group>/src/pages/`에 있다(이행한 화면의 계산은 `src/mock/`).
- 서버 대역은 `packages/mock-server`다. 앱에 남는 것은 `src/dev/mock-assembly.tsx`·`src/dev/DevTools.tsx`와 실제 Registry·contracts를 함께 보는 통합 테스트 `src/*.test.ts`(파일명 = 검증 대상)다. 적합성 묶음 `src/server-conformance.test.ts`는 `MOCK_ENDPOINTS`와 `MODULE_MOCK_ENDPOINTS`를 그대로 읽고(lint가 그 import만 허용), 엔드포인트가 params를 선언하면 이 테스트의 `PARAMS` 표에 표본을 넣어야 통과한다(EV 두 엔드포인트는 선언한 `limits.maxHours: 8` 때문에 사례별 `context`로 fixture의 30분 구간을 쓴다). 역할 어휘는 `[...registry.permissions, ...modulePermissions(registry)]`다.
- `src/dev/DevTools.tsx` — 역할 전환·응답 시나리오 시뮬레이터(`topBarTools` 슬롯, 레일 아래). 운영 코드 아님.

## 규칙

- 메뉴 화면 작성법은 [README "페이지 작성 가이드"](README.md#페이지-작성-가이드-consumer-규칙)가 원본이다. 요약: 최상위 `PlatformPage`, 메뉴 데이터 조회는 `useMenuQuery(endpoint, params)` + `QueryView`(운영 콘솔의 Kernel 저장소 조회만 `usePlatformQuery` 예외, ADR-0019), 이동은 `linkTo()`, page 상태는 등록된 `pageKeys`만.
- 페이지는 `packages/*`를 수정하지 않는다. 공통 부품이 부족하면 필요 사항을 보고하고 플랫폼 작업으로 올린다.
- 메뉴를 추가하면 해당 그룹 패키지(`menus/<space>/<group>/src/index.ts`)의 `manifests`에 선언하고 06 §5(Menu Extension Contract)·§29(Platform Done)를 확인한다. 메뉴 화면 3개 이상 연속 제작은 사용자에게 범위를 먼저 확인한다.
- `@ap/mock-server`는 화면이 직접 import하지 않는다 — 규칙은 [menus/AGENTS.md](../../menus/AGENTS.md). 운영 빌드 제외는 `check:prod-graph`.
- 디자인 시스템 CSS(`@ap/ui`의 `styles/*`)는 앱이 개별로 가져오지 않는다 — `src/style.css`는 `@ap/ui/styles.css`만 `@import`한다([packages/ui/AGENTS.md](../../packages/ui/AGENTS.md)).

## 검증

`pnpm --filter @ap/platform-web test`로 좁혀 본 뒤 루트 검사(루트 `AGENTS.md`)에 더해 `pnpm dev`(http://127.0.0.1:5173)로 역할 전환·시나리오 시뮬레이터를 써서 화면을 확인한다.

스크립트(#153): `build`는 mock 데모(`--mode mock`, CI와 CSS selector 비교가 쓴다), `build:prod`는 `AP_PLATFORM_ASSEMBLY`가 없으면 실패하고 `scripts/typecheck-assembly.ts`로 조립 모듈 타입을 검사한다, `check:prod-graph`는 운영 모듈 그래프에 mock·`src/dev`가 없음을 확인한다(CI는 `--force-mock`·`--force-mock-build`로 검사가 아직 무는지도 확인). 설계 이유는 [ADR-0009](../../docs/adr/0009-production-assembly-injection.md)·[체크리스트 §1](../../docs/integration/real-server-checklist.md), 조립 계약 타입은 `src/platform-assembly.d.ts`다.

lint(#153): `@ap/mock-server`는 `src/dev/**`·`src/server-conformance.test.ts`·`src/published-metrics.test.ts`에서만, 메뉴 `/mock` 서브패스는 `src/dev/**`에서만 import할 수 있고 `src/main.tsx`는 FeedbackOps origin 서브패스만 허용된다. 원본은 `tooling/eslint/src/index.js`(`app` 프리셋). `import.meta.glob('./dev/*')`은 lint가 못 보므로 `check:prod-graph`가 잡는다.
